# Core: release unused startup-catalog fields before opening a session

**Production diff: `source.patch` only.** It changes `crates/proteus-core/src/core/session_store/remote/prepared.rs` on Core `b2d2e6de`.

Startup asks storage for candidate descriptors. After filtering to root sessions with a local path, startup needs only each timestamp and the owned path. Previously the descriptor vector's remaining entries retained unused session keys, workspace paths, record locations and descriptor slots during each candidate open. This change moves the timestamp and path into a smaller record, drops the other fields before sorting, and trims excess vector capacity. It keeps the existing ordered-input check and stable sort.

With any two eligible entries, the comparator is unchanged: descending signed timestamp, then descending `PathBuf` order. Dropping pathless records before the stable sort cannot affect that order. It can change whether the 32-entry fast-path threshold is reached; it cannot change which paths are tried. No deduplication, string conversion, locator or storage protocol change. The existing open/validation/empty-cache/error/fallback code is unchanged.

## Observed allocation pressure

Selected native Linux x86-64 Rust 1.95.0 measurements, requested bytes live, stock → candidate. Allocator scope starts before the catalog request and ends after the returned prepared session drops. Each row is an isolated fixture, not process memory.

| Catalog fixture | At first open | At entry to cold display validation | Sort-phase requested high-water |
|---|---:|---:|---:|
| 128 ordered medium-path descriptors | 42,664 → 9,256 B | 42,960 → 9,552 B | 42,624 → 9,216 B |
| 128 shuffled medium-path descriptors | 42,664 → 9,256 B | 42,960 → 9,552 B | 62,080 → 9,216 B |
| 4,096 shuffled short descriptors | 753,681 → 200,721 B | 753,977 → 201,017 B | 1,376,256 → 331,776 B |
| 4,096 reverse medium-path descriptors, success on attempt three | 1,339,428 → 278,564 B | 1,339,724 → 278,860 B | 1,961,984 → 409,600 B |

The 4,096-row short example retains **552,960 fewer requested bytes (540 KiB)** at both open and validation entry. The covered decoded input occupancy was the same for both arms (753,673 B). The stock sort scratch was 622,592 B versus 131,072 B at the candidate's sort. In the ordered controls neither arm sorts the catalog: this does not re-credit the historical optimization.

Projection and sorting are separate phases in the receipt. For the same 4,096-row short shuffled fixture, the projection reported a high-water of 753,673 B in both arms, before the sort. The candidate reports retaining 131,072 B of candidate-vector capacity, down from 622,592 B. Whole-interval requested peak including JSON decoding was unchanged at 3,899,665 B. Whole-interval peak including typed reply construction (without JSON decode) was 1,376,256 → 753,673 B for that shuffled fixture. Both arms return with zero tracked live bytes. Shrinking can add a reallocation, especially with few rows; no CPU or latency benefit is asserted.

The guard covers 17 catalog shapes via both JSON decode and a separate typed reply construction, in both JSON map layouts and both build profiles. It rejects any increase in observed whole-interval requested peak, also when a moved realloc is conservatively treated as temporarily retaining old and new requests. This does not see allocator-internal copying for a nominally in-place realloc, reserved allocator pages, worker buffers, full cold journal validation, end-to-end startup RSS, or disk timing. Read `verification.json` for all phase peaks, realloc counts, capacity observations and fixtures.

## Executed behavior

The isolated Rust harness executes the actual Core `catalog::candidates` request adapter, `prepare_latest_workspace_session`, `PreparedSession`, and saved-view read/write functions with pinned typed cache and catalog DTOs. The transport, open outcomes, cold validated-history input and summary estimation are test boundaries; the underlying worker, filesystem and journal validator are not run. The warm and empty-cache fixtures are generated by the real cache writer; the exact selection path either reads that cache or reaches the display-validator boundary and returns a cold prepared session. The exact cold display projection then publishes and reloads a named revision in the harness.

The 29 parity cases compare raw received ListCandidates JSON, request arguments, exact open path bytes and order, cache and validation calls, selected views, and errors. Cases include empty/singleton/31/32/33/128, already ordered/reverse/shuffled, nonroot/pathless records, timestamp ties, duplicate paths retried after failure, comparator-equal but byte-distinct paths, a typed Unix non-UTF-8 case, transport/unexpected/malformed replies, open/validation errors, empty cache refresh, first success and exhaustion. The non-UTF-8 paths are injected into the typed response because the JSON PathBuf format cannot carry them; this is not a claim of built-in support for such paths.

JSONL and SQLite shape cases use synthetic typed responses derived from the [pinned common Modules catalog](https://github.com/Proteus-harness/Proteus-modules/blob/331cfc20bbaf821ab07de49868426da29ebdeb64/storage/session-storage/src/service/sessions.rs#L79-L101). The shared provider's comparator uses timestamp and opaque session key, while Core uses timestamp and path. The ordinary shapes use path-bearing keys and fixed-width leaf names like the built-in implementation; deliberately opposed opaque-key ties are a separate legal contract control, not evidence of a built-in mismatch. The proof does not claim new worker captures, and previous #335 captures are historical only.
