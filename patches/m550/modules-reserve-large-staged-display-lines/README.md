# M425 Modules: reserve scratch for large staged display records

One production leaf `storage/session-storage/src/display.rs` and one build-independent patch. The worker's private display spool already counts bytes as each compact JSON line successfully stages. For lines above the 4 MiB page budget it retains a bounded offset/length hint (at most 127 under the existing 512 MiB stage limit). `ReadDisplayRecords` tries to reserve that much scratch only at an exact staged offset, only if the private file still has the requested extent, then still uses the old full read, newline check, JSON decode, measured record bytes, and page cut. Cursor accounting follows actual consumed bytes; it resets on rewind and discards a suspect offset on partial read failure. The returned pending record is still the same original decoded owner and no separate size makes a record authoritative. Thin stages do not allocate hints.

Not #633: the historical Core change reserved a single record in the downstream renderer's independent host spool. This change affects the Modules worker's earlier private spool, before transport, including a giant deferred between a tiny predecessor and suffix. No protocol, canonical source fence, default SDK pin, page cap or backend change.

Actual production worker linked in default and preserve_order using original 0c1b7572 SDK/contracts/semantics. Running its real stdio `OpenDisplaySnapshot` → `ReadDisplayRecords` reaches private stage (`Some` projection can only be returned after `DisplayWriter::finish`, and the display endpoint requires the stored stage). Eight independent stock/candidate comparisons at exactly 4,194,304 and 4,194,305 bytes with JSONL and SQLite, across both map layouts, verify the tiny first record, deferred giant, independent limit/pending continuation, same and different limit rewind, suffix, empty last page, exact strict records, old feature negotiation, and stale-handle errors. Every compared reply digest matched after only deterministic replacement of generated snapshot UUID; canonical source files had identical bytes before and after.

Four JSONL matched pairs additionally changed one byte in the fresh synthetic canonical prefix after the giant was already pending. Both original and candidate reject the `limit=1` continuation before using that staged record; restoring the same canonical bytes returns the original giant on that same handle. The full worker route runs only these small boundary fixtures. Successful build/runtime disk samples and exact source/ELF/feature pins are included.
