# Desktop: consume owned Codex item history replies during projection

Patch is against the exact M350 Desktop files. Independent of #597 in `src/transcript/mod.rs`. Consume the receiver's existing, fully decoded JSON object one row at a time by **moving**, not cloning, its `data` array and cursor. Release unrelated response fields before walking the array. Use the input allocation for the two primary text kinds where it is already tight and within the display limit; fall back to the same shared projector for all other values. The normal live event path still uses that same projector, not an owned history fast path.

**Scope.** The actual Codex resume path requests `thread/items/list` with limit **50**, even for a long archive; a later page uses the same receiver. The default framing cap is **8 MiB (8,388,608 bytes)**. The fixture is a 5,926,476-byte JSONL payload before newline with 50 rows; it is not a synthetic 50,000-row reply. Page ordering, cursors, item kinds, status fallback, millisecond times, unknown/malformed rows, non-string cursors and absent/malformed data errors stay unchanged. The live tail trim and 128 KiB text cap are not changed. A multibyte character straddling the display cap still produces the same marker; a field exactly at the cap still has no marker. The wire fixture checks an over-cap frame against a lower configured frame limit through the actual native transport.

Use `python3 proof.py [--vendor /path/to/cargo-vendor]` with Rust 1.95.0; `--vendor` makes Cargo offline. The packet contains the actual complete Codex service module and native JSONL client's exact Rust sources, not a lifted mock service. The peer is a deterministic synthetic subprocess. The wrapper selects only those two native components; package checksums match Desktop's upstream lock. The proof builds stock and candidate in separate target dirs to avoid cross-package Cargo cache reuse, checks and reverses the source patch, runs the existing unit tests plus the wire contract in both default and `preserve_order` modes. The opt-in smoke test against an installed vendor CLI is not run. No model requests, no GPUI/Desktop executable or RSS benchmark; allocation numbers count bytes requested in the calling thread, excluding the transport-reader thread and the synthetic peer. The normal Proteus API path (`/history/page`) is independent, not measured or changed.

On this fixture the default-map calling thread requested about 5.216 MB → 0.190 MB during resume and 5,183,775 → 157,840 bytes on the subsequent page (314 → 265–266 and 250 → 202 allocation/reallocation calls). Ordered JSON similarly reduced page allocation from 5,188,471 → 162,536 bytes. A moved string still occupies memory; these differences are avoided request volume, not the residual page size.
 Resume includes subscription/thread bookkeeping; only its small allocation counters may vary within the explicit proof tolerance. Page allocation results match exactly across isolated reruns.
