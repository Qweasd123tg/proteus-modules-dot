## Production assessment

No blocking correctness defect found in the narrow lazy-hash production diff.

- One existing prepared SELECT remains. An actual row invokes the supplier; missing-row `QueryReturnedNoRows` alone maps to `Some(false)` without hashing. Prepare, position-conversion, and other SQL errors remain `None`. Supplier `None` returns `Ok(None)` and then `None`, never a mismatch that would retry serialization.
- Existing rows still stream expected JSON into SHA-256; stored payload and checksum are borrowed and checked for BLOB type, per-row byte limit, expected checksum equality, and digest of actual stored payload. A short/different checksum is mismatch, not absence. Interior holes are detected by the actual key lookup, not lengths or counts.
- Missing rows retain bounded serialization plus digest of the exact insertion bytes. Changed/corrupt existing rows retain the second bounded serialization plus digest of those exact bytes; no deterministic-Serialize assumption is introduced for their insertion checksum.
- `MAX_BYTES` is 64 MiB **per serialized row**. Both streaming and materializing writers accept exactly the limit and reject the first chunk exceeding the remaining allowance. Missing rows now use only the latter guard. There is no cumulative all-row/database byte budget in the inspected baseline or candidate, and this change neither introduces nor removes one. `MAX_BLOBS` concerns source fingerprint enumeration, not a total payload-byte quota.
- **Rejection-path memory tradeoff:** previously an oversized or late-failing absent row could fail during `hash_serialized` without constructing a payload Vec. It now enters `serialize_bounded` directly and may accumulate an accepted prefix before failing. `Bounded::write` checks each incoming chunk against `MAX_BYTES.saturating_sub(self.0.len())` before `extend_from_slice`; thus the retained logical payload length never exceeds 64 MiB, but the guard is not a Vec-capacity, allocator peak-memory, or RSS cap. Capacity can exceed logical length through growth, and large single rejected chunks versus many accepted chunks have different allocation profiles. Existing-row first-pass rejection remains streaming. Equal `None`/rollback behavior is not resource equivalence; the candidate cannot claim universal memory improvement. No stronger rejection-memory contract was found in the supplied sources, so this is an explicitly disclosed tradeoff for the bounded proposal, not a detected contract violation.
- Generic serializer invocation changes intentionally: absent keys 2 → 1; SQL errors before callback/invalid positions 1 → 0; unchanged existing keys remain 1; changed/corrupt existing keys remain 2 if the first succeeds. Stateful serializers may therefore persist different values or avoid a failure previously arising on a second invocation for absent keys. Do not describe universal observable equivalence for arbitrary `Serialize` implementations.
- Update write transaction, source recheck, COMMIT, connection-close rollback, gate lifetime, and replacement path are unchanged. `read_model::save` propagates a failed row with `?`, dropping the transaction before replacement. `Updater::row` by itself does not poison the updater after failure; this is pre-existing, so rollback claims should refer to caller/drop behavior, not immediate rollback within `row`.
- Supplied production caller `read_model/sqlite/save.rs` covers conversation, transcript and context rows; usage/header use `one`; finish writes source via `one`. Transcript common-prefix increments only for true matches, so the first missing/holey/changed row still ends the prefix. Header/source validation is unchanged. Replacement uses the eager-hash Reader wrapper, preserving existing behavior and reader snapshot handling.
