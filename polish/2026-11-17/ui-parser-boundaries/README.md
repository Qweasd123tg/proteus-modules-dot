# Двойные карточки diff, выделение слова и границы блоков Markdown

Три воспроизводимых расхождения и один отдельный тест для существующего поведения. Патчи независимы. Этот каталог в **proteus-modules-dot** не меняет Desktop или Extensions: ниже описан результат применения к конкретным версиям, а не состояние приложения после слияния сюда.

| Что видно пользователю | Доказательство до → после |
| --- | --- |
| Один изменённый файл с некоторыми управляющими символами в имени представлен двумя карточками | 4 настоящих diff от Git 2.52.0: 2 карточки → 1 на каждом входе |
| Выделение слова захватывает знак умножения/деления и оба операнда | Обе функции выделения: целиком `déjà×мир` → отдельно `déjà`, `×`, `мир` |
| Закрытый блок Markdown с разделителем CR ошибочно считался незакрытым | На чистой функции: 1 из 2 тестов упал до, оба проходят после; 27 сочетаний в положительном тесте |

### 1. Одно изменение файла — одна карточка

[Исправление Desktop](diff-git-control-paths.patch) к [парсеру](https://github.com/Proteus-harness/Proteus-desktop/blob/7b1c96e70395aafc7531c0698450f306112db6ed/crates/diff/src/parse.rs). Git [кодирует](https://github.com/git/git/blob/e1ec09b23c8e0deb21a0b95ac5996422277395d4/quote.c#L205-L208) четыре байта короткими последовательностями: BEL, BS, VT, FF → `\a`, `\b`, `\v`, `\f`. Раньше декодер оставлял обычные буквы. При сопоставлении с настоящим путём из FileInfo парсер создавал дополнительную карточку. Меняется только декодирование этих четырёх случаев, не формат файла, пакет или обработка путей на диске.

Прямой Rust-тест исходного diff crate: 8/8. С новым тестом на старой реализации: 8/9; с исправлением: 9/9. Отдельно проверили четыре настоящих результата `git diff --no-index` на одноразовых локальных парах файлов: до правки у каждого две карточки, после одна; сохранены оригинальный текст diff, путь и счётчики +1/−1. GUI не запускался.

### 2. Общая классификация символов при выделении слова

[Исправление Desktop](word-boundaries.patch): две реализации копировали диапазоны букв. Внутрь Latin-1 попали знаки `×` и `÷`; выбор слова считал их такими же буквами, как соседние символы. Новый общий предикат используется и в [нативном поле](https://github.com/Proteus-harness/Proteus-desktop/blob/7b1c96e70395aafc7531c0698450f306112db6ed/vendor/gpui-base/src/input/base/selection.rs#L79-L89), и в [выделении inline-текста](https://github.com/Proteus-harness/Proteus-desktop/blob/7b1c96e70395aafc7531c0698450f306112db6ed/vendor/gpui-base/src/text/inline.rs#L1623). У этих путей различается обработка конца строки текста, поэтому целиком функции не объединялись.

Исходные два теста проходили; с новой регрессией на исходной версии 2/3, с патчем 3/3. Сравнение каждого пути до/после для строки `a{символ}b` и выбора на позиции символа: 1 112 064 допустимых Unicode-значения, отличия ровно для `×` и `÷`. Отдельно проверены прежнее поведение на конце текста и предел поиска 128 соседей в каждую сторону. Это проверка функций на Rust, не симуляция клика в окне.

### 3. CR тоже завершает строку в закрытом Markdown-блоке

[Исправление Extensions](markdown-cr-fences.patch) к [fences.rs](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/markdown-render/src/fences.rs#L89-L113). Вершинный узел Code имеет позиции в исходных байтах. Вспомогательная функция повторно искала границы строк, но искала только LF. Для «открывающий маркер, CR, содержимое, CR, закрывающий маркер» она возвращала None. Патч распознаёт CR, CRLF и LF, не переписывает байты содержимого и не принимает незакрытую конструкцию за закрытую.

Положительная матрица: 3 типа маркеров × 3 варианта первого разделителя × 3 последнего; отрицательные проверки включают незакрытый и неправильный маркер. В [тестах закреплённого markdown-rs 1.0.0](https://github.com/wooorm/markdown-rs/blob/1506572f9b406431402928f3a8b3df0b4ae2d8f5/tests/code_fenced.rs#L313-L338) зафиксированы исходные смещения для CR и CRLF. Их прочитали, но не запускали. Проверена точная функция определения границ; интеграцию с полным парсером и окно не проверяли.

### 4. Отдельно: тест единиц длины SVG, не исправление вычислений

[Только тест Desktop](svg-physical-length-test.patch) к [budget.rs](https://github.com/Proteus-harness/Proteus-desktop/blob/7b1c96e70395aafc7531c0698450f306112db6ed/src/ui/extensions/declarative/images/budget.rs). Для абсолютных единиц сравнивается результат с 96 px с допуском; неподдерживаемые относительные и недопустимые длины должны вернуть None. В стенде с точной функцией оба числовых теста прошли. Подмена делителя для сантиметров 2,54 → 25,4 сохранила зелёным прежний числовой пример in/px, а новый тест обнаружил 9,6 px вместо 96. Это расширение проверок; не меняет XML, рендеринг или защитные лимиты изображения.

### Что оставили как есть

- Чистая неизменённая модель вкладок: 70/70 тестов. Идея объединять pin при слиянии двух снимков одного tab ID отклонена. В [производственном вызове](https://github.com/Proteus-harness/Proteus-desktop/blob/7b1c96e70395aafc7531c0698450f306112db6ed/src/ui/workspace/windows.rs) обычный перенос уже несёт pin; конфликтующие версии могут быть устаревшими, и объединение рискует воскресить снятую отметку.
- Для пустого диапазона строк в Rope нашли подозрительную арифметику, но не установили путь из интерфейса и не проверили точную библиотеку Rope. Причины менять это поведение не доказаны.

### Базы и проверка

Desktop `7b1c96e70395aafc7531c0698450f306112db6ed`; Extensions `ef064381d2194d95faef2b85f6cc3a1c34c6b975`. Использованы нативные изолированные проверки на Rust 1.95.0; для crates/diff и модели вкладок использовались уже собранные совместимые зависимости serde. Это **не** проверка целых workspaces или запущенного приложения. Функции и тесты просмотрены независимо.

[Контрольные суммы](SHA256SUMS) и [Git blob до/после](applicability.txt) позволяют проверить перенос. В отдельной копии нужного upstream на указанном SHA выполните для выбранного патча `git apply --check --whitespace=error /path/to/file.patch`. Локально для каждого выполнены прямое и обратное наложение и побайтовое сравнение результата с проверенным кандидатом, а после отката — с оригиналом.
