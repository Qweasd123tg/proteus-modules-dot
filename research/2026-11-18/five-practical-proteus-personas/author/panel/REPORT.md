# UX-проба 3/5: автор Rust-панели, взаимодействие без Core

**Что получилось:** копируемый исходный пример в `example/`, не готовое установленное расширение. Четыре новых файла, **79 строк**: 13 Cargo, 10 manifest, 22 адаптер, 34 модель + UI. Три действия. Никаких правок upstream и ни одного дополнительного продуктового крейта. Проверочное окружение и отчёт в эти 79 строк не входят.

**Вход:** [README: состав Rust-пакета](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/README.md#L107-L130) объяснил, что писать под `packages/<id>`, SDK уже в workspace. [Настоящий манифест Files](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/files/extension.json#L7-L21) показал именно боковую `panel`. [Инструкция Desktop](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/docs/extensions.md#L3-L16) нужна для независимости от Core. [PROTOCOL](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/PROTOCOL.md#L485-L492) дал имя поля `disabled`; [SDK::ui](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/sdk/src/ui.rs#L5-L28) показал `.with` для него. Для связки с действиями нужны [обязательный render и необязательный action](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/sdk/src/lib.rs#L59-L75); действующий [TPS action](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/tps/src/main.rs#L130-L135) меняет локальное состояние, [main](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/tps/src/main.rs#L171-L173) передаёт его `run`. Из SDK/примеров брались публичные сигнатуры и строители, не реализация транспорта.

**Фактический путь чтения:** три пользовательских руководства (README, PROTOCOL, extensions.md); корневой Cargo, Cargo SDK и Cargo образца; manifest Files; публичные API SDK и короткие участки TPS. Только при верификации понадобились точные объявления Desktop виджетов и их полей. Никакой обычной анкеты, файлов пользователя, работающего репозитория пользователя или доступа к Core для панели нет. Предыдущая проба #193 проверяла статичный Python-список, а не Rust-пакет, обработчики и согласованность состояний.

**Где застрял:** установка `dependencies.core: false` и использование только чисел/кнопок не позволяют собрать полный SDK без заранее имеющегося `ureq`: он обычная, а не условная, [зависимость SDK](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/sdk/Cargo.toml#L9-L13). Это естественный предел проверенной офлайн-среды, не доказательство неисправности проекта и не основание предлагать патч SDK. Изолированная проверка отвечает на другой вопрос: корректен ли собственный UI и переходы независимо от доставки? Отдельная техническая мелочь стенда: внешнего `/usr/bin/time` нет, до вызова Cargo он остановил первый замер. Повторено с Python perf_counter; это не неудача продукта.

**Личная оценка 3/5.** Модель и три кнопки просты (2/5): по текущему значению строится одна карточка. Но подготовка проверяемого пакета требует разнести «нет зависимости от Core» и «есть зависимость от SDK» и найти самостоятельный путь до проверяемой логики после отсутствующего офлайн-кэша. Самое полезное улучшение для следующего автора: поставить рядом минимальный Rust пример с кнопкой, проверкой чистого UI отдельно от `cargo check` и точным описанием требований к заранее заполненному кэшу. Уверенность высокая в модели/доступности кнопок на уровне схемы; в сборке и живой интерактивности нет положительной проверки.
