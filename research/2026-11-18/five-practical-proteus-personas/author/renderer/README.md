# Tiny Tally: собственный язык блока, без изменения Desktop

**Мой результат как автора: 3/5 по трудности.** Я написал исходный пакет из четырёх файлов и лицензии: он превращает строки `метка: число` в таблицу, складывает повторения и показывает общий итог. Его настоящая функция рендера собрана и выполнена через Cargo offline. **Готового бинарника расширения нет:** полноценный `cargo check` с официальным SDK остановился на недостающей в локальном кэше зависимости `ureq`. Это ограничение данного опыта, не дефект продукта и не свидетельство успешной сборки. Настоящий Desktop пакет не открывал.

## Что видит автор блока

````md
```tiny-tally
Paper: 3
Ink: 2
Paper: 4
```
````

Результат функции: карточка **Total: 9**, в ней строки **Paper | 7** и **Ink | 2**. Группы сохраняют порядок первого появления, регистр значим, пробелы вокруг названия и числа игнорируются. Разрешены неотрицательные целые в десятичной записи, включая 0; отрицательные значения, дроби, пустое название, лишнее двоеточие или переполнение отвергаются с номером исходной строки. Строки пропускаются, только если они пустые. Ошибка возвращает собственный читаемый `text`, а не частично посчитанную таблицу; это выбор автора языка, не проверка системного fallback. Пустой блок тоже возвращает подсказку. См. [фактический вывод](evidence/samples.log), [файл с блоком](checks/fixtures/example.md).

## Как я пришёл от пустой папки к исходному пакету

1. Нашёл в [README Extensions](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/README.md#L28-L37) поставляемый **json-render**. Для меня это наиболее близкий рабочий образец, но не отдельный генератор проекта. У обычной панели другой контракт.
2. По [манифесту образца](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/json-render/extension.json) и [правилам content](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/PROTOCOL.md#L626-L658) создал [extension.json](tiny-tally/extension.json): свой уникальный id и lowercase `languages`, команда на одноимённый бинарник и `surfaces.content.v1`. Объявил [независимость от Core](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/docs/extensions.md#L3-L15). Не копировал чужие preview, инструкции или язык SVG.
3. Сделал [Cargo.toml](tiny-tally/Cargo.toml) для [обычного workspace](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/Cargo.toml#L1-L15) с `packages/*`; [main.rs](tiny-tally/src/main.rs) обрабатывает только content и передаёт `language/source` в собственную логику, по [штатному адаптеру](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/json-render/src/main.rs#L12-L28). Код адаптера написан; обработчик, протокол и хост **не запускались**.
4. В [tally.rs](tiny-tally/src/tally.rs) отделил чистый `render(&str) -> serde_json::Value` от адаптера. Для этих трёх виджетов разрешённое дерево достаточно мало, чтобы построить его непосредственно и независимо проверить относительно конструкторов SDK. [Файл лицензии](tiny-tally/LICENSE-GPL) соответствует лицензии родительского workspace. Для доставки исходный пакет кладётся в `packages/tiny-tally` полной рабочей копии. Не путать каталог исходников и устанавливаемый пакет: манифест указывает на `bin/tiny-tally`, а готовый платформенный бинарник не входит в этот результат.

## Где было неудобно, а где нет

- Конструкторы [table](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/sdk/src/ui.rs#L145-L147) и [card](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/sdk/src/ui.rs#L71-L73) просты. Скрытая цена структуры: даже числовая ячейка должна быть **строкой**, а число ячеек должно совпадать с числом колонок ([тип](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/declarative/widget.rs#L303-L306), [проверка](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/declarative/widget.rs#L744-L753)). Случай с числом — **намеренный тест**, не ошибка, с которой я столкнулся при нормальном запуске.
- Не сразу ясно, что **регистрация имени не равна парсингу Markdown**. [Документация](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/PROTOCOL.md#L634-L658) обещает передачу завершённого блока верхнего уровня; цитаты, списки и незакрытые блоки не подходят для первого smoke-теста. При двух владельцах языка важен порядок включённых расширений. В этом опыте живую диспетчеризацию не проверял.
- Самая неприятная практическая деталь: «функция рисует локальную табличку» и «пакет собирается offline» — разные вещи. SDK системно зависит от `ureq`; отключение зависимости манифеста от Core не удаляет зависимость сборки SDK. На чистой рабочей станции с доступом к зависимостям результат может отличаться. А отдельный Cargo-манифест, который тестирует ровно `src/tally.rs`, пришлось сделать самому.
- **Что бы я изменил первым:** один короткий starter `content-text-to-table` со связанными в одном месте четырьмя исходными файлами, закрытым top-level fence и официальным `cargo test` для чистого рендера без сборки SDK. Смог бы начать с изменения грамматики, а не с поиска правильной поверхности и подбора проверяемых границ.

## Стоит ли вообще заводить язык?

**Для одной готовой таблицы я бы не заводил.** Штатный [json-render](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/json-render/README.md#L22-L46) уже понимает карточки и таблицы. Вот [эквивалентная готовая визуализация](checks/fixtures/equivalent-json-render.md). В этом случае без оград: **24 байта** в `tiny-tally` против **126 байт** minified JSON. Важнее байтов то, что в JSON автор сам должен свернуть повторяющийся Paper и пересчитать заголовок Total. Наша грамматика кодирует именно эти правила; штатный формат описывает уже вычисленные строки. Для повторяемых рукописных отчётов я бы выбрал новый язык; для автоматического вывода уже готовых значений — JSON.

**Уверенность:** высокая в семантике написанной функции и форме трёх проверенных узлов; средняя в оценке удобства (это один опыт); факта готовности к установке нет.

## Повторение без запуска хоста

Нужны Rust/Cargo 2024, совместимые локальные зависимости в offline-кэше. Проверено с rustc 1.95.0 и локальным serde_json 1.0.151; это не утверждение об идентичности всех зависимостей lockfile полного workspace.

```sh
cargo test --offline --locked --lib --manifest-path checks/logic/Cargo.toml
cargo run --offline --locked --example samples --manifest-path checks/logic/Cargo.toml
python3 checks/public_shapes.py /path/to/Proteus-desktop-extensions /path/to/Proteus-desktop
```

Последний шаг принимает **читаемые закреплённые исходники** и rustc/Cargo в PATH. Он проверяет git blob двух файлов и компилирует лишь точные декларации трёх узлов, небольшой блок их проверки и три конструктора (не запускает проект). Отдельно: после копирования `tiny-tally/` в `packages/` полной рабочей копии можно запросить **только компиляцию**: `cargo check --offline -p extension-tiny-tally`. В моём окружении этот последний шаг заблокирован, как указано выше.
