# Proteus глазами пяти потенциальных пользователей и авторов

**Для разовой задачи я бы не писал плагин.** Готовый Markdown даёт сравнительную таблицу, а `json-render` добавляет нативную карточку без Rust. Написать небольшую панель или собственный текстовый формат оказалось посильно. Сложнее понять, где увидеть первый результат и как доказать себе, что расширение действительно работает с нужной версией Proteus. У backend-модуля эта последняя ступень заметно выше.

Пять отдельных ИИ-агентов выполнили пять заданий и сами оценили трудность. Это **не интервью с пятью людьми**, не слепой тест новичков и не время обучения: участники уже знакомы с кодом Proteus. Время ниже — прошедшее время конкретного прохода, вместе с чтением, написанием и проверкой; граница окончания описана в каждом журнале. Пробы шли параллельно. Баллы не усредняем: **1/5** — один очевидный шаг по руководству, **5/5** — без помощи команды не справиться.

### Как это выглядело в пяти пробах

1. **«Хочу посмотреть диаграмму».** На языке пользователя поиск оказался хрупким: «диаграммы Markdown» тоже ничего не дало, тогда как `Mermaid` сработало. Найденный по документации маршрут: **Клиент → Расширения → Диаграммы Mermaid → Пример**. Не нужно устанавливать ещё один пакет или подключать модель ради демо; расширению нужен Node.js ≥20. В дополнительной проверке мы действительно превратили [три узла](user/catalog/mermaid/diagram.mmd) в [этот SVG](user/catalog/mermaid/diagram.svg) штатным движком из репозитория, с Node 24 и без worker. **Окно и саму кнопку не открывали.** [Маршрут и результаты поиска](user/catalog/REPORT.md).
2. **«Мне нужна таблица, а не плагин».** Для трёх цен и сроков лучший путь — [обычная таблица Markdown](user/visual/examples/simple-table.md). Если нужен именно вид карточки, есть [готовая просьба для чата](user/visual/examples/paste-into-chat.txt) и [пример ожидаемого ответа](user/visual/examples/expected-answer.md). Важное различие: исходник, введённый **пользователем**, по умолчанию остаётся буквальным текстом. Штатные визуализации здесь проверены на **подготовленном ответном блоке**: модель его не генерировала. Неудачные варианты подсказали, что цену-ячейку нужно записать строкой, а заголовок принадлежит карточке, не самой таблице. [Подробности](user/visual/README.md).
3. **«Хочу две кнопки и сброс».** В [счётчике](author/panel/example/) отделить состояние от рисования оказалось удобно: одна и та же модель объясняет подпись и доступность кнопок на границах 0 и 999. Больше внимания потребовало согласование ID, имени бинарника, manifest и строк действий. Получившиеся деревья сверены с настоящими конструкторами SDK и соответствующей частью схемы Desktop. Полный `cargo check --offline` остановился на незакэшированном `ureq` общего SDK, хотя этой панели не нужен Core. **Это не ошибка компиляции кода панели и не проверенные живые клики.** [Четыре файла и инструкция](author/panel/README.md) · [мнение автора](author/panel/REPORT.md).
4. **«Хочу свой маленький язык».** [Tiny Tally](author/renderer/tiny-tally/) принимает `Paper: 3`, `Ink: 2`, `Paper: 4` и сам выдаёт строки 7 и 2, итог 9. Так собственный формат делает полезное вычисление, а не просто экономит скобки JSON. Чистая реализация собрана Cargo офлайн, пройдены 5/5 тестов; ошибка во второй строке не даёт частичной таблицы. Дерево сверено с используемыми ветвями реального Desktop-типа. Полный адаптер также не собрался из-за отсутствующего `ureq`. Для одного статического отчёта автор выбрал бы `json-render`; для регулярного ввода с суммированием — свой формат. [Примеры и границы](author/renderer/README.md).
5. **«Хочу дать модели новый инструмент».** [Счётчик слов](author/backend/word-count/) принимает строку и возвращает результат с исходным `call_id`. Попробовали **официальный starter без изменений**: `cargo build --locked --offline` не смог получить отсутствующий в кэше закреплённый SDK `59da60a`. Простая подмена SDK тоже не заработала из-за несовпадающего lock. Только отдельная копия с уже имевшимся официальным `b2c285f` **и соответствующим lock** собрала полный бинарник за 26,3 с при той первой сборке. Запускался собственный библиотечный тест на типах SDK, в том числе Unicode-пробелы и ошибочная схема. Не проверялись регистрация, обмен с worker и вызов моделью. Это не проверка рекомендованного pin и не совет менять lock в основном проекте. [Как повторить](author/backend/REPLAY.md) · [что автор счёл сложным](author/backend/REPORT.md).

### С чего бы я начал улучшение

1. **Дать результат до настройки.** В найденной карточке каталога предложить видимое **«Попробовать без модели»**, ведущее к уже существующему примеру. Рядом дать правильное ожидание: «визуализируется в ответе; ваше сообщение показывает исходный текст». Проверка успеха: человек, введя «диаграмма» в единственном числе, находит нужную карточку и может открыть демонстрацию, не настраивая модель. Уточнить, какие встроенные демонстрации всё же требуют локального инструмента вроде Node.
2. **Одна проверка для автора до запуска хоста.** Дать два коротких поддерживаемых starter: `action → state → widget` для панели и `text → widget` для content-расширения. Команда вроде *«проверить пример»* должна выдать итоговое дерево и понятную ошибку с местом, где нарушена схема. Рассмотреть отделение UI-конструкторов от HTTP-зависимости или готовый набор офлайн-зависимостей. Это предложение, не существующая команда. Критерий: новую ошибку поля можно исправить без регистрации worker и серверного аккаунта.
3. **Сделать совместимость backend-starter проверяемой.** Показать вместе ревизию SDK, toolchain, lock и короткий тест `аргументы → ToolResult`. Предусмотреть ясное сообщение, чего не хватает локально, и разделить три состояния: «логика проверена», «бинарник собран с совместимой версией SDK», «модуль зарегистрирован и вызван». Исследование дошло до первых двух только на явно оговорённом альтернативном SDK; третье не подтверждено.
