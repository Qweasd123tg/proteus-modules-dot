## Главное для Proteus

1. **Возобновляемый диалог, durable engine и безопасное повторение effect — три разные задачи.** PydanticAI отделяет pending approvals, message snapshots, effect ledger и backend activities. В Proteus значительная часть соответствующего ownership уже существует; не нужно делать второй Core в модуле.
2. **Максимальная гибкость не означает, что любой runtime plugin можно исполнить в replay.** PydanticAI допускает dynamic discovery, но требует зарегистрированного durable boundary и повторной worker-side validation. Несовместимые runtime additions отклоняются.
3. **Реальный полезный gap — consumer фактов.** У Proteus уже есть journal/projection/replay/eval consumers. Можно спроектировать узкий read-only recovery inspector для оператора, но нельзя получить raw effect facts из обычного ConversationView или дать модулю скрытый доступ к session files.
4. **Практический quote consumer уже реализован отдельно:** `evidence.verify_spans` проверяет exact bytes независимо прочитанного source artifact; он не утверждает source authenticity, semantic truth, durable resume safety или permission на memory write.

## 1. Approval: не переносить bool как полномочие

PydanticAI различает deferred внешнее исполнение и запросы approval. Helper проверяет, что IDs результатов принадлежат ожидаемой категории; массовое approve_all — явная политика caller, а не безопасность по умолчанию. Capability может решить pending calls inline; оставшиеся запросы возвращаются как terminal output. Это **механизм управления run**, а не persisted inbox или удостоверенная человеческая подпись. [Типы и category binding](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/_deferred.py#L29-L105), [inline handler](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/capabilities/deferred_tool_handler.py#L13-L75).

Consumer важнее формата: resume ищет последний model response, не разрешает заменить уже сохранённый tool result; duplicate IDs batch отклоняются; override_args утверждённого call повторно валидируются через manager. Inline resolution проходит один раз; повторный defer становится остатком pending batch, а не скрытой бесконечной очередью. [Resume](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/_agent_graph.py#L805-L857), [approval validation](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/_tool_execution.py#L674-L718), [one-shot resolution](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/_tool_execution.py#L1094-L1180).

**Уже есть в Proteus:** call identity, lifecycle owner, requested→approval→resolved проверяются в journal. WorkflowContinuation — продолжение того же host-reviewed root turn без нового user message; оно не равно долговременному human wait. Не переносить foreign approved=true через эту границу. [Journal validation](https://github.com/Proteus-harness/Proteus-core/blob/1fc3ef223d10322815dd9290a50d045bc95402bb/crates/proteus-core/src/core/session_journal/projection.rs#L266-L341), [continuation contract](https://github.com/Proteus-harness/Proteus-core/blob/1fc3ef223d10322815dd9290a50d045bc95402bb/crates/proteus-contracts/src/contracts/workflow.rs#L84-L103).

## 2. Recovery: история разговора не является effect ledger

StepPersistence имеет отдельные step events, snapshots и tool-effect records. Восстановление читает newest и settled frontier, unresolved records и completed/failed tool names. В коде recovery намеренно нет запуска tools или переписывания history. Completed effect ещё не означает, что normalized result вошёл в checkpoint; failed не доказывает отсутствие внешнего действия. [Формы фактов](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_types.py#L29-L128), [recovery consumer](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/recovery.py#L1-L35).

После settled CallTools node сохраняется snapshot с returns, которые ещё не обязательно находятся в текущем message list. На ошибке сохраняется live history, complete/interrupted определяется pairing. Default continuation не выбирает interrupted frontier; explicit opt-in и проверка effects остаются обязанностью orchestrator. Error hook не заменяет checkpoint до hard kill. [Boundary/error capture](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_capability.py#L487-L566), [settled node snapshot](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_capability.py#L668-L726), [continue/fork consumer](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_helpers.py#L61-L95).

**Уже есть в Proteus:** raw ToolEffectRecorded и final ToolResultRecorded — разные journal facts; AfterTool failure сохраняет settled raw result. Current JournalProjection содержит полный records и unresolved/interruption sets. Важная тонкость для UI: unresolved_tool_calls — только calls без result **и без effect**; effect-without-final-result нужно читать из existing records. EvalReport уже агрегирует effect/result, replay fixture хранит raw_result отдельно. Это не отсутствие ledger и не обнаруженная runtime ошибка. [Raw/final boundary](https://github.com/Proteus-harness/Proteus-core/blob/1fc3ef223d10322815dd9290a50d045bc95402bb/crates/proteus-core/src/core/bound_tools/hooks.rs#L92-L130), [projection](https://github.com/Proteus-harness/Proteus-core/blob/1fc3ef223d10322815dd9290a50d045bc95402bb/crates/proteus-core/src/core/session_journal/projection.rs#L544-L620), [existing eval consumer](https://github.com/Proteus-harness/Proteus-core/blob/1fc3ef223d10322815dd9290a50d045bc95402bb/crates/proteus-core/src/core/eval_report.rs#L130-L160).

## 3. Persistence: lifetime key и transaction важнее слова durable

Run ID не должен переиспользоваться как multi-turn conversation ID. Durable registration distinguishes retry того же registration от нового run. Snapshot key имеет run-local sequence/step/state, а replay-local snapshot comparison не читает меняющийся внешний store для выбора следующей ветки. [Registration](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_capability.py#L236-L267), [snapshot producer](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_capability.py#L331-L389).

В PostgreSQL consumed snapshot keys живут независимо от retained snapshots; claim key, messages и snapshot записываются в transaction. Retention сохраняет newest и newest complete, даже когда они выходят за простой last-N window. File backend делает другие шаги: snapshot replace, затем отдельный key-log append; прочитанный replacement helper не делает fsync. Нельзя приписывать всем stores одну crash guarantee. Это статическое различие алгоритмов, **не воспроизведённый corruption/crash bug**, и не аудит DB configuration. [PostgreSQL transaction](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_postgres.py#L337-L377), [retention](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_store.py#L133-L152), [file writes](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/src/pydantic_ai_harness/pydantic_ai_harness/step_persistence/_store.py#L694-L731).

**Применение:** будущая correction-memory операция должна иметь реальный backend conditional write + independent idempotency record; host authority и conflict policy задаются отдельно. Quote witness не создаёт ни CAS, ни persistent receipt store.

## 4. Durable execution: настоящая backend boundary, а не DTO

Backend binds operation identity, transport/codec, config и callable/registered primitive. Temporal backend создаёт named activities и worker handlers. Dynamic discovery, validation и call имеют producer/consumer chain; worker повторно получает реальный tool и валидирует args. Нельзя после регистрации просто добавить произвольную executing capability в run: она не имеет зарегистрированного durable unit. [Backend](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/_operation_backend.py#L74-L193), [Temporal registration](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_operation_backend.py#L96-L224), [dynamic producer](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/_base.py#L1302-L1397), [runtime additions](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/_base.py#L784-L842).

Opt-out activity wrapping разрешён не всем: Temporal отвергает его для dynamic/MCP tools и sync tools. Это tradeoff в пользу детерминированного replay, а не безусловная максимальная plugin свобода. Actual Temporal server/SDK internals здесь не проверены; код adapter не доказывает exactly-once внешней операции. [Config gate](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_durability.py#L401-L432).

Resource lifecycle зависит от расположения процесса. Same-process units могут держать один lazy-entered toolset с lock и close на run exit. Serialized units без доступа к объекту resolve/enter его отдельно; «тот же run» не гарантирует прежнюю MCP/browser session. [Owned lifecycle](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/_toolset.py#L128-L216).

## 5. Cancellation и concurrency: не смешивать разные свойства

Обычный batch разбивается sequential barriers, но non-barrier tools параллельны. Ordered-event mode меняет presentation/exception order, не превращает effects в serial execution. При сбое уже completed returns собираются в interrupted history, даже если отдельный event ещё не был выпущен. [Batch algorithm](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/_tool_execution.py#L886-L978).

Drain использует shield и ожидает unwinding; Temporal wrapper shield-ит handle, отправляет один cancel и ждёт configured cancellation resolution. Собственного fixed total drain timeout в этих wrappers нет. У Proteus другая уже существующая policy: bound invocation даёт cooperative cancel settlement grace500ms. Нельзя назвать перенос shield алгоритма безусловным улучшением: надо выбрать bounded wait/abandon/reconciliation semantics. [Drain](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/_utils.py#L312-L329), [activity wrapper](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_activity_execution.py#L38-L53), [Proteus settlement](https://github.com/Proteus-harness/Proteus-core/blob/1fc3ef223d10322815dd9290a50d045bc95402bb/crates/proteus-core/src/core/bound_tools/invocation.rs#L8-L122).

Temporal использует workflow clock/UUID и patch marker для старых histories; обычный process-local cancellation token внутри durable context отвергается. Continue-as-new — opt-in handler с обязанностью собрать реальные resume arguments. Это не synonym для Proteus same-root WorkflowContinuation. [Clock/identity](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_durability.py#L458-L493), [token rejection](https://github.com/pydantic/pydantic-ai/blob/715651ef7fd3994395e85070ba3d6096c5b211c9/pydantic_ai_slim/pydantic_ai/durable_exec/_base.py#L844-L856).

## Реальные consumer proposals, не очередной каталог DTO

### A. Уже созданный evidence.verify_spans

Use case: исследователь цитирует pinned source, reviewer проверяет локальный artifact через разрешённый host reader. Выход связывает exact digest/span с source/config/path/call IDs. Отдельный [реальный research use case](../round3/EVIDENCE-SPANS-RESEARCH-USECASE.md) содержит настоящий OpenHands artifact/hash/span, не только Unicode fixture.

Модуль прошёл независимый source review; compilation/runtime CI в этом research report не утверждается. Runtime status требует отдельной квитанции CI на точном commit модуля.

### B. Read-only recovery inspector — сначала app/host consumer

Use case: после прерывания оператор видит tool effect recorded, final result recorded, uncheckpointed/unknown categories и выбирает расследование, а не автоматический replay.

Минимальная реализация может опираться на **существующую** validated JournalProjection на app/Core side. Нужны: выбранная host-авторизованная session, revision/record boundary, correlated fact categories и ясное отсутствие execute/resume grant. Не нужна новая persistence и не нужен новый execution owner.

Если требовать это именно от внешнего tool module, нужен отдельно одобренный bounded/redacted host read contract: ConversationView полного journal намеренно не содержит. Нельзя обойти это прямым session-directory FS read. Existing eval/replay остаются отдельными consumers, не дублируются.

### C. Durable review inbox — только при реальной долгой задаче

Use case: подготовленная fact correction ждёт reviewer за пределами одного process/turn. Proposal хранит artifact digest, target block revision, exact proposed replacement и desired action; reviewer decision связан с этой версией. После restart host заново проверяет authority, target revision и backend idempotency. Это **не исполнено и не реализовано**.

Минимальные обязательства: authenticated approver; pending identity с expiry/cancel state; transactional decision store; claim/attempt ownership; explicit stale-decision handling; actual conditional-write backend и reconciliation. Ни Pydantic deferred DTO, ни WorkflowContinuation, ни evidence receipt сами этого не дают. Пока нет нужного backend — лучше bounded in-turn approval или read-only report.
