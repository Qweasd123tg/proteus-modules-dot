# Прототип host-owned mutation leases

**Статус:** небольшой прототип автомата состояний на Rust, не подключённый к Proteus Core.
Используется только `std`; файловых операций, процессов и сетевых вызовов нет.
Это не новый file tool, async runtime или параллельный scheduler; флаги
`supports_parallel_tool_calls` не меняются. Сборки, тесты, benchmarks и CI не запускались.

## Что перенесено из Pi

[Очередь файловых изменений Pi](https://github.com/earendil-works/pi/blob/ad702637fdf6fbd3f965c5dba0b14bae100b74eb/packages/coding-agent/src/core/tools/file-mutation-queue.ts)
сериализует операции с одинаковым ключом файла. В [реализации write](https://github.com/earendil-works/pi/blob/ad702637fdf6fbd3f965c5dba0b14bae100b74eb/packages/coding-agent/src/core/tools/write.ts#L66-L87)
очередь удерживается до завершения текущего filesystem await даже после отмены.
Здесь перенесён **принцип владения ресурсом до завершения эффекта**, а не сама очередь путей.
Захват нескольких ресурсов, incarnation ID, типизированное подтверждение завершения
и карантин workspace — предлагаемые контракты Proteus, не свойства, приписываемые Pi.

Pi write также вызывает `mkdir(parent)`: одного ключа целевого файла недостаточно
для доказательства полноты footprint. Ни process-local map Pi, ни эта библиотека
сами по себе не координируют независимые процессы.

## Один окончательный владелец на стороне host

Доверенный владелец workspace последовательно вызывает один `Coordinator` и хранит
его независимо от futures вызывающей стороны. `InvocationId` — не RAII guard:
удаление ID или requester future не освобождает сохранённый lease. У `Coordinator`
нет `Clone`, срока истечения или callback освобождения при drop. Сам владелец должен
оставаться жив, пока возможны эффекты; ограничения при его падении описаны ниже.

Для эксплуатации **все участвующие writers должны обращаться к одному реальному
владельцу** через host/IPC либо согласованный механизм OS locks. Два экземпляра,
локальный mutex внутри модуля или одинаковая строка workspace этого не обеспечивают.
Операции между несколькими workspace требуют общего домена владения, а не отдельных
координаторов, каждый из которых считает свой участок независимым.

Захват после `before_tool` защищает **только эффекты инструмента, допущенные после
этой точки**. Произвольный hook может записывать раньше; такие записи не защищаются
задним числом. Pre-/after-tool hooks, внешние редакторы, nested callbacks и прочие
writers должны явно участвовать в том же coordinator/OS-протоколе. Вставка в
`invoke_allowed` сама по себе не означает безопасность всего workspace.

Соседний [прототип resource admission policy](../resource-admission-policy/README.md)
предлагает API:

```text
AdmissionPolicy::plan(&PendingQueue, &ResourceSnapshot)
    -> Result<GrantPlan, AdmissionError>
```

`GrantPlan` можно скопировать или сконструировать: это **предложение, не lease и не
разрешение на dispatch**. Невыполнимый demand возвращается как ошибка, не частичный
план. Epoch, revisions и доступную ёмкость проверяет тот же доверенный host owner.
Будущий адаптер должен согласованно резервировать capacity и mutation resources до
начала эффектов; отменить промежуточную резервацию можно лишь при доказанном отсутствии
dispatch. Этот общий транзакционный адаптер здесь не реализован; второго независимо
исполняющего scheduler нет. Права по-прежнему определяются policy/approval.

Аргументы, идентичности, epoch, nesting и `SettlementEvidence` — **утверждения
доверенного host**, а не факты, проверенные библиотекой. Нельзя напрямую превращать
ответ модели или tool payload в эти значения. Доступ к `&mut Coordinator` остаётся
за host boundary. Типизированный enum явно выражает требуемое доказательство,
но сам не доказывает остановку записей и не расширяет filesystem/sandbox permissions
или право invocation вызывать host callbacks.

## API и переходы

| API | Поведение |
| --- | --- |
| `new(workspace, owner_incarnation)` | Создаёт одного владельца; incarnation задаётся host и уникален между его перезапусками. |
| `enqueue(epoch, footprint, nesting)` | Ставит запрос в очередь; host связывает ID с неизменным окончательным вызовом. Nested acquisition отклоняется. |
| `try_admit(id)` | Захватывает весь отсортированный набор без дубликатов либо ничего. Более ранние конфликтующие запросы нельзя обогнать; независимые — можно. |
| `mark_dispatched(id)` | Переводит Reserved → Dispatched **до** запуска эффекта; отклоняет ушедшего requester и workspace с unknown barrier. |
| `requester_departed(id)` | Отменяет только Queued. Для Reserved/Dispatched/Unknown удерживает lease; сама не отправляет отмену процессу. |
| `report_unknown(id)` | Переводит Dispatched → Unknown, сохраняет footprint и блокирует новые admission и dispatch в workspace. |
| `settle(id, evidence)` | Освобождает Reserved только с `NeverDispatched`, а Dispatched/Unknown — с `EffectsQuiescent` или `EffectTreeExited`. |
| `status(id)` | Возвращает epoch, footprint, phase и состояние requester только для чтения. |
| `forget_terminal(id)` | Удаляет лишь завершённую историю после сохранения host-аудита. Номера ID не переиспользуются. |

### Жёсткие ограничения размера

| Константа | Предел |
| --- | --- |
| `MAX_RECORDS` | 256 записей всего, включая terminal records. |
| `MAX_RESOURCES_PER_FOOTPRINT` | 128 входных ключей до удаления дубликатов. |
| `MAX_OWNER_IDENTITY_BYTES` | 1024 UTF-8 bytes отдельно для workspace и owner incarnation. |
| `MAX_RESOURCE_KEY_BYTES` | 1024 UTF-8 bytes на resource key. |

Переполнение числа записей/ключей или размера owner identity возвращает типизированную
`Error::Capacity`; слишком длинный resource key — `Error::InvalidFootprint` с индексом.
Проверки выполняются до вставки состояния и расходования sequence ID. Пустая owner
identity по-прежнему недопустима. Пустой footprint/ключ **в пределах входных caps**
по-прежнему означает `WorkspaceExclusive`; явно неизвестный footprint host передаёт
как `WorkspaceExclusive`. Oversized вход отвергается, а не молча обрезается.

Активные/Unknown leases никогда не вытесняются. Terminal records освобождаются только
явным `forget_terminal` после сохранения host-аудита; при заполнении всех 256 записей
новые enqueue отклоняются. Сохранённые Vec/String пересоздаются из ограниченных slices,
чтобы не удерживать чрезмерную backing capacity переданных значений.

Это пределы числа элементов и байтов содержимого, **не точный предел всей памяти
процесса**: исходные caller-side allocations, внешние копии ID/records, временное
сосуществование входа и нормализованной копии, структуры контейнеров и накладные расходы
allocator не входят в гарантию. До передачи больших данных host нужен собственный
ограниченный входной протокол; этот API не может отменить уже выполненную аллокацию.

Нет частичного захвата, расширения активного footprint, автоматического retry,
таймеров, futures, запуска workers или очереди пробуждений. Host определяет, входит
ли ожидание очереди в deadline, отменяет его через `requester_departed` и повторно
проверяет admission по событиям изменения состояния; busy polling не требуется.

Configuration epoch сохраняется для привязки и аудита, **но не входит в ключ
конфликта**. Новая epoch не освобождает старый lease и не создаёт независимую область
блокировок. Host сохраняет семантику идентичности между epoch либо сначала дожидается
завершения эффектов во всём домене. Сбросить coordinator для обхода барьера нельзя.

## Контракт footprint

`Resources` означает, что host установил **полный и стабильный набор конфликтов**
окончательного вызова. Строки — непрозрачные идентификаторы, не canonicalizer путей.
При enqueue ключи сортируются, дубликаты удаляются; пустой список или пустой ключ
превращаются в `WorkspaceExclusive`. Для shell, неизвестного/неполного footprint и
неподдерживаемой идентичности host обязан выбирать exclusive самостоятельно.

- Rename учитывает source, destination и затронутые parent/namespace resources.
- Patch захватывает весь набор изменений до первой записи.
- Create/mkdir/remove учитывают родителей, изменение пространства имён и остальные затронутые ключи.
- Symlinks, hardlinks, регистр, отсутствующие пути и операции над поддеревом требуют
  совместимых host-идентификаторов. Библиотека определяет пересечение только точным
  равенством строк; иерархию путей она не анализирует.
- Host повторно проверяет идентичность при admission и защищает её от изменений до
  использования. Одного `realpath` перед незащищённой записью недостаточно. Если
  нельзя корректно представить aliases/поддеревья или обеспечить эту проверку,
  необходим workspace-exclusive режим.
- Даже exclusive защищает только участников протокола и не заменяет безопасную
  работу с путями, OS permissions и sandbox.

Host фиксирует окончательный вызов и связывает точные args/epoch с ID. Изменение до
dispatch делает эту привязку недействительной. Queued можно отменить и описать заново;
для Reserved сначала требуется явное `NeverDispatched` settlement. Dispatched/Unknown
нельзя скрыто поставить заново с другим или расширенным footprint.

Nested mutation acquisition отклоняется, даже для независимых ключей. Будущая
интеграция требует явного контракта использования поднабора parent lease и завершения
всего дерева эффектов. Неявный reentrant lock или ложный `TopLevel` скрывают deadlock
или расширение доступа. Существующему nested host-callback пути Core нельзя молча
выдать ещё один lease: его владение и полномочия пока требуют отдельной интеграции.

## Ответ requester не равен завершению эффекта

В закреплённом [Core invocation boundary](https://github.com/Proteus-harness/Proteus-core/blob/125a9eb4088991513e9f61d899469be2076e266c/crates/proteus-core/src/core/bound_tools/invocation.rs)
после timeout/cancel invocation продолжают опрашивать до 500 ms, а результат этого
ожидания отбрасывают перед формированием ответа. Это **не доказательство остановки
физических эффектов**. Успешный `ToolResult` и cancel ACK также недостаточны, если
worker или делегированные операции могут продолжать запись.

Доверенный owner отслеживает фактическое время жизни эффектов после завершения/drop
requester. Он может передать отмену, дождаться или остановить исполнителя в пределах
существующих полномочий; сохранение lease не продлевает права invocation на host calls.

- `EffectsQuiescent`: все записи и делегированные/удалённые эффекты завершены,
  invocation больше не может начать изменение.
- `EffectTreeExited`: то же свойство обеспечено для всего дерева исполнителей,
  способных изменять ресурсы. Выход RPC wrapper или родительского процесса недостаточен,
  если detached child либо удалённая операция ещё могут писать.

При неизвестном исходе или потере supervision вызывается `report_unknown`: барьер
останавливает новые admission **и запуск уже зарезервированных операций**. Ранее
начавшиеся эффекты могут завершаться; карантин их не откатывает. Каждый Unknown
удерживает свой барьер до trusted settlement. Timeout, новая epoch, drop future,
cancel ACK и ошибка результата его не снимают. Автоматически повторять операцию с
неясными эффектами нельзя. Settlement снимает защиту порядка, но не обещает успех,
rollback или атомарность изменения нескольких файлов.

Прототип хранит состояние только в памяти и сам не переживает падение owner.
Для production нужны supervision и устойчивое восстановление unknown-state либо
остановка/сверка всех старых workers до новых admission. Новый incarnation отвергает
старые ID, **но не доказывает остановку старых workers**. Потеря или замена coordinator
не являются допустимым способом settlement.

## Точка интеграции — без патча Core

1. Сохранить существующие [validation, before-tool hooks и policy/approval](https://github.com/Proteus-harness/Proteus-core/blob/125a9eb4088991513e9f61d899469be2076e266c/crates/proteus-core/src/core/bound_tools.rs#L294-L396).
   Hook может заменить вызов: эффективные tool/spec/args следует повторно проверить.
2. В `BoundTools::invoke_allowed`, до `tool.invoke`, доверенный адаптер фиксирует
   вызов, определяет полный footprint либо exclusive fallback, связывает epoch/lineage
   и ставит запрос владельцу workspace.
3. Owner перепроверяет идентичность, захватывает весь набор и фиксирует dispatch до
   первого effect-capable poll/send. Supervision живёт независимо от requester future;
   локальный RAII guard вокруг существующего future этого не обеспечивает.
4. Сохранить timeout/cancel ответы requester, но отдельно передавать отмену owner и
   отдельно — доказательство физического settlement. Если 500 ms истекли без него,
   отметить Unknown, а не освободить lease.
5. Подключить nesting, всех участников, идентичности и recovery после перезапуска
   прежде, чем считать независимые mutations параллельно-безопасными. Этот crate не
   основание переключать `supports_parallel_tool_calls`.

**Неподключённые части:** реальный workspace host owner/IPC или согласованная OS
координация, Core effect supervision/settlement adapter и общий capacity+mutation
transaction adapter. Это технические условия интеграции, не уже реализованные
возможности. Изменения production scheduling и измеренного ускорения нет.

## Сценарии для последующей проверки пользователем

Это ожидаемое поведение, **не выполненные тесты и не отчёт об успешной проверке**:

- Разный порядок одинаковых ключей нормализуется одинаково; rename захватывает всё или ничего.
- Независимые вызовы могут резервироваться вместе; более ранний конфликтующий
  запрос, включая exclusive, нельзя обогнать.
- Отмена Queued не требует settlement; отмена Reserved требует `NeverDispatched`
  и запрещает последующий dispatch.
- Drop/timeout requester сохраняет dispatched lease и после 500 ms.
- Unknown A блокирует новый B и dispatch уже Reserved B даже при независимых ключах.
- Settlement одного Unknown не снимает барьер другого; `NeverDispatched` не подходит
  для Dispatched/Unknown.
- Новая epoch не обходит конфликт; stale/wrong-owner ID не освобождает более новый
  вызов; очистка истории не удаляет активный lease.
- Повторный dispatch/settlement и nested acquisition отклоняются, не перезапускаются.
- Превышение caps не вставляет запись и не расходует ID; terminal records учитываются
  в лимите, активные/Unknown не вытесняются, oversized footprint не обрезается.

Исходники изучались только чтением. Сборки и тесты оставлены пользователю по его просьбе;
при подготовке этого прототипа clones, CI, публикация и upstream mutations не выполнялись.
