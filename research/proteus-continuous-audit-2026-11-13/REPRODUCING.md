# Как читать и повторять проверки

## Проверка доставки без выполнения кода продукта

Из этого каталога:

```sh
python3 restore_evidence.py --verify-only
python3 restore_evidence.py --group reconnect-state --output /tmp/proteus-reconnect-evidence
```

Вторая команда создаёт новую папку с `evidence/reconnect-state/`, проверяя SHA-256 до записи. Существующую папку она не перезаписывает. Без `--group` восстанавливаются все наборы, около 108 MB текстов. Для новых прогонов удобнее отдельная рабочая копия: программы из evidence этот helper **не запускает**.

1386 JSON/JSONL файлов собраны в 33 `RAW_DATA.tar.gz`; архивы содержат только текст, не программы или базы данных. Их имена после восстановления совпадают с именами из исходных отчётов, и прежние локальные SHA256SUMS остаются исторически проверяемыми для включённых файлов. Исходные manifest отдельных пакетов могут также перечислять исключённый cache или путь до перекладки; актуальный состав публикации задаёт только корневой `MANIFEST.json`.

## Повтор одного finding

1. Откройте конкретный REPORT/README и его addenda. Сверьте источник, baseline SHA, SDK pins и тип доказательства. `main` может уже уйти вперёд.
2. Подготовьте отдельные checkout указанных Proteus-репозиториев. Сборочные команды, Rust/toolchain, manifests и необходимые компоненты различаются. Здесь намеренно нет единого «запусти все»: наборы не являются одним Cargo workspace.
3. Восстановите нужный каталог. Проверьте у воспроизводителя `--help` и исходник. Некоторые ранние scripts сохраняют абсолютные ROOT/CORE/MODULES пути исходного запуска; замените их своими локальными путями или передайте предусмотренные аргументы. Изменение путей не равно изменению проверяемого production-кода.
4. Применяйте test-only patch только к соответствующей временной pinned копии. Не применяйте candidate fix вместо regression и не складывайте независимые patches в общий checkout без проверки конфликтов.
5. Используйте только новые синтетические профили, сессии, репозитории и loopback endpoints. Worktree/cleanup probes намеренно проверяют удаление временных данных; запуск на рабочем проекте не предусмотрен. Не нужны настоящие API keys или пользовательские сессии.
6. Сначала сравните observational output и положительный контроль, затем desired-invariant regression. Ожидаемый exit 1/101 до исправления не следует трактовать как неисправный runner. После patch повторите оба и смежные gates.

## Что не следует выводить из публикации

- Публикация проверила целостность текста и переносимость контейнера доказательств, **не повторила 95 наборов**.
- Exact-source headless adapters заменяют GUI scheduler/rendering. Они не доказывают частоту гонки или полный native click path.
- Fake-model и synthetic HTTP позволяют детерминированно проверить runtime/wire contract, но не оценивают качество live LLM.
- Положительный контроль одного набора не подтверждает весь продукт. Совместимость четырёх `main`, полный GUI/portable и restricted sandbox требуют отдельных прогонов.
- Candidate patches в отдельных каталогах иллюстрируют узкое направление исправления и не объявляются готовыми к upstream.

## Исключения из evidence

43 файла не включены: производные SQLite read caches, иконные caches и source `AGENTS.md`. Точный список и причины в `MANIFEST.json`. Собранных executable, build targets и дублирующих ZIP здесь нет. Исходные тексты, включая большие raw synthetic journals, сохранены без потери данных; сжатие tar/gzip обратимо. Безопасные фиктивные значения вроде `fixture-not-a-secret` остаются, настоящие учётные данные не нужны.
