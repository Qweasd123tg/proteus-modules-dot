# Proteus: ориентир и аудит документации

Срез 4 ноября 2026. Исследовательские заметки и предложения, а не изменённая спецификация или утверждённый план. Проверка по документации и исходникам; сборка и тесты не запускались.

## Зачем нужен Proteus

Proteus — конструктор разных агентных систем: небольшого специализированного агента, coding-agent, системы с памятью или комбинации идей из Hermes, Codex, Claude Code и других проектов. Цель — взять понравившийся механизм, реализовать или заменить подходящий модуль и продолжать пользоваться своей платформой.

[Продуктовая спецификация](https://github.com/Proteus-harness/Proteus-core/blob/bf3af030dd0a6c7323d067f95098319252eef14a/docs/product/spec.md) уже описывает этот замысел. Codex — первый пример сборки, а не определение платформы. Чат, модель и инструменты разработки нужны не всем агентам.

## Пакет возможности как целевой опыт

Пользователю ближе установка целой возможности одним пакетом и одним действием. Например, пакет памяти может объединять логику агента, инструменты, обработчики и панель Desktop. Аналогия — пакетная система Linux: одна возможность снаружи, несколько компонентов внутри.

Это **целевой пользовательский опыт, а не описание уже реализованного формата**. Внутренние части могут сохранять разные типизированные контракты, права и жизненные циклы; единая установка не означает универсальный всемогущий API.

Сегодня в Desktop уже есть [общий каталог](https://github.com/Proteus-harness/Proteus-desktop/blob/6e66189b50c112cf13448fc1feaa1eee5a3c85d6/examples/catalog/README.md), который знает расширения клиента, Agent Plugins, skills и MCP. Он пока не устанавливает backend process modules, а запись каталога представляет один тип. Установка цельной возможности из разных частей пока не заявлена как работающая.

Вопросы для отдельного проектирования: состав пакета и совместимость версий, зависимости, выбор профиля, установка и активация, права, обновление, откат и удаление. Нет необходимости заранее вводить всё это или менять runtime ради одного описания цели.

## Карта проекта

- [Core](https://github.com/Proteus-harness/Proteus-core): contracts, сборка агента, жизненный цикл, разрешения, история и API.
- [Modules](https://github.com/Proteus-harness/Proteus-modules): реализации workflow, моделей, инструментов, контекста и hooks.
- [Desktop](https://github.com/Proteus-harness/Proteus-desktop): приложение, общие элементы UI, каталог и интеграция с Core.
- [Desktop Extensions](https://github.com/Proteus-harness/Proteus-desktop-extensions): отдельные UI-пакеты, панели и форматы отображения.

Core↔Modules и Desktop↔Extensions — разные границы ответственности. Похожий транспорт не делает их дублями; пользователю не нужно изучать эти границы для обычного подключения готовой возможности.

## Три уровня расширения

1. Выбрать или заменить реализацию существующего контракта через конфигурацию.
2. Написать новую реализацию существующего контракта: например, другой поиск, workflow или hook.
3. Изменить общую границу Core, если конкретная задача не выражается имеющимися контрактами. Новый самостоятельный slot — не то же самое, что новая фича.

Правило проверки слотов существует, чтобы не плодить одноразовые интерфейсы. Действующая [процедура](https://github.com/Proteus-harness/Proteus-core/blob/bf3af030dd0a6c7323d067f95098319252eef14a/docs/architecture/slot-governance.md) требует две работающие независимые реализации для принятия нового slot; это не относится ко всем новым модулям. Порог не меняется этой заметкой.

Существуют подтверждённые по исходникам примеры переноса идей без нового slot, например [ограниченный адаптер Claude command hooks](https://github.com/Proteus-harness/Proteus-modules/blob/21b29f31de5cbe94951a20eac9354119113bd028/hook/claude-command-hooks/README.md). Он не означает полной совместимости с Claude Code. Standalone workflow возможен без модели и диалога, но произвольный предметный вход и durable settlement пока ограничены: см. [текущее состояние](https://github.com/Proteus-harness/Proteus-core/blob/bf3af030dd0a6c7323d067f95098319252eef14a/docs/product/scope.md).

## Где документация может запутать

1. Общая цель верно описана в Core, но точки входа остальных репозиториев объясняют главным образом локальные технические правила. Полезно ссылаться на единый spec, а не копировать четыре версии видения.
2. Стоит отделить запрет модулю самостоятельно создавать новые права и host contracts от другого вопроса: общего каталога и описания состава пакета.
3. Инструкции проверки conversational Turn не стоит применять буквально к standalone операциям, создавая фиктивный чат.
4. Ограничение provider-specific типов конкретным путём model-pack в Core AGENTS можно сформулировать через границу соответствующей model implementation, не закрепляя единственный pack.
5. Правила совместимости с Codex относятся к режиму, который обещает parity. Заимствование отдельной идеи не делает все сборки копиями Codex.
6. Уточнить различие между поставляемыми рекомендуемыми наборами и привилегированными реализациями: удобные defaults не обязаны получать особые права.
7. В Desktop документы перемешивают концепции, детали запуска и частные UX-правила. Краткая каноническая страница подключения и единый словарь помогут больше, чем новый параллельный менеджер.

### Проверенный дрейф справочников

- Core README предлагает удалённый флаг portable.py --fast; свежая начальная сборка описана в Desktop BUILDING.
- README ещё описывает aggregate reference-module как обычную поставку, тогда как установщик использует самостоятельные process packages.
- Во вступлении modules.md фигурирует model/v12, хотя актуальный контракт v13.
- Modules README указывает Python 3 без уточнения: package.py использует возможности Python 3.11+.

Это предложения исправить тексты, а не признак того, что все перечисленные функции проверены запуском.

## Сравнение с DeepSeek Harness

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) действительно разделяет близкую идею: сервисы, события, цикл агента и другие части подключаются плагинами Cordis. Там проще добавлять новые сервисы и точки композиции. Proteus предлагает более узкую и явно версионируемую процессную границу с authority по контракту и конкретному вызову. Оба подхода имеют типизацию и ограничения; процесс сам по себе не является полноценной песочницей. Rust сам по себе не доказывает превосходство в скорости или безопасности без измерений.

Полезные темы для изучения: жизненный цикл пакета, различие «установлен / включён / активирован», восстановление после неудачного обновления и восстановление дерева агентов. Это источники идей, не поручение копировать Cordis целиком.
