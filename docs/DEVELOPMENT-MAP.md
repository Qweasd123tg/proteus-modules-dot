# Карта разработки

## Где менять поведение

| Задача | Владелец изменения | Здесь |
|---|---|---|
| Добавить инструмент, hook или context provider | Независимый process module с актуальным SDK | `examples/`, `hook/` и process-module примеры в `research/` |
| Изменить алгоритм выбора или ранжирования | Чистая библиотека + явный adapter у её владельца | Новые `modules/` внутри [исследования архитектур](../research/agent-architectures-20261028/README.md) |
| Изменить permissions, admission, отмену или settlement | Host/Core; данные модуля не создают полномочий | Датированный source patch в `foundation/`, `ownership/` или `research/…/runtime-fixes/` |
| Убрать лишнюю сериализацию или копирование запроса | Владелец конкретного representation/model adapter | Минимальный patch с базовым commit и описанием владения |
| Ускорить пересборку одного компонента | Cargo/package boundary и соответствующий launcher | `build-speed/desktop/`, `build-speed/extensions/` |
| Изучить чужого агента | Отчёт по закреплённым первичным исходникам | `research/`; donor behavior и предложение для Proteus описываются отдельно |

## Минимальная поставка

Для нового компонента достаточно кода, manifest и README с назначением, коротким примером подключения, ограничениями и статусом проверки. Дополнительные manifests и verification runners нужны только при конкретной задаче, а не автоматически для каждой библиотеки.

Для изменения upstream достаточно небольшого patch, точной исходной ревизии, перечня затронутых путей и объяснения изменения. Независимые исправления стоит оставлять отдельными patches. Не смешивайте очистку документации с изменением runtime semantics.

Не копируйте на главную страницу SDK версии, длинные команды и результаты каждого модуля: они быстро расходятся. Ближайший к коду README — источник инструкций компонента; главная страница только ведёт к нему.

## Чего избегать

- Deep clone больших history/tools/schema только для сортировки или передачи владения. Сначала проверьте, не нужна ли копия для независимого snapshot, ветки или retry.
- Повторного JSON-разбора уже полученного `Value`, когда проверка исходных bytes не является отдельным контрактом.
- Второго cache, scheduler или journal без необходимости. Сначала найдите существующего владельца и точку расширения.
- Скрытого расширения доступов ради удобства. Selection, metadata и cached facts не заменяют host permission check.
- Документации о старом aggregate binary как о текущем shipping-пакете. Aggregate test fixtures могут оставаться корректными для своих тестов.
- Заявлений «модуль подключён» для pure Rust prototype без SDK/host adapter; «оптимизация измерена» для изменения, доказанного только по исходнику.
- Обновления frozen evidence задним числом. Новый результат сохраняется отдельно со своей ревизией; старый остаётся историческим.

## Проверка

Проверка должна соответствовать затронутому поведению. Read-only source review и применимость patch не равны компиляции или runtime test. При этом отсутствие численного benchmark не требует оставлять явно ненужную allocation/copy: безопасное устранение лишней работы и оценка размера ускорения — разные вопросы.

Для изменений из текущего исследовательского пакета статус проверки указан в его README. Никакой общей команды «пересобрать и проверить всё» эта карта не добавляет.
