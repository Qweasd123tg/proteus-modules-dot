# Освобождение последнего владельца process broker

Узкое исправление Proteus-core для завершения старого runtime после замены
сборки. База: [`befd30516aefa6f0a0ad5db9924ad4957160b8dc`](https://github.com/Proteus-harness/Proteus-core/commit/befd30516aefa6f0a0ad5db9924ad4957160b8dc).

## Дефект

При поддерживаемой конфигурации нескольких exports одного component
`ContextDispatcher` удерживает provider, provider — client, а client — общий
`ComponentBroker`. Слабая ссылка в обёртке invocation scope не устраняет эту
цепочку: внутренний dispatcher остаётся сильным владельцем.

После освобождения вызывающего future и старого registry последним владельцем
broker может оказаться dispatcher в `PendingInvocation`. Его удаление при
finish/reset происходит на потоке самого broker. Прежний destructor сначала
блокирующе отправлял Shutdown в собственную ограниченную очередь, затем
безусловно вызывал join собственного потока. Полная очередь блокирует первый
шаг; свободная очередь не устраняет ошибку self-join.

Это подтверждённая исходниками цепочка владения и достижимый порядок событий,
а не заявление о воспроизведённом runtime-инциденте.

## Исправление

`broker-final-owner.patch` различает два случая:

- Последний владелец освобождается **на потоке broker**: установить общий
  stop-флаг, уведомить существующий ProcessWake; не отправлять в собственную
  очередь и не выполнять self-join. Основной цикл выполняет обычный cleanup.
- Освобождение **на другом потоке**: сохранить прежние FIFO Shutdown и
  синхронный join. Уже поставленные Cancel/Inspect не пропускаются.

Цикл читает revision пробуждения перед проверкой stop-флага. Существующие
generation checks, завершение worker, abort callbacks и освобождение pending
state остаются на прежнем пути. Новых registry, потоков-reaper, зависимостей
или публичных контрактов нет.

Stop наблюдается на следующей границе проверки в основном цикле, а не
немедленно внутри каждого обработчика. Например, finish(A) может освободить
последнего владельца через dispatcher A, установить self-stop и затем ещё
активировать уже ожидающий B через admit_queued_roots; handle B не обязан
удерживать broker. Это ограниченное продолжение текущего обработчика/итерации
до выхода, а не новый барьер admission. Подобное продолжение возможно и при
асинхронно поступающем внешнем Shutdown. Исправление **не гарантирует**
немедленный запрет новых dispatch или новых внешних эффектов после self-stop.
Последующий reset, terminal settlement pending-вызовов и worker cleanup
остаются существующими.

## Проверки и ограничения

Добавлены, но **не запускались**, process-free regression sources:

- finish/reset × пустая/полная control queue при последнем владельце внутри
  настоящего PendingInvocation;
- детерминированная проверка внешнего FIFO Shutdown и join: тест получает
  Inspect и сам Shutdown до запуска цикла, возвращает их в очередь в том же
  порядке, затем проверяет обработку и завершение. Sleeps не используются.

Fixtures не вызывают connect/ensure_worker и не запускают child process.
Watchdog ограничивает ожидание, но не освобождает потенциально зависший поток
старой реализации; при разрешённом запуске нужен внешний timeout test process.

Автор и независимый reviewer проверили точные Git blob identities, применение
и обратную применимость patch, whitespace, побайтовое совпадение дерева после
применения и rustfmt для трёх изменённых/новых файлов. Проверены все 21 Rust-файл
поддерева v3: единственные исходные run-callsite и BrokerInner initializer
обновлены. Метаданные: `SOURCES.json`, `CALLSITES.json`, `STATIC_CHECKS.json`.

**Не выполнялись:** компиляция, type checking, Cargo, tests, scripts, CI и
runtime. Перед merge требуется обычный разрешённый gate protocol crate.
Нет утверждений о производительности, измеренном освобождении процессов или
effect quiescence: abort callback не является доказательством прекращения всех
внешних эффектов. Взаимные зависимости destructor разных brokers не изменены.

Независимая проверка: `REVIEW.md`. Контрольные суммы: `SHA256SUMS`.
