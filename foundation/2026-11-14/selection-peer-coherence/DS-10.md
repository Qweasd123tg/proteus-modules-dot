# DS10: independent live SessionStore metadata caches can regress after peer hibernation

Status: independently reviewed source-only cache-coherence finding, P3. Independent review caveats are incorporated. Base: Core `89997df995df7c39b713e16aba216ecb19c8f497` + delivery PR87–89; tree `00a3c04a70d7927d1688ea155142025f596a2874`. Later upstream changes require revalidation. Unix-specific read_metadata path. No Rust/project code or repository tests executed; only the author-created abstract Python state model ran. Distinct from retired-handle DS-6 and speculative-prefix DS-4: both handles remain active, all writes complete, no deletion or failed append is needed.

## Ownership mismatch

`session_store.rs:SessionStore` stores writer in Arc<Mutex<JournalWriterState>> and read_metadata in a separate Arc<RwLock<Option<CachedReadMetadata>>>. A `.clone()` shares both. However each independent `SessionStore::open` resolves the same shared writer through writer_for_session_dir while setting read_metadata to Default::default(), creating a distinct metadata cell. The registry sharing is intentional and covered by lifecycle_tests.

`session_store/writer.rs:hibernate_writer` locks the shared writer, copies initialized revision/usage into only this handle family's read_metadata, then calls writer.hibernate. `session_journal/storage.rs:hibernate` sets initialized=false and clears validation/usage/model_context. It does not notify other metadata cells.

`session_store/usage.rs:usage_snapshot` prefers initialized writer usage, but when absent immediately returns its own cached_read_metadata without a source fingerprint or shared epoch check. `session_store.rs:history_revision` does the analogous fallback. `read_model.rs:CachedReadMetadata` stores only revision and usage, no source version/fingerprint.

## Sequential source-derived witness

1. A is initialized with valid canonical state S1. A.hibernate_writer copies usage U1/history revision r1 into metadata cell MA and clears writer projection.
2. B independently opens the same session directory. It shares A's writer but has a different metadata cell MB. B appends valid additional history/model facts, yielding S2, U2 and r2. Both handles remain alive and non-retired.
3. A reads usage/history_revision while writer is initialized: it returns U2/r2 from shared writer. Its MA remains U1/r1; these getters do not refresh MA.
4. B.hibernate_writer copies U2/r2 into MB, then clears the shared writer.
5. A repeats the reads without any intervening canonical mutation: it returns stale U1/r1 from MA, while B returns U2/r2. Thus an A read can regress solely because peer B released decoded state. A direct cold projection remains S2.

For history_revision alone ordinary append_history supplies r1/r2. To demonstrate usage change, append valid distinct model request/response or turn lifecycle facts, since usage projection revision does not advance on history mutation alone. Do not invent a usage change from append_history only.

## Integration reachability and bounds

`AgentRuntimeBuilder::resume_from_session_dir` is public and constructs an independent SessionStore::open. Separate live runtime objects can therefore share a local writer while retaining separate read_metadata cells. Normal runtime release_history calls store.hibernate_writer. Runtime::usage_snapshot directly delegates to the store without first refreshing canonical state. A completed older runtime retained while a second runtime resumes and performs another completed turn is a possible consumer.

This is not a claim that the standard HTTP registry normally constructs duplicate live servers for one path. A public/library multiple-runtime or independently prepared-store path is sufficient for the source candidate; shipped-product frequency is not measured. A plain clone of A cannot demonstrate the issue because it shares MA. Cold newly opened A with no cached metadata also does not take this stale fast path.

`catalog/prepared.rs` can intentionally seed cached (even provisional stale) metadata into a store for display. This witness instead starts with valid current metadata, observes newer canonical data through the same handle, and then falls back to an older version solely on hibernation. It is therefore stronger than claiming all provisional startup caches are bugs.

`runtime/resume.rs:refresh_cached_resume` only runs when deferred validation is set; it is not a general periodic peer-invalidation mechanism. validate_cached_resume on a later run reloads nonresident state and can repair A, so do not claim incorrect continuation necessarily follows. Refresh/write/next admission can heal the stale metadata. No canonical journal corruption or resurrection occurs.

## Proposed regression and invariant, NOT RUN

Construct two independent stores, verify shared writer and distinct metadata Arcs in an internal test. Execute S1/A.hibernate → S2 via B → A reads S2 → B.hibernate → A reads again. Assert A cannot regress to S1 without a journal rollback/replacement. Repeat with an ordinary clone as a negative control, and a new uncached handle as another. Keep all handles active; no retired path. Use an existing valid usage fixture for U2 rather than a malformed or synthetic journal line.

A shared committed metadata summary associated with the shared writer generation can survive hibernation while bulky history is dropped. Alternatively validate handle-local metadata against a shared mutation/version counter before accepting it. A filesystem fingerprint on every getter is not the only option. An active/retired enum alone does not solve disagreement among active peer metadata caches; any DS-6 lifecycle redesign should account for shared cache provenance separately.
