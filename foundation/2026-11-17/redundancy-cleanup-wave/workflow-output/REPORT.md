# Вывод workflow: заимствовать один раз, усекать один раз

Ограниченное предложение изменения исходников Modules `b7e3ca3c23b9440c8c1a9e1d15386d02ef8586c7` с неизменённой фактической зависимостью Core, закреплённой на `185225a7103088c444788374ca425d230060f55a`. Это только локальный кандидат: исходники upstream, установленный runtime, закреплённые зависимости и действующий CI workflow не изменены.

## Изменение и эквивалентность

Один чистый путь сборки вывода в `workflow/coding-workflow/src/output_text.rs`:

- `tool_result_summary` сохраняет заимствованные строки output/error после `trim`, пока `join` не создаст итоговую owned-строку. У двух временных строк `to_owned()` нет самостоятельной идентичности или последующего потребителя. Правила `trim`, пропуск пустых полей, порядок output перед error и разделители-переводы строк не меняются.
- `truncate_chars` получает префикс через один итератор Unicode scalar values, затем проверяет наличие ещё одного scalar value. Отдельного подсчёта всех scalar values в исходном тексте больше нет. Следующий элемент существует тогда и только тогда, когда исходное число scalar values превышает лимит; это верно также для пустого ввода и нулевого лимита. Единственный production-caller по-прежнему использует 2 000. Точный суффикс `\n[truncated]` сохранён.

Production diff: +5/−4 строки. Убраны временные owned-строки и второй полный проход по вводу; измеренного выигрыша скорости, памяти или задержки это не доказывает. Полная сводка по-прежнему собирается до усечения, поэтому ограниченный расход памяти не заявляется.

## Узкая native-проверка

На исходном production и финальном кандидате с Rust/Cargo 1.95.0 проходят одни и те же пять методов: четыре существовавших метода вывода/учёта токенов и один новый метод с матрицей границы вывода (шесть ASCII/Unicode cases, 1 999/2 000/2 001 scalar values). Это пять различных методов, исполненных дважды, а не десять различных тестов. Новый метод проходит и на baseline: это проверка эквивалентности, а не воспроизведение прежнего дефекта.

Команда после активации установленного toolchain:

```sh
CARGO_NET_OFFLINE=true python3 scripts/test.py -p coding-workflow --lib tests::output_helpers:: -- --nocapture
```

Штатный scoped runner разрешает неизменённую закреплённую зависимость Core и запускает только указанный фильтр. Все пять методов проходят, ещё 100 методов отфильтрованы. Проверки rustfmt затронутых файлов и git diff проходят. Строгое прямое применение patch воспроизводит байты кандидата; обратное применение восстанавливает точные исходные байты. Cargo.lock не изменён. Имена тестов и идентификаторы исходников приведены в `VERIFICATION.json`.

Четыре существующих теста сохранены: placeholder, fallback к результату инструмента, fallback при пустой истории текущего turn и учёт токенов проверяют разные результаты. В этом узком просмотре безопасного безусловного удаления тестов не установлено.

## Границы

Проверены metadata PR165/166 и PR167–181. В существующих dot-артефактах выполнен поиск этого source target; такой же кандидат не найден. Текущий upstream main вернул ровно два baseline blob, записанных в manifest. Это не исчерпывающая дедупликация всех исторических веток.

Логика Core accounting/deadlines, process/cancellation/security, durable delivery и все темы HOLD не изменены. Отдельная гипотеза об изменении внутреннего типа оценки токенов оставлена без правок, чтобы не расширять эту чистку до accounting.

Полные workflow suite/workspace, process/HTTP/provider fixtures, cancellation/security controls, native UI, portable/установка, hosted CI и benchmarks не запускались. Эти чистые helper tests не выполняли процессные сценарии или обращения к внешнему провайдеру. Пакет не квалифицирует эти границы и не закрывает никакой HOLD.
