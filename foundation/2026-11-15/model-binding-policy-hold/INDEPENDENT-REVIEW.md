# Independent model-selection provenance review

Verdict: HOLD an automatic predicate-sharing patch. A smaller shared projection is technically possible, but the current contracts do not select the invalidation policy needed to call it a faithful fix. This is the known hot/cold preference family, not a new severity claim. No code/tests/runtime or capability probes were executed.

Read available recovered Core binding/restore, hot profile publication, runtime reload/settings and reasoning_reload tests, plus pinned config.rs and configuration docs. Fresh source identity for recovered files remains for coordinator verification.

Hot publication separately detects active alias/default ModelRef changes and default ReasoningConfig changes. Runtime can therefore keep an explicit model when only reasoning defaults change, and keep reasoning across unrelated settings edits. Published defaults still update for subsequent reasoning re-enable. The existing reasoning_reload test explicitly treats profile rename as unrelated while retaining an override; it exercises the runtime API, not full app-server hot/cold persistence.

Cold binding is broader: resolved profile path, profile.name, active alias, selected ModelConfig, opaque model-route data and matching component descriptions. ModelConfig contains provider/model/stream/reasoning; declared ProviderProfileConfig.reasoning_efforts is NOT copied into it and must not be claimed part of this hash. A changed binding rejects the whole saved model+reasoning selection. Reusing that hash for live invalidation would erase both overrides for changes that currently reset only one or neither, including stream/profile-name changes.

A route-only projection cannot by itself settle compatibility. Changed opaque route/component data does not establish that the selected model/effort is invalid; unchanged serialized route does not establish unchanged external model capabilities. User model selection consults the current catalog and can adjust effort, whereas restore uses provider matching and model-specific tool shaping without applying the same full catalog-selection normalization. A common byte hash is neither a capability version nor a record of which dimension the user explicitly overrode.

Finite next prerequisite: choose an invalidation matrix for model default, reasoning default, alias/provider identity, opaque route/component revisions, stream/display-name changes and changed catalog capabilities. State whether each preserves, resets or revalidates each explicit override, what happens when capability discovery is unavailable, and how persisted v1 bindings migrate. Keep no-model and failed-reload behavior explicit. Then share only the selected typed projections/decision boundary, with hot/cold paired controls and existing independent-override tests. Do not introduce a broad route framework or infer this policy solely from the old persisted hash.

This HOLD is about unresolved preference semantics, not fundamental impossibility or a demand for more abstraction. No source patch or publication is recommended by this pass.
