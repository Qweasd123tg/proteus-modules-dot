# Independent architecture review: Reload versus accepted Save

Source-only verdict: the proposed local accepted-profile revision is a coherent minimal direction, not an arbitrary framework. No patch reviewed or code/tests run. Read existing SettingsView load/accept/update/discard, manual accept_save and catalog acceptance/rebase paths from the supplied current Desktop snapshots.

Current load only checks dirty on success. An accepted save can clear dirty without incrementing edit_revision; catalog ACK likewise does not represent itself as a local editor change. A reload issued before that acceptance can subsequently overwrite the newly accepted baseline. Current saving/catalog-busy flags describe work in flight, not which baseline a completed read predates. Comparing snapshot values would add payload comparisons and still cannot distinguish equal-valued acceptances or ABA transitions. Incrementing edit_revision for ACKs instead would change its existing classification contract.

A private accept_snapshot boundary can own baseline/state replacement plus incrementing profile_revision. Both accept and accept_save's newer-editor branch must use it. Catalog acceptance delegates to accept_save and therefore participates naturally. Increment for every accepted snapshot, including value-equal ones: this is local acceptance order, not server revision or content identity. Preserve draft/editor clearing only in accept; the newer-editor branch must retain them exactly as before.

Load captures profile_revision and edit_revision. A mismatched profile revision rejects old success and old error before they replace state or feedback. A success with a changed edit revision must not replace newer raw edits even if edit/undo or reset made dirty false again. Retain the existing dirty guard as well: a read may begin while the draft is already dirty and receive no subsequent edits. Error handling for unchanged profile epochs can retain existing policy; avoiding stale profile errors is not a requirement to hide every error following an unrelated local edit.

One boundary must be checked before implementation: concurrent load invocations. Accepted-profile revision is not load request identity. If multiple reads may run, an old completion must not clear the newer request's reloading state, and accepting the first response may not implement the desired newest-request policy. Verify actual controls/callers enforce one in-flight read, or narrowly guard load admission; do not claim arbitrary overlapping-load correctness from the new counter. Addon/history requests are separate owners and remain outside this fix.

Proposed exact tests should cover manual and catalog ACK before old read success/error; newer-editor save-ACK branch; dirty-at-read-start; edit then undo/reset; ordinary clean successful reload; ordinary current-epoch read failure; and the actual load admission invariant. These are requested coverage, not executed results. No need to disable Save or widen reconciliation policy merely to enforce this baseline-acceptance invariant.
