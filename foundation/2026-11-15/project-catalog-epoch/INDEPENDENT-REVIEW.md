# Independent PN-1 contract review

Source-only verdict: a bounded project-catalog admission fix is justified by current DESIGN and existing refresh precedent. Do not mechanically reject all callbacks or broaden it into creation retry. No code/tests/runtime were executed; this is the known PN-1 family, not a new finding.

open_project captures navigation but Core set_sessions and Codex per-row mutation occur before finish_project_navigation checks it. Navigation freshness and catalog epoch are distinct: a current-epoch response from obsolete navigation can still usefully merge metadata without selecting a destination; an obsolete epoch must not mutate catalog metadata even when navigation is current. Existing refresh_sessions and Codex page paths already reject obsolete epoch responses. DESIGN explicitly protects deleted rows from stale catalogs and later navigation from older project responses.

A private read-only project catalog helper capturing canonical project, chosen agent, original navigation generation and request-time epoch is a small coherent direction. On obsolete epoch: reject before set_sessions/session_projects changes or Codex upserts; re-read only while the original navigation remains current, retaining its project/agent/generation. Do not call open_project/begin_navigation again and do not repeat creation. On current epoch: merge first, then use the existing navigation guard. Repeated churn may postpone completion; no bounded progress guarantee follows. Existing async error presentation must not be silently claimed epoch-filtered if the generic call helper handles errors outside the proposed success callback.

Important limit: deletion advances epoch at both start and finish. A read started between those points can have the current epoch while containing a row in deleting_sessions. The normal Codex page path additionally filters that set; current project merge/selection does not. Epoch checks alone therefore fix obsolete-generation admission, not every pending-deletion selection race. Either keep this scope explicit, or select a coherent pending-deletion behavior before claiming the full deletion invariant. Avoid silently creating a new session merely because a pending deletion was filtered from an otherwise available catalog.

Core start_chat/new_session callbacks also carry opened acknowledgements plus bulk catalog data. If adopting an epoch-aware catalog setter, preserve opened.session_dir/workspace metadata and finish_chat_creation/add_chat logic independently of whether the bulk list is accepted. A stale bulk list can request a read-only refresh; it must not suppress the acknowledged created session or trigger a second new_session call. Shared set_sessions(epoch)->bool alone does not solve Codex project upserts, nor pre-setter mutations or navigation policy. Review all caller effects if expanding that API; otherwise keep PN-1's read-only helper bounded and document the creation-admission gap.

The proposed same-agent retry must use the captured agent rather than reread preferences. Existing finish_project_navigation/new_chat_in behavior should not be represented as a new universal agent-selection guarantee without tracing that fallback, which currently consults preferred_agent again. No larger framework is necessary, but actual callback controls must cover stale/current epoch crossed with stale/current navigation, pending deletion, and acknowledged creation exactly once before a broader invariant is claimed.
