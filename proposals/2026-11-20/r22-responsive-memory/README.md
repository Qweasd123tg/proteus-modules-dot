# Proteus R22: отзывчивость активного чата и память холодных архивов

## База и сценарий

Core `048378da7cbe890d8bf8a0152e55eb28ecb5013d`, Modules `cf999371f6e564376565738bebc3416aad12f908`, Desktop Api из `7ccb6c8634c40f450d83bb6e9eff891dc776ee6b`. У detached-worker — ровно проверенный бинарник #228, если не указано иначе. Это 4 одновременных запроса к синтетическим архивам по 125 тыс. строк отображения, 96 неоткрытых архивов и отдельная активная сессия с прогретым состоянием для одного хода на тестовой модели. У архивов 100 текущих модельных сообщений после компакции. На каждую руку — новые процессы и приватная копия по тому же абсолютному пути. Производные индексы выбранных архивов отсутствуют; ОС-кэш не контролируется. Desktop Api ограничивает каждый запрос истории 30 с; /send и SSE наблюдаются отдельно. Полный GUI и память процесса Desktop не измерены. PSS здесь — сэмплированное дерево процессов сервера; это не Rust live heap и не RAM всей системы.

Проверка: 50 строк начала и конца, ID/роль/текст, отсутствие `base` на неизменной исходной истории, равенство отпечатков полных 50-строчных ответов, согласованная ревизия latest/pinned внутри прогона, неизменный канонический архив, один записанный и завершённый активный ход и точная история на входе тестовой модели. Не переносить эти доказательства на произвольные некомпактированные истории, SQLite или реальные модели.

## Что держало активное возобновление

Диагностический Modules со штатным SDK инструментирует ожидание и удержание общего `State`. Идентификаторы RPC и одинаковые монотонные часы связывают его с синтетическим HTTP-запросом через наблюдающий relay. Тот не подменяет мьютексную телеметрию, а лишь связывает этапы. Патч диагностический, не предназначен для установки или сравнения рекордов; в этом прогоне параллельно шли сборки.

Активный `Resume` ждал **8 110,615 мс**. Из них **8 105,197 мс** совпали с удержанием State четырьмя `OpenDisplaySnapshot`. После захвата: **1,140 мс** весь hold, **0,048 мс** материализация Resume, **0** повторно прочитанных записей: writer fold переиспользован. Matched durable TurnOpened ACK **8,813 с**, первый SSE-текст **12,036 с**. Активный AcquireWriter использовал новый writer, но восстановил один канонический батч за менее 1 мс после начала восстановления. Commit держал State 1,937 мс; этап между Commit и видимым ACK включает транспорт и планирование, его нельзя целиком приписать диску.

Каждое архивное открытие держало State 1,72–2,30 с, в том числе 1,61–2,14 с занял строгий проход, внутри него 1,06–1,51 с чтение и разбор, 0,32–0,34 с семантический fold и 0,22–0,30 с запись staging. Строки отображения не равны каноническим записям: в этом корпусе 1 251 запись на выбранный архив. Это объясняет выигрыш от отделения тяжёлого чтения, а не необходимость ослаблять ревизии или корректность журнала.

Комбинированный диагностический прогон подтвердил механизм: `Resume` ждал State **6 806,001 мс**, из них **6 805,730 мс** перекрыты четырьмя архивами. На SDK stdout он ждал около 0,0002 мс. Уже после возвращения Resume общая линия вывода стала вторичной задержкой: успешный TurnOpened Commit держал State 1,842 мс и ждал stdout SDK 117,589 мс; это с relay и конкуренцией фоновой сборки, не продакшен-латентность. Интервалы вывода двух архивных страниц перекрыли ожидание ACK на 117,49 мс. У 80 архивных ответов медиана фактической записи в выходной канал во время кодирования — 102,77 мс; медианы to_value, preflight и ожидания stdout — 18,71, 10,53 и 53,98 мс соответственно. Эти медианы нельзя суммировать как оценку конкретного RPC. Отдельный synthetic smoke подтвердил, что метрика различает время фактической записи под backpressure и время ожидания замка другим RPC.

## Изолированный эксперимент: ограничить обычную порцию display records

На точное detached-дерево #228 наложена только новая цель 1 MiB для обычного ответа `ReadDisplayRecords`. Действующие границы контракта, канонический путь, одиночная большая запись и проверка идентичности неизменны. Это не глобальный лимит памяти. SDK и Core не меняются. 67 storage-тестов прошли, включая добавленный тест курсора на JSONL и SQLite. Один существующий ручной тест производительности пропущен. Прогон с relay подтвердил дробление 20→53 ответов на выбранный архив и максимум около 2,73→1,03 MB на frame; речь только о наблюдённых JSON кадрах, не о пиковом объёме аллокаций.

Четыре прогона P,D,D,P без relay, соседство сторон обращено во второй паре (параллельные сборки не контролировались):

| Detached + 1 MiB | Исходный detached | Макс. запрос истории D→P | Первый SSE-текст D→P |
| ---: | ---: | ---: | ---: |
| 644,5 МиБ | 975,9 МиБ | 22,59→20,62 с | 150→124 мс |
| 842,3 МиБ | 909,9 МиБ | 21,86→15,78 с | 109→136 мс |

Обе пары дают меньше PSS, разброс эффекта большой. Клиент прочитал 4/4 архива в каждой руке при исходном 30-секундном дедлайне. Без relay наблюдаем первый текст и верхнюю границу ACK по SSE, не точное время durable ACK. Сравнение не снимает прежний HOLD для архитектуры #228.

## Где Core держит лишние байты

В сборке Core (Linux x86-64, точный набор Cargo features) `AppTranscriptMessage` имеет шаг 640 B: данные tool и subagent лежат прямо внутри каждой строки, даже когда отсутствуют. На этой трассе в момент пика дерева R21 одновременно были материализованы минимум 375 тыс. строк (три архива уже прошли render и проверки prefix, но ещё сохраняли страницы). У диагностического варианта с Box на редких полях размер 128 B, то есть на 512 B меньше на элемент. Это 61,0 МиБ на 125 тыс. и ≥183,1 МиБ места именно в слотах в том R21 снимке, не эквивалент гарантированного падения PSS. Патч меняет публичные *Rust* типы полей, хотя JSON/SerDe остаются совместимы. Нельзя предлагать его без миграции Rust-клиентов; для production лучше приватный compact row в Core от рендера до записи индекса, с преобразованием только выбранного окна в прежний DTO.

Отдельно обнаружен независимый источник удержания: cold history page делал `into_iter().skip().take().collect::<Vec<_>>()`. На установленном rustc 1.95 сборщик переиспользовал предыдущую ёмкость 131 072 при выходе всего 50 строк или даже нуля. Реальный тип из Core и точная цепочка в микропроверке удерживали backing allocation **80 МиБ** до сериализации ответа. Явный небольшой выходной Vec сохраняет значения и удерживает **31,25 КиБ / 0** после извлечения окна. Это не экономия во время построения архива и не самостоятельное доказательство снижения пикового RSS.

## Что применять

- Патч Modules с мелкими порциями зависит от detached-патча [#228](https://github.com/Qweasd123tg/proteus-modules-dot/pull/228), он не накладывается как самостоятельное изменение на main. `experiments/README.md` фиксирует точную исходную tree и SHA; двухэтапная привязка специально сохранена.
- Диагностические патчи в `diagnostics/` не переносить в production. SDK строится из пина `0c1b7572313230e5d123e95c722e1258a2e9ecd6`. `state-trace1.json` и `combined-trace1.json` — уже сведённые интервалы, не канонические журналы или payload.
- Скрипты в `bench/` рассчитаны на стенд R20/R21 [#231](https://github.com/Qweasd123tg/proteus-modules-dot/pull/231). Поместить их в `r22/` и `r22/stand/` в корне локальной копии стенда. Использовать одинаковую абсолютную корневую папку для обеих рук, старый HEAD/Core, указанные бинарники, исходные 30 с и синтетический seed; не перенастраивать профиль между сравниваемыми руками. Сверять SHA и полные хэши пограничных строк, сравнивать не только среднее, но оба направления пар.

## Цель в 100 МБ

Сначала определить поверхность: тихий чистый backend, backend после закрытия четырёх архивов, открытый Desktop+backend или жёсткий пик всех процессов. Выбор меняет архитектуру. Недавно запущенный backend уже около 62–64 МиБ PSS при живой контрольной сессии в этом стенде. Это не измерение полного Desktop и не обещание, что память возвращается к этому уровню после больших архивов.

Для пика backend при первом открытии без индекса одного уменьшения структуры недостаточно: Core материализует весь transcript, а worker строго воспроизводит журнал и временно хранит историю до финальной compaction. Сначала не строить в Core весь вектор для обычной постраничной истории: потоковое построение дисковых листьев с ограниченным окном, прежняя валидация и fallback для операций, меняющих старые строки. Затем измерить и ограничить поток worker (decode, live fold, сериализация больших ответов) и отдельно замерить Desktop. Целевой критерий: определённый набор процессов, приложение без индекса, согласованный размер записей, честный максимум PSS и неизменные контракты / 30 с / миллисекундный foreground. Никаких выводов о 100 МБ на любом журнале из одного синтетического теста.

## Повтор без сборок: 8 сравнительных прогонов

Порядок P,C,B,D,D,B,C,P; D — точный detached #228, P — detached с порциями по 1 МиБ, C — только компактный Core на исходном detached, B — оба эксперимента. Между прогонами не шли наши сборки, relay отключён, ОС-кэш не сбрасывался. Пары по порядку каждой руки. Первые и последние 50 строк побайтово совпали на уровне канонической JSON-нормализации клиента между всеми руками (включая timestamp, phase и adornments). Все восемь прошли проверки и 30 с для каждого из четырёх открытий, первый текст появился при четырёх незавершённых запросах истории. Точные пики отдельных процессов нельзя складывать: они взяты в разные моменты.

| Вариант | Пик backend PSS, МиБ (два прогона) | Самый долгий запрос истории, с | Первый текст, мс |
| --- | --- | --- | --- |
| Detached #228 | 923,0 / 1087,0 | 16,47 / 17,26 | 120 / 102 |
| 1 МиБ | 809,7 / 858,5 | 21,48 / 14,43 | 104 / 95 |
| Compact Core | 563,3 / 491,0 | 15,53 / 15,39 | 124 / 127 |
| Вместе | 721,8 / 449,4 | 15,86 / 15,85 | 125 / 103 |

Компактный Core снизил пик в обоих прогонах на 39–55% относительно соответствующего detached; его нельзя вливать в таком виде из-за публичного Rust API. В комбинации получился лучший отдельный результат 449 МиБ, но эффект не складывается предсказуемо: в другом прогоне комбинация хуже компактного Core. Для оценки стабильности предпочтителен приватный компактный тип и повтор на других корпусах. Порции 1 МиБ выиграли PSS в четырёх сравнениях из четырёх; худший архивный вызов временами замедлялся. Самостоятельный патч ёмкости 50-строчного ответа прошёл пять целевых тестов Core с исходным worker; в этой серии PSS для него не измерялся. В первой секунде после архивных ответов медианы PSS оставались 391–791 МиБ во всех руках, несмотря на 61–64 МиБ до запуска запросов: простой сразу после использования не равен свежему процессу.

Слияние #228 или экспериментального изменения публичных Rust типов этим отчётом не предлагается. Маленький безопасный для API патч буфера лежит отдельно от диагностик и POC. Во внешние репозитории ничего не вносилось.
