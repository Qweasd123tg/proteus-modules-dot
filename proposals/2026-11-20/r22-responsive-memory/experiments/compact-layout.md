# R22 sparse rich cards: one-axis diagnostic patch (Core)

The original Core/SDK/storage source checkouts are unchanged. This private proof uses a clean additional checkout at Core `048378da7cbe890d8bf8a0152e55eb28ecb5013d` with `compact-rows.patch` applied. It boxes only the two optional rich shapes in the public Rust row and adjusts their construction/dereference. JSON (including nulls and absence of terminal/session where applicable), HTTP and cache formats, text and source validation, staging, model handling and archive/foreground concurrency are unchanged. Not a source-compatible change for code constructing or moving the Rust fields. Do not ship as-is without reviewing all consumers including Desktop, or keep the compact representation internal. Tool/card-rich workloads incur a new allocation per present card; not measured here. No product fix for the same-session limitations of #228.

## Strong placement evidence (existing R21, no new workload)

`correlate.py` joins HTTP windows, per-session relay request/response IDs and time-aligned process PSS from existing R21. Specified cohort: four first-open synthetic sessions with 125,000 completed plain text-only rows, 100 model messages after final compaction, ordinary Desktop 30 s API. The strict replay still sees 125,000 canonical messages *before* that final replacement. In cold-cache recovery, `remote/view.rs:SessionReadModel::from_validated` calls render, display_prefix, then cache::summary's Describe. It returns the owned transcript in the model. In `project_sourced_read_model`, `save_read_model` (including the final HEAD WriteCache) borrows the model; the vector is still returned to `rebuild_transcript`, so is live throughout that interval.

At the detached #228 sample with maximum cold tree PSS, 14.4966 s from first HTTP start, three sessions had run this Describe but not reached final WriteCache ACK, so at least 375,000 complete row values were alive simultaneously (not a count inferred from PSS). The fourth had not called Describe. Same sample: 891.718 MiB tree / 526.022 Core / 322.138 worker. Worker-only peak 420.642 MiB was earlier at 8.589 s, not simultaneous. With stock worker, ≥250k rows at measured tree peak. Sampler and relay timings do not pinpoint single heap allocations.

x86-64 exact Core size_of: **640 → 128 bytes**. Both 8-byte aligned. The old option slots are 360 B (tool) + 168 B (subagent); the new slots are one pointer each. This removes 512 bytes of inline extent per plain row, 61.035 MiB for 125k completed rows; **183.105 MiB at 375k**. Counts refer to Rust live element storage (not text, vector spare capacity, allocation overhead or residency). No direct PSS or speed outcome inferred. Stock exact executable `108a024…` has 0x280=640 bytes in Vec<AppTranscriptMessage> drop glue; verified `stock-disassembly.log`. Cargo resolves `serde_json/preserve_order` in Core. Using a worker or bare-contracts rlib with different serde_json feature selection yields the wrong tool and row sizes for Core.
