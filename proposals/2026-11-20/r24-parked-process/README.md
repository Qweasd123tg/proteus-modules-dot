# Proteus R24: припарковать завершённого агента, не потеряв задачу

В R23 десять агентов требовали около 270 МиБ после завершения при сохранённых процессах и около 48 МиБ после их освобождения. Штатный режим освобождения при этом терял возможность продолжить задачу. Здесь проверяется исправление этой семантики, а не расширение лимитов.

Кандидат для Core `048378da7cbe890d8bf8a0152e55eb28ecb5013d`. Выключен по умолчанию, при включении требует `max_idle_processes = 0` и leaf-агентов. Пул живёт столько же, сколько родительский Core. Только успешно завершённый ход подходит для парковки; подвисший вызов, ожидающееся подтверждение и перенос работающего процесса не поддерживаются. До публикации компактной привязки требуется выход старого процесса. При продолжении старый task ID ведёт к точному сохранённому журналу, роль и workspace задаёт сервер. Перед отправкой нового хода проверяются журнал, владелец и конфигурация. Расхождение не становится новой задачей и не порождает автоматический повтор. До 64 сохранённых привязок, текущие лимиты сессий и исполнения не меняются.

Это эксперимент для рассмотрения. Он не обеспечивает восстановление родительского процесса, не делает переносимым произвольное внутреннее состояние внешнего модуля и не доказывает работу 100 агентов. Источники полномочий, границы запуска и ограничения описаны в `authority.md`. Проверка в `acceptance.md`.

## Проверка через пользовательский интерфейс инструментов

В финальном снимке Core `fb0b180a778ec33c23a0af11db9abc86d04f57a9` прошли 40 реальных process-тестов: 26 в `process_agent_pool` и 14 в `process_agent_control`. Использован dev-бинарник этой же сборки с настоящим stock JSONL worker. Тест запускает A, фиксирует его остановку, запускает независимого B, затем вызывает `followup_task` по прежнему адресу A. Три разных PID; старые процессы не живы после завершения. A сохранил физический UUID/путь и логический ID, вернул непредсказуемое значение из первого хода и добавил ровно один успешный ход (четыре записи, прежний префикс 5005 байт неизменен). Единственное инструментированное чтение не повторилось. Журнал B не изменился при продолжении A. После штатного независимого добавления хода в B устаревшая привязка B отклонена до продолжения. Неверный ID, родитель, роль или workspace отклонены до запуска. Этот тест не моделирует реального внешнего провайдера.

Точный патч к исходной ревизии: `core-candidate.patch` (SHA-256 `7101fac77b96aa3c0e0c6e73ff1bb68554b942323cf1b219fc4a8d4073fd3571`). Отдельный `measure/driver.patch` изменяет только пример измерения; он не нужен для применения Core-кандидата. Подключать через отдельную тестовую конфигурацию и только при предсказуемом состоянии инструментов.

Регрессии потери writer lease: оба целевых unit-теста прошли. Типизированный InvalidWriterLease и потеря процесса worker после проверки приводят к отказу возобновления, без повторного захвата по устаревшему допуску. Штатное поведение незакреплённого writer по-прежнему восстанавливает lease. Сверка ревизии и трёх документов конфигурации делается на том же writer до запуска следующего хода.

## Однопарный замер на настоящих дочерних процессах

Один leaf, два хода, один и тот же dev Core и driver, тестовая модель, файл 4 КиБ. Закреплённые reference и JSONL worker, без GUI. Сравнение park (нет живого процесса между ходами) и retain (тот же PID продолжает); оба подтвердили один и тот же исходный task ID и историю, прошли проверку журналов, смены/сохранения PID, ожидаемого дерева процессов, replay. Данные в `measure/comparison.json` и `measure/compact-proof.json`.

| Величина | Park | Retain |
| --- | ---: | ---: |
| Медианный PSS+SwapPss между ходами, МиБ | 58,62 | 129,42 |
| Живых процессов между ходами | 6 | 12 |
| Второй ход: до первого forwarded tool call, мс | 299,56 | 208,62 |
| Второй ход: до завершения | 4,535 с | 4,451 с |
| Выборочный пик всего прогона, МиБ | 134,98 | 133,82 |
| Медианный PSS+SwapPss после второго хода, МиБ | 59,02 | 131,24 |

Разница между ходами 70,80 МиБ; на пике экономии не видно. Дополнительные ~91 мс наблюдались в этой паре до вызова инструмента, а не чистое время старта/сетевой модели и не прогноз production. Первую попытку не включали: один переходный снимок после освобождения родительских компонентов попал в окно idle. Финальный стенд режет края окна одинаковым фиксированным отступом 200 мс по монотонным часам, затем требует полный состав в каждом допустимом снимке. Нет измерений 5–100 для этого кандидата.
