# R24. Два хода, один task ID, живой процесс родителя

Сравнение **park** (max_idle_processes=0, durable_parking=true) с **retain** (cap=N, durable_parking=false). Одинаковый кандидат, родительский max_depth=1, одинаковые роли/бинарники и два полноценных хода в обеих руках. Данные синтетические, сеть/платная модель не нужны. Не измеряет перезапуск родителя, машину с холодным page cache, 100 агентов или стоимость больших контекстов.

## Запуск

Временная рабочая копия кандидата Core на базе 048378da7cbe890d8bf8a0152e55eb28ecb5013d. Применить **только на стенде** `git apply /abs/path/to/driver.patch`. Собрать **и** `proteus`, **и** `multiagent_perf` из одного дерева и в одном профиле. Драйвер статически линкует AgentControlRuntime: не заменять только CLI, не использовать старый r23/driver. Путь Core должен быть абсолютным (run.py разрешит его), basename ASCII до 15 байт, отличным от имён других процессов.

```sh
# В checkout кандидата, пример:
cargo build --locked --offline --release -p proteus-core --jobs 1 --bin proteus --example multiagent_perf
# В директории стенда:
bash pair.sh /abs/multiagent_perf /abs/proteus /abs/proteus-reference-module /abs/worker-stock /abs/new-pilot 1 pilot
# Только после прохождения функциональных ворот и пилота:
bash pair.sh /abs/multiagent_perf /abs/proteus /abs/proteus-reference-module /abs/worker-stock /abs/new-n5 5 abba
bash pair.sh /abs/multiagent_perf /abs/proteus /abs/proteus-reference-module /abs/worker-stock /abs/new-n10 10 abba
```

Для привязанной рабочей копии reference: `r16-cancel/target/debug/proteus-reference-module` (SHA256 fbecc2702f11014d546f0223de6bf405aa5162f7a2d07028a866f943d734bd66), storage: `r19-root/bin/worker-stock` (d9929cc7592c7c5f537b8a9c63b8cb5d09ae5a6ffc7c7306e48940bcb4c7c44e). Не смешивать с R23 на 32 КиБ/один ход. Здесь фиксированы 4 КиБ, 500 мс задержки fake model, 80 мс интервал измерений, 500 мс ожидания после settle перед каждым окном idle и ещё 1,8 с наблюдения. Отдельный новый root вывода, new workspace/config/home, один родитель на руку. Первая пара проверяет работоспособность, но не даёт распределения: подтверждать измерение перекрёстным ABBA. Рук одновременно не запускать. Linux /proc, доступ к собственным smaps_rollup; 512 МиБ **выборочный** сторож (не cgroup hard limit), 120 с на драйвер, 120 с на каждый последовательный replay. Exit на первой ошибке, исходные данные сохраняются, ложного passed нет.

## Что должно пройти

1. Закончить первый synthetic read_file, дождаться результата. Снять префикс каждого единственного журнала во время интервала **до подачи** второй задачи. Следующий запрос содержит только исходный task ID, не получает server locator из стенда. Сопоставить запрос/оба handle/оба результата, ту же пару durable session ID+dir, два разных turn ID. Физический root thread на холодном открытии может смениться (по одному на ход), в retained обязан остаться тем же. Не путать его с публичным ID задачи.
2. Подтвердить ровно один open/settle/успешный read_file effect в каждом сегменте; полный неизменный байтовый префикс первой записи, ненулевая предыдущая history revision во втором open. Для каждого хода по две прямых пары request/response и один tool-finished в живом event log, по два успешных read-only replay на журнал без изменения SHA. Прямые model calls не включают возможные вспомогательные вызовы hook; это явно разные метрики. До второго tool effect в model request (прямом или от hook) должна присутствовать запись Tool с уникальным call ID из первого хода; одного флага о восстановлении недостаточно. Изоляция от другой задачи и отказы проверяются отдельно функциональными тестами.
3. По PID **и времени запуска** сверить одновременно замеченный состав для обоих активных раундов. В parked окнах до/после resume ровно родитель + его 5 workers; в retain дополнительно N Core и по 5 workers каждого. Принадлежность снимка окну определяется только временем на Linux CLOCK_MONOTONIC: начало/конец чтения /proc должны целиком попасть внутрь гарантированного интервала по скобкам времени запуска драйвера и фиксированным отступам по 200 мс от обоих краёв. События из stdout могут отставать, ярлык фазы снимка не влияет на отбор. Для конца берётся минимум фактической границы и объявленного 1,8 с. Минимум три пригодных снимка за окно, те же исходные процессы на втором ходу в retain, полностью сменившаяся группа в park. Обе группы полного размера видны в активном состоянии.
4. Результат `comparison.json`: медиана суммы PSS+SwapPss только пригодных снимков interround и final; отдельно нижняя выборочная оценка пиков и время от начала второго раунда до первого/последнего forwarded tool call и до всех settled. Это задержки пачки на fake модели, **не** чистая длительность cold spawn, attach или network first token. Иначе профилировать отдельными маркерами. В обоих раундах полный overlap N прямых model requests по служебным событиям.
5. `python3 -B -m unittest discover -s . -p 'test_verify.py'` проверяет редьюсер на выдуманных PID и журналах, не доказывает работоспособность кандидата. При отсутствии реального прошедшего pilot/ABBA публиковать только протокол, не цифры R24.
