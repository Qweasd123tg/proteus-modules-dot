# Core: one full render scan for explicitly committed text replies

Base: Proteus-harness/Proteus-core `048378da7cbe890d8bf8a0152e55eb28ecb5013d`. Apply-check the included patch against that base. Independent proposal, not a diff to place after #240; the sources overlap. This package does not change Core upstream. The earlier model-free prototype is incorporated here and is not counted separately.

When writing an already-validated local display spool, track final root bindings and at most one pending text part ID. The complete spool qualifies only if each successful, one-message/one-part text model response has its own later explicit HistoryMutated commit before any next response or end. No tool calls and no non-text history alongside those replies. The unchanged fallback handles missing commits, tools, streamed message records, unsupported response forms, hard resets, hosted parts, cap overflow and unstaged input. Only the full renderer's reads change: for the eligible bound fixture it was four local rendering reads, now one. Authoritative verification, staging, and the separate prefix/index read still occur. Incremental and committed append paths are unchanged.

69 focused tests passed (42 journal including the three new differential/fallback tests, four read-model, seven startup, 16 remote view). Release comparisons use the exact R24 checkpoint build as a common base and the stock JSONL worker; release candidate differs only by this production patch. Model replies were generated by a local deterministic fake through the ordinary bound runtime (not manually written journal rows). On 100 complete text turns with all derived display caches absent, 8/8 pairs consumed less Core process CPU up to checkpoint ACK: paired median −158.15 ms (−23.9% of the stock median). All eight removed about 31.4 MB in logical Core reads; that is not physical disk I/O. Core VmHWM paired median −646 KiB, no observed material peak regression here. Whole attach ACK paired median −168 ms (−2.46%, 6/8 faster) did **not** meet the preregistered wall-time gate; this is not a Desktop, first-token or production workload claim. The mixed eight-turn fixture with a genuine read_file turn had zero cold-specific read savings and exactly matched the fallback outputs. All transcript/cursor/checkpoint/canonical journal and normalized complete derived caches matched the tested reference; prepared-cache comparisons did not show a Core CPU win.

Attribution against the prior local one-scan prototype (R32): a separate eight-turn text fixture with a 49,252-byte final response removed 1,831,496 cold-specific logical read bytes by paired median; mixed history stayed at zero. This short control does not show a reliable latency win. Its prepared-cache Core CPU showed a small flagged increase on the first eight pairs (paired +2.21 ms R32→R34); it does not measure rendering and merits a repeat. Separately after restore, both builds supplied all 200 prior text messages or all 18 prior mixed messages unchanged to the next actual model request, on isolated copies. This verifies context retention, not model comprehension.

The independent 16-pair repeat on this same short R32/R34 control did not reproduce the prepared-cache CPU warning (paired −0.46 ms, 10/16 lower), while the cold-specific logical read change repeated at −1,831,497 bytes. Both runs are retained; no prepared-cache acceleration or cost guarantee.
