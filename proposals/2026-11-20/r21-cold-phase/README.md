# R21: где ждёт активный чат при первом открытии четырёх архивов

Проверены настоящие сетевые вызовы Desktop API (Rust, штатный лимит 30 с), Core HTTP/SSE и внешний JSONL worker. В каждом прогоне четыре архивные страницы по 125 000 отображаемых строк открываются впервые, одновременно с независимым активным чатом. Ещё 96 архивов не открываются. В синтетическом корпусе после compaction у длинных архивов остаётся 100 актуальных сообщений для модели; это **не** проверка восстановления 125 000 сообщений текущего контекста или охлаждённого диска.

## Разложение задержки

Этот опыт меняет только worker: Modules `cf999371f6e564376565738bebc3416aad12f908` или прежний эксперимент #228 (detached capture). Core `048378da7cbe890d8bf8a0152e55eb28ecb5013d`, Desktop API `7ccb6c8634c4`, один и тот же синтетический корпус. Проведено по одному прогону в инструментированном режиме. Байтовый relay наблюдает вход и выход JSON-RPC по ID, не сохраняет содержимое или пути из ответов. Из-за вмешательства relay сравнивать абсолютные числа с обычным R20 нельзя.

| Наблюдение | Stock | Detached #228 |
|---|---:|---:|
| Последняя из 4 первых страниц | 28,12 с | 18,20 с |
| От отправки /send до появления запроса Commit(TurnOpened) в relay | 7 734,3 мс | 23,8 мс |
| Запрос Commit → проверенный durable ACK в relay | 15,1 мс | 4,5 мс |
| ACK → SSE TurnStarted | 54,9 мс | 2,25 мс |
| От /send до первого текста | 10,88 с | 0,140 с |
| Архивов ещё ожидают ответа на момент ACK | 4 | 4 |
| Наблюдаемый пик PSS дерева, МиБ | 800 | 892 |
| Наблюдаемый пик PSS worker, МиБ | 240 | 421 |

Сопоставление ACK проверяет ID запроса, operation ID, ID/тип durable record, turn ID и session ID. Перед Commit stock ждал ACK `AcquireWriter` 1,828 с и `Resume` 5,863 с; в detached 11,4 и 1,2 мс. Это интервалы RPC, **не** прямые замеры захвата mutex. Чтение кода stock показывает, что `OpenDisplaySnapshot` выполняется под общим `State`. Вынос этой работы из общей блокировки подтверждает возможность обслужить другой чат, но этот опыт **не** снимает ограничения #228 при одновременном изменении той же сессии и не делает его готовым релизом. Пики отдельных процессов могли приходиться на разные моменты.

У каждого архива в обоих вариантах 20 ответов `ReadDisplayRecords` (~53,44 МБ), 320 `WriteCache` (~8,57 МБ запросов). Суммарный интервал между первым запросом страницы и последним ответом по одному архиву, включая межзапросные паузы: 11,35–17,90 с против 2,97–4,46 с. После последнего ответа до `Describe` Core выполняет рендер, prefix и сопутствующую работу, но не выставляет отдельных таймеров: 2,18–4,18 с против 1,34–1,94 с. Это не измерение времени только рендера или размера его вектора. Интервал первого–последнего `WriteCache`: 4,14–5,78 с и 3,16–8,49 с; суммарное ожидание самих WriteCache отдельно: 1,61–2,50 с и 1,24–2,18 с. Эти диапазоны по архивам перекрываются и не складываются в общее время. 316 перемежающихся чтений внутри этапа записи после первого сохранённого объекта не нашли кеш в каждом архиве. Эти промахи не означают, что предварительные проверки можно убрать на всех путях.

Во всех руках проверены IDs, роли и тексты последних 50 строк, первые 50 на той же pinned revision, затем снова latest; журналы и blobs проверены по исходному digest; активный ход проверен по каноническому журналу (контекст, один durable user append, соответствующий model request, точный ответ, settlement). Неактивные сессии не запускались. Полный UI и p95 не проверялись.

## Контроль кандидата WriteCache

Кандидат отдельно от #228 переносит только построение ограниченного cache envelope и расчёт точного ETag из `State`. Общий допускающий lock удерживает не более одного подготовленного буфера на экземпляр сервиса; фоновые durable операции не берут этот lock. Сверка session locator и полного fingerprint/двух ревизий, `sync_data`, atomic rename, проверка целевой сессии, temp cleanup и точная эвикция остаются в прежней секции. При ошибке подготовки ответ для устаревшего/несуществующего источника по-прежнему `etag: None`; ошибки актуального сохранения не превращаются в успешный ACK. Кандидат не меняет storage protocol, lock строгого открывания архива и логику чтения. Он не является исправлением ожидания до Commit.

**Решение: не включать по результатам этого опыта.** Код кандидата `1c843c93dc2efcc6c16983cf8c3d0ca417f8a11d`, база `cf999371f6e564376565738bebc3416aad12f908`. Те же Core/Desktop и корпус; менялся только worker, прогоны выполнены последовательно: кандидат, затем рядом новый stock. Все проверки прошли, одинаково по 320 WriteCache на архив. Ранний stock приведён для видимого разброса, он не является вторым чистым A/B.

| Наблюдение | Ранний stock | Кандидат | Следующий stock |
|---|---:|---:|---:|
| Последняя из 4 первых страниц | 28,12 с | 23,78 с | 24,45 с |
| Медиана длительности этапа WriteCache по 4 архивам | 5,13 с | 4,98 с | 4,16 с |
| Медиана суммы ожиданий WriteCache RPC по 4 архивам | 2,16 с | 2,71 с | 1,94 с |
| Проверенный ACK от /send | 7,75 с | 8,26 с | 7,13 с |
| Первый текст активного чата | 10,88 с | 10,55 с | 9,14 с |
| Наблюдаемый пик PSS дерева, МиБ | 800 | 751 | 873 |

У наблюдаемого времени первой страницы и PSS стало меньше в одном сравнении, но целевой этап хуже соседнего stock, физический диск и причинность разницы не проверены. Перенос сериализации не объясняет многосекундное ожидание перед Commit. Как следующий замер, разделить подтверждённо крупный этап публикации на сериализацию, `sync_data`, точный quota scan и ожидание State, не заменяя проверку источника или quota таймером/приближённым счётчиком. Строгий проход по невиденным canonical данным обязателен; отдельно можно сокращать повторную передачу и удержание тел готовых строк.

В тестах JSONL и SQLite совпали ETag и сохранённое значение; устаревший fingerprint/revision вернул пустой ACK, не затёр текущий кеш и не оставил named temp. `cargo test --offline --locked --jobs 1 -p session-storage -- --test-threads=2`: 61 passed, один исходный performance-тест ignored. Release worker собран, `git diff --check` чист. Полный workspace/GUI тест не проводился.

### Повторить

Linux, Python 3, release-бинарники с закреплёнными хешами, Rust Desktop API bridge из R20, эталонный provider и исходный R19 corpus manifest/digest. `run.sh` задаёт пути к ним; при переносе в другое окружение укажите свои проверенные копии, не подставляйте хеш непроверенной сборки. Запускать руки последовательно в свежих синтетических каталогах, без параллельной компиляции. `summarize.py` соединяет matched RPC с границами отдельных archive requests; сырой протокол не нужен для чтения итоговой таблицы.

```sh
bash r21-cold/run.sh stock stock-125k
bash r21-cold/run.sh detached detached-125k
python3 r21-cold/summarize.py r21-cold/evidence/{stock-125k,detached-125k}
# Отдельный односторонний кандидат и новый stock; перед запуском сборку закончить:
bash r21-cold/compare.sh
```
