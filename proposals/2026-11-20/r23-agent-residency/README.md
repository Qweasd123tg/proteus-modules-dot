# Proteus R23: цена активного дочернего агента и резидентности

Измеряет 1/5/10 настоящих дочерних `proteus server stdio` через штатный Rust AgentControlRuntime. Модель синтетическая, без API-трафика. У каждого peer настоящий workflow, context и read_file на локальном файле 32 КиБ, два вызова модели за ход и долговечный JSONL-журнал. Отдельный замер четырёх архивов из R22 отвечает на другой вопрос; не смешивать эти пики.

- Core `048378da7cbe890d8bf8a0152e55eb28ecb5013d`, release с SHA-256 `108a024d2edad562490d1c475b38b454151cfa1398ff6f569cc27beaf9e5e208`.
- Modules `cf999371f6e564376565738bebc3416aad12f908`, точный stock storage `d9929cc7592c7c5f537b8a9c63b8cb5d09ae5a6ffc7c7306e48940bcb4c7c44e`.
- Штатный Rust пример `multiagent_perf` собран из Core с `cargo build --offline --release --locked -p proteus-core --example multiagent_perf --jobs 1`, SHA-256 `d8f3df863570316d44257b3d19d9e600bd1702c116ffefb302aff368241c9731`.
- Синтетический reference component SHA-256 `fbecc2702f11014d546f0223de6bf405aa5162f7a2d07028a866f943d734bd66`; именно этот debug-модуль из проверенного R21 стенда, одинаковый во всех руках. Повтор на отдельном release reference и реальных моделях не заменяется цифрами отсюда.

Исходный Python профиль в этой ревизии не включает storage и на stock CLI падал до работы с `stdio session has no durable directory`. Изменён только файл стенда: явно подключен существующий stock `session_storage/jsonl`, бинарник включён в манифест. Ни драйвер, ни сервер, ни лимиты продукта не менялись. `stand/run.py`: передать четыре проверенных бинарника в `--driver --binary --module --storage`. Для воспроизведения используется 32 КиБ, задержка синтетической модели 500 мс, одно задание на peer, 80 мс между выборками. `run.sh` рассчитан на расположение локальных бинарников как в предыдущих стендах; прямой вызов Python подходит для произвольного checkout. Используется изолированная временная конфигурация со своими локальными тестовыми сессиями.

PSS+SwapPss по одновременно наблюдаемому дереву Linux без GUI/родительского inference; максимум выборочный, а не точный. Idle выбирается после завершения всех ожиданий, +500 мс до начала окна; медиана пригодных снимков с ожидаемым количеством peers. Teardown после явного освобождения родительских ресурсов. Готовность в метрике времени: последний из peers получил ответ модели с командой read_file, не готовность по сетевому healthcheck. Реальная конкурентность проверена отдельно по ModelRequestPrepared/ModelResponseReceived. Результат требует ожидаемого количества завершённых ходов и совпадения read-only replay без изменения журналов.

## 12 одноходовых прогонов

Порядок сравнения: сохранять N процессов, освобождать сразу, освобождать сразу, сохранять N. В каждой руке последовательно 1, 5, 10; все 12 прошли. Диапазоны ниже по одинаковым рукам из двух повторов; для пика показаны обе руки.

| Дочерних агентов | Пик дерева, МиБ | После завершения с продолжением, МиБ | После завершения без продолжения, МиБ |
| ---: | ---: | ---: | ---: |
| 1 | 97,4–98,8 | 97,4–97,8 | 46,6–46,8 |
| 5 | 176,5–182,1 | 174,1–175,7 | 47,2–47,3 |
| 10 | 272,5–273,5 | 269,3–270,5 | 47,6–48,1 |

На 10 все 10 запросов модели реально перекрывались, все успели выдать первый вызов read_file через 312–363 мс от старта драйвера; все ходы завершились через 4,32–4,42 с, в том числе фиксированная искусственная задержка модели. Это не задержка команды живого пользователя: на родителе модели не было. На пике замера SwapPss равен нулю. После явного teardown всего родительского реестра в одном драйвере остаётся около 16–18 МиБ.

На 10 резидентных peers 66 наблюдаемых процессов: 6 на peer (Core, 4 reference-компонента, 1 JSONL worker) + 6 у родителя. На двух пригодных снимках, ближайших к медиане окна, 105–106 МиБ приходилось на 10 Core, 109–110 МиБ на их reference-компоненты, 25 МиБ на storage, остальное на родителя. Доли PSS делят общие отображения, это не сумма независимых RSS. В переходе 1→10 пик вырос примерно на 175 МиБ (~19 МиБ на дополнительного агента в данном диапазоне); это не измерение 100 и не обещание линейности.

Освобождение процесса по завершении почти не меняет пик активной работы, но возвращает примерно 222 МиБ после десяти ходов. Эти задачи при этом **не продолжабельны** через штатный task ID: 0/10 резидентных привязок. Это не демонстрация durable parking. Контроллер отдельно ограничивает 64 агента на родительскую сессию. Практический следующий шаг: завершить одного агента, освободить процесс, возобновить тот же task ID из хранимой сервером привязки к тому же журналу, проверить одну новую запись завершённого хода без повторного исполнения первого. Только затем сравнивать 100 сохранённых задач и ограниченный активный пул.

Отдельный контроль продолжения: 10 агентов, cap=10, два последовательных хода на исходных task ID. Сэмплер видел те же десять PID peers (без замены), было 20 завершённых ходов в тех же десяти журналах и 40 вызовов модели. Каждый ход прошёл replay с неизменным журналом. Это проверка продолжения с оставленными процессами, не после их освобождения. Второй ход имеет другую историю; его задержка не используется для одноходового сравнения.
