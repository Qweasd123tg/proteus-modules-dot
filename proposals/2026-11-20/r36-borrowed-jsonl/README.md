# JSONL: разбор полной строки прямо из буфера

База: Modules `9469e3b12529d08b1f4a76882693e2065e842c51`. Патч независим от переиспользования terminal record, политики размеров inline payload и шестнадцатеричного форматирования SHA-256.

Если полная строка уже находится в буфере `BufReader` размером 64 КиБ, декодер получает её slice без временного `Vec` и копирования. Для строки на границе буфера остаётся исходный ограниченный `read_until`. И прямой путь, и fallback используют одну проверку строки, те же байты для SHA-256, тот же декодер и тот же канонический fold. Смещения, фиксированный диапазон чтения, учёт внешних blob и EOF не меняются. Нового буфера на живой snapshot нет. `memchr 2.8.0` уже закреплён в lockfile; добавилась прямая зависимость, не новая версия в workspace.

## Проверка механизма

`allocation_probe.rs` изолирует только framing и сравнивает число строк и хеш полного набора строк с длинами. File open, первый 64-КиБ буфер и объекты после разбора JSON не входят в счётчики. На неизменном синтетическом журнале mixed56 SHA-256 `3934fe12ddbeddfb618bb0a35bfeaf6aaf2a50634c058f6d70ddadb6c6a70fbe`:

- 676 из 909 строк разобрались из существующего буфера; **909 → 233** новых heap allocations, 242 reallocation в обеих ветках.
- Запрошенные framing-аллокации с учётом запросов reallocation: **23 420 088 → 17 362 933 байт** (−25,9%). Это сумма запросов к аллокатору, не retained bytes, peak RSS или экономия дискового I/O.
- Для 12 000 мелких строк borrowed 11 975; для последовательностей «длинная строка, две коротких» borrowed 60/90. Для 128 строк целиком на fallback счётчики одинаковы. Контроль границы 64 КиБ / 64 КиБ + 1 и чтение после `Interrupted` также сверили exact framing.
- Для больших строк дополнительный поиск разделителя в первом фрагменте может стоить CPU; скорость и суммарный peak процесса не измерялись. Сначала нужен release A/B worker на одинаковом профиле и проверка stock/candidate wire + checkpoint + полный кеш. Эти данные не относятся к всей работе JSON-парсера или к прогону восстановления из соседнего эксперимента.

Новый backend test сохраняет два длинных inline payload между короткими строками; сравнивает раскрытые записи, SHA-256 после каждой записи, итоговый EOF и возврат к началу. `final-suite.log` содержит результаты (64 теста библиотеки и 2 процесса прошли, один ручной perf-тест пропущен) узких пакетов `session-storage` и `proteus-session-storage-module`. Прямой offline Cargo с тем же pinned harness понадобился потому, что штатный Python runner запрашивает метаданные всех платформ, включая отсутствующий в локальном кеше пакет другой платформы.
