# Desktop: не обходим архив Codex заново после каждой выгрузки страницы

База: Proteus-harness/Proteus-desktop `b6a7ec2d8d7e486c8aba01291aa8c89774c4cded`. Изменяемый модуль, реализация подсчёта, DTO и Cargo-зависимости совпадают с `7ccb6c8634c40f450d83bb6e9eff891dc776ee6b`, на которой началась проверка. `git apply --check source.patch` проверен на точной новой базе.

При превышении 200 строк история по-прежнему сначала выгружает целые страницы без подсчёта байтов. Первый нужный обход одновременно считает объём всего окна и отдельно объём ближайшей к удалению страницы. Дальше из суммы вычитается только удаляемая часть, без повторного обхода оставшихся строк. Перед последним удалением (две страницы → одна) нет расчёта для уже ненужной следующей итерации.

Сохраняются бюджет 8 МиБ, границы целых страниц, защита видимой области и допуск одной слишком большой страницы, поведение пустых и перекрывающихся страниц, ключи строк и порядок изменений списка. При переносе суммы сохраняется модульная арифметика релиза; исходный `usize`-подсчёт с проверками переполнения по-прежнему обнаруживает переполнение. Окно и deque страниц меняются только вместе: в начале сохраняется точная длина снимка; при принятии страницы добавляется разница длин после слияния; при выгрузке удаляется ровно записанный диапазон, при возврате к live обе структуры очищаются.

Проверки:
- 48 существующих unit-тестов транскрипта и Codex-проекции, 16 384 перехода со сверкой точных данных/ключей/изменений/курсоров, 14 принятий производственного размера (50 строк на страницу) в обоих направлениях, 250 искусственных граничных сумм в сборках с проверкой переполнения и без.
- Две байтовые выгрузки из четырёх страниц: 450 → 250 вызовов подсчёта строки и 289 350 → 144 750 обходов узла JSON, симметрично в обе стороны.
- Одна выгрузка с JSON в оставшихся строках: 144 900 → 72 450 обходов. Если тяжёлый JSON содержится именно в удаляемой странице, 26 150 → 26 150 (пересчёта этой страницы нет). Без выгрузки, при защите видимой области, при ограничении строк и переходе две → одна счётчики совпали.
- Это изолированные прогоны настоящего кода свёртки архива и проекции с синтетическими историями. Нативный GUI, RPC, осцилляции частоты в фоновой нагрузке, RSS и сколько раз сценарий возникает у реального пользователя не измерялись. Для времени: `rustc 1.95.0 -C opt-level=3 -C overflow-checks=no` для проверяемого кода, одинаковые заранее собранные rlib зависимостей Desktop (`proteus-contracts` 7cbc720, `serde_json` с `preserve_order`, debug); это не end-to-end release-бинарник.

SHA-256: `e8d775cb61f8817a6ac9a928cc890fad9495bd3ef3f106264bce5df491d9aaeb`.

В повторе на 31 паре AB/BA медианное отношение candidate/stock по CPU для двух выгрузок: 0,638 при движении к старым строкам и 0,681 при движении к новым. Для одной выгрузки тяжёлого удаляемого края: 0,966 / 1,044 при тех же счётчиках обхода. Без выгрузки тяжёлого окна: 0,997 / 0,984. Защищённая видимая область дала разное направление (+6,6% / −6,3%), а лёгкий контроль без выгрузки прибавил +35 / +22 нс. Поэтому выигрыш ограничен сценарием повторного дорогого пересчёта, не любой прокруткой. Сырые счётчики и пары в приложенных JSONL.
