# Proteus: стоимость разнесения компонентов по процессам

На штатном Core, без изменений рантайма: тот же тестовый executable под четырьмя ID или под одним ID. Процессы разных агентов не объединялись. Модель, workflow, context, policy, hook и file tool не менялись; JSONL worker отдельный для каждого. Профиль родителя менялся вместе с профилем peers, поэтому это сравнение всего дерева.

| Peers | Процессы во всём дереве | Пик PSS + SwapPss, раздельно → вместе (MiB) | Покой, раздельно → вместе (MiB) |
| --- | --- | --- | --- |
| 1 | 12 → 6 | 97–97 → 81–82 | 96–97 → 81–81 |
| 5 | 36 → 18 | 176–180 → 128–129 | 173–175 → 125–126 |
| 10 | 66 → 33 | 272–276 → 185–185 | 268–268 → 179–180 |

На десяти одновременно работавших peers семейный пик упал на 32–33%. Ускорение не подтверждено: два парных прогона 4.338 → 4.732 с и 4.360 → 4.293 с. До последнего входа в модель разница тоже меняла знак. На пике своп нулевой. Это Linux, PSS дерева с шагом 80 мс, не RSS одного процесса и не оценка памяти Desktop, реальных провайдеров или ста агентов.

ABBA: split-1, aggregate-1, aggregate-2, split-2; в каждом блоке 1 / 5 / 10 peers; один ход, 32 KiB синтетических данных, локальная fake-модель. 64 хода, 128 запросов к модели, одно чтение на ход, полный ответ совпал по SHA-256; replay сверился и не изменил журналы. Проверено полное перекрытие запросов по событиям. Медианы покоя включают только полную ожидаемую топологию; один замер на переходе к teardown исключён. Пик не фильтровался по фазе. Источники: Core 048378da7cbe890d8bf8a0152e55eb28ecb5013d; storage worker из Modules cf999371f6e564376565738bebc3416aad12f908. Бинарники и все прогоны в results.json.

## Воспроизведение

Собрать исходный пример Core `multiagent_perf` и CLI в release, stock JSONL worker в release и тот же тестовый reference module в dev. Указать пути через переменные окружения. Для повторной проверки PSS-дерева всем четырём бинарникам нужны имена процессов из reducer: driver, core-stock, worker-stock и proteus-reference-module.

```bash
OUT=/tmp/proteus-topology-new
for mode in split-1 aggregate-1 aggregate-2 split-2; do
  python3 stand/run.py --driver "$DRIVER" --binary "$CORE" \
    --module "$REFERENCE" --storage "$STORAGE" --topology "${mode%-*}" \
    --output "$OUT/$mode" --counts 1 5 10 --rounds 1 --payload-kib 32 \
    --delay-ms 500 --interval .08 --timeout 45 --max-pss-mib 512
done
python3 reduce.py "$OUT"
```

## Что это меняет для архитектуры

Это эксперимент с уже реализованным механизмом, не патч штатных профилей. Консолидация имеет смысл для совместимых экспортов внутри явно общего домена доверия, отказов и перезапуска. Не склеивать по имени файла: в [штатном OpenCode](https://github.com/Proteus-harness/Proteus-core/blob/048378da7cbe890d8bf8a0152e55eb28ecb5013d/configs/opencode.config.toml#L29-L46) runtime и модель используют один launcher, но переменная API-ключа нужна только модели. Связывание меняет доступ к окружению и последствия сбоя. Ни cross-agent sharing, ни сохранение изоляции при объединении разных пакетов здесь не проверены.

Независимо от размера процессов, [парковка #234](https://github.com/Qweasd123tg/proteus-modules-dot/pull/234) держит слотовый permit до checkpoint/reap. Для очереди нужен отдельный A/B с одним слотом, одинаковым idle cap 0 и вторым свежим агентом, вставшим в очередь до завершения первого. Для длинного журнала нужен ABBA с одним неизменяемым JSONL, исходным checkpoint и готовой/отсутствующей display-проекцией: запрос последней записи на новом JSONL snapshot может декодировать весь журнал, а промах display добавляет ещё один полный проход. Это разбор исходников, а не замер задержки.
