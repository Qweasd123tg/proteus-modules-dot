# Прототип: последняя страница из сохранённой проекции

Точная база Core: `048378da7cbe890d8bf8a0152e55eb28ecb5013d`.
Локальный коммит: `2547f15f2a7b511c20b9b34ecf2d4872557608b7`.
Патч применяется через `git am core-prepared-page.patch` к чистой базе.
Изменены только путь выборки страницы внутри Core, его тесты и справка.

- Здоровая последняя страница: один запрос `OpenSnapshot` вместо двух (по одному `ReleaseSnapshot` на открытие). Сначала читается существующий HEAD и проверяются хеши нужных объектов; **после** чтения сравнивается полная тройка `(session, revision, content_sha256)`. Время последней проверки задаёт момент, на который ответ был актуален.
- Если именной индекс нового источника успели опубликовать, но замену HEAD последующая операция не выполнила, читаем именной индекс, сверяем его источник и повторно проверяем момент актуальности после чтения тела. Это чтение не обязано восстанавливать сам HEAD. Обычная смена ревизии без нового индекса не является попаданием.
- Запрошенная явно ревизия не обязана совпадать с текущим журналом: имя и содержимое её страниц по-прежнему проверяются. Формат и правила base, операции записи, сроки ожидания, lease, admission и создание сессии не менялись.
- Полностью отсутствующий или структурно испорченный HEAD: как на базе, сразу переходим к строгой проекции; не добавляем предварительного открытия канонического снимка, которое на холодном источнике само может требовать полного прохода. В существующем API нельзя использовать `ReadCache.source` как свидетельство актуальности журнала. Новый протокол, формат, СУБД, фоновый catch-up не предлагаются этим патчем.

**Цена компромисса:** отставший, но корректный HEAD может заставить прочитать отбрасываемую старую страницу. Старая страница освобождается до попытки прочитать новую именную. Не более 50 возвращаемых строк не означает не более фиксированных MiB: штатный формат допускает большие отдельные строки. Полный header содержит список страниц, проверка которого зависит от числа листьев. У хранилища `OpenSnapshot` может переигрывать журнал, если валидный durable catalog/prefix недоступен. НЕ заявляем O(1) в целом, ускорение первого полностью неиндексированного открытия или меньший системный PSS. Нужен отдельный замер, а не экстраполяция числа RPC.

Три новых regression-теста в штатном Core unit target: контроль стоимости попадания и равенства с pinned; потеря заключительной публикации HEAD и конкурентное изменение источника на чтении именной страницы; конкурентное изменение на чтении исходной HEAD-страницы. Результаты проверок и действительные параметры сборки см. в сопроводительных логах. Тестовая обёртка с `fail_head` не создаёт фальшивый текущий источник: точку гонки задаёт новая запись в модели журнала. Это не само по себе процессный нагрузочный тест.

## Проверено

Локальные 24/24: 16 `core::session_store::remote::view::tests::` (в том числе три новые),
4 `app_server::read_model::tests::`, 4 `app_server::http::tests::session_reads::`.
Последние два набора используют реальный stock JSONL storage worker и process
reference fixture. Форматирование workspace, `git diff --check` и применимость
патча в обе стороны прошли. Это не полный workspace test, не SQLite/process
conformance и не GUI-тест. Для проверки в обычной среде с Modules checkout:

```sh
python3 scripts/test.py -p proteus-core --lib core::session_store::remote::view::tests::
python3 scripts/test.py -p proteus-core --lib app_server::read_model::tests::
python3 scripts/test.py -p proteus-core --lib app_server::http::tests::session_reads::
cargo build --release --locked -p proteus-core --bin proteus
```

Здесь использован Cargo test с заранее связанными процессными fixtures (не полный wrapper,
который собирает все внешние modules). Для тестового исполняемого файла только
`proteus-core` собран с opt-level=0, codegen-units=64. Измеряемый бинарник
собран отдельно штатным release-профилем, без этих overrides.
