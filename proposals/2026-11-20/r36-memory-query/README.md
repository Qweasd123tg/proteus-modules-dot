# JSONL memory: передавать готовый MemoryQuery без нового JSON

**База:** `Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51`. Изменён один файл `context_provider/memory-pack/src/lib.rs`; SQLite и сохранение фактов не менялись. Локальный commit `b9bf34066a024185ee26ee548fd8a65d548578e1`. SHA-256 `source.patch` — `51f8e65e5e77d40477e66e1702d4c7142d084ca6e42cfa62b7491616f523ac32`.

Провайдер уже проверяет JSON-метаданные и получает `MemoryQuery`. Инструмент проверяет строковый аргумент и сам создаёт `MemoryQuery`. Затем приватный метод вновь сериализовал эту пару `String + usize` только для того, чтобы соседняя функция снова разобрала её. Теперь она получает `&MemoryQuery`. На закреплённой версии Core у обоих полей обычные serde-реализации без дополнительных правил: сериализация и чтение результата не могли отклонить корректный типизированный запрос. Внешние проверки, отмена инструмента, обработка отсутствующего файла, порядок, регистр, ограничение и ошибки повреждённого JSONL остались на прежних местах.

**Проверка поведения:** stock и candidate возвращают побайтово одинаковые JSON-ответы или сообщения об ошибках у обоих export-обработчиков во всех девяти сценариях (единственная нормализация — временный путь в ошибке). Сценарии включают Unicode и экранирование, `usize::MAX`, нулевой лимит с повреждённым файлом, неверный тип, отличающееся поведение отрицательного лимита в tool/provider и отмену до чтения. `wire-parity.jsonl` содержит данные проверки; это прямые вызовы JSON-обработчиков, не попытка измерить IPC.

**Замер:** реальный `JsonlMemoryStoreModule::recall`, Linux, release, три повтора каждой из 15 пар на одинаковых данных. Счётчик считает Rust-запросы `alloc`, `alloc_zeroed` и `realloc` после создания `MemoryQuery`, до освобождения результата. Это сумма запрошенных байтов, не пик памяти и не end-to-end задержка. Остальные выделения сканирования остаются.

| Сценарий | Запросы Rust, до → после | Запрошенные байты, до → после |
|---|---:|---:|
| Существующий файл, совпадение 16 байт UTF-8 | 23 → 21 | 11 101 → 10 957 |
| Существующий файл, нет совпадений, ASCII 4 096 байт | 24 → 20 | 27 176 → 10 637 |
| Существующий файл, нет совпадений, 65 536 байт с управляющими символами | 47 → 20 | 731 397 → 10 637 |
| Нулевой лимит / отсутствующий файл, ASCII 16 байт | 2 → 0 | 144 → 0 |

Для обычного короткого запроса выигрыш невелик; основная польза — убрать лишний JSON-переход между двумя типизированными функциями. Все 45 пар: `allocations.csv`. Чтобы повторить тест с Rust 1.95 и существующим offline-кэшем Cargo:
```sh
CARGO_TARGET_DIR=/path/to/reusable-target python3 probe.py /path/to/Proteus-modules 9469e3b12529d08b1f4a76882693e2065e842c51
```
Стенд использует два временных клона и сам применяет `source.patch` к одному из них. Исходники стенда не входят в патч.

**Gates:** `cargo fmt --all --check`, `git diff --check`, `cargo test --locked --offline --release -p memory-pack --lib` — 3 теста прошли. Штатный Python runner блокируется общей offline Cargo metadata: отсутствует Android-only `android_system_properties 0.1.5`; прямой Linux-target запущен с исходным lockfile. Изолированная release-сборка/установка `package.py --profile release --package memory-pack --install` успешна, SHA-256 бинарника совпадает с manifest (`a6b6ab8fe17f7bdcb955119b6b190c8a334c0c385acd93b5be2d894701b02fe8`). Полный workspace, другие ОС и пользовательская установка не затрагивались.
