# 50k: повторный тест смены только JSONL worker после #220

**Что проверяем.** В #220 одиночная проверка на 50k меняла сразу два слоя. Здесь Core во всех запусках уже содержит оба патча #220 (проверка префикса и передача курсора); меняется только release-бинарник session-storage. A = штатный worker, B = кандидат с проверенной границей. Реальный `AgentAppServer`, процессный JSONL и синтетическая фиксированная модель; это **не** замер у провайдера, живой сети или на Desktop. Core собран с `opt-level=1`, зависимости и storage в release. Оба бинарника, Core и fake module одни и те же между парами, кроме указанной подстановки.

**Метод.** Четыре свежие временные сессии последовательно, два блока AB/BA; Linux, CPU affinity 2 у теста и дочерних процессов, общая машина (ядро не резервировалось). 50 000 строк в истории отображения, каждый append хранит 100; компакция оставляет 100 активных. Таймер send запускается после записи и возобновления при первом ходе; построение фикстуры и всё последующее чтение для проверки исключены. В каждом результате 21 149 817 байт до запроса; целостность байтового префикса, отсутствие архивных сообщений в запросе, успешный ответ ассистента и 50 002 строки по курсору проверяются. В каждый запрос действительно вошло 101 сообщение (100 активных плюс новое). Число сообщений отображения не равно числу записей JSONL.

**Вывод.** На этом входе 99,20–99,66% времени целого send приходится на подготовку отображаемой истории. Новый worker сокращает время этой фазы на 3,86% в первой паре, но увеличивает на 9,13% во второй. Эти 2 пары **не доказывают устойчивое улучшение или регрессию** от замены только worker. Число возвращённых журнал-записей и в A, и в B: 537 (507 один раз и шесть пять раз). Шесть проходов, тринадцать ответов на ReadRecords; число внутренних прочтений/декодирований в worker этим счётчиком **не измеряется**. Четыре теста из четырёх прошли, провалов нет.

**Отличие от времени модели.** В последнем столбце времени выше из полного send вычтено только монотонное время completed_transcript. Это верхняя граница для fake-вызова плюс подготовка, IPC и сопутствующая работа, а не изолированная задержка модели. Дополнительные диагностические запуски B в отдельной временной папке не входят в сравнение AB/BA. Только после сигнала SETTLE_BEGIN извлечены шесть записей хвоста нашего синтетического журнала, начиная с соответствующей смещению CASE границы. Проверены совпадение exchange_id, success и число сообщений. Разность между журнал-записями запроса и ответа — интервал между системными timestamp_ms перед отправкой commit в worker (включает инфраструктуру, не время непосредственно внутри модели). В двух отдельных запусках окно запроса–ответа равно 14 / 14 мс, а монотонное время последующего completed_transcript — 14 525,541 / 9 807,259 мс. Полный send — 14 564,603 / 9 862,372 мс; turn_opened→turn_settled по записям — 24 / 25 мс. Оба контрольных Rust-теста прошли. Первоначальная версия внешнего парсера ожидала DTO вместо дискового формата; исправленный reader прочёл шесть дисковых записей первой пробы и успешно повторил проверку на новой сессии. Отметка turn_settled в журнале уже записана **до** последующей подготовки transcript, поэтому разность turn_opened→turn_settled не описывает видимую пользователю задержку.
