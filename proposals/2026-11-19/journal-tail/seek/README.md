# JSONL: первая страница после проверенной старой границы

Кандидат Modules, не новый протокол. Порядок наложения: [Proteus-modules 37b3d9c4](https://github.com/Proteus-harness/Proteus-modules/tree/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979) → [предыдущий кандидат CompareSnapshots](compare-r7.patch) → [эта добавка, включая три теста](seek.patch). Оба патча проверены последовательным применением на чистое дерево. В данном A/B обе стороны **уже** имеют первую оптимизацию. Схема, writer/recovery, публичные дескрипторы и SQLite не требуют изменений.

При полном открытии service и раньше проходил весь снимок, проверяя последовательность, семантику записей и SHA. На единственной старой границе с ненулевым номером теперь сохраняются ещё смещение конца фактически прочитанной строки и копия потокового состояния SHA-256. Это не позиция underlying file descriptor: BufReader мог прочитать вперёд. Нет таблицы смещений по всем записям и нет передачи состояния между открытыми файлами. Если полный проход не завершится, handle не выдаётся.

При новом или непоследовательном запросе точно от этой границы worker **сначала пересчитывает SHA всех байтов фиксированного диапазона открытого файла**, включая хвост самого snapshot, затем переходит к сохранённому смещению, сбрасывает прочитанное вперёд, ограничивает остаток и продолжает хеширование с сохранённого состояния. Чтение до конца проверяет весь итоговый SHA как раньше. Непрерывные страницы просто продолжают текущий курсор. Без известной границы, при наличии внешнего payload где угодно в снимке и в SQLite остаётся обычное чтение с начала для непоследовательного запроса. Изменённые stamps по-прежнему сначала вызывают полный fold. Один лишь тёплый descriptor не создаёт точки перехода.

## Измерение

Два независимых release worker, настоящий Storage SDK по stdio, одна и та же сессия/фиксированные байты в обеих ветках каждой пары, отдельный writer. 0, 128, 512 или 2 048 старых записей с текстом ~704 байта (операция **replace**, ограничивает активную историю одной записью). Оба reader открывают и освобождают старый снимок. Writer добавляет три коротких сообщения. Каждая сторона открывает новый снимок, сверяет его со своим прежним дескриптором, читает первую страницу от старого номера с limit=1, затем оставшиеся две записи. Проверяются handle в ответе, номера, все сообщения и следующий курсор. Большой случай: 2 852 548 байт фиксированного JSONL. Это **не** полная загрузка GUI, пользовательский ход или модель.

8 независимых пар новых worker на размер; порядок A/B, B/A чередуется. На каждую независимую пару один первый доступ и ещё три возврата к тому же cut. Worker привязаны к CPU 6, Python к 4, общий Linux x86-64 хост нагружен также другими работами, файловый кеш не сброшен. Время с отправки RPC до получения и разбора ответа, миллисекунды. До/после — отдельные медианы; Δ — медиана парных относительных изменений. Сумма четырёх RPC — open, compare, page1, page2; подготовка/запись/закрытие вне таймера. В CSV дополнительные поля процессных часов не используются для выводов об экономии CPU (учёт микрозапросов может быть грубым).

| Старых | Первый ReadRecords, мс | Δ парная; быстрых пар | Сумма четырёх RPC, мс |
|---:|---:|---:|---:|
| 0 | 0,194 → 0,206 | +11,0%; 3/8 | 1,027 → 1,222 (0/8 быстрее) |
| 128 | 1,685 → 0,453 | −73,0%; 7/8 | 6,956 → 5,739 (5/8) |
| 512 | 9,702 → 1,008 | −89,0%; 8/8 | 24,086 → 12,989 (8/8) |
| 2 048 | 39,003 → 3,016 | −91,9%; 8/8 | 92,999 → 57,841 (8/8) |

При нулевой границе новый seek не используется, выигрыша нет: в этом прогоне сумма даже выросла примерно на 0,20 мс. Следующая последовательная страница не получает такого же ускорения; на 2 048 записях медианы для неё 0,364 / 0,296 мс. Не приписывать кандидату отдельное улучшение времени открытия/сравнения: семантический проход и полная проверка байтов остались. Последовательные и повторные результаты не считались независимыми парами. [Сводка](evidence/summary.csv), [сырые пары](evidence/pairs), [таймер и проверки](bench.py).

## Проверки и воспроизведение

Обычный Cargo 1.95 с `--release --locked --offline` подтвердил тот же результат ([журнал](evidence/cargo.log)). Целевые проверки оптимизированной сборки: [36 unit прошли, 1 штатный ручной замер ignored](evidence/unit.log); [2/2 теста отдельного SDK worker по восстановлению после смерти процесса прошли](evidence/process.log). Новые unit-тесты проверяют число реально декодированных записей и точное число байтов полной SHA, вторую страницу и EOF, повтор страницы, тёплый/неизвестный cut, испорченный/пропавший внешний blob до точки перехода и подмену по обе стороны от cut без зависимости от сравнения файловых stamps. Полный Modules workspace не запускался.

Обычное воспроизведение (Linux, Rust/Cargo 1.95.0, LLD, зависимости из Cargo.lock, Python 3.9+):
```sh
bash reproduce.sh /path/to/Proteus-modules /new/path/results 6
```
Последний аргумент необязателен, укажите CPU своего хоста; для закрепления самого драйвера запускайте скрипт через taskset. Отдельные Cargo target directories нужны для исключения случайного повторного использования worker. [SHA использованных бинарников](evidence/binaries.sha256) относятся к конкретной сборке измерительного хоста, не к ожидаемому воспроизводимому хешу бинарника на любом компьютере.

Точно измеренные бинарники локально слинкованы Rust 1.95.0 с одним набором Cargo release зависимостей: production library и driver main собраны без cfg(test), opt-level=3, Linux x86-64, LLD. Тесты отдельно включают штатные счётчики. [Точная команда relink в виде скрипта](relink_exact.py) сопоставляет зависимости с Cargo fingerprints, включая bundled SQLite. Для повторного использования именно такого прогретого кеша задаются RUN_ROOT (там находятся checkout baseline и candidate с применёнными выше патчами), CARGO_RELEASE_CACHE (каталог release с deps/.fingerprint/build) и RUST_1_95 (корень toolchain). Затем для каждого arm запустить сначала `python3 relink_exact.py ARM lib`, затем `python3 relink_exact.py ARM worker`. Если отпечатки этого кеша отсутствуют, использовать обычный Cargo-скрипт выше, а не подставлять зависимости наугад.

**Отдельная поправка для переносимости.** В существующем байтовом верификаторе преобразование остатка из u64 в usize раньше происходило до ограничения размером 64 КиБ. Для 32-битного процесса и остатка, кратного 4 ГиБ, это может дать нулевую длину чтения и отвергнуть корректный большой снимок. [Самостоятельная однострочная правка](portable-prefix-chunk.patch) ограничивает 64-битное число до преобразования. Для x86-64 выражения тождественны. Тем не менее **этот hunk не входил ни в один измеренный бинарник**; обычный reproduce.sh измеряет только две основные заплатки. Для реализации на 32-битной цели накладывать третьим и квалифицировать на этой платформе. Нативный 32-битный прогон не выполнялся.

## Контроль противоположной формы и рекомендуемое ограничение

Цена проверки всего файла может превышать цену обычного короткого сканирования. При одной старой записи (685 байт), 2 048 новых записях (итого 2 851 178 байт) и запросе лишь первой новой записи исходный r7 и исходный r8 дали **0,586 → 2,968 мс**, ухудшение во всех 6 независимых парах ([сырые результаты](evidence/opposing.csv)). Поэтому **не применять один только seek.patch как общий быстрый путь**.

[Отдельная поправка late-cut-only.patch](late-cut-only.patch) ограничивает переход случаями, когда старые байты занимают не меньше половины снимка. Так объём обязательного перечитывания для seek не может более чем вдвое превысить размер старого префикса. Если условие не выполнено, работает штатное чтение с начала. Это грубая граница по байтам, а не оптимальный эмпирический порог для всех дисков и процессоров. Произвольные веса, новые настройки и угадывание стоимости декодирования записей не нужны.

r7 против **нового** worker с ограничением:
- При том же крошечном cut обычное чтение восстановлено: первый RPC 0,715 / 0,508 мс в 6 новых парах ([данные](evidence/guarded/opposing.csv), [стенд](opposing.py)). Разброс на коротком RPC существенен; это не обещание ускорения обычного чтения.
- Большие cut при маленьком хвосте: 128 — 1,200 / 0,352 мс; 512 — 4,131 / 0,726 мс; 2 048 — 16,840 / 3,286 мс ([сводка](evidence/guarded/summary.csv), 4 новые пары на размер; 4/4 быстрее на каждом размере). Сравнивать только внутри этих пар, нагрузка машины отличается от первой серии.
- Guard-сборка b09cc12204a7ae86a650566c314339c26f180788784ec632555fa7b46da06b74: [37 unit прошли, 1 ручной ignored](evidence/guarded-unit.log); [2 process recovery прошли](evidence/guarded-process.log). Внутренний guard-тест дополнительно считает, что в контрпримере декодированы именно две записи и отдельного полного SHA нет. Эта сборка **не** использовалась для опубликованных выше восьми пар неограниченного seek.
- Повторить можно имея r7-worker и worker после compare-r7.patch, seek.patch и late-cut-only.patch: `python3 opposing.py /path/to/r7-worker /path/to/guarded-worker out.csv --pairs 6`. Для основной формы вызвать bench.py для тех же worker по схеме reproduce.sh, с разным порядком. Portable-prefix-chunk.patch к обеим сериям не относится.
