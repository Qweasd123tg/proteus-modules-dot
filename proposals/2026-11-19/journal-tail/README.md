# Proteus: почему короткий хвост всё ещё дорого читать

Продолжение [#220](https://github.com/Qweasd123tg/proteus-modules-dot/pull/220), те же upstream Core `8ea2cdaf` и Modules `37b3d9c`. Все журналы синтетические, настоящий AppServer/JSONL worker, провайдер fake, без Desktop GUI. Эти материалы не меняют upstream.

1. [Пройти к проверенной позиции JSONL](seek/README.md). Старый worker при каждом ReadRecords этого суффикса начинал по байтам с нуля. Новый worker хранит одну позицию, подтверждённую на уже строго прочитанном snapshot. Продолжить хеш с этой точки разрешено только после проверки текущих байтов фиксированного диапазона; отдельные blob и неизвестная граница оставляют старое чтение. [Реальный A/B хода](full-turn/README.md): 50k архив / ровно 101 сообщение в запросе, время подготовки истории 9,28→6,79 с и 9,45→7,90 с. 27 сценариев передачи/целостности проверены независимо. Короткий префикс с большим хвостом сначала замедлился; отдельное ограничение сохраняет штатный путь для этой формы, после него один проверочный 50k ход занял 6,75 с.
2. [Не запрашивать один и тот же короткий хвост пять раз](suffix/README.md). Отдельный bounded Core-кандидат, компонентный replay из 2k: 6→2 ReadRecords, 143→101 мс на проекцию. Не складывать с seek; стек обоих патчей не замерен.
3. [Профиль до оптимизации](backend-profile/README.md). На 50k stock JSONL ReadRecords вернул 537 записей, но worker декодировал 3 042, включая пять перезапусков префикса; время крупных стадий ниже. После оптимизации основным кандидатом остаётся полный семантический fold префикса, не пропуск строгих проверок и не создание дубликата истории.
4. Два отрицательных контроля: [isolated r7 worker на 50k](r7-recheck/README.md) оказался быстрее в одной паре и медленнее в другой; [подсчёт байтов вместо буфера](size-control/README.md) не улучшил реальный ход. Прежние узкие выигрыши меньших стендов на 50k не экстраполировать.

5. [Компонентные кандидаты для следующего слоя](fold/README.md): проверять ID добавленной партии, не пересоздавая два индекса всего старого префикса, и перемещать уже валидированное финальное состояние вместо его копии. На 20k архивных строках в партиях по 100, compacted до 100 активных, компонентная медиана fold 284→136 мс. 261→28 МБ — суммарные запрошенные bytes за проход, не пиковая RSS. На полном пользовательском ходу это ещё не замерено.
