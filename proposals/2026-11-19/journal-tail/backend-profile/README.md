# Атрибуция: почему 537 записей для Core означали 3 042 разбора в worker

Измерен тот же синтетический AppServer с #220 Core display+cursor и 101 сообщением в запросе (перед запуском активный контекст 100, архив 5 000 или 50 000). Точечные диагностики API worker выделены по меткам конца пользовательского хода; стенд с трассировкой меняет абсолютные тайминги. Это счётчики внутри worker и вложенные тайминги, не независимые суммы CPU всех процессов.

На 50k исходный (до патча CompareSnapshots из #220) JSONL-worker, один trace: подготовка истории 11,07 с, его storage handlers 7,07 с. Внутри них OpenSnapshot 2,59 с (507 проверок семантики), CompareSnapshots 2,87 с (1 014 декодирований, 501 применение семантики), ReadRecords 1,60 с при 3 042 декодированиях и 537 возвращённых записях, все обращения ReadCache+WriteCache вместе 12,5 мс. 3 042 = 6 × 507; даже 6-строчный ответ не означал шесть прочитанных записей. 127,22 МБ — суммарные байты декодированных входных записей, не физический диск или объём IPC. Прочие ~4,0 с за пределами storage handlers нельзя автоматически приписывать одному этапу без дополнительной трассировки.

На одном инструментированном прогонах A/B с уже применённым CompareSnapshots (как в основном [A/B хода](../full-turn/README.md)) ReadRecords в worker вернул прежние 537 записей за 13 RPC, но реально декодировал 3 042 → 537 записей (127,22 → 21,47 МБ), а время обработчиков ReadRecords 1 749,7 → 467,7 мс. При этом fast seek отдельно пересчитал SHA для 106,02 МБ, то есть пять раз по 21,2 МБ. Это не устранение всего I/O, а отказ от повторного декодирования. Последующее OpenSnapshot в B заняло 2,34 с; 1,98 с внутри него — работа полной семантической проверки 507 записей. Этот профиль не использовать вместо парных рабочих таймингов.
