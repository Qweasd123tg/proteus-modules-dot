# Две независимые правки к строгой свёртке
База: Proteus-core `8ea2cdaf4195` + кандидаты #220 `display.patch`, `cursor.patch` и `active-ids.patch`. Схема wire, storage, число чтений и семантика checkpoint не меняются. Ни одна правка не переносит наблюдение сырых фактов до строгой проверки.
- [Забрать уже проверенный результат](move-final.patch): Core проверяет итоговую history_revision, сохраняет два поля, затем перемещает активную историю из единоличного владельца, а не клонирует её. При 100 активных сообщениях с 160 байт текста: 201 выделение/52 800 байт → 0/0; при 5 000 с 1 024 байт текста: 10 001/6 960 000 → 0/0. Время этой операции не сравниваем: consuming-вариант одновременно освобождает валидатор. Число byte allocations не означает изменение RSS. Проверены идентичность конверсии и адрес исходного вектора. Само по себе не решает задержки при 50 000 архивных и 100 активных строках.
- [Проверять ID небольшого добавленного блока, не строя заново обе таблицы всего префикса](batch-ids.patch). Только у уже валидного префикса и если append добавил строго меньше половины итогового числа сообщений: временные множества содержат только новые ID. Из них удаляются совпадения со старым префиксом, затем новые сообщения и части проверяются последовательно. Первое сообщение об ошибке остаётся тем же. Однострочная ветка #220 сохранена. Ошибочное предыдущее состояние, крупный append, замена, checkpoint, инструментальный результат остаются на полной проверке. Никаких постоянных индексов. Повторный просмотр старых ID остаётся: это не линейный алгоритм на весь журнал.

## Измерение отдельно от IPC

Стенд: прямой вызов production `JournalValidationState::apply_sequenced`. Старые сообщения добавляются блоками по 100, текст 160 ASCII-байт в каждой, в конце Replace с compaction оставляет 100 последних. Размер входа и все ID совпадают. Проверены точный канонический результат и ревизия. В таблице время только свёртки, не создание входа/финализация. Медиана четырёх AB/BA-пар на общей машине, native rustc 1.95.0 release opt-level=3. Выделенные байты всего за свёртку измерены отдельно; это не объём единовременно живых данных.

## Почему строгий проход остался

`ReadRecords.validate_response` проверяет привязку, канонический размер, последовательность и границы страницы, но не все правила жизненного цикла журнала. Вторая свёртка у Core не является доказанно лишней на границе произвольного выбранного storage. Даже совпадающий hash/ревизия заголовка кеша не подтверждает валидность переданной последующей записи. Для повторного использования нужен либо сам локальный валидатор того же открытого snapshot плюс независимо доказанный неизменный префикс (с ограничением памяти/времени жизни), либо отдельно согласованная версия контракта и явная модель доверия. Отдельная передача текущих выводов безопаснее; она не выдаёт кэш дисплея за полномочия writer.
