# Четыре холодные страницы и активная отправка на исходном коде

Отдельная частичная диагностика, не сравнение патчей. Core stock
2aad0ba29311f0dbf7c107efc281abc1202ce4c4 (SHA c43ec1f9…b9a9e),
Modules stock 2c2cee47ea76df12c6e208839594e32470a2c3f1 с worker-логированием
границ mutex (SHA e98021de…7f2). Core и broker не инструментированы.
100 независимых сохранённых синтетических архивов, четыре запроса по
125 000 отображаемых сообщений, отдельная активная A. Отправку A
инициировали сразу после увиденного захвата блокировки холодной операцией.

- Три ответа: HTTP 400 с исходным общим текстом
  history source cannot be fingerprinted, около 30,276 с каждый.
- Четвёртая страница: 79,785 с. Для этого запроса проверены позиции
  и содержание последних 50 строк до финального контроля.
- Отправка A: ошибка execute timed out через 57,292 с; это не latency
  нормального ответа. Число принятых durable действий после ошибки
  по этому прогону не утверждается.
- Трасса storage: первый OpenSnapshot одного архива держит общий
  mutex около 26,874 с; остальные запросы архивов отмечены waiting.
  Затем видно изменение PID storage. В новом процессе строгий
  OpenDisplaySnapshot ещё около 26,963 с держит mutex, пока
  другая операция ждёт. Это реальное ожидание в обслуживающем
  процессе, но не точный диагноз причины сброса поколения broker.

Строгий завершающий oracle ожидал, что все четыре выбранных журнала
откроются. Фактически открылись два, дальнейшие проверки старых
страниц и финального SHA не запускаются. Поэтому включены только
сохранённые до assert ошибки, worker trace и ответ A. Не считать
это успешно завершённым perf-стендом для всего набора.
