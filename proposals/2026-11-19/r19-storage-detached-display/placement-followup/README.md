# R19: один повторно используемый поток для тяжёлого display fold

Диагностика поверх #228, не релизный патч. Один и тот же бинарник worker
`789e8bdaf887935498b4f93acfb262a9867354ee217d22b5051b728c548de4d4`;
Core `048378d`, worker tree до диагностической правки
`5261c122a6ed19676c00c8ca6ada3ecf1af3dd15`. Тот же синтетический корпус:
4 × 125 000 исторических строк, остальные 96 архивов короткие, у длинных
после compaction в текущей истории 100 сообщений. Настройки glibc по умолчанию.

Меняется только место вызова display build: на SDK-потоке запроса либо на
одном выделенном потоке. В обоих случаях исходный gate #228 остаётся, передача
без буфера, канонические чтения, путь active commit, staging и выдача результата
в SDK не переезжают. Лог подтвердил четыре разных Rust thread ID в direct и
один ID для всех четырёх тяжёлых вызовов в same (во всех запусках).
Это не самостоятельное доказательство соответствия thread → glibc arena.

| Метрика | A → B | A → B в обратном порядке запуска |
|---|---:|---:|
| Worker PSS через ≈60 с, МиБ | 390 → 266 | 304 → 265 |
| PSS всего дерева через ≈60 с, МиБ | 637 → 499 | 547 → 537 |
| Выборочный пик дерева, МиБ | 870 → 805 | 813 → 851 |
| Первый непустой SSE-текст, мс | 103 → 225 | 106 → 217 |
| Верхняя оценка durable открытия по SSE, мс | 20 → 17 | 20 → 30 |

Все четыре холодных, тёплых latest и pinned запроса, неизменность канонического
архива и результат активного чата прошли во всех четырёх arms. PSS рабочего
процесса после минуты ниже в обеих парах; результат по общему пику меняет знак,
первый текст медленнее в обеих парах. Поэтому это диагностическая подсказка про
владение временной памятью, а не основание переносить решение в main. Два прогона
на условие не дают p95. Нет ускорения модели или результатов Desktop.

Воспроизведение: поверх `final.patch` применить `placement-probe.patch` и собрать
release worker. К копии исходного стенда #228 применить
`allocator-followup/arena-sampler.patch`, затем `stand-placement.patch`.
Запускать `archives.py` как в основном README, с `--extended-idle --minute-idle`
и `--fold-placement direct` либо `same`, порядок direct/same/same/direct.
Для измеренных задержек не подключать внутрипроцессный диагностический sampler.
Worker stderr пишется отдельно; `python3 summarize.py result-a result-b …`.

Отдельная инструментированная пара с `malloc_info` раз в 0,5 с:
число heap arenas около 10 с **7 → 8**, свободные блоки арен
**133 → 264 МиБ**, worker PSS **120 → 267 МиБ**. Это отдельный измерительный
режим, в котором знак idle эффекта поменялся. Совпадение ID потока не означает,
что весь процесс использовал меньше арен: есть другие SDK-потоки и сериализация.
Проба не отслеживала привязку каждой отдельной аллокации к арене. Не складывать
эти цифры с неинструментированными запусками и не приписывать выигрыш конкретно
созданию арен.
