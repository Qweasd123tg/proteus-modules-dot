# R19: где заканчивается ускорение

Текущая пара: Core `048378da7cbe890d8bf8a0152e55eb28ecb5013d`, Modules `cf999371f6e564376565738bebc3416aad12f908`. Core уже содержит прежний патч verified cold history целиком; накладывать его повторно не нужно. Эксперимент с HTTP admission из #226 в этой базе отсутствует.

**Первый рубеж:** открытие большой холодной истории не держит блокировку, необходимую другому чату для записи. Подтверждение этого инварианта: A получает durable ACK до снятия барьера на B; B выдаёт тот же locator, два номера ревизии, SHA, resume state и номера строк, что и последовательный прогон. Наличие первого SSE текста или HTTP 200 само по себе не заменяет эти проверки.

**Следующий рубеж:** четыре холодные истории по 125 000 сообщений + активный чат проходят одним и тем же HTTP-стендом. Сравнивать отдельно время до первого текста, успешность A и всех четырёх B, последнее/закреплённое тёплое окно, пик PSS дерева и память после завершения. Один запуск на каждой стороне не даёт p95. Фиксация SQLite может удерживать WAL до освобождения handle; это отдельный показатель, не блокировка writer и не обещание низкого места на диске.

**Что ещё мешает.** Даже после вынесения OpenDisplaySnapshot обычный холодный OpenSnapshot по-прежнему может делать строгий replay под State. Эту операцию вызывают в том числе для проверки актуальности latest. Тёплый pinned page и latest нельзя складывать в одну цифру. Для latest нужно проверять источник и до, и после чтения: кэш не знает, не появилась ли более новая версия. Подмена этого требования TTL или пропуском хеша только спрячет ошибку.

**Архитектурная граница:** общий путь «зафиксировать конкретную версию → проверить вне общего замка → опубликовать результат только для нужного поколения». Закреплённая версия и текущий HEAD несут разные обещания. До штатного использования нужно сохранить поведение, когда одновременно меняется именно читаемая сессия; эксперимент может вернуть явный конфликт, а текущий Core его не повторяет. Не включать его по умолчанию из-за одного успешного прогона.

**Точка остановки:** после изоляции фоновой работы время одной холодной истории будет ограничиваться проверкой ещё не засвидетельствованных канонических байтов, декодированием и визуализацией. Дальше выигрывать надо на объёме работы: поддерживать проверяемый индекс/проекции при записи, а не повторять полную проверку ради окна в 50 строк. Мерить, где реально остался масштаб O(история) и какую память требует один одновременно восстанавливаемый архив; не обещать универсальный минимум в МБ без рабочей нагрузки.

**Контракт, который ограничивает большой пример.** Сейчас display RPC возвращает в одном ответе handle и весь `StorageResumeState`, включая `conversation.messages`; отправитель преднамеренно возвращает `projection: None` при превышении 32 MiB сериализованного состояния. Тогда Core возвращается к обычной строгой загрузке через `OpenSnapshot`. Вынесение только успешного display пути не доказывает изоляцию этого fallback. Поднимать лимит ради результата не стоит: можно умножить одновременно живые копии по обе стороны SDK. Сначала подтвердить, какой путь реально взяла конкретная история, затем отделить ограниченный просмотр от полного resume, если именно это осталось дорогим.
