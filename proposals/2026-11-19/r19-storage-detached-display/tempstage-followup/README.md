# R19: что стоит вторая временная копия истории

Изолированная диагностика точных release Core `048378d` и worker #228, тот же
корпус 4 × 125 000 исторических строк и 96 коротких архивов. Не патч продукта.
Обычный worker продолжает писать staging в выделенный каталог в обоих вариантах.
В варианте B у Core отдельный заведомо отсутствующий `TMPDIR`, поэтому его
локальный временный файл открыть нельзя. Сами журналы, persistent cache и
аргументы запросов не меняются. Это тест недоступности временного каталога Core,
не точечная продуктовая настройка одного вызова; могут быть затронуты и другие
необязательные временные файлы Core.

На Core его номинальные 512 МиБ учитываются отдельно **на один writer**. В #228
отдельная worker-квота покрывает staging его зарегистрированных снимков и
одного строящегося снимка **на экземпляр storage service**. Оба числа считают
записанные байты файлов, не RSS, heap или PSS. Отказ временного файла Core
после успешного projected open использует тот же worker snapshot и повторяет
display RPC. Отказ самой проекции в worker ведёт по другому пути, через
каноническое восстановление. Сокращение лимита Core не отделяет эти расходы.

Порядок A/B/B/A. Все четыре холодных запроса, latest, pinned и целостность
канонического журнала с активной записью прошли в каждом прогоне.

| Метрика | Core staging включён (A, два прогона) | Core staging не открывается (B, два прогона) |
|---|---:|---:|
| Холодные страницы (мин–макс на прогон) | 15,37–17,65 / 13,04–15,46 с | 35,17–37,67 / 36,35–39,73 с |
| Пик логического размера Core temp (сэмпл) | 103 / 108 МиБ, до 3 fd | 0 |
| Пик логического размера temp обоих процессов на одном сэмпле | 258 / 298 МиБ | 204 / 204 МиБ |
| Пик PSS дерева (сэмпл) | 940 / 1090 МиБ | 1051 / 1039 МиБ |

Файлы наблюдались через `/proc/PID/fd`: только закрытые для имён, но ещё
открытые дескрипторы из двух выделенных каталогов. Оба каталога были на
**overlayfs**, а не на системном `/tmp` (tmpfs в этом окружении). Это
логические размеры, не доказательство резидентности или полноты page cache.
Выделенная cgroup с `memory.current` недоступна, а монтировать/менять систему
для этого теста не нужно. Не сравнивать эти абсолютные пики как совместимые с
предыдущими запусками на другом расположении временных файлов. Знак эффекта
на PSS здесь не повторился, а отказ Core staging последовательно увеличивал
время чтения архивов. Не выключать или урезать его вслепую.

Повторить: скопировать `stand/` основного пакета и наложить `tempstage.patch`.
В обычную команду `archives.py` добавить `--core-stage on|off` и
`--mount-label` из `stat -f -c %T DIRECTORY`, где лежит каталог результатов.
Для подсчёта вызовов вместо этого наложить `counted-tempstage.patch` на
новую копию и положить рядом `count_wire.py`. Обёртка пересылает байты как есть,
но влияет на тайминги; её timings не включены в таблицу.

### Независимый подсчёт RPC

В двух дополнительных запусках с обёрткой считаются `ReadDisplayRecords` по
точному ID handle. По каждому из четырёх больших handle Core сделал
**20 запросов и один старт с `after_seq=0`** при доступном tempfile против
**60 запросов и три старта** без него. Пятый маленький handle: 1 → 3.
Все проверки данных в обоих запусках прошли. Значит, на этом корпусе
worker проекция не исчезла: без собственной перематываемой копии Core
заново читал тот же снимок, а не строил новую каноническую историю.
Временные файлы не стоит дублировать без необходимости, но без альтернативы,
которая сохраняет повторное чтение локальным, их простое отключение
переносит нагрузку на RPC.
