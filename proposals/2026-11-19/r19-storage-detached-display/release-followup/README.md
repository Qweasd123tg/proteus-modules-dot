# R19: срок жизни snapshot после построения display-модели

Это диагностика существующего #228, не изменение продукта. Core `048378d`:
`SessionReadModel::from_validated` вычисляет transcript и prefix до синхронного
`ReleaseSnapshot` в Drop. Пока вызов ждёт, модель уже построена, но ещё не
вернулась к вызывающему коду. В worker удаление snapshot (включая временный
файл и read transaction) идёт под State, которым пользуется и канонический
`OpenSnapshot`. Это проверка исходников, не замер Core heap.

**Контроль на точном release worker #228** (`714ef623…527a5b`, SDK v3):
в A открыть display snapshot, дописать новую запись, убедиться, что WAL A
нельзя усечь из-за старой snapshot-транзакции. В отдельной B проверить
эксклюзивную блокировку SQLite на независимом read-only соединении. Послать
открытие B и дождаться, пока worker откроет её файл (inotify). Пока B удерживается,
отправить `ReleaseSnapshot(A)`. Обе ветки используют один и тот же бинарник
и одну и ту же B; меняется только тип открытия.

| Открытие B | ACK release до снятия блокировки B | Staging fd A в этот момент | WAL A в этот момент |
|---|---:|---|---|
| Каноническое OpenSnapshot | 0 из 3 | Открыт | TRUNCATE занят; 10 кадров, обработано 8 |
| Вынесенное OpenDisplaySnapshot | 3 из 3 | Уже закрыт | TRUNCATE успешен |

Оба варианта правильно вернули B. После ACK release staging A закрыт,
WAL A усекался, старый handle отклонялся. В канонической ветке ACK release
пришёл через ≈430–431 мс при намеренном удержании 400 мс; в контроле display —
0,27–0,34 мс без ожидания разблокировки. Не интерпретировать этот диапазон
как обычную production latency или вклад в PSS: время удержания задаётся
стендом. RPC запускаются напрямую, нет полного Core/HTTP прогона.
Повторить из каталога: `python3 wire.py /path/to/worker open_snapshot` и
`python3 wire.py /path/to/worker open_display_snapshot`; Linux, Python/SQLite,
только синтетические временные данные.

**Не повторяя A/B по потокам.** В `placement-foreground.jsonl` уже записанные
точки из предыдущего прогона direct/same/same/direct. До наблюдения durable user
append: 39→45 мс в первой паре и 42→84 мс во второй. Интервал от этого SSE
события до первого текста: 64→180 и 64→133 мс. Это границы наблюдения по SSE,
не длительности функций и не причинная атрибуция задержки.

Для следующего A/B: разнести Core Drop wall time, wait перед State и физическое
освобождение handle; отметить число одновременно живых снимков, байты staging и
живую память Core при публикации. Включить удержанный канонический read как
контроль и SQLite WAL как отдельную наблюдаемую величину. Нельзя чинить это
путём запуска неограниченной асинхронной уборки.

В таком Core-контроле барьер должен поставить удержанное чтение B после
завершения `Describe`, но до входа в Drop: summary тоже делает синхронный
`Describe`, который иначе замаскирует отдельную задержку release. Если
локальная staging-проекция отсутствует, ещё нужны чтения с worker;
не переносить release раньше без сохранения этой зависимости.
