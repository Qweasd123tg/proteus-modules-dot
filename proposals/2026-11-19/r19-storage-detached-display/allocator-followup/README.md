# R19: пик и удержание аллокатора после архивного чтения

Отдельная диагностика Linux/glibc, не изменение Core, Modules или настроек поставки. Тот же Core `048378d` и тот же корпус из четырёх длинных (по 125 000 исторических строк) и 96 коротких архивов, с тем же синтетическим активным чатом. SHA канонического набора `2c24c1898a8593186328dd91fff646aa0f809758d0396c9ce959fd4488d1e375`.

У #228 один отдельный допуск для display/catalog на экземпляр storage service. 512 МиБ — бюджет временных **файлов проекции**, не heap. Обычный cold `OpenSnapshot` всё ещё использует отдельную блокировку и может пересекаться с display fold. Защита display освобождается по возврату из сервиса, до SDK JSON и flush; она также не владеет рендером и публикацией Core. Это проверенные свойства исходников, а не доказательство, что какой-то из этапов сам вызвал весь пик.

## Что проверено

1. **A/B/B/A без пробника в процессе.** Тот же бинарник worker #228 и только `MALLOC_ARENA_MAX=2` в окружении storage worker варианта B, факт проверен в окружении живого процесса. Core не получал эту настройку. Все холодные и тёплые проверки и канонические проверки активного чата прошли. Выборочный пик дерева: 956 → 735 МиБ и 1043 → 850 МиБ (обратный порядок). После примерно 10 секунд простоя дерево: 514 → 524 и 711 → 559 МиБ, устойчивого выигрыша здесь не показано. Первый текст: 108 → 102 и 113 → 494 мс. Две пары не устанавливают p95 и не обосновывают новое значение по умолчанию.
2. **Сэмпл glibc в отдельном диагностическом прогоне.** `malloc_info` в том же worker увидел через ≈10 секунд у stock 233 МиБ свободных блоков арены, у #228 284 МиБ; PSS worker в этих прогонах 227 и 280 МиБ. Сравниваются разные единицы: free в аллокаторе не эквивалентен резидентным страницам. Для иллюстрации эффекта физической памяти есть однократная проверка ниже. Пробник не участвует в приведённом выше замере задержки, не рекомендуемый профиль запуска.

Следующий тест до переноса в main: общий допуск только для тяжёлой части фонового восстановления до завершения нужного жизненного цикла, штатный короткий ACK вне него. Отдельно подтвердить поведение при записи в ту же сессию, а не лечить ошибку глобальным увеличением timeout. Не заменять ограничение живых данных периодическим `malloc_trim`.

### Проверка возврата страниц

3. **Один trim после простоя в том же процессе #228.** После всех четырёх ответов и успешного активного запроса выждали около 10 секунд. В отдельном диагностическом потоке один раз вызван `malloc_trim(0)`; успех записан в trace. Медиана PSS storage worker до/после: **453 → 79 МиБ**; всё дерево **700 → 326 МиБ**. PID тот же; после измерения успешно проверены latest и закреплённые страницы, канонический SHA неизменен. Это причинный тест для *остатка в данном прогоне*: около 374 МиБ были возвращаемыми страницами, а не обязательными живыми данными. Он не раскладывает рабочий пик по фазам и не доказывает такой размер остатка во всех запусках. Один trim не трогает код поставки, не выполняется после каждого архива и не является предлагающимся исправлением.

## Повторить

- Используйте те же версии worker/Core и golden fixture; команда и аргументы исходного стенда описаны в [основном README](../README.md). Скопируйте оригинальный каталог `stand/` заново для каждой разновидности и примените ровно один из патчей к `archives.py` (из копии: `patch -p1 -i /absolute/path/to/arena-limit.patch`). Все измеренные варианты добавляют `--extended-idle`, ставящий сопоставимые метки примерно 1 и 10 секунд до тёплых запросов.
- Для A/B используйте `arena-limit.patch`; запускайте A без нового значения, B с `--worker-arena-limit 2`, в порядке A/B/B/A. Это изменяет только окружение worker.
- Для инструментального сэмпла используйте `arena-sampler.patch`; соберите `cc -O2 -Wall -Wextra -Werror -shared -fPIC -pthread -o arenas.so sample-glibc-arenas.c`, добавьте `--allocator-sampler /absolute/path/to/arenas.so` вместе с `--extended-idle`. Опциональный лимит применяется так же. Для причинной проверки trim вместо этого используйте `one-time-trim.patch` и соберите `sample-trim-idle.c`, добавьте `--trim-idle-once`. Пробники используют glibc и заранее выбранный локальный каталог синтетического стенда; не добавляйте их к поставляемому окружению.
- `python3 allocator-summary.py results/control-1 results/arena2-1 …` пересчитывает метрики из `summary.json`, `trace.jsonl` и, при наличии, `arena-trace.txt`. [Сводка](runs.jsonl) и [детали проверок](evidence.json) приложены. PSS дерева суммирует значения живых процессов на одном сэмпле, без Desktop. Инструментированные измерения не объединялись с неинструментированными.
