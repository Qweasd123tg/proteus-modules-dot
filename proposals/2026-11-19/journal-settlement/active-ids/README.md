# Узкая оптимизация проверки ID при append

**Граница.** Proteus-core, pin `8ea2cdaf4195ae24e941354f68d4e97335d139d7`, shared crate `proteus-session-semantics`. В `JournalValidationState::apply` штатная проверка при каждом добавлении одного сообщения заново заполняла два временных HashSet всеми ID активных сообщений и их частей. Накопленный префикс уже проверен, а тип операции Append гарантирует, что старые элементы не переставляются и не меняются.

[Патч](active-ids.patch) сравнивает новый ID сообщения и, если есть, единственный новый ID части со старым префиксом. Сначала проверяется сообщение, затем часть, как раньше. Тело и смысл сообщения, принадлежность сессии, последовательность, стабильность части и все прочие правила валидируются прежним путём. Метод не создаёт нового индекса/кеша. Размер самого JournalValidationState на проверенном x86_64 target остался 352 → 352 байта; это не измерение суммарного heap. После изменения нескольких сообщений, записи с несколькими частями, Replace, Checkpoint или вставки результата инструмента остаётся полная проверка. Если предшествующая проверка ID упала, append тоже полностью перепроверяет активную историю. Это сохраняет обнаружение повреждения даже при попытке продолжить использовать уже отвергнутый объект.

Сумма сравнений со старыми строками в худшем случае **остаётся квадратичной** для N отдельных добавлений. Убраны именно повторные построения таблиц, аллокации и хеширование всего префикса на распространённой узкой ветке. Изменение не отключает полный replay Core и не разрешает доверять произвольному cursor.

## Проверка и измерение

[Probe](probe.rs) подаёт N **отдельных** правильных записей `HistoryMutated::Append` (1 сообщение, 1 текстовая часть, 720 ASCII-байт). Все идентификаторы, тексты, последовательность и ревизии одинаковы для обеих сборок. Измеряется построение строгого состояния с нуля, только цикл `apply_sequenced`; генерация входа, освобождение состояния и проверка результата после цикла исключены. Каждая сборка проверяет все итоговые message ID, их порядок, длину и ревизию. Нет storage worker, IPC, чтения файла, дисплея, генерации модели или пользовательского хода. Такой компонент используется в хосте и storage; для изменения поведения уже поставленного worker его надо отдельно пересобрать с изменённой версией crate.

Release rustc 1.95.0, одинаковые opt-level=3, codegen-units=16, debuginfo=0; обе версии исходного crate заново собраны с той же pinned группой уже собранных зависимостей. 5 чередующихся A/B процессов на общедоступном CPU; цифры ниже — медиана, не прогноз для другой машины. [Все прогоны](pair.log). Счётчик аллокаций включён в отдельном прогоне, без него измерена задержка.

Результаты относятся только к указанному набору append, не к любому workflow, который может часто писать checkpoint, multipart или много записей другого типа.

Штатные тесты включают сохранение идентичности и точного порядка ошибок, повторное использование отвергнутого состояния, восстановление после Replace, коллизии результата инструмента и checkpoint. Штатный runner: release с opt-level=1 только у зависимости jsonschema; компонентные измерения от него независимы.
