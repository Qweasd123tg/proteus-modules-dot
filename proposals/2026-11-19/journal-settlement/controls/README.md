# Независимые проверки точного префикса и проекции

Core `8ea2cdaf4195ae24e941354f68d4e97335d139d7`, Modules `37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979`. Здесь нет патча продукта. Это маленький внешний стенд над реальным JSON-RPC worker, плюс один тест производного tool-index для тестового стенда Core. Каждый сценарий заново создаёт временные каталоги. Никаких существующих пользовательских сессий, живой модели, аккаунтов, сети или внешних tools.

**Результат:** все **15** сочетаний «сценарий × backend» прошли на штатном release worker и на кандидате с сохранённой границей префикса. Для дополнительного контроля прошли и на штатном debug worker. Это проверка семантики, не замер времени. Логи: [release до](stock-wire-release.log), [release после](candidate-wire.log), [debug до](stock-wire.log). В первой строке каждого лога SHA-256 проверенного исполняемого файла. Для иной сборки повторить, а не переносить результат по названию ветки.

```bash
python3 worker_controls.py /absolute/path/to/proteus-session-storage-module
```

Требования: Python 3.9+ под Linux, JSONL и SQLite exports указанного компонента. При первой ошибке скрипт завершается с ненулевым кодом; не запускать с `python -O`.

| Проверка | Какой результат считается правильным |
|---|---|
| Обычный append, оба backend | Старый snapshot возвращает только старые сообщения; новый – старые и новые. Завершённый handle нельзя использовать для чтения, но его описание прежнего префикса можно сравнить с живым handle. Неправильный digest или history_revision при совпадающем session_seq не принимается. |
| Смена writer и процесса, оба | Второй процесс не захватывает активный writer. После освобождения получает правильную revision, не принимает просроченный token/handle, повтор ACK старой операции под новым lease возвращает ту же запись. Новая запись видна; публикация cache для старого source отклонена. |
| Два клиента одного worker, оба | Им выдаются разные tokens одного поколения; одинаковый operation_id идемпотентен. Операция с новым id и устаревшей expected revision отклоняется. Снятие одного lease не отзывает второй. |
| Отдельный reader работает при живом writer, оба | После первой страницы reader writer добавляет запись. Вторая страница того же snapshot заканчивается старым концом. Новый snapshot видит append и подтверждает происхождение от старого. |
| Compaction, затем Replace, оба | Да, сырой префикс сохранён; **нет**, из этого не следует, что старые строки разговора сохранились. После compaction current отдаёт замену, BeforeReplacement указывает на прежние данные. После явного reset предыдущая history revision недоступна из текущего snapshot, но остаётся читаема из старого закреплённого snapshot. |
| Испорченный/отсутствующий disposable cache, оба | Валидный preview был доступен; сломанный/отсутствующий файл даёт miss и не меняет каноническую историю. |
| Атомарная замена JSONL | Равная длина, количество, идентификаторы и revision, но ранее видимый текст изменён. Новый открытый FD видит новую ветку и не подтверждает старую. Уже закреплённый старый FD возвращает старую. |
| Изменение JSONL на месте после получения proof | Та же длина, inode и восстановленный mtime. Compare и чтение следующей страницы со старого handle не должны silently accept изменённый pinned prefix. После возврата исходных байтов сравнение и чтение проходят. |
| Пропавший/испорченный внешний payload JSONL | Изменяется **только** payload blob, журнал не изменён. Новый descriptor сохраняет hash и revision журнала. Strict Compare на warm handle и на уже проверенном handle (как с предыдущей границей, так и с самим собой), а также canonical read / tail-page отвергают испорченный blob. В отсутствии файла canonical read тоже даёт ошибку. После восстановления все ожидаемые данные доступны. |

### Почему это ограничивает оптимизацию

1. [Семантическое состояние валидатора](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-session-semantics/src/journal/projection.rs#L24-L46) содержит историю, устойчивость частей, record IDs, открытые/закрытые turn и execution, контекст, model requests/responses и tool lifecycles. `StorageResumeState` без этих индексов не заменяет checkpoint валидатора. При новом процессе/неизвестной границе безопасен проверенный replay, а не возобновление от произвольного cursor.
2. Анкеры должны относиться к конкретной session/incarnation и **тому же** fixed snapshot; session_seq, history_revision и raw digest выполняют разные роли. [Warm descriptor](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/service/views.rs#L22-L79) может быть предварительным. SQLite pin поддерживает read transaction, для JSONL inline возможна строгая проверка байтов того же FD. [Внешний payload](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/codec.rs#L118-L139) проверяется отдельно на доступность, размер и digest. Полную перегидратацию нельзя молча заменить сравнением digest строк журнала. Тесты выше меняют файлы между запросами, а не утверждают атомарность при произвольных одновременных изменениях нескольких физических файлов.
3. [Проверка независимости display-суффикса](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/transcript/journal/append.rs#L58-L109) выходит далеко за число новых сообщений: удержанная часть checkpoint должна совпасть полностью, включая metadata, и быть явно committed; новая ссылка на старый call/message/part/turn/exchange, поздний tool-result, citation, обновление hosted card, compaction/replace могут менять уже показанные строки. Inline display-кеш не даёт полномочий исполнять инструменты. В latest-tool-index последняя подходящая строка того же **имени** побеждает; `denied` и `failed` её не замещают. Это не live MCP-discovery и не статус доступности инструмента.
4. Публиковать только после полного успешного чтения и проверки источника; ошибка поздней страницы не должна превращаться в публикацию частичных данных. Неполный/повреждённый display cache – miss независимо от успешного чтения заголовка. Возврат старого preview допустим только по уже существующему явно provisional display API, не как canonical history. Для нового persisted witness дополнительно связывать cursor с source заголовка и точным проверенным состоянием; не повышать уровень доверия отсутствующим или ошибочным полям.

### Покрытие Core

На baseline Core прогнаны **29** существующих тестов (`journal::append::tests`, `journal::tests::replay_frontier`, `core::session_store::remote::view::tests`); [результат](stock-core.log). Это штатные тесты из локального baseline-бинаря, содержащего отдельную SSE-инструментацию прошлого эксперимента, не полный прогон рабочего пространства. Исполнять на чистом checkout:

```bash
cargo test --locked -p proteus-core --lib -- journal::append::tests journal::tests::replay_frontier core::session_store::remote::view::tests --test-threads=1
```

[Дополнительный test-only контроль](tool_control.rs) вставляется в конец `crates/proteus-core/src/core/session_store/remote/view/tests.rs` в одноразовой тестовой копии: две страницы; одинаковое имя инструмента, разные call ID; после второго принятого вызова происходят failed/denied; потерянный индекс восстанавливает точный call, включая effective_args; без нужной исходной страницы — miss, а не частично восстановленное значение. После изменения источника старый индекс не выдаётся как свежий.

Оценка покрытия не равна доказательству всех interleavings: нет тестов электрического отказа fsync, разрыва протокола посреди байта или другого backend/ОС. Для допуска к релизу дополнительно нужны штатные CI, паритет функций на той же сборке и измерение пика памяти: индекс идентичностей, собранный в одном проходе с валидатором, сокращает чтения, но может жить одновременно с ним.
