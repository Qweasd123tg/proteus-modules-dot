# Кеш отображения: что перечитывается при записи

**На проверенном закрытии хода штатный Core не переписывал все старые страницы, но перечитывал каждую из них. Кандидат Core оставил чтение только хвоста; одна лишь очистка кеша секундную задержку не объясняет.** При 5 000 строк дисплея и 100 активных сообщениях Core записал не 5 000 строк, а четыре ключа: два новых блока данных, заголовок данной ревизии и HEAD. Зато storage, даже когда места хватает, четыре раза прошёл каталог кеша: 429 проверок метаданных файлов, суммарно 0,80 мс на этом прогоне. При тысячах *файлов*, а не сообщений, один такой проход уже измеряется миллисекундами и аллоцирует мегабайты.

## Проверка в настоящем ходе

Core `8ea2cdaf`, Modules `37b3d9c4`. Тот же стенд короткого синтетического хода с моделью-фикстурой; новый отдельный нативный JSONL worker с [измерительной правкой](diagnostics.patch) считает обычные файлы .storage-cache-*.json и времена непосредственно до/после `evict`; запись диагностической строки идёт **после** таймера. Один владелец каталога, без параллельных изменений. Запись данных и расчёт etag **не входят** в это время. В каждой строке и модели переданы 101 сообщение, активная история до хода 100. [Ход](turn.log), [события worker](turn-cache.log), [суммы](turn-summary.txt).

| Старых строк дисплея | Первый кеш: записей / проверок файлов | Новый ход: записей / проверок файлов | Данные кеша, записанные за ход | Только eviction за ход |
|---:|---:|---:|---:|---:|
| 100 | 6 / 21 | 4 / 33 | 8 201 Б | 0,14 мс |
| 2 000 | 45 / 1 035 | 4 / 189 | 16 015 Б | 0,31 мс |
| 5 000 | 105 / 5 565 | 4 / 429 | 28 015 Б | 0,80 мс |

При первом наполнении чистого каталога проверено 1+2+…+105=5 565 файлов. При тёплом ходе старые payload-страницы не были записаны заново. Замер считает успешные **записи**, а не все чтения: новое содержимое проверяется Core по хешу; при полном fallback старые страницы могут быть прочитаны и захешированы снова. Отдельно у model_context на append-пути всегда вызывается полный write_section, а соседние Usage-факты обычно объединяются: нельзя считать, что каждой строке или каждому ходу соответствует отдельная строка контекста. Ссылки: [публикация](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/session_store/remote/view/cache.rs#L119-L215), [инкрементальный путь](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/session_store/remote/view/incremental.rs#L33-L65), [eviction](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/service/cache.rs#L101-L139).

## Старые страницы именно читаются: независимый A/B Core

Дополнительно на двух реальных сборках Core при неизменённой реализации storage (только [регистрация факта чтения](reads-diagnostics.patch)) посчитаны существовавшие ранее ключи. В каждой сессии сначала фиксируем точный набор всех успешно записанных `display-data-*` до первого опубликованного HEAD, затем на новой ревизии считаем удачные чтения **тех же** файлов. На stock это первый ход после запуска с уже построенным кешем, а не гарантия того, что *каждый* последующий ход повторит работу. В кандидате применены оба патча Core из раздела display: раздельные вклады не измерялись. [Исходный след](reads-stock.log), [кандидат](reads-candidate.log), [подсчёт](summarize_reads.py).

| Старых строк | Старых ключей | Различных старых ключей прочитано: до → после | Всего чтений этих ключей: до → после | Старых envelope-байтов прочитано: до → после |
|---:|---:|---:|---:|---:|
| 100 | 4 | 4 → 1 | 5 → 1 | 94 335 → 17 297 |
| 2 000 | 43 | 43 → 2 | 44 → 2 | 754 060 → 17 752 |
| 5 000 | 103 | 103 → 2 | 104 → 2 | 1 795 000 → 17 752 |

До и после получены полные ожидаемые итоги (102 / 2 002 / 5 002 display-строки), те же 101 сообщение в model request. При 5 000 строках на 99,0% меньше байтов именно ранее созданных **cache envelopes**. Это длины прочитанных файлов, не физический диск, не весь journal, не общий IPC, не суммарная память и не сокращение времени на 99%. На каждый ответ Modules и Core по-прежнему выполняют обычную обработку; общее время хода измеряется отдельно. Для воспроизведения обоих запусков применить reads-diagnostics.patch вместо diagnostics.patch; перед второй сборкой Core задать новый путь к пустому логу при сборке Modules или разделить лог двух запусков, затем запустить summarize_reads.py для каждого из них.

## Изолированная стоимость большого каталога

Linux x86-64, временные данные на tmpfs; release Rust 1.95.0. Настоящий worker с протоколом JSON-RPC по stdin/stdout, JSONL и SQLite. Драйвер отдельно создаёт N файлов: у каждого своё имя, его содержимое копирует исправный маленький cache envelope текущего worker (данные не обязаны быть различными, чтобы проверить обход квоты). Затем перезаписывает один и тот же короткий ключ; число файлов остаётся N+1, сумма заметно ниже 128 МиБ. До и после совпадают имена, возвращенные value и etag сверены; лимит не отключён. Это не заявка, что в типичной сессии столько файлов. Измеряется полное время ожидания ответа WriteCache, не весь ход; быстрый tmpfs не моделирует HDD/SSD. [Исходный уровень](results.json): для 0 / 256 / 2 048 / 8 192 дополнительных файлов медианы JSONL 0,29 / 0,70 / 4,75 / 14,84 мс; SQLite 0,38 / 0,66 / 4,40 / 20,24 мс (по 9 измерений после 2 разогревочных, медиана 3 независимых прогонов). Не складывать с секундной задержкой другого стенда.

**Небольшой [кандидат](evict.patch) для Modules, не исправление всего закрытия хода.** Код по-прежнему читает метаданные **каждого** файла после **каждой** записи. Пока перебирает файлы, сохраняет уже полученное имя без двух построений полного пути. Если сумма уже не выше квоты, старые кандидаты не сортируются; удалять всё равно нечего. При переполнении сохранены прежнее стабильное упорядочение по mtime и порядок обхода при равных временах, защита только что записанного ключа, граница 128 МиБ, проверка ошибок и удаление старейших. Изменений в journal, snapshots, fsync, source/etag, записи или восстановлении сессии нет.

[Отдельное A/B](comparison.json): 5 пар свежих процессов/сессий; порядок AB/BA чередуется, времена записей исходных файлов детерминированно перемешаны. Worker и Python на разных закреплённых CPU. Медиана 5 внутрипроцессных медиан из 9 RPC, мс:

| Других файлов | JSONL до → после | SQLite до → после |
|---:|---:|---:|
| 0 | 0,26 → 0,27 | 0,43 → 0,39 |
| 2 048 | 4,13 → 2,74 | 4,49 → 2,14 |
| 8 192 | 14,76 → 12,20 | 16,09 → 10,44 |

При 8 192 файлах в обеих реализациях после было быстрее в 4 парах из 5, а не во всех. Соседняя нагрузка и планирование в VM дают разброс. На пустом контроле выигрыша не заявляем. Самое устойчивое изменение: [счётчик запросов аллокатора](allocation_probe.rs) вокруг только evict на настоящем каталоге с 8 192 соседями показал 65 556 → 16 400 вызовов, 4 939 961 → 2 170 920 Б суммарных запрошенных размеров и 1 605 632 → 1 081 576 Б пика живых запрошенных размеров. Это **не RSS всего процесса**. По три повтора, [до](allocation-base.log), [после](allocation-opt.log).

Проверено по 29 штатных тестов storage и [один контроль](quota_control.rs) до и после: ровно 128 МиБ никого не удаляет; превышение на 1 МиБ+1 байт требует убрать два старейших; текущий key старше обоих, но остаётся; временный, посторонний файл и каталог не затронуты. Контроль использует sparse-файлы: в расчёт квоты штатно входит длина, а не выделенные блоки. [Лог до](tests-base.log), [лог после](tests-opt.log). В локальном стенде библиотека, worker и test binary собраны rustc с opt-level=3 против уже готовых release-зависимостей закреплённого Cargo.lock. Полный workspace/GUI, стенд конкурентных cache writers, реальный накопившийся пользовательский каталог и замер latency **с удалением** не запускались. Воспроизведение на Linux: `sh reproduce.sh /путь/к/Proteus-modules /новый/каталог`. Для трассы хода применить только diagnostics.patch к чистым Modules, собрать worker командой `PERF7_CACHE_TRACE=/абсолютный/путь/к/новому/файлу cargo build --release --locked -p proteus-session-storage-module`, привязать его как PROTEUS_TEST_SESSION_STORAGE_MODULE к стенду реального хода раунда 7 и вызвать `python3 summarize_trace.py /путь/к/файлу`. Инструментация в кандидат не входит.

**Приоритет:** для секундного завершения сначала устранять повторную работу над журналом и отображением. Не заменять строгую квоту таймером или периодической очисткой и не доверять счётчику, который другой процесс может сделать устаревшим. Если профиль реальной долгоживущей сессии покажет тысячи файлов, до смены протокола стоит проверить отказ от записи промежуточных состояний одного и того же инструмента, которые полный rebuild тут же заменяет в latest-per-name индексе; отдельно сохранить доступ по старым опубликованным ревизиям. Для чтения прежних payload-страниц нельзя делать выводы по одному списку записей.
