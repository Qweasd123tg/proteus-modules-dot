# Сверка снимков без второй сборки истории

Кандидат для [Proteus-modules `37b3d9c4`](https://github.com/Proteus-harness/Proteus-modules/tree/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979). Семантика/контракты закреплены на Core `4c032eeb` в Cargo.lock Modules; это не патч Core, Desktop или каталога. [Патч с тестами](compare.patch).

На [исходном пути](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/snapshot.rs#L81-L105) успешная сверка префикса ещё раз строит полное семантическое состояние вплоть до запрошенной ревизии; декодирование продолжается до конца снимка. JSONL отдельно декодирует все записи, чтобы вычислить хеш префикса; SQLite читает payloads префикса отдельным запросом для SHA. Это происходит даже если только что открыт **полностью проверенный** снимок.

На уже обязательном [холодном проходе](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/service/views.rs#L23-L65) кандидат запоминает максимум одну предыдущую границу: фактические `(session_seq, history_revision, SHA-256)` после применения записи. Из кеша берётся **только номер записи, за которой смотреть**. Из переданного старого descriptor не берётся ни одно доказательство. Результат сохраняется только после успешной проверки всего снимка вместе с проверенным концом. Прошлый handle можно освободить. Дополнительная память ограничена одной парой счётчиков и одним хешем на handle; лимит handles уже 32. Историю/индекс записей не сохраняем. Схема на диске, протокол и writer recovery не меняются.

На известной границе и конце полностью проверенного снимка:
- **JSONL только с inline-данными** заново хеширует весь фиксированный диапазон байтов открытого файла, даже при неизменном `mtime`. Не перечитывает хвост, добавленный за границей *самого снимка*. Подмена внутри снимка, даже после старой границы, отвергается.
- **JSONL хотя бы с одним внешним payload** использует исходный полный путь. Хеш журнала удостоверяет ссылку, но не наличие и содержимое файла blob. Признак внешнего payload ставится при настоящем декодировании и не сбрасывается при перемотке данного снимка.
- **SQLite** не перечитывает payloads: записи и их порядок уже зафиксированы read transaction открытого снимка (исходный контракт `RecordSnapshot::source_version`). Речь о поддерживаемой модели SQLite; произвольное физическое повреждение активного файла в обход SQLite не моделируется.
- Неизвестная старая граница, тёплый descriptor без полной валидации и новый процесс без сохранённой границы используют прежний путь сравнения. Тёплый cache не становится authority. Неверные SHA или `history_revision` не подтверждаются. Начало и конец различаются даже если `session_seq != history_revision`.

## Что измерено

Локальный native `StorageService::execute`, Linux x86_64 AMD EPYC 9V74. Rust 1.95.0, opt-level=3, lld; в измерительном бинарнике сохранены штатные test-only счётчики. Обе версии вручную слинкованы с одним набором Cargo release-зависимостей; [скрипт воспроизведения](reproduce.sh) собирает тот же production-код и test probe обычным Cargo. Подготовка: N записей с текстом ~704 байта; открыть и освободить старый снимок; дописать одно короткое сообщение. Замер холодного открытия нового снимка и трёх последовательных успешных сравнений с прежней границей. ФС настоящая, записи committed, OS cache мог оставаться тёплым. Нет процесса IPC, модели, сети, UI или полного агентного хода. Хост разделялся с другими задачами.

После одной незачтённой пары 8 учтённых пар, порядок AB/BA меняется, CPU affinity 5. Для «сравнение» каждая пара использует медиану трёх сравнений на одном снимке; «открытие + первое» складывает стоимость одного нового холодного открытия и его первого сравнения (подготовка/append вне таймера). Время до/после: медианы по 8 процессам; Δ: медиана парных отношений.

| Backend / старых записей | Compare до → после | Холодное открытие + первый Compare | Парная Δ второго |
|---|---:|---:|---:|
| JSONL / 128 | 2,993 → 0,115 мс | 9,089 → 2,124 мс | −57,6%, 8/8 |
| JSONL / 512 | 41,005 → 0,498 мс | 79,026 → 33,294 мс | −55,4%, 8/8 |
| SQLite / 128 | 1,993 мс → 0,852 мкс | 8,240 → 2,365 мс | −56,3%, 8/8 |
| SQLite / 512 | 35,592 мс → 1,452 мкс | 72,322 → 34,174 мс | −48,4%, 8/8 |

При 512 старых записях новое холодное открытие **по-прежнему декодирует 513 записей** в обоих вариантах и обеих БД. Сверка отдельно: JSONL 1 026 → 0 декодирований (но после патча всё ещё SHA по всем 712 453 байтам); SQLite 513 → 0. Счётчик `dedicated_verify_bytes` в CSV учитывает отдельную проверку; ноль у baseline **не** означает отсутствие чтения/хеширования во время декодирования. Не переносить снижение времени сверки на полное закрытие хода; неизвестные границы и сессии с JSONL-блобами не имеют этого быстрого пути.

[Сырые пары](results/samples.csv) · [сводка, включая пустую границу](results/summary.csv) · [probe](probe.rs). Обычные unit-тесты обеих версий и process recovery прошли: baseline 29+2, кандидат 33+2; два ignored замера в unit suite, один из них вызван явно. Guard'ы включают восстановление/потерю ACK, отклонение подмены старого содержимого и нового хвоста, отсутствие/порчу внешнего blob, различие двух счётчиков, неверный SHA, тёплый или неизвестный prefix. Полный Modules workspace не запускался.

Воспроизведение на Linux с Rust/Cargo и pinned dependencies: `bash reproduce.sh /path/to/Proteus-modules /new/output --cpu N`; CPU выбирается из доступных на этой машине.
