# A/B: один Storage worker, тот же Core

Один и тот же Core `8ea2cdaf` (устойчивый фокусный release-стенд из #219), два paired сборочных артефакта Modules `37b3d9c4`. Меняется только worker (см. [шаблон патча и отдельные контроли](../storage-worker/README.md)). Работает действующая полная проекция Core, не сокращённый алгоритм рендеринга; модель и окно не запускаются. Синтетический журнал: одна строка ~720 байт на старую запись, после подготовки и зафиксированного префикса добавляется одна короткая строка. Сделаны AB и BA на одном ядре CPU (Core и его дочерний процесс); 5 измерений на размер в каждой фазе, сравнение числа и текста строк обязательно.

| Старых записей | Медианы штатного worker в двух фазах | Медианы worker-кандидата |
|---:|---:|---:|
| 0 | 7,17 / 7,30 мс | 6,39 / 5,78 мс |
| 128 | 59,53 / 63,11 мс | 30,69 / 27,52 мс |
| 512 | 282,14 / 296,82 мс | 146,44 / 123,45 мс |
| 2 048 | 2 361,90 / 2 211,55 мс | 825,30 / 808,98 мс |

Итого в этой нагрузке подгрузка проекции при 2 048 старых записях примерно в 2,7–2,9 раза быстрее только за счёт worker. Это не полный пользовательский ход, не сценарий больших вынесенных в blobs записей и не универсальный выигрыш. На inline JSONL старые байты всё равно проверяются хешем. При отсутствии известной границы или наличии отдельных blob порядок полной проверки сохраняется. Оба worker запускались отдельно через настоящий транспорт SDK Core; все четыре выбранных теста прошли.

Сырые серии: [stock 1](storage-base-1.log), [candidate 1](storage-candidate-1.log), [candidate 2](storage-candidate-2.log), [stock 2](storage-base-2.log). Описание и исходники того же setup: [тест Core](probe.rs), [измерительный патч](instrumentation.patch), [скрипт воспроизведения](reproduce.sh). Для ручного AB/BA указывайте соответствующие полные пути в `PROTEUS_TEST_SESSION_STORAGE_MODULE`; `PROTEUS_TEST_REFERENCE_MODULE` и Core не менять. Paired Modules worker собраны тем же Rust 1.95 release-профилем, с одинаковыми зависимостями, включая bundled SQLite.
