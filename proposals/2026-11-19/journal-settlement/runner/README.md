# Why the pinned AgentControl runner is not a warm-turn baseline
Core 8ea2cdaf4195ae24e941354f68d4e97335d139d7; Modules 37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979. No production changes or publication.

- The unchanged examples/performance/history-scale/fixtures.py:profile selects workflow, context and policy but does not select or export session storage. app_server/http.rs:87–90 now requires one before binding. Supplying PROTEUS_TEST_SESSION_STORAGE_MODULE configures the example seeder only; it does not fix the generated peer configs. Compacted --mode agent-control runs the cold HTTP preflight before starting a measured round.
- core/agent_control/process/child.rs:47–56 launches --config CONFIG --cwd CWD --new-session --parent-session-id UUID server stdio. The runner launcher accepts exactly the old 7-argument form, rejecting the current 9-argument argv (executed Python check). Its own passing unit checks use the obsolete 7-argument fixture.
- Merely allowing the new argv and replacing fresh child creation by a prepopulated resume does not reproduce AgentControl's startup contract. child.rs:182,305 waits for and binds exclusively a durable Runtime/SessionStarted event. app_server/stdio/session.rs:14–35 and core/runtime/builder.rs:284–286 deliberately don't re-emit that event for populated resumed sessions. Receiving a session_snapshot alone doesn't satisfy the parent. Passing through --parent-session-id to a resumed child is not an alternative: main.rs:106 explicitly requires --new-session server stdio, and stdio.rs:36 rejects resume plus parent id.
- Once a storage component is configured, the original memory/CPU subject classifier still counts only the reference module and Core. The storage child falls into controller. This does not change wall latency but would underreport subject memory/CPU/IO.
