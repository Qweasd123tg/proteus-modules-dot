# Proteus: что на самом деле тормозит закрытие длинного хода

Продолжение [#219](https://github.com/Qweasd123tg/proteus-modules-dot/pull/219). Здесь кандидаты для переноса и сырые измерения, без установки или изменений в основных репозиториях. Запускался настоящий Core + storage, но без Desktop GUI.

- [Полный ход с одинаковым запросом к модели](real-turn/README.md). Те же 101 сообщение в запросе, архив от 100 до 50 000 строк. Закрытие первого хода выросло с ~50 мс до 1,08–1,39 с при 5 000, в одном 50 000-строчном прогоне до 23,18 с. Из логов видны пять проходов Core с начала. Это исходный уровень одного синтетического стенда, не прогноз для любой сессии.
- [Убрать повторный семантический replay в Storage, если точная граница уже проверена](storage-paired/README.md). На прежней компонентной нагрузке #219 с тем же Core кандидат в worker сократил подготовку истории на 2 048 старых inline-записях с 2,21–2,36 до 0,81–0,83 с. Хеш данных проверяется, обработка неизвестной границы и вынесенных payload не упрощена. Это независимый от Core-кандидатов выигрыш.
- [Независимые проверки целостности](controls/README.md) на обоих worker: повреждённый blob, изменения без изменения длины, логический compaction, реальный конкурентный writer и restart, проверки неизменного старого snapshot и нового snapshot.

- [Core: первое закрытие и четыре повторных доказательства префикса](display/README.md). Два кандидата передают курсор из того же валидированного чтения, а также используют уже пройденную в строгой проверке часть, не сканируя её повторно для identity-ключей. Доказательство совместимости хранится только для открытого snapshot. На полном ходе с неизменённым worker, 2 000 строк: 440–471 → 161–195 мс в двух AB/BA сериях; в 5 000 строк число переданных записей 285 → 87. Одно сравнение на 50 000: 23,18 → 11,54 с, ещё слишком долго. 57/57 фокусных тестов; перепроверка старого источника остаётся обязательной.
- [Shared journal validator: не пересобирать множества ID на каждой одиночной строке](active-ids/README.md). 2 048 одночастных синтетических append в парном strict fold: медианы 255 → 10 мс; не общая задержка хода. Быстрый путь использует ранее доказанную уникальность и без дополнительного индекса проверяет только новые ID; все остальные варианты идут через старую проверку.
- [Профиль работы файлового кеша](cache-eviction/README.md). Спровоцированная нагрузка на тысячи cache-файлов подтверждена, но в проверенном реальном ходе эвикция заняла менее 1 мс даже при 5 000 строках. Микропатч не считать исправлением основной задержки. Более важный отдельный диагностический эффект Core: из старых файлов кеша при 5 000 строк прочитано 1 795 000 → 17 752 байт. Это не полный I/O.
- [Штатный history-scale runner](runner/README.md) проверен на совместимость с этим pin; для расчётов выше использован другой реальный AppServer стенд, а не выдуманные данные runner.
