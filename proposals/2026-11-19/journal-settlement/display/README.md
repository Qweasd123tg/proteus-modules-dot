# Одно доказательство старого журнала и курсор при первом закрытии

Два **раздельных** патча поверх Core `8ea2cdaf4195ae24e941354f68d4e97335d139d7`, применять по порядку: [объединение проверок](display.patch), [точный курсор при публикации](cursor.patch).

1. При доказанном совпадении префикса Core уже читает все его записи для обязательной валидации. Пока они открыты, тот же проход собирает старые identity-ключи для проверки независимости новых событий. Этапы рендеринга запрашивают только суффикс по тому же фиксированному snapshot, не начинают новый CompareSnapshots перед каждой фазой. Закрытые/подтверждённые данные остаются привязаны к точному snapshot; каждый ReadRecords сверяет идентичность, позиции, полное продвижение и ошибки.
2. Старт, холодное восстановление и фоновое обновление теперь публикуют append cursor из **того же** валидированного чтения, из которого взяты display rows. Штатный полный путь создавал правильные rows, но сохранял header без cursor, поэтому первый ход после холодного start не мог даже запросить инкрементальную проекцию. Устаревшее чтение не запишется под более новой ревизией.

Иллюстрация с настоящими выбранными production-модулями, контролируемое backend-хранилище: 130 записей известного префикса + один дописанный факт. В кандидате один CompareSnapshots, ReadRecords с after `[0,64,128,130,130,130,130,130]`; старый дизайн имеет два полных прохода и повторяет CompareSnapshots в четырёх фазах отображения. Сам storage ещё может прочитать старые данные, чтобы найти позицию суффикса, и обязан проверять его бэкенд-инварианты. Не обещать число прочитанных дисковых байтов на основе числа DTO. В выбранном наборе 57/57 тестов, включая старые регрессии и отрицательные сценарии: неподтверждённая граница, ошибка чтения, rediscovery tool, старое чтение и свежая ревизия, отсутствующая страница. [Лог](native-tests.log).

Это не "отключение строгой проверки" и не сохранение копии истории между ходами. Replace/compaction, затронутые старые identity/citation, невозможность безопасной публикации или плохой кеш оставляют штатную полную проекцию; ошибку чтения нельзя маскировать как cache miss. Не приписывать этому патчу выигрыш отдельного Modules worker без A/B. Полный upstream CI не запускался.

## A/B через полный ход с fake-моделью

Тот же AppServer и вход, что в [реальном диагностическом ходе](../real-turn/README.md), тот же неизменённый штатный release worker. Меняются только оба production-патча Core. Парные серии AB/BA по одному запуску на размер в каждой фазе, отдельное CPU ядро; Core обеих версий opt-level=1, зависимые crates release. Не считать диапазоны статистическим интервалом.

| Архив | Штатная подготовка истории, фаза 1 / 2 | Два Core-патча, фаза 1 / 2 | Передано записей в Core за закрытие |
|---:|---:|---:|---:|
| 100 сообщений | 35,7 / 45,1 мс | 31,5 / 34,4 мс | 35 → 37 |
| 2 000 сообщений | 440,3 / 471,3 мс | 161,3 / 195,3 мс | 135 → 57 |
| 5 000 сообщений | 972,1 / 896,0 мс | 893,3 / 641,4 мс | 285 → 87 |

В 2k и 5k штатный путь пять раз возвращает весь журнал. После патча Core один раз читает всё для обязательной проверки, затем пять раз получает только шесть новых записей: один раз для proof и четыре раза для преобразования в UI. На маленьком журнале «меньше вызовов» не заявлено, даже переданных записей на две больше. История на каждом размере сохранила исходные байты префикса и требуемое количество видимых строк; запрос к fake-модели содержал те же 101 сообщение. Не переносить linearly в 50k, не считать GUI или провайдер. Сырые [A1](display-first-1.log), [B1](display-candidate-1.log), [B2](display-candidate-2.log), [A2](display-first-2.log).

### Совместимость двух слоёв

В отдельной серии 2×2 на том же входе обе версии worker работали с обеими версиями Core. На 5 000 строк четыре измерения соответственно: 1 105 мс (stock/stock), 973 мс (Core/cтарый worker), 923 мс (старый Core/новый worker), 518 мс (оба кандидата). Каждый вариант прошёл checked full turn. Это по одному запуску, не устойчивая оценка комбинированного выигрыша. На небольшом вводе одно измерение медленнее остальных, не выдаём его за регрессию без повтора. [Stock/stock](combined-stock-stock.log), [Core/stock](combined-candidate-stock.log), [stock/worker](combined-stock-candidate.log), [Core/worker](combined-candidate-candidate.log).

На 50 000 строк один штатный и один проверенный кандидатный ход: 23,18 → 11,54 с в подготовке истории, 2 535 → 537 журнал-записей передано в Core. Это разовая, непарная по порядку проверка масштабирования, не оценка типичной задержки. [Stock](../real-turn/repeat.log), [кандидат](display-50k-candidate.log).
