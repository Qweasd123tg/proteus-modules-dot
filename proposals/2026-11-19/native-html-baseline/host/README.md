# Финальный вариант: ленивая фоновая копия только для штатного RichText

На 32 коротких сообщениях **время до завершения работы тестового GPUI хоста снизилось с 1,60 до 0,95 мс**; повтор на другом ядре: **2,30 → 1,01 мс**. После простоя при 32 живых состояниях дополнительный занятый Rust heap составил **1 492 160 → 839 272 Б** (−44%). Это **не** замер первого кадра или RSS. Независимым пользователям `TextViewState::html` не приходится оплачивать отложенный разбор в первом `push_str`: проверено реальное исполнение этой ветви, а не только равенство результата.

**Что сравнивалось.** Исходная [GPUI-база Desktop](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L530-L594) против [финального патча](../candidate/defer-rich-text-only.patch), SHA-256 `a5bd0504829a4f3716c81928ca54a8fa1d48a26145c17807434926bbe9f1d6e6`. Из фактического `RichText::new` в каждой копии взято и скомпилировано **точное выражение создания состояния**: в исходной версии это `TextViewState::html(html, cx).scrollable(false)`, в предлагаемой версии `TextViewState::html_for_replacements(html, cx).scrollable(false)`. Отдельная сборка для независимого потребителя напрямую вызывает прежний public `html`. Настоящий GPUI Fast TestAppContext создаёт entity и выполняет реальную очередь, фоновые задачи, HTML/parser и фиксацию результатов. От оболочки RichText заимствовано выражение конструктора, а не сама оконная оболочка: здесь не измерялись layout, paint, renderer-процесс или видимый текст на экране.

### Две стороны изменения проверены отдельно

* На **public default** все 24 сценария / 96 промежуточных наблюдений совпали с исходником **целиком**, включая число и объём синхронных и фоновых парсерных вызовов, срабатывания пользовательских HTML-хуков, readiness, ошибки, ревизии, committed source, представление AST, читаемый текст и select-all/copy. Результат четырёх отдельных бинарников, в том числе криптографические отпечатки полных журналов, в [proof.json](proof.json). Это не утверждение о равенстве абсолютного времени выполнения для любого потребителя.
* На **scoped RichText** те же 24/96 наблюдений совпали по семантике. На девяти из десяти HTML от настоящего расширения (54–4096 Б) фактические числа разборов изменились с 1 sync + 1 worker на 1 + 0. На 4097 Б остаётся 0 + 1. Заведомо неизменённые строки, 65 быстрых замен, вытеснение крупной/малой версии, настоящий custom HTML-hook, смена конфигурации, явный append, Markdown и некомпонуемые HTML-фрагменты также прошли сравнение.
* Отдельный контртест: после простоя базы-таблицы 4096 Б явно был добавлен хвост 11 Б. **Public default до и после патча**: worker уже разобрал 4096 Б до append; после append — ровно один вызов на новых 11 Б. **Scoped RichText**, только при намеренном `push_str` вместо штатного `set_text`: до append 0, после append 2 вызова на 4096+11 Б. У всех одинаковый итоговый AST. То же проверено на HTML 200 Б; на 4097 Б даже scoped-ветка остаётся на старом пути. Выбор нового конструктора осознанно оставляет эту цену за нестандартным использованием.

### 32 сообщения: работа всего хоста до idle и память

| Входной HTML | Парсер: sync + worker на всю партию, до → после | До idle, CPU 4, мс | До idle, CPU 7, мс | Дополнительные живые байты в idle, до → после |
|---|---|---:|---:|---:|
| Типичный: по кругу 5 форм (54, 152, 114, 200, 239 Б) | 32+32 → 32+0 | 1,60 → 0,95 | 2,30 → 1,01 | 1 492 160 → 839 272 |
| Богатый: таблицы/ссылки ровно 4096 Б | 32+32 → 32+0 | 17,55 → 10,90 | 12,42 → 5,84 | 7 541 576 → 4 053 448 |
| Простой 4097 Б, отрицательный контроль | 0+32 → 0+32 | 0,87 → 0,82 | 0,83 → 0,76 | 1 325 416 → 1 325 416 |

На CPU 4 целиком синхронная фаза типичной партии заняла 0,794 → 0,826 мс, богатой — 9,10 → 10,55 мс. Она не содержит второй проход, и её ускорение не обещается. Малую разницу в контроле 4097 Б не приписываем патчу: число разборов и учтённые объёмы heap идентичны. Абсолютные времена разных строк также не сравнимы по одному размеру: у таблиц сложнее DOM, чем у простого текста.

[Первый прогон](timing.json) и [повтор](repeat.json): 6 независимых пар процессов AB/BA, 1 прогревочная и 16 измеренных партий на процесс; медианы внутрипроцессных медиан; один CPU на серию, общая машина. Время с создания первой самостоятельной entity до возврата GPUI `run_until_parked` после создания всех 32. Отдельно записаны возврат первой/последней синхронной операции. В обеих timing-версиях стоят два relaxed atomic add на входе в **реально вызванный** парсер (счёт и байты); эти метки также пропускаются, когда исчезает вызов. Пользовательских измерителей аллокаций в timing-процессах нет. Отдельная серия с GlobalAlloc измерила трафик: для типичной партии суммарно запрошено 4 176 482 → 2 529 566 Б, 12 274 → 7 414 вызовов alloc/realloc. Не суммировать трафик с живыми байтами.

[Живой heap](live-results.json): отдельный release executable, 4 свежие пары AB/BA; системный Rust allocator обёрнут с учётом alloc, alloc_zeroed, realloc старого размера в новый и dealloc на всём протяжении жизни процесса. Прирост относительно прогретой базы до создания второй партии; все 32 состояния удерживаются. На типичной партии сразу после синхронного создания живые байты **одинаковы**, +993 384 на обеих сторонах; после idle различаются. Максимальный прирост логически живых запросов — 1 492 926 → 1 008 792 Б. Не включены служебные страницы аллокатора, прямые C-выделения, Core и GPU. После освобождения состояний и контейнера обе версии вернулись к одинаковой дельте −1024 Б (в базе уже был буфер вектора handle-ов).

### Как повторить

Linux, Rust 1.95; нужны публичный Desktop на `210cc9f274ffe40533b390a0d9e940f251a9fa22`, Cargo, Python и `patch`. [Исходный корпус](cases.jsonl) содержит source и выданный расширением HTML. Отдельные копии и Cargo target разделены; инструмент сверяет Git blobs, SHA патча и производственное выражение конструктора, затем проверяет срабатывание ветви по фактическим вызовам. Выберите доступный CPU, каталог результатов должен быть новым:

```sh
CPU=4 bash reproduce.sh "$PINNED_PROTEUS_DESKTOP" "$NEW_WORK"
```
