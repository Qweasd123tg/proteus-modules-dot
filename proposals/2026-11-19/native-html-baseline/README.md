# Короткий HTML в Desktop: второй документ можно не строить заранее

**Предложение:** включать [ленивую фоновую базу](candidate/defer-rich-text-only.patch) только для карточек, заменяющих HTML целиком. После короткой успешной замены GPUI уже имеет документ, готовый для первого макета. Раньше фоновый обработчик строил такое же дерево и держал его только на случай будущего дописывания. Патч оставляет у обработчика короткий исходник (не более 4 096 байт) и настройки для восстановления собственного дерева, если дописывание действительно понадобится. Первое дерево не разделяется с обработчиком. Общего кеша нет. Только retained RichText выбирает новый конструктор `html_for_replacements`. Обычные публичные `html` и `markdown` остаются на прежнем алгоритме: у них фон заранее готовит дерево перед `push_str`.

**Пока не переносить в upstream без проверки на целевой машине:** на отдельном контроле восемь длинных однородных HTML обработались медленнее на 6–9% по медианам пар; четыре длинных HTML реального Markdown-расширения не показали устойчивой разницы. Ни время первого кадра, ни RSS приложения не измерены. [Отрицательные контроли и цена дописывания](controls/README.md).

Это **следующая стадия после #217**: не разбор Markdown в расширении и не два этапа нормализации одного HTML-документа. Здесь повторялся весь вызов нативного HTML-парсера для синхронного показа и затем фоновой базы. Порог относится к **байтам готового HTML**, не к длине текста чата.

## На что это влияет

Настоящие Rust `gpui-base::TextViewState`, dispatcher и очередь GPUI в официальном тестовом окружении. 32 независимых состояния, удерживаются до окончания фоновой работы. Небольшие сообщения включают обычный/экранированный текст, ссылку и таблицу; HTML предварительно получен от поставляемого release-расширения. Время до простоя, не время до кадра. Живая память — сумма **запрошенных Rust-аллокатору и ещё не освобождённых байтов сверх исходного состояния**; не RSS/PSS всего Desktop. [Стенд, строки и сырые серии](host/README.md).

| При 32 новых состояниях | Вызовы нативного HTML-парсера, UI + worker | Время до простоя | Живой heap после простоя |
|---|---|---|---|
| Короткие сообщения, 54–239 Б | 32 + 32 → 32 + 0 | 1,60 → 0,95 мс; повтор 2,30 → 1,01 мс | 1 492 160 → 839 272 Б (−0,62 МиБ) |
| Ссылки и таблицы, ровно 4 096 Б | 32 + 32 → 32 + 0 | 17,55 → 10,90 мс; повтор 12,42 → 5,85 мс | 7 541 576 → 4 053 448 Б (−3,33 МиБ) |
| Обычный HTML, 4 097 Б | 0 + 32 → 0 + 32 | 0,87 → 0,82 мс в этой серии; [отдельный контроль](controls/README.md) | 1 325 416 → 1 325 416 Б |

В четырёх A/B-парах сразу **после синхронной части** живой heap обеих версий для каждого сценария одинаков до байта. Разница возникает, когда прежняя версия создаёт вторые деревья. На настоящем Desktop число открытых/загруженных карточек и их разметка зависят от пользователя. Не умножать эти величины на размер истории.

## Первое отображение, смена версий и обратная сторона

- В [реальном макетном и paint-коде GPUI](layout/README.md) проверены **8 состояний тестового окна**. Заголовок, ссылка и абзацы дали высоту 100,5 и положение следующего элемента 100,5 ещё до простоя в обеих версиях; после замены таблицей обе величины стали 79. Совпали содержимое для копирования, сброс выделения, число подложек и подчёркиваний. Это тестовый текстовый backend, без системных шрифтов и оконного композитора. Пиксели и время кадра рабочего приложения не измерялись.
- Изменений очереди не маскируем: после 65 быстрых замен исходный обработчик сделал **два**, а не 65 фоновых разборов. Перезаписанная и ещё не обработанная версия может вообще не стать отдельной задачей. На длинном потоке из #217, где подтверждалась каждая из 64 редакций, только первые **4** принятых HTML подходили под порог. При передаче группами по восемь не подходил ни один. [Проверка по хешам принятых деревьев](coverage/README.md).
- Штатный [RichText поставляемого Desktop](callers/README.md) использует полную замену, не вызывает HTML `push_str`, а одинаковый HTML пропускает. До входа в такой виджет могут вмешаться виртуализация и отбор актуальной ревизии. У независимых пользователей библиотеки публичное дописывание есть. На первом отдельном `push_str` **явно выбравший новый режим** объект **откладывает работу до дописывания**, а не убирает её за всю жизнь документа. [Прямой контроль задержки](controls/README.md). Ждать улучшения именно этого вызова нельзя.
- Пример, почему это нельзя заменить склейкой строк: база `<b>red`, затем отдельная дельта `plain`. Правильный раздельный разбор оставляет жирным только `red`; единый разбор склеенной строки делает жирным и `plain`. Ещё одна ловушка: даже копирование вектора разобранных блоков разделяет изменяемое выделение параграфа. Оба контрпримера проверены на Rust. [Владение и семантика](ownership/README.md).
- Только успешный встроенный HTML без пользовательского HTML-парсера в opt-in виджете может перейти на ленивый путь. Ошибка, смена конфигурации, Markdown, большие документы и активные parser hooks не пропускают нужный разбор. По 24 сценариям совпали **96 наблюдений** как для opt-in карточек, так и для прежнего публичного конструктора: ревизии, готовность, текст, выделение и copy, ошибка, число вызовов hooks. Отдельно доказано освобождение старого дерева при замене 120 000 Б на 9 Б. [Исходники кандидата](candidate/README.md), [проверки поведения](focused/README.md).

**Граница решения:** не меняем порог и не кэшируем AST между UI и worker. В отдельном измерении при одних и тех же 4 096 Б второй проход только до DOM стоил 16 мкс CPU для простого текста и 154 мкс для таблицы. [Данные стадии DOM](dom-cost/README.md). Вне поставляемого replace-only сценария оцените задержку первого явного append и цену небольшого дополнительного состояния у worker.
