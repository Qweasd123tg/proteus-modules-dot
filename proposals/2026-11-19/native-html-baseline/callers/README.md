# Какие обновления действительно получает HTML-виджет

**Вывод:** на закреплённом пути сообщения Desktop заменяет HTML целиком; видимый первый разбор нужен, а фоновое дерево той же короткой строки ему не понадобится. Публичный API GPUI всё же разрешает отдельные HTML-append. Поэтому ни безусловно удалить BaselineAck во всей библиотеке, ни заменить первый поздний append совместным полным разбором двух строк нельзя. Проверял исходники и реальные ответы процесса расширения. Окно, момент paint, число принятых ревизий и экономию в миллисекундах эти наблюдения не измеряют.

## Откуда приходит HTML

1. Штатное расширение [компилирует GFM и возвращает rich_text](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/a35cea08be83ee8e5ecbfce9ef5050a1c00eb247/packages/markdown-render/src/inlines.rs#L217-L221). Это свойство ответа, не вызов виджета.
2. [Входящий View](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/runtime.rs#L511-L549) передаётся в show_with_revision после проверок; [принятый root готовится](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/view.rs#L294-L313). [Ветка Node::RichText](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/fields.rs#L266-L283) вызывает prepare_rich_text. Отброшенный/неподготовленный root нельзя автоматически прибавлять к числу разборов.
3. [RichText](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/rich_text.rs#L16-L52) владеет закрытым Entity. Новый id создаёт TextViewState::html; [сохранённый id извлекается из HashMap](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/rich_text.rs#L79-L101). Равный HTML не вызывает set_text; изменившийся передаётся полностью. В production Desktop src и внутренних crates не найдено другого прямого владельца TextViewState. Переданная в Slots::sync сущность используется для инвалидации layout, а не push_str.
4. [TextView::new(&state)](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/text_view.rs#L201-L223) не содержит нового текста. [При render](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/text_view.rs#L755-L775) он может обновить конфигурацию; set_element_text вызывается только при Some(text). Публичные TextView::markdown/html со строкой работают через эту отдельную ветвь; компонент GPUI для [подсказок использует Markdown](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-component/src/input/popovers/mod.rs#L20-L31).
5. В [set_text/push_str](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L334-L385) только непустое успешное **Markdown**-состояние может преобразовать новую строку с общим префиксом в append. HTML всегда заменяется, если вызывают set_text. Однако публичный [тест HTML push_str после освобождения очереди](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L1996-L2019) требует сохранения старых блоков.

**Нативный свидетель.** Оригинальный release ELF на пяти полностью синтетических ревизиях одного view вернул один и тот же id `prose-0`. Размеры HTML: **17, 17, 30, 89, 28 Б**; число inline-слотов: **0, 0, 0, 1, 0**; первый и второй HTML побайтно равны. В четвёртом `<span data-content="inline-0">…</span>` возникает из inline math. [Данные и хеш stdout](results.json). Это наблюдение о выводе расширения, не утверждение, что все пять кадров успели смонтироваться.

Важная граница: [Slots::sync](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/inline_content.rs#L35-L45) ничего не создаёт для изначально пустого набора. При изменении слотов [регистрация html_inline безусловна](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/inline_content.rs#L94-L114), даже когда удаляют последний слот. Для последующего изменения eligibility определяется **фактической конфигурацией парсера** у конкретного состояния, а не правилом «в этом JSON нет inlines». Изменившиеся parser hooks могут сами вызвать отдельную замену/разбор; это не дубликат BaselineAck.

## Возможные количества, не профилирование

Пусть N≥1 разных коротких (HTML ≤4 096 UTF-8 байт) полных **уже подготовленных** замен у одного живого retained state; ни одной другой команды, ошибок или custom HTML parser hooks; worker в конце освобождает очередь. UI синхронно читает N HTML и готовит первые кадры. В stock [worker](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L1266-L1350) берёт до 64 запросов за группу, последняя полная замена вытесняет предыдущие. Поэтому **ceil(N/64)…N** фоновых парсов, а не фиксированно N. Для отложенной базы HTML — ноль фоновых разборов в этой закрытой последовательности. Например: один статичный текст **2→1** разбора суммарно; 16 замен **17…32→16**; 64 замены **65…128→64**; 65 замен **67…130→65**. Драйвер дополнительно проверяет границы перебором допустимых последних групп для N до 130. Это количество разборов, не время, и не статистика пользовательских чатов.

| Сценарий | Что действительно может измениться |
|---|---|
| Тот же HTML при том же состоянии и конфигурации | Нет новой задачи; ничего не ускоряется. |
| Большая замена (>4 096 Б) | Один обычный background replace, а не маленький синхронный baseline. |
| Маленькая и большая замены в одной группе | Маленький worker-запрос уже мог быть вытеснен; экономия может быть нулевой. При уничтожении state не гарантируется завершение pending worker вообще. |
| Маленький HTML без hooks; отдельный append **после** парковки | Чтобы сохранить stock, worker в этой операции должен разобрать сохранённый короткий baseline, затем отдельно дельту. Суммарно за всю историю число разборов не изменится, а этот конкретный append может замедлиться. |
| Baseline + append уже объединены старым merge | Это `!append + Compatible`, а не BaselineAck. Оставить один обычный полный разбор, старые selection-compatible/full-parse флаги. |
| Markdown, неуспешный sync parse, зарегистрированные HTML parser hooks | Не откладывать существующий BaselineAck. Пользовательский callback не обязан сохранять отсутствие побочных эффектов. |

## Независимый выбор конструкции

Из рассмотренных вариантов достаточно сохранить только сырой UpdateOptions на worker после успешного короткого HTML без hooks, арбитража merge и проверки режима. Для отдельного первого append разворачивать baseline перед штатным отдельным разбором дельты; при новом полном replace пропускать его построение. Простой enum с взаимоисключающимися Parsed / Deferred не удерживает старое большое дерево вместе с отложенной строкой. Всегда проходить прежний yield-budget. Штатная проверка устаревших ревизий остаётся на получателе. Патч соседнего исполнителя реализует именно это, отдельный дублирующий diff здесь не нужен.

Почему не проще: (1) передать «clone готового AST» не эквивалентно передаче неизменяемого снимка; (2) заново разобрать **склеенный** HTML при первом позднем append меняет структуру. Например, для двух отдельно разобранных фрагментов `<p><b>old` и `new</b></p>` второй текст без bold; в одном документе «oldnew» целиком bold. [HTML блоки не содержат spans](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L1360-L1395), теги [b/strong дают bold](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/format/html.rs#L494-L502). (3) Добавление специального публичного «никогда не append» конструктора потребовало бы отдельно определить push_str для возвращаемого того же типа, не давая выигрыша для штатного пути сверх ограниченной ленивой базы.

Воспроизведение: `python3 callers.py PATH_TO_DESKTOP PATH_TO_EXTENSIONS PATH_TO_RELEASE_MARKDOWN_RENDER`. Скрипт сверяет Git blob-идентичности файлов с [pins.json](pins.json), проверяет реальные source-level ветви и вызывает локальный release-бинарник, собранный через `cargo build --release --locked -p extension-markdown-render`. Это не запуск GPUI TestAppContext и не измерение FPS/памяти.
