# Цена одного повторного построения HTML DOM для короткого сообщения

**Вывод.** Убирать лишний фоновый проход имеет смысл, если widget действительно получил отдельный baseline и он не понадобился для append. Не менять порог синхронного первого layout по этим измерениям. Байт недостаточно для предсказания цены: при тех же 4 096 Б текст, 15 ссылок и таблица из 25 строк дали соответственно ~10–16, ~85–93 и ~154–167 мкс дополнительной работы DOM-стадии в двух прогонах. Для короткого «Готово.» речь идёт лишь о ~4 мкс. Нет результата о том, на сколько ускорится кадр, всё сообщение или весь Desktop.

**Что проверено.** 10 управляемых сообщений реально пропущены через протокол расширения [markdown-render](https://github.com/Proteus-harness/Proteus-desktop-extensions/tree/a35cea08be83ee8e5ecbfce9ef5050a1c00eb247/packages/markdown-render). В [cases.jsonl](cases.jsonl) сохранены исходный текст, язык и **точный HTML виджета**; 4 095/4 096/4 097 относятся к *выходу* в UTF-8, а не длине Markdown или числу символов. Пакет содержит ссылки с entity в параметрах, Unicode, заголовки, strong/code/em, таблицы, переводы строк и plain text с экранированием. Образец `md-selection` пригоден для теста выделения, но этот стенд не проверяет жест/буфер обмена. Частоту подобных сообщений у пользователей мы не оценивали.

В двух release-сборках Rust 1.95.0 под Linux x86_64/AMD EPYC 9V74 [подготовка](prepare.py) проверяет Git blob SHA и извлекает неизменённые [cleanup_html и построение RcDom](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/format/html.rs#L95-L132), включая настоящий [HTML5ever minifier](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/format/html5minify/mod.rs#L180-L190). Один проход в таблице — весь этот путь, который внутренне дважды вызывает HTML5ever (исходник → нормализованный HTML → DOM). Сравнение 1×/2× вызывает ту же функцию с теми же байтами и освобождает временный DOM каждого прохода. Это **граница до** построения GPUI BlockNode, планировщика, рендера, layout и paint. Здесь нет подмены их измерений.

На одном закреплённом CPU, по 32 разогрева и 14 чередующихся пар на случай; время одного образца усреднено по пакету. Основной повтор использует CLOCK_THREAD_CPUTIME_ID, отдельно записывает wall clock; у второго прохода больше CPU во всех 14 парах для каждого входа. Глобальный аллокатор измерен в отдельной сборке без включения в таймер. Ниже парная медиана дополнительного CPU для `2× − 1×`, а не latency UI.

| Вход настоящего рендерера | HTML, Б | Доп. CPU, мкс | Доп. alloc/realloc | Доп. запрошено, Б |
|---|---:|---:|---:|---:|
| «Готово.» | 54 | 3,63 | 51 | 20 438 |
| Экранированные `<`, `&&`, `>`, кавычки | 114 | 9,38 | 68 | 21 690 |
| URL c query и entity | 152 | 8,60 | 82 | 22 968 |
| Markdown: heading, ссылка, стили, текст для выделения | 200 | 15,55 | 137 | 27 232 |
| Небольшая Markdown-таблица | 239 | 21,86 | 189 | 31 982 |
| Plain рядом с порогом | 4 095 | 9,55 | 53 | 32 705 |
| Plain на пороге | 4 096 | 16,25 | 53 | 32 708 |
| 15 Markdown-ссылок на пороге | 4 096 | 93,09 | 625 | 72 757 |
| Таблица из 25 строк, 24 ссылки | 4 096 | 153,97 | 1 299 | 125 821 |
| Plain выше порога (только искусственный контроль) | 4 097 | 9,79 | 57 | 40 999 |

Запрошено — сумма размеров allocation/reallocation, не расход ОЗУ. При двух последовательных проходах число запросов и сумма размеров ровно удваиваются, но дополнительная живая запрошенная память от временных DOM после возврата равна нулю; максимумы каждого отдельного прохода не складываются. Например, у таблицы 4 096 Б peak запрошенных живых байтов **53 301** при 1× и **53 301** при 2×. Ни память удерживаемого GPUI AST, ни RSS здесь не измерены.

[Исходный worker](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L1266-L1307) сначала объединяет запросы. Нельзя зачислять «минус один parse» каждой поступившей версии: объединённый replace+append может всё равно требовать parse, отложенный append может впоследствии затребовать базу, а текущий [порог full replace](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L539-L590) уже исключает второй проход на 4 097 Б. Не терять первого синхронного результата и не обобщать на custom HTML parser hooks либо Markdown с другими правилами.

**Воспроизведение:**

1. `python3 fixtures.py /path/to/markdown-render /tmp/cases.jsonl`; сравнить с сохранённым `cases.jsonl` (SHA256 `7bd0aa8b884654e9d39b8a9df03c02985bd5b1a63eb7491924df7c669ba5e843`). Отправляется по одному живому hello/render на fixture, без файлового ввода пользователя. Исходный ELF SHA256: `e6a4c907941b4032cd519df6d5c467cdec920367676c9860aa0fe644a5e67014`.
2. `python3 reproduce.py /path/to/Proteus-desktop /tmp/cost-results --cpu N` на Linux с Rust/Cargo 1.95.0. Опционально `--offline` при наличии зафиксированных crates. Продуктовый checkout не меняется.
3. [Сырые CPU/wall пары](clock-results/timing.jsonl), [аллокатор](clock-results/heap.jsonl), [сводка](clock-results/summary.json). Предварительный независимый [wall-only прогон](results/summary.json) оставлен для проверки разброса, с [исходными парами](results/timing.jsonl). Величины на другой машине не обязаны совпасть. Граница и паритет реального TextViewState проверяются другим стендом, а не этим опытом.
