# Проверка владения AST в GPUI

Пин Desktop: `210cc9f274ffe40533b390a0d9e940f251a9fa22`. **Между двумя виджетами нельзя делить готовое дерево по совпадению строки.** У конкретного экземпляра TextView можно повторно использовать исходную строку и конфигурацию парсера. Безопаснее всего не отдавать в worker уже нарисованные узлы и не платить за отдельную его базу до реального append.

* [ParsedDocument](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/document.rs#L15-L20) хранит исходник и `Arc<Vec<BlockNode>>`. Клон документа разделяет весь вектор. Явный клон вектора тоже не отделяет все runtime-поля: [InlineNode](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/node.rs#L1006-L1047), Paragraph, CodeBlock и custom-блоки удерживают ссылки на состояние выделения. [При отрисовке/Copy](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/inline.rs#L576-L610) оно меняется. `Mutex` защищает доступ, но не изолирует выделение двух виджетов. `PartialEq` намеренно не доказывает изоляцию.
* У Paragraph и Table есть кэши: при глубоких клонах создаются новые mutex-слоты, но уже рассчитанные значения в них могут разделяться. Это не равнозначно свободно переносимой геометрии. Пример: [ширины таблицы](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/node.rs#L2029-L2074) учитывают оконную текстовую систему и стили; [CodeBlock](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/node.rs#L2482-L2505) разделяет кэш и сравнивает конкретный callback подсветки. [Retained layouts](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/inline.rs#L384-L412) хранятся на UI-потоке по адресу InlineState; worker не должен рендерить элементы, переносить StyledText/Rc или выполнять UI-callbacks.
* [NodeContext кадра](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L1139-L1154) строится заново. Из результата parse берутся только offset и ссылки, а стиль, image resolver, действия, highlighter, обработчик ссылок, расширения, fade, reveal и highlights — текущие у View. [ImageNode](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/node.rs#L857-L891) может лениво декодировать data URI в OnceLock. Пользовательский [resolver](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/node.rs#L2711-L2717) имеет приоритет при **рендере**, а не при parse. Менять resolver, загружать картинки в worker или переиспользовать один frame-context между View нельзя.
* Пользовательский [MarkdownNode](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/markdown_ext.rs#L112-L135) содержит `Arc<dyn Any + Send + Sync>`: это не обещание чистоты или неизменности payload. Парсер может зависеть от захваченной конфигурации. Одного текста или равенства структур недостаточно. Для обычного HTML единственная точка вызова пользовательского парсера в [format/html.rs](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/format/html.rs#L469-L483) — HTML inline parser. Патч оставляет эту ветвь без изменений.
* В одном TextView после **асинхронного** commit [worker уже оставляет себе clone того же результата](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L1266-L1283). Он только парсит; [изменение структуры вектора идёт через COW](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L1361-L1419). Это не основание для разделения между независимыми View. Отправка уже нарисованного синхронного baseline в worker того же виджета также сохраняла бы идентичность выделения и cache/состояния расширений там, где раньше делался независимый parse. Локальность не доказывает эквивалентность этого изменения.

## Почему узкая отсрочка предпочтительнее

Синхронный parse малой замены нужен: [is_ready](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/state.rs#L274-L282) и высота доступны при первом layout. Если эту работу просто убрать, первый layout увидит незавершённое/старое содержимое. Альтернатива проверенного кандидата `defer-short-html.patch`: сохранить синхронный commit, а для штатного HTML ≤4096 байт **после успешного parse**, без HTML inline parser, сохранить у worker ограниченный source + исходную ревизию/config. По отдельному следующему append он сначала строит собственный исходный baseline, потом применяет дельту. Реальная цена первого раздельного append — перенесённая туда работа; это не доказательство ускорения первого append или всей отрисовки.

Обязательные инварианты при ревью: применять отсрочку **после** существующего merge_pending_options; если замена и append уже были получены одной группой, сохранить штатный полный parse; сохранять прежние правила full-replace revision/selection compatibility; на неудачном полном parse оставлять последнюю успешную базу, не замещать её пустой; не посылать в UI второй фиктивный commit. В рассмотренном патче это выдержано. Не распространять вывод на Markdown (last-span, link refs, парсеры) или на HTML с parse hooks без отдельного доказательства.

## Два воспроизводимых контрпримера

1. Программа [selection.rs](selection.rs) с исходным определением BlockState и его методами: выставление Full у A видно в B=A.clone(), независимый C не выделен; при этом A==C. Очистка B снимает выделение у A. [Вывод](selection.txt). Дополнительно [диагностика настоящего обычного Markdown-параграфа](widget-alias.rs) выполнена в двух нативных бинарниках: и поверхностная копия ParsedDocument, и глубокий клон его Vec сохраняют выделение исходного параграфа; независимо распарсенный параграф не выделен. [Оба вывода](widget-alias.txt). Проверка использует реальный модуль виджета, не имитирует рендер окна.
2. После отдельно обработанной базы `<b>red` явный HTML `push_str("plain")` разбирает дельту как самостоятельный фрагмент: жирным остаётся только «red». Полный parse конкатенации делает жирным и «plain». [Проверка](fragment.rs) на штатном минификаторе и html5ever; [вывод](fragment.txt). В GPUI тэг b [непосредственно ставит bold](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/vendor/gpui-base/src/text/format/html.rs#L494-L501). Это проверка семантики фрагментов и владельцев, не замер окна или времени.

Воспроизведение двух примеров: `bash reproduce.sh /path/to/Proteus-desktop fresh-output-dir`; используются Rust 1.95.0 и штатные html5ever 0.27.0 / markup5ever_rcdom 0.3.0. Никаких изменений в рабочий код или GitHub эта проверка не вносит.
