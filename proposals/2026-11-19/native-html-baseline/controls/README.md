# Цена первого дописывания и отрицательные контроли без счётчиков внутри парсера

**Проверка на финальном opt-in патче.** Два интерфейса кандидатной библиотеки сравнивались с одной baseline. У обычного публичного `TextViewState::html` регрессия первого явного дописывания из общего прототипа не воспроизвелась, парсер до/после приходит к нему с заранее созданным базовым деревом. Оптимизированный `html_for_replacements` выбран только у штатной поверхности RichText, которая не вызывает HTML `push_str`. Если кто-то намеренно использует новый конструктор и явно дописывает, работа по восстановлению базы действительно уходит в этот первый вызов: для 32 таблиц 4 096 Б до idle **1,93 → 8,24 мс** и **2,39 → 8,23 мс** в двух сериях. Результат сохраняется; общая ветка для любого HTML **отвергнута**.

Отдельный риск вне точки оптимизации — монотонный синтетический HTML, 53 755 байт без разметки внутри одного параграфа. Для 8 состояний opt-in путь показал **+9,3% и +6,2%** по парным медианам времени в двух сериях, несмотря на отсутствие экономии парсов при таком размере. На четырёх HTML по 62 481 Б из действительного Markdown-рендерера такого направления нет. Не делать вывода «все большие входы быстрее» или «регрессий нет». Механизм различия на длинной строке не изолирован; это повод для проверки на целевой машине перед интеграцией.

Временная граница: для `init` от начала создания всех состояний до окончания их фоновой работы. Для `append` первое создание и приведение к idle происходят **до** таймера; измеряется только первая добавка `<p>tail-marker</p>` каждому состоянию и выполнение worker. Все TextViewState удерживаются до конца; содержимое и готовность проверяются вне таймера. Ничего не рисуется. Две сборки в разных каталогах с настоящими неизменёнными функциями: нет атомарных счётчиков parser API, записи логов или измерительного аллокатора внутри них. Выбор конструктора в клиенте фиксирован при компиляции. Каждая библиотека принудительно пересобрана и проверена по source path; дополнительно правильность opt-in подтверждена в [независимом стенде](../host/README.md).

На каждом ядре 12 чередующихся AB/BA-пар отдельных процессов на каждый сценарий. В образце два прогрева, затем 8 пакетов с одинаковой нагрузкой. Колонки — независимые медианы по процессам и медиана 12 парных отношений wall time; процент не обязан совпадать с отношением двух колонок. Сырые данные содержат также process CPU nanoseconds (Linux CLOCK_PROCESS_CPUTIME_ID) и число пар, где стало быстрее. CPU-time не включает другие процессы/ожидание планировщика, но не устраняет влияние частоты/кеша. Состояния одного пакета обслуживает один закреплённый CPU.

## Повтор

Нужны Rust/Cargo 1.95, Python, Linux x86_64 и подходящий CPU. Для `CONTROL_TARGET_BASELINE` / `CONTROL_TARGET_CANDIDATE`, если их задавать, используйте только отдельные каталоги этого опыта: сценарий очищает target **только** для выбранного crate. Бинарники stock и candidate собираются из закреплённых исходников и полного финального патча; изменения одного только Desktop call site не копируются в stand-alone probe, вместо них выбираются те же публичные конструкторы.

```sh
python3 fixtures.py /tmp/new-generated-fixtures
python3 long_input.py ../host/cases.jsonl "$STOCK_MARKDOWN_RENDER" /tmp/new-generated-fixtures/prose.md > /tmp/cases-plus.jsonl
python3 build.py "$PINNED_DESKTOP" ../candidate/defer-rich-text-only.patch ../host/Cargo.lock /tmp/new-control-build # add --offline if all dependencies are cached
python3 drive.py /tmp/new-control-build/baseline-probe /tmp/new-control-build/opted-probe /tmp/cases-plus.jsonl --cpu 5
# For the public constructor use candidate-probe in place of opted-probe.
```
