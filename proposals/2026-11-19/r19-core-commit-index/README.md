# Не строить индекс подтверждённых частей, когда он никому не нужен

Изолированный патч на Proteus-core `048378da7cbe890d8bf8a0152e55eb28ecb5013d`.
Меняется renderer и добавляется один регрессионный тест. Нет изменений в admission, HTTP, Desktop, storage, формате журнала или проверке источника. Патч не устанавливался в upstream.

Renderer использует ID подтверждённых частей только для одного решения: показывать ли сообщения ответа модели. На базе первый проход хеширует все ID даже по журналу из одних изменений истории, затем выбрасывает множество перед вторым проходом. Кандидат на первом проходе устанавливает только наличие потенциально значимого ответа модели после последнего сброса. Если такой ответ есть, в уже существующем втором проходе собирает подтверждения **по всему зафиксированному префиксу**, включая записи до сброса и после ответа. Иначе этот временный индекс не выделяется. Число проходов не меняется, как и обработка ошибок, даты карточек, правил видимости и live-turn.

**Контрольный пример.** На 125 000 синтетических сообщений по одной уникальной части, сгруппированных по 50 в запись, два рендера дали одинаковую полную выдачу: 125 000 строк, два прохода, тот же digest всех полей в исходном порядке, все тексты и даты проверены. В конце первого прохода относительно его начала живая выделенная Rust-куча составляла **+4 456 464 байта на базе, +0 в кандидате** во всех пяти парах. Это net requested bytes, не суммарное число аллокаций и не пик RSS/PSS: последующие даты, дедупликация и готовые строки по-прежнему занимают память. Стенд подаёт фиксированные typed records в настоящий renderer; здесь не измеряются JSON parsing, процесс хранения, HTTP, Desktop или время до первого токена. Время отдельных проходов в логе диагностическое.

**Поведение.** 49/49 изолированных тестов неизменённого transcript-модуля с реальными Contracts и Session Semantics прошли на кандидате; все пути обращения к подменённому storage scanner в этом отдельном тестовом стенде завершаются panic и не были вызваны. Среди сценариев: обмен до/после frontier; поздняя фиксация делает видимым соседнее сообщение ответа лишь до следующего сброса (новый регрессионный тест); live turn, compaction, hosted cards, clock step, ошибка каждого прохода, корректность append относительно полного renderer. См. `evidence/renderer-tests.log`. Это не запуск полного Core или системный HTTP-бенчмарк.

**Что уже в свежем main.** Между `2aad0ba` и `048378d` два коммита: `0c1b757` уменьшает удержание схем инструментов, стоимость проверок journal ID и копирование ответа SDK; `048378d` интегрирует packed display/prefix, двухпроходный случай для простой истории, восстановление с подтверждённым источником и исправления доставки. Полный патч предложения #224, включая его тест, применим **в обратном направлении** к актуальной базе. У предложения #226 всё наоборот: implementation, затем route regression применяются **вперёд**, admission не включён. Само по себе чистое применение не доказывает совместимость клиентов или преимущество под нагрузкой.

**Почему не удалены две проверки тёплой latest-страницы.** В `remote/view/cache.rs::transcript_page` при unnamed cache hit есть `RemoteCacheSource::read` до декодирования и перед выдачей; на текущем пути это два `OpenSnapshot` и два `ReleaseSnapshot`. Первый отбрасывает устаревший заголовок до чтения больших страниц, последний обнаруживает изменение во время чтения. Получение объекта `ReadCache {source: Some(...)}` не доказывает текущего канонического состояния: у поставляемого worker это привязка к источнику, с которым *был записан кеш*. Named-путь читается по закреплённой ревизии. Оптимизация в этом пакете не меняет ни одной из этих гарантий и не решает конкуренцию за mutex worker.

## Применение и воспроизведение

1. На чистой указанной базе запустить `git apply --check /path/to/commit-index.patch`, затем `git am /path/to/commit-index.patch`. Дерево результата должно быть `eef61c0447f4f30c33af0b9bd981def509e21174` (ID коммита при локальном применении может отличаться).
2. Обычная проверка в полном checkout с module fixtures: `python3 scripts/test.py -p proteus-core --lib app_server::transcript::`. Для изолированных стендов используйте Rust 1.95 и один чистый target; из checkout Core выполните `cargo build --release --locked -p proteus-core --bin proteus`. Полный бинарник в микрозамере не запускается: используются его однозначно выбранные release rlibs.
3. На Linux из каталога пакета (подставьте пути):
   ```sh
   REPO=/path/to/Proteus-core
   DEPS=$REPO/target/release/deps
   RUSTC=$(command -v rustc)
   BASE=048378da7cbe890d8bf8a0152e55eb28ecb5013d
   python3 stand/renderer-tests.py "$REPO" HEAD "$DEPS" "$RUSTC"
   python3 stand/isolated.py "$REPO" "$BASE" HEAD "$DEPS" "$RUSTC" --rows 125000 --pairs 5 > pairs.log
   python3 stand/check.py pairs.log
   ```
   Если в `deps` несколько версий одной библиотеки, стенд откажется выбирать произвольную; укажите новый target. Команды рендера требуют `lld` и не запускают внешние компоненты. `SHA256SUMS` фиксирует файлы этого пакета.
