# Рабочий процесс хранения: где действительно исчезает копирование

Два независимых патча к Proteus-core `2aad0ba29311f0dbf7c107efc281abc1202ce4c4`. Они не меняют wire-протокол, семантику хранения, формат и пределы журнала, правила допуска или SHA. Это **не подтверждённое ускорение открытия**. Основной интерес — снижение работы с деревьями JSON на границе SDK.

## SDK: переместить непрозрачные входные параметры

На входе Rust SDK уже есть разобранное дерево JSON. Раньше типизация обёртки `ProcessComponentInvocation` заставляла Serde ещё раз обходить и собирать контейнеры непрозрачного поля `params`. Патч временно заменяет только **присутствующее** поле на null, оставляет каноническую типизацию/валидацию структуры, после чего возвращает владение реальным payload. Отсутствующее поле не добавляется. Семантика ошибок, target, lineage, callbacks, frame limits и проверки конкретного слота остаются прежними. В отличие от R13 (готовый **исходящий** ответ) правится **входящий** запрос; изменённый SDK должен попасть в отдельную сборку внешнего worker.

Четыре формы значения реально сняты с WriteCache синтетического AppServer (#222 + R13, история из 5000 сообщений, 100 активных). Абсолютные пути в копии head заменены синтетическими строками той же длины. В микротесте было проверено, что каждый полный WriteCache соответствует typed contract, а старый/новый декодеры обёртки дают равный результат. Фиксированный Linux CPU, 14 чередующихся замеров для времени, 35 повторов в замере, отдельно подсчёт обращений к аллокатору. Копирование фикстуры, разбор входных байтов, последующая обработка storage и уничтожение результата не входят в таймер. Точность значительно лучше для сумм, чем для операций короче 1 мкс; системный вызов таймера не вычитался.

| Значение JSON | Байты | CPU обёртки до → после, мкс | Аллокации до → после | Запрошено байтов до → после |
|---|---:|---:|---:|---:|
| Архивный блок | 135 417 | 252,7 → 2,0 | 447 → 0 | 288 088 → 0 |
| Отдельная страница | 20 801 | 46,77 → 0,91 | 260 → 0 | 139 928 → 0 |
| Компактный prefix | 224 359 | 1,78 → 0,44 | 6 → 0 | 3 792 → 0 |
| Head | 13 307 | 30,66 → 0,87 | 145 → 0 | 94 000 → 0 |

Это новые запросы аллокатору **внутри одного вызова декодера**, не RSS и не число выделений целого SDK/worker. Крупные строки до оптимизации уже могли передавать свои буферы без копирования, поэтому компактный prefix мало выигрывает.

**Восемь проб настоящего отдельного JSONL worker**, одинаковый #222+R13 AppServer, два worker с одинаковым применённым R13 outbound-изменением, одинаковый CPU, порядок A/B/B/A. Fresh worker и новые отдельные канонические синтетические журналы, ОС-кеш не сбрасывался, машина была нагружена. У всех восьми проверены структура cold IPC, чтение страниц, первая публикация и завершившийся первый send. Готовность, prepare+launch:

| История | A1 → B1 | A2 → B2 |
|---|---:|---:|
| 50 000 | 3,721 → 4,363 с | 4,387 → 4,289 с |
| 125 000 | 10,855 → 14,262 с | 8,993 → 9,188 с |

Сквозного выигрыша в этой выборке нет. Этот патч не стоит выбирать как главное средство ускорить холодный запуск интерфейса.

## Контракты: убрать временную сортировку уже упорядоченных ключей

Второй небольшой патч оставляет прежний поток байтов SHA-256. Лишь для реально неупорядоченных объектов строится сортируемый список ключей. Сюда входит сборка serde_json с preserve_order. В обычной конфигурации BTreeMap обходится без временного Vec на каждом объекте. Вывод hex производится в одну строку. Встроенные и независимые пробы сверяют digest с SHA от отсортированных компактных JSON-байтов, включая вложенные несортированные объекты, Unicode, числа и граничные строки. Отдельно прогнаны оба варианта serde_json.

От варианта с BufWriter **отказались**: на реальном 135-КБ блоке CPU уменьшался, но компактный 224-КБ prefix замедлялся (212 → 256 мкс). Не сравнивать абсолютное время разных наборов прогонов. Опубликован только вариант **без** дополнительного буфера, см. evidence/hash_final_cpu.csv; таблица с его результатами ниже. Пересборка host и/или worker необходима для эффекта на соответствующей стороне. Отдельного замера AppServer с этим вторым патчем нет.


| Форма | CPU одного полного etag до → после, мкс |
|---|---:|
| Архивный блок | 359,00 → 338,12 |
| Отдельная страница | 55,88 → 63,87 |
| Компактный prefix | 291,52 → 293,85 |
| Head | 42,29 → 34,90 |

12 чередующихся замеров на вариант. Тот же SHA на каждом входе; это CPU одной операции, не всей записи кеша. Разброс и замедление отдельной страницы не позволяют считать этот патч ускорением всех форм; он предложен только для снятия лишних аллокаций.

## Проверка и повторение

- В применяемых патчах нет стендовой инструментации. Проверить на чистой базе: `git apply --check /path/to/patches/*.patch`. Изменения независимы от #222 и R13.
- Микротест: `bash stand/run-local.sh /abs/stock-core /abs/core-with-both-patches /abs/new-output`. Нужны Linux, Python, Cargo и зависимости Core. Через `taskset -c N bash ...` можно закрепить CPU. В сыром CSV ingress: fixture, variant, sample, repeat, среднее CPU-нс, число аллокаций, запрошенные байты. Для hash: fixture, variant, sample, repeat, bytes, среднее CPU-нс, etag. Результаты с счётчиком аллокаций не используются для оценки времени. Для интеграционного A/B используется ранее предоставленный стенд R13, вариант полного пути (не ready-bound), один неизменённый AppServer.
- Точечное тестирование SDK: strict-routing/opaque payload, лимиты фреймов, типизированный session_storage, callbacks, reentrancy, cancellation и отдельный child-process transport. Полный workspace, SQLite AppServer и GUI не проверялись. Версии в замере: Core 2aad0ba, Modules 2c2cee4 с тем же ранее применённым R10, что в R13.
