# Bounded, index-backed transcript window (experiment, not production wiring)

The renderer no longer needs to construct *any earlier display row* for a certified archive, even to answer the first backwards scroll. A single immutable staging file is the data file for every page. There is no second transcript payload spool, provider-specific code, durable format change or unverified “last N records” shortcut. The stage itself still contains the entire journal's display records. No canonical records were deleted.

## Why this narrow admission is exact

1. This experiment accepts only the completed-view query (no live-turn filter) and starts from a strict, successful validation of the *whole*, fixed journal. An actual hook may observe the typed facts while validation/staging is in progress but must never expose a partially accepted index. Non-display records are filtered by the same official classifier as baseline. Untrusted external input cannot provide spans. Provisional projected-state reads must not silently become strict recovery.
2. Until the first compaction there are only history appends of one conversation-scope Text part per message, apart from turn-open and successful-settlement facts that produce no rows without any model/tool display events. Strict active-history uniqueness prevents repeated message or part identities across these appends. Each nonblank text therefore makes exactly one row; blanks make none. The first message/part occurrence eligible for dates is its append record, *not* the minimum wall-clock time. The final row runs through the existing shared renderer, preserving spelling, Unicode, roles, phases, and the journal date.
3. A compacting Replace is invisible only when every included part already appears in the exact positive witness of the last 512 part IDs. In the full renderer, all such parts have already gone through dedup, even invisible blank text. The strict validator enforces stable payloads for repeated IDs; rehosting does not create rows. Once any compaction happened, a subsequent append might legally reuse an old inactive part. It disqualifies the whole index, no matter how ordinary it looks. A compaction with an out-of-window or novel part and any real reset/checkpoint also disqualify. This is deliberately conservative; it is *not* special casing the name/source of a compaction or relying on a row count.
4. An interim/final model message, a tool or subagent fact, an unsuccessful settlement or an unknown display record vetoes the **entire** prefix index. Never just skip such a record: a much later commit/call may make a previous model-response row visible, and a failed turn can contribute a row of its own. A decline uses the existing complete renderer against the same snapshot. No mixed-session gain claimed.
5. Every nonempty append batch gets a 24-byte span (cumulative display count, actual byte offset and byte length) in an anonymous side file. Empty batches and proven invisible compactions get no entry. To read a window, binary-search that file, directly seek to overlapping batches and render only requested nonblank rows. Dates are read from their records, including on a backward clock step. Earlier pages are direct seeks on the *same file and revision*. No cache-head race, disk re-open, or mutable log offsets are assumed in this microbenchmark.

## Limits and integration contract

- Fixed witness: 512 part UUIDs. Index capped at 16 MiB. Existing data stage max 512 MiB. New cap for an indexed batch: 256 KiB, maximum page 50 rows. A read hydrates at most 50 indexed records (usually 1–2) / 12.5 MiB of stage input and returns at most 50 rows. Memory for parsing a single record depends on its contents but its input is bounded. These caps mean ineligible, never truncated user history. Per record work at stage time still touches all text; the algorithm is not sublinear startup, strict validation remains mandatory.
- Data plus index handles must be inseparable and bound to a verified session/revision; actual UI/worker must not accept a bare offset or a caller-injected file. Validate/flush both before publishing. On any staging/index/decode/seek error discard the disposable index and call normal replay, rescanning the immutable source if staging itself has failed. Durable app-server cache pages and strict continuation are unchanged here.
- A production service still needs a bounded, cancelable owner for these file handles that preserves the previous cursor’s page during immediate append, provides whole-history/export correctly, publishes background caches atomically after source verification, and enforces a global disk/file-descriptor budget. First send, nested turns, simultaneous resume, eviction, injected cache faults, backend parity and click-to-first-paint must be tested before claiming app readiness. No global handle registry, delayed cache job or production switch is included.
- Strict validation, original worker transfer, original stage serialization and pre-existing journals are never removed by this study. Typical real tool/model-driven runs fall back. A single ordinary subsequent live turn can invalidate this archive index at the *new* revision. For that case, test the existing independent-append proof with a separately pinned prefix+suffix composition, not naïve last-N-record truncation.

## Verification and reproduction

This directory's Rust modules are test-only. In an isolated disposable Core checkout based on 2aad0ba with the R13 history-only render patch applied, run:

```sh
python /path/to/tail-study/install-test.py /path/to/disposable-core
cd /path/to/disposable-core
cargo test --locked --release -p proteus-core --lib 'transcript::journal::tests::round14::' -- --test-threads=1
R14_TAIL_BENCH=125000 cargo test --locked --release -p proteus-core --lib 'round14::bench_window' -- --nocapture --test-threads=1
```

Our local isolated test binary used the actual project renderer and real prebuilt Contracts/SessionSemantics rlibs, with inert stubs only for store APIs that this test never calls; no full workspace rebuild. The mixed-fact fixture is adapted from the existing R13 synthetic test. R13 and candidate stage **the same strictly validated typed records** to a new anonymous JSONL file per run. R13 reads its actual two-pass full renderer; the candidate additionally builds its index during the same stage write and returns the exact requested window. Test checks byte-for-byte JSON against full reference, including two representative pages in every timing iteration and all boundaries of a smaller separate adversarial fixture. Staging time is reported separately to avoid claiming a full app latency or omitting index construction. This is local on a warm OS page cache, fixed logical CPU; no storage worker, provider request, on-disk durable cache publication, real desktop frame or network was timed. No timers for results without a successful final test.

## Measured run, 50,000 rows

Stage = 20,934,432 bytes / 500 nonempty 100-message records and one trailing retained-100 compaction. R13 stage + full render: 334.02 / 322.74 ms. Candidate stage + index + exact first 50: 89.86 / 89.72 ms. Once staged, first 50 took 0.29–0.34 ms and 1 record (41,808 bytes); nonaligned earlier page 0.42–0.47 ms and 2 records (83,616 bytes). Separate side index: 12,000 bytes. Same data, ABBA ordering, CPU 8. Fixture setup and strict validation not in either sum. See raw successful run. Tests: 53 selected renderer tests passed; one unrelated longer R13 benchmark excluded, no full workspace/CI/GUI run.

## Measured run, 125,000 rows

52,316,499 stage bytes and 30,000 index bytes (1,250 nonempty batches). R13 full render after staging: 2,740.70 / 1,457.17 ms; candidate tail after index staging: 0.282 / 0.237 ms, both reading one 41,912-byte record. Older 50 took 4.365 / 0.285 ms, two batches / 83,616 bytes. Combined stage + render: R13 4,917.61 / 1,785.57 ms vs candidate 288.19 / 342.77 ms. Shared machine is noisy: notably the first baseline stage alone took 2,176.92 ms vs the last 328.41 ms; do not quote a universal latency multiplier or extrapolate this to Desktop. Strongest evidence is the amount of work (one/two nonempty batches, bounded page object, exact bytes), not the first timing. Setup (including the in-memory fixture builder and strict validation) was outside all four measurements and is not a production recovery timer.
