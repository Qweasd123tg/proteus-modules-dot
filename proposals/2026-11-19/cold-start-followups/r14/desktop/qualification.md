# R14: восстановить нужный чат при запуске своего Core

**Пара патчей:** `core-preferred.patch` для Core `2aad0ba29311f0dbf7c107efc281abc1202ce4c4` и `desktop-preferred.patch` для Desktop `fcc30413b12374d622abbba5a8832e10b62fdf3f`. Оба проходят `git apply --check` на соответствующих исходных commits. Подсказка необязательна: новый Desktop с прежним Core не получает оптимизацию, но не передаёт неизвестных CLI-флагов. Интерфейс HTTP/SSE не меняется. Новых внешних зависимостей нет.

Desktop при старте берёт первый абсолютный адрес Proteus из действительно нужных вкладок (включая command target / owner), а не из всех сохранённых. Передаёт адрес только собственному HTTP-процессу. При успешном открытии Core сразу восстанавливает B, а следующий штатный `POST /resume B` возвращает живой handle. Журнал каждого чата по-прежнему определяет его собственный workspace; `bootstrap.cwd` и новый чат без source_session_dir остаются в проекте запуска. Помощник не влияет на строгий `--resume-session`, явный `--new-session`, stdio, attach, Codex-only и Fresh/profile switch. Если подсказка недоступна, Core использует прежний алгоритм «последняя непустая родительская сессия текущего workspace, иначе новая».

Это **не** перенос readiness до открытия истории. На верном B `http_ready` по-прежнему публикуется после его подготовки. Общий Boot-барьер split/mixed, количество нужных вкладок и запрос SSE не меняются. Если A=B, лишнего replay не было и до патча. Глубоко повреждённый или очень медленный адрес может израсходовать часть прежнего 90-секундного бюджета до fallback; при отсутствующем адресе отвечает обычный storage. В сценарии Fresh этот патч не устраняет лишнюю подготовку Core. Не меняйте Desktop pin на произвольный hash: при выпуске сначала поставить Core с поддержкой подсказки, затем указывать проверенный commit при обновлении поставки.

**Desktop:** изолированная сборка настоящих startup/backend/HTTP и Codex-модулей, без GPUI, с DTO из Desktop pin. 67 тестов модулей прошли; отдельно прошла синтетическая проверка настоящего запуска дочернего процесса (путь с пробелом, отсутствие наследования чужой подсказки). Один штатный тест установленного Codex пропущен. Проверены верный B вместо скрытого A, `resume stale → bootstrap → resume latest`, Fresh без подсказки, прежние split/owner/Codex сценарии. GUI, layout/presentation, запуск с большим реальным профилем и wall-clock ускорение не измерялись.

**Core:** собран обычный полный lib-test executable текущего Core, из 725 зарегистрированных тестов запущены 5 focused (все прошли). Новый тест использует настоящий модуль хранения, журнал с разным содержимым в A и B и настоящие HTTP handlers. После одного и того же `POST /resume B` в контроле зарегистрированы **2** живых handle (A+B), с верной подсказкой **1** (B). В обоих случаях история B равна исходной, его рабочий каталог соответствует B, а новый несвязанный чат открывается в A. Удалённая подсказка приводит к обычному выбору A; остальные четыре проверки покрывают независимость адресации, source/default workspace для новых сессий, live reuse и Fresh vs latest. Это количество живых runtime в данном сценарии, не число открытий файлов и не выигрыш времени/RSS.

Повторная проверка полных трёх групп `http::tests::addressing`, `http::tests::sessions`, `startup::tests` на том же обычном executable: **14 passed** (входят в них и упомянутые пять, не суммировать). Финальная форматированная версия также прошла повторную отдельную сборку с регистрацией только этих пяти тестов, production-функции не заменены.
