# Один проход по inline payload JSONL

База: Proteus-modules `2c2cee47ea76df12c6e208839594e32470a2c3f1`. Меняется только десериализация объекта `payload` в канонической JSONL-записи. Сгенерированный Serde-десериализатор внутренне тегированного enum сначала создавал рекурсивное дерево Content, затем собирал из него serde_json::Value. Новый visitor читает поля непосредственно в соответствующие типы. Форматы файла, хеша и IPC не меняются. Не менялись ограничения размера, сверка владельца и версии, decode/validation вложенной записи, SHA-256 внешнего blob или неизменяемого префикса. Порядок полей произвольный; неизвестное, повторное, неполное, смешанное множество полей отвергается. Для позиционной формы сохранён исходный reader. Для SQLite код не менялся.

## Проверка и воспроизведение

На чистом checkout указанной версии выполните `git apply --check storage-single-pass-payload.patch`, затем `git apply storage-single-pass-payload.patch`. Проверка `cargo test -p session-storage --lib`: отдельная проверка соответствия старой схеме сравнивает результат/отказ для JSON с обоими вариантами, перестановками, отсутствующими и повторными полями, числами, вложенными значениями и позиционной формой. Локально программа тестов собрана прямым rustc из затронутого crate на уже собранных release-зависимостях; 49 прошли, 1 ручной бенч игнорировался. Полного workspace/GUI-прогона не было.

Соберите контроль и кандидат в отдельных рабочих копиях. Для сравнимости оба worker в измерении использовали одинаковые ранее проверенные R10 semantic-validation и R13 moved-result SDK; это не два разных поколения SDK или изменение формата. Можно взять свои релизные сборки на одинаковых зависимостях. На Linux из stand/:

```sh
python3 seed.py /path/to/stock-worker /tmp/new-synthetic-fixture
python3 bench.py /tmp/new-synthetic-fixture/info.json /path/to/stock-worker /path/to/candidate-worker --pairs 4 --cpu 6
```

Источник: реальный JSONL worker записал 125 000 различных синтетических Unicode-сообщений чанками по 100, затем replace на последние 100; итого 1 251 запись, 51 325 207 байт, 125 100 вхождений сообщений. Перед каждым измерением новый процесс; файловый кеш ОС не очищался. Замер от отправки `open_display_snapshot` до разбора ответа тестовым peer: строгая проверка, возобновляемое состояние, локальный staging display. Лимит 64 на последующее чтение страниц; полная последовательность и состояние сравниваются после таймера. Это не AppServer/GUI, не полная отправка или публикация. Время процесса из /proc с точностью в один tick. VmHWM не равен сумме когда-либо выделенных байтов.

Микропрофиль `run-payload-probe.sh /path/to/patched/modules /path/to/synthetic/journal.jsonl /tmp/new-probe-dir` измеряет **только** разбор payload, без typed JournalEntry, семантического fold и IPC. В counting-сборке старый/новый reader: 3 781 773 → 3 019 914 alloc/realloc (-20,1%); 602 928 208 → 383 392 720 запрошенных байт (-36,4%). Четыре wall samples каждого, без счётчика в пути: медианы 1,218 → 0,743 с; среда нагружена, акцент на воспроизводимых счётчиках. Это не экономия 220 МБ пиковой памяти. Сырые значения в evidence/mini.csv.

## Настоящий OpenDisplaySnapshot

Четыре чередующиеся пары с одинаковым журналом, свежий отдельный worker на CPU 6. Медиана строгого ответа 3,901 → 2,965 с (-24,0%), CPU процесса 1,880 → 1,450 с (-22,9%). Во всех четырёх парах знак один и тот же; общая машина была нагружена. VmHWM после открытия, наоборот, слегка выше: 149 962 → 151 218 КиБ (+0,84%). Экономии пиковой памяти не обнаружено. Хеш источника, состояния всех 100 активных сообщений и полной упорядоченной выдачи 1 251 display-записи одинаковы. Первая пара проверяет все страницы после таймера, все пары проверяют точный fingerprint/revision и состояние. Сырые wall/CPU/память в evidence/process.csv. Аналогичный RPC был 1,256 с в отдельном прежнем интеграционном прогоне R13 с другим журналом и нагрузкой: его нельзя складывать с этим выигрышем или вычитать из всей задержки UI.
