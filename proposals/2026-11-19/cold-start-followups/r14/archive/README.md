# R14: ограниченный размер чтения архивной страницы

**Локальный патч Core поверх #222** (базовый коммит 68eaace25670935f5a87274337c6977df6a961a4). Никаких изменений worker, протокола, курсора или канонического журнала. Новый физический формат применяется при создании/перестроении кеша; старые сохранённые группы остаются читаемыми, но не становятся быстрее до перестроения. Старый бинарник не декодирует новый формат: возврат к старой версии требует возможности перестроить одноразовый кеш из журнала; это не миграция канонических данных.

## Почему не seek или memo

session_storage/v2 возвращает из ReadCache целый JSON-объект. У него нет byte-range, условного чтения по etag, подтверждения наличия актуальных старых байтов или multi-get. ReadBlob и ReadBlobByHash также возвращают целое содержимое; PutBlob к тому же требует writer lease. Путь из descriptor не даёт Core полномочий открывать файлы worker. Мемоизация уже проверенного объекта между запросами скрыла бы удаление/замену этого объекта. В этом изменении каждый запрос читает storage, как прежде.

Новые группы содержат независимые raw-DEFLATE-кадры в base64 внутри обычного content-addressed JSON. Сохраняются SHA-256 всего физического объекта, логический SHA каждой затронутой страницы, число строк и десериализация **всех** строк запрошенной страницы до нарезки. Запись сохраняет пределы #222 (8 страниц и 256 KiB в несжатом виде), добавляет предел на само сериализованное тело: **не более 2× размера наименьшей логической страницы** и не более 256 KiB. Подбирается меньшая группа либо исходный singleton. На чтении эти ограничения проверяются для нового формата; распаковка ограничена фактическим лимитом и указанным размером страницы. Гарантия относится к телу объекта, не к RPC вместе с заголовком и не к доле страницы при запросе одной строки. Старые несжатые группы эту границу не обещали. Крупные строки и последние 50 строк сохраняются прежним способом. Локального состояния между запросами нет.

## Фикстура и результаты

6 403 синтетических типизированных строк; одинаковый внешний R10 worker SHA-256 6a92678775ba4fbde99deec876a6d7f8cc034edddb2eefe9758d121c37f5d9a6 через реальные stdio RPC, включены обе проверки контракта. Ядро страницы из production-файлов каждого варианта, warm OS cache после формирования и полной проверки. A/B/B/A, один CPU 5, по 4 полных прохода в каждом запуске. r12-a/r12-b и r14-a/r14-b означают отдельные прогоны, не доверительные интервалы. Проверяется полное совпадение каждого результата с исходным диапазоном **после** таймера. Это не измерение нативного UI, всей сети или AppServer-клика.

На последнем окне размер не изменился: 18 260 Б и два RPC. На SQLite с такой же нагрузкой: старая выровненная страница 4,49/4,77 → 0,58/0,44 мс; полный проход назад 904/1003 → 105/129 мс, 19,29 → 1,15 МБ. Файлы final-*/summary.jsonl и исходные CSV сохраняют остальные квантили и отдельные измерения. Не представлять две пары как гарантию устойчивого p99.

Отдельный A/B/B/A на том же текстовом корпусе с **исходным Core до #222** (2aad0ba): выровненная страница 0,66/1,06 → 0,40/0,61 мс и 17 086 → 7 859 Б; весь проход 209/217 → 96/103 мс, 4,38 → 1,15 МБ. Сырые данные: stock-control/. Это сравнение подтверждает восстановление потерянного в #222 поведения по объёму и времени на данном корпусе, не на любом архиве.

**Цена на другом типе данных.** Второй корпус: детерминированные текстовые строки из псевдослучайных символов, группы по 50 строк с длиной 12 или 600 символов. У #222 полное чтение объекта превышало наименьшую логическую страницу до 26,72 раза; у R14 максимум 1,80. Время прокрутки 884/947 → 204/232 мс; ответы 36,12 → 12,00 МБ, но RPC для прохода 148 → 203; check+write RPC при холодном сохранении 40 → 150 и для экспорта 20 → 75. Для текста с повторениями сохранение в обоих вариантах 36 check+write RPC. Не считать ускорение холодной записи или UI на всех данных доказанным; меньшие группы могут заметно проигрывать при больших накладных расходах отдельного RPC.

## Проверка и воспроизведение

Для production нужен только framed-packs.patch, применяемый поверх #222. Чисто применяется git apply --check. Добавлены miniz_oxide 0.8.9 и adler2 2.0.1; Core уже использует base64 0.22. Имеется пакетный lockfile.

Для замеров нужны rustc 1.95.0, закешированные зависимости Core в target/release/deps и native build outputs, внешняя программа session-storage-module и Linux taskset. При необходимости возьмите miniz_oxide отдельно из собранных release deps; --codec-deps указывает каталог с ним. Не запускайте проверки через каталог реальной пользовательской сессии.

    python3 build.py r12 /checkout/222 /target/222 --rustc /path/rustc
    python3 build.py r14 /checkout/framed /target/framed --rustc /path/rustc
    SAMPLES=48 OUT=my-ab CPU=5 bash run.sh /path/session-storage-module
    R14_NOISY=1 SAMPLES=24 OUT=my-noisy CPU=5 bash run.sh /path/session-storage-module
    R14_STORAGE=sqlite SAMPLES=24 OUT=my-sqlite CPU=5 bash run.sh /path/session-storage-module
    python3 summarize.py my-ab

Четыре регрессии в tests/packs.rs покрывают сохранность старых плоских групп, границы, недействительное/удалённое содержимое после успешного чтения и ограничение распакованной страницы. Проверка units.py использует настоящий Core-источник и contracts с in-memory cache double. Пример: python3 units.py /checkout/framed /target/framed --rustc /path/rustc . app-qa.py предназначен **только** для отдельной QA-копии; адаптирует существующий интеграционный тест с 121 до 953 строк, включая переход через две исторические группы и проверку восстановления при четырёх типах ошибок.

Фактически выполнен release libtest настоящего Core с четырьмя тестами групп и одним увеличенным AppServer-тестом через внешний JSONL worker: **5/5 прошли** (app-qa.log). Сверены полная история и два окна, включая 370..420 через границу групп, восстановление полного/страничного ответов при missing/malformed/checksum/unwritable кеше, отказ на неверной ревизии и чтение после shutdown без изменения байтов журнала. Для этой проверки в QA-копии отключалась регистрация остальных тестов; это не полный workspace gate, не нативный GUI и не интеграционный AppServer-тест на SQLite. SQLite проверен отдельно через компонентный протокол, как описано выше.
