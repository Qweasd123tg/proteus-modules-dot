# Готовая первая страница без второго построения архива

**Статус:** проект минимального производственного изменения и проверяемая модель гонок, а не фоновый publisher в Core. Отдельный патч в этом каталоге только портирует существующее исправление R9 на #222. Измерения R13 «без записи» остаются нижней оценкой, не временем открытия этого дизайна.

## Что блокирует простое `spawn(save_read_model)`

В #222 `PreparedSession::into_display_view` строит модель фиксированного снимка A, записывает весь производный кеш и затем перечитывает хвост. Он может уже принадлежать B. Аналогичная проблема есть в `read_model::refresh_in_background`. Подключить существующий R9 `project_validated_view` (порт для #222 приложен) перед следующим изменением. Это устраняет смешивание summary/revision/usage A с rows/cursor B. При отсутствии именованной страницы A текущий безопасный fallback R9 — вернуть все проверенные строки A без курсора.

После наивного переноса записи в фон сразу ломаются ещё три вещи:

1. `http/sessions.rs::history_page_json` даже для открытой сессии заново открывает store; про объект, временно оставленный в AppServerHandle, он не знает. На cache miss `read_model::rebuild_transcript` заново валидирует и рендерит архив. `AppServerHandle::transcript` делает аналогичный fallback при полном экспорте.
2. Writer публикует B до окончания работы над A. Контракт WriteCache отвергает **любую** запись для уже неактуального A. У `view/committed.rs::publish_committed_view` нет именованной A или валидного общего индекса PREFIX, и он переходит на полную `project_read_view`. Нельзя лечить это ожиданием дописи HEAD A перед допуском send. Ещё хуже — записать A под меткой B.
3. Письмо в кеш не проверяет/не приобретает право на запись журнала. `runtime/resume.rs::validate_cached_resume` обязан как прежде получить канонический `prepare_resume_state` под writer lease. Это легитимная работа первой отправки, а не второй display-render, и её не надо «оптимизировать» повторным использованием display-состояния.

## Узкая первая реализация (без изменения wire-протокола)

На Unix, только для **проверенной холодной** ветви. Тёплый сохранённый экран, другие платформы и неподдерживаемые или превышающие лимит случаи оставить на существующем пути. До объявления курсора нужно гарантировать его доступность. Не нужен глобальный кеш истории по пути, новое событие «диск готов» или второй исполнитель агента.

| Граница (пути под crates/proteus-core/src/) | Изменение API и инвариант |
|---|---|
| `core/session_store/remote/prepared.rs`, `view.rs`, новый `view/ready.rs` | Из холодной ветви вернуть `PreparedDisplay { store, view, work: Option<ReadySeed>, cached_source }`. После `RemoteValidatedRead::open_for_display` и `SessionReadModel::from_validated` взять точный источник из исходного cursor, не из нового HEAD. Переместить, а не клонировать model в seed. Выдать `[len.saturating_sub(PAGE_ROWS)..len)`, summary и usage из того же model, cursor.revision = source.revision(), cursor.before = start, base=None. Только после успешной регистрации seed/pin; ошибка этапа рендера — ошибка открытия, а не пустой экран. |
| `app_server/handle.rs`, `app_server.rs::launch_inner` | Контроллер `PendingDisplay` принадлежит поколению **активной сессии**. Установить pin до attach_runtime/выдачи snapshot. Запускать worker после успешной сборки/restore runtime, не удерживая handle целиком. На раннем выходе освобождать reservation по RAII. Уже существующий HTTP lifecycle gate дедуплицирует одновременный resume одного пути. Если несколько независимых entrypoint в одном процессе должны разделять работу, использовать слабую фабрику singleflight по **идентичности экземпляра storage service + полному SessionLocator** до валидации; join после рендера не устраняет двойной cold. При доступе сверять полный RemoteCacheSource (session locator, обе ревизии, SHA), не timestamp, path, snapshot_id или один номер history_revision. Не добавлять предварительный OpenSnapshot на каждое cold-открытие: без тёплой backend-подсказки он сам может пройти весь архив. |
| `app_server/http/sessions.rs::history_page_json`, `app_server.rs::transcript`, `app_server/read_model.rs` | Направлять активный путь через handle. `pin_named(revision) -> Option<ReadLease>` берёт Arc под коротким mutex. `lease.page(before)` клонирует максимум 50 строк, `lease.export()` копирует/стримит строки один раз, без ReadRecords/повторного render/cache repair. Проверять bound (`end <= total`, иначе ошибка, не cache miss). Для экспорта live эпизода сохранить существующую сборку `snapshot.transcript.skip(50)`; pin брать для **cursor данного снятого snapshot**, а не для «текущей» записи. Неименованный latest допускает seed только при совпадении с фактическим источником до и после чтения; при гонке — текущая строгая ветвь с coalescing для **нового** источника, не возврат A как B. Именованное A продолжает отвечать после append B при том же incarnation. Cold HTTP без активной сессии должен остаться read-only. |
| `view/committed.rs`, `app_server/transcript/journal/append.rs`, `view/prefix.rs`, `app_server.rs::completed_transcript_from_commit` | Отделить существующее доказательство от persistence: `certify_committed(base, committed) -> CertifiedSuffix | NeedsFull`. Проверять start == A, end == canonical resumed state revision и тот же locator, полный канонический prefix по SHA, независимость всех видов identity/visibility от старых строк, точное число добавленных сообщений. Не упрощать логику checkpoint, скрытых частей/результатов, цитат. На независимом append сделать B как `{ Arc<A.rows>, added_rows, base=(A.revision,A.rows.len()) }`; выдавать хвост B через срезы обоих сегментов. A остаётся читаемой в процессе. Сохранить доказанные новые history hashes и exact identity delta; общий prefix A **не** мутировать параллельно с его сериализацией. Простой первый вариант (если байты доказанно в бюджете) — отдельная копия сертификата для B; более экономичный — read-only проверка относительно A, отдельная additive delta и объединение для persistence вне send. Никакого полного render, чтения старых паков или ожидания фоновой очереди при нормальном первом send. В текущем коде всё равно остаётся O(активной канонической истории) при проверке hashes и отдельный writer Resume. При недоказуемом suffix (Replace/compaction, внешний writer, capture failure) блокировать/перестраивать **новый** источник ровно один раз по обычному строгому пути, не создавать фиктивную append-связь. |
| `view/cache.rs`, `view/cache/pages.rs`, `app_server/control_plane.rs::shutdown` | `persist_ready(seed, stop, epoch) -> Published \| Displaced \| Failed \| Cancelled`. Вызовы storage без mutex реестра, runs и writer lease; фоновые cache RPC могут всё равно конкурировать за общий worker. Перезапускать B по оригинальному B, использовав общие неизменяемые строки A, а не подменять source у старого задания; сохранить existing bounded packing либо открыть iterator across two segments, без полной конкатенации архива. Проверки stop между страницами, ограничение RPC в полёте; named directory затем source-guarded HEAD **последним**. Старый epoch не меняет новое состояние, не освобождает чужой pin, не посылает новый snapshot. Для mutable singleton PREFIX также действует проверка источника (несовпавший SHA — miss). При закрытии: закрыть admission фонового задания, отменить, дождаться settlement реально запущенного блокирующего I/O, затем удаление; токен/abort spawn_blocking сам I/O не прерывает. При dropped HTTP waiter не отменять общую работу для оставшихся подписчиков; не делать Arc-цикл worker→server. |

**Fallback к строгости не закрывает дыру сам по себе.** Если A не успела сохраниться до append, named cache для A так и не появится обычным WriteCache(A). Не освобождать A только потому, что B успешно опубликовалась или HEAD ACKнул. Первую неперсистированную именованную A держать до закрытия этой сессии (или до доказанного доступного именованного backing), независимо от судьбы HEAD. У B может быть отличный от A latest. Дальнейшие курсоры нельзя выдавать без заранее зарезервированного backing: на втором неподдержанном поколении или при fault исчерпанного бюджета переходить к прежней синхронной ветви **до выдачи нового курсора**, при неуспешной записи — полная проверенная история без нового курсора. Невозможно одновременно обещать неограниченное число исторических ревизий, вечную доступность после перезапуска, запрет durable writes и ограниченную память.

**Реальные лимиты, а не счётчик сеансов.** Глобальный лимит одновременно живых seeds/jobs, байтов моделей + exact prefix + текущий suffix + копия на время сериализации, числа строк и одиночной строки; отдельно ограничить staging/temp + новые generations. Не использовать `size_of::<Vec<_>>()` или только длину JSON в качестве меры резидентной памяти: вложенные строки, Value, HashSet и capacity тоже платные. Для строгой реализуемой границы больших архивов возможна локальная неименованная tempfile с лимитом реально записанных байт, индексом смещений/длин каждые 50 строк, проверенным versioned framing и отдельными лимитами чтения/одиночной строки. Только display, не durable/cache/journal; временный файл удаляется по RAII. При неопределимой или превышенной стоимости до регистрации — старый синхронный путь. Отдельно померить время подготовки/дополнительный CPU этого backing: R13 этого не мерил. Admission/graceful fallback важнее произвольных magic numbers. RSS, max pinned bytes и scratch в перегрузке — обязательные результаты перед выбором боевых чисел.

**Граница внешнего writer.** Контракт WriteCache обещает отвергнуть устаревший источник, но в проверенной локальной реализации JSONL worker проверка текущего SHA выполняется перед записью temp+fsync, а перед rename ещё раз проверяется session_id, не SHA. Этого достаточно для сериализованных запросов одного экземпляра при соответствующих блокировках, но нельзя делать вывод об атомарности относительно двух независимых storage процессов на одном каталоге. Обязателен cross-process barrier-тест «A в write-cache после проверки → другой writer публикует B → завершить A», включая singleton PREFIX и HEAD. Если backend может перезаписать новое старым, исправлять атомарный publication fence/общее поколение на стороне backend либо явно оставлять эти запуски вне fast path; Core preflight или source read после rename не синхронизация. Именованные неизменяемые данные + строгий fresh check до/после latest остаются обязательны даже если CAS проходит. Не расширять права display до доступа к journal-файлам по пути.

## Критерии приёмки на настоящем AppServer

1. Барьер в перехватчике **до** вызова inner WriteCache, не под mutex backend. Холодный cache miss при 0/1/49/50/51/100/121 и большом архиве. Получить snapshot и старую страницу/полный export, пока барьер закрыт; сверить все поля JSON со строгим эталоном, ordered IDs, границу и SHA журнала. Пагинация/экспорт не вызвали ReadRecords/OpenDisplaySnapshot/полный renderer. Неверный before — ошибка, 0 — пустая страница.
2. Барьер остаётся закрытым. Завершить настоящий send с test model и независимым append. Измерить admission, первый token/event, settled отдельно. По счётчикам один обязательный writer-validation, ни одного дополнительного full display render. Проверить B page, A page и экспорт A/B через разделённые barriers, live overlay без дублей. Критическая проверка не должна «успевать случайно»: без снятия барьера send действительно заканчивается.
3. Выпустить старый publisher после B, отдельно после записи named-A и до HEAD-A. Проверить, что запоздалый ACK/ошибка не меняют effective B/pin и lease не приобретается display-запросами. Реальный R0 незаписан, а поздний запрос по его курсору остаётся корректным. Сценарии с fault/corrupt/missing page/ENOSPC, oversized строки/prefix, исчерпанием числа jobs/памяти; удалить старую named запись и проверить политику для активных pins и после закрытия.
4. Контроль противоположной ветви: checkpoint с совпадающим SHA, который впервые явно коммитит скрытую часть, старый ToolResult/CallId, Replace, canonical corruption, external append; не обещать certified append, не выдавать rows из A за B. Неименованный latest при смене между проверками не выдаёт A. Сессия с тем же человекочитаемым путём после delete/recreate не видит старый pin; два service instance с одинаковым path/UUID изолированы.
5. Многократный одновременный resume и быстрый shutdown/delete/смена вкладки: один seed/job на источник/owner, отсутствие чтения чужого поколения, старый late callback не снимает нового owner/pin, нет зависших blocking jobs/leases и временных файлов. Один медленный export уже держит Arc, отмена одной заявки не отменяет других.
6. Отдельно JSONL и SQLite, несколько независимо запущенных workers, холодный и тёплый native Desktop; p50/p95 до первой реальной отрисовки, first send/scroll/export и до конца фоновой работы; CPU/RSS/I/O в конкуренции с writer, число строго полных рендеров, исходные и переданные байты. Не выдавать моделирование или синтетический AppServer таймер за эти результаты.

`interleavings.py` проверяет только предполагаемые инварианты компактной модели pin двух ревизий. Он перебирает 1 260 допустимых порядков семи событий в нормальном режиме и ещё 1 260 с отказом кеша плюс проверки отмены, latest/recreate и границ. Это не полный runtime, не доказательство атомарности процесса хранения, не бенчмарк. Для запуска: `python3 interleavings.py`.
