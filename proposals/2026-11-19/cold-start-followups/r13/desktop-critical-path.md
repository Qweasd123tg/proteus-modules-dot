# Proteus Desktop: что на самом деле ждёт историю

Исходники: Desktop [fcc3041](https://github.com/Proteus-harness/Proteus-desktop/tree/fcc30413b12374d622abbba5a8832e10b62fdf3f); Core [2aad0ba](https://github.com/Proteus-harness/Proteus-core/tree/2aad0ba29311f0dbf7c107efc281abc1202ce4c4). Это анализ локальных ревизий и изолированные тесты, **не замер запуска GUI**.

**Кадр окна и кадр чата.** [main.rs:45–100](https://github.com/Proteus-harness/Proteus-desktop/blob/fcc30413b12374d622abbba5a8832e10b62fdf3f/src/main.rs#L45-L100) читает preferences и начинает подготовку сервера в другом потоке перед инициализацией GPUI, регистрацией шрифта, тем и окна. [Workspace::new](https://github.com/Proteus-harness/Proteus-desktop/blob/fcc30413b12374d622abbba5a8832e10b62fdf3f/src/ui/workspace.rs#L188-L219) не ждёт результата на UI-потоке: если он уже готов, применяет его до paint, иначе показывает оболочку и применяет его позже. Не складывать длительности этих параллельных веток. `window.create` отмечается в конструкторе; `chat.transcript.layout` означает prepaint непустого видимого диапазона, а не физически показанный кадр. Текущие first-маркеры общие для процесса: для split нужен идентификатор чата, иначе выдержка может относиться к другой вкладке.

**Проверка гипотезы о двух восстановлениях.** [Desktop запускает Core](https://github.com/Proteus-harness/Proteus-desktop/blob/fcc30413b12374d622abbba5a8832e10b62fdf3f/src/backend.rs#L34-L65) без ключей выбора сессии. [Core сначала открывает последнюю непустую родительскую сессию workspace, либо новую](https://github.com/Proteus-harness/Proteus-core/blob/2aad0ba29311f0dbf7c107efc281abc1202ce4c4/crates/proteus-core/src/app_server/startup.rs#L7-L24); только потом выставляет [http_ready](https://github.com/Proteus-harness/Proteus-core/blob/2aad0ba29311f0dbf7c107efc281abc1202ce4c4/crates/proteus-core/src/app_server/http.rs#L91-L116). Desktop затем [последовательно](https://github.com/Proteus-harness/Proteus-desktop/blob/fcc30413b12374d622abbba5a8832e10b62fdf3f/src/ui/workspace/startup.rs#L261-L306) шлёт /resume для обязательных вкладок.
- Совпадает A=последняя=сохранённая: [Core находит живой handle](https://github.com/Proteus-harness/Proteus-core/blob/2aad0ba29311f0dbf7c107efc281abc1202ce4c4/crates/proteus-core/src/app_server/http/lifecycle.rs#L167-L187); второй POST не означает второй replay истории.
- A=последняя, B=сохранённая: A успевает восстановиться, даже если B единственная нужная. Затем отдельно восстанавливается B. При дорогом cold A это лишняя работа на пути к B; конкретная экономия GUI не измерена.
- Fresh при смене конфигурации: spawned Core делает то же автоматическое открытие A, затем Desktop явным /new-session создаёт требуемую пустую сессию. Это не та же операция, что простой /resume начального handle: new-session вызывает start_session, публикующий SessionStarted.
- Attach: Desktop не владеет запуском чужого сервера; не менять его default/session. Codex-only: Core не запускается. Скрытые вкладки и неактивные chat areas уже ленивые; скрытый command target или owner активной области может действительно потребоваться. Насильный отказ от их подготовки без управления готовностью ломает контекст команд.
- У split/mixed дополнительный барьер: [Boot](https://github.com/Proteus-harness/Proteus-desktop/blob/fcc30413b12374d622abbba5a8832e10b62fdf3f/src/ui/workspace/startup.rs#L160-L204) публикуется только по окончании всех обязательных /resume, а при смешанных чатах ещё и Codex resume + model list. Ускорить показ активной истории можно отдельной готовностью выбранной вкладки; просто переставить её первой, сохранив общий барьер Boot, недостаточно. У каждой пачки/подписки должны сохраниться адрес чата, FIFO, единственный SSE и проверка поколения при смене области.

**Самая чистая архитектурная ставка:** отдельный opt-in режим только для сервера, порождённого Desktop: сначала HTTP + пространство профиля без автоматического открытия истории; для сохранённых адресов открыть ровно нужные сессии, для настоящего Fresh создать ровно одну новую с теми же lifecycle-событиями. Если требуется восстановление и ни одно подходящее сохранённое состояние не открылось, лениво применить обычный latest → fresh в прежних случаях. Не менять stdio/CLI-поведение и семантику bootstrap в подключениях к существующему серверу. Не подставлять безусловно существующий --resume-session: недоступный адрес остановит сервер до http_ready; [launch_inner](https://github.com/Proteus-harness/Proteus-core/blob/2aad0ba29311f0dbf7c107efc281abc1202ce4c4/crates/proteus-core/src/app_server.rs#L609-L626) возьмёт cwd от B, а [HttpLaunchContext](https://github.com/Proteus-harness/Proteus-core/blob/2aad0ba29311f0dbf7c107efc281abc1202ce4c4/crates/proteus-core/src/app_server/http/state.rs#L43-L63) — от выбранной сессии. Сессия другого проекта не должна менять workspace новых чатов по умолчанию. HTTP-ready не должен означать готовность данных: мерить до первого правильного B layout/предъявления, проверять checksum, а не до более раннего открытия сокета.

**Проверено:** на настоящих исходниках Desktop fcc3041 изолированно собраны unchanged startup.rs + все его native Rust tests, HTTP, SSE pump, Codex driver, tabs и контракты из desktop pin 7cbc7206. Все 15 существующих тестов startup прошли; весь headless-набор: 65 прошли, 1 ignored. Synthetic HTTP и Codex peers, без запуска GPUI и без Core в этих тестах. Отдельно 4 существующих Core lifecycle-теста прошли в ранее собранном бинарнике 8ea2cda c его совместимыми workers: same-session reuse, fresh vs latest, independent addressed sessions/immutable bootstrap, cross-project source/default. Файлы этих lifecycle-тестов, HTTP-state, HTTP-lifecycle и launch_selected не менялись между 8ea2cda и 2aad0ba; это не исполнение всего текущего Core. Затраты/миллисекунды на GUI и выгода кандидата не измерены.
