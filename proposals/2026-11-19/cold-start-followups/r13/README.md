# Proteus: следующий предел холодного открытия

База Core 2aad0ba29311f0dbf7c107efc281abc1202ce4c4. Сравниваем с ранее опубликованным патчем упаковки архива #222, который в основной Core пока не влит. В тесте используется одинаковый отдельный JSONL worker с R10, синтетический архив из пакетных Unicode-сообщений и 100 активных сообщений. Всё собрано в изолированной копии, кеш ОС не сбрасывался. Это AppServer, не замер от клика по Desktop и не замер сети.

## Изменения

1. **Компактный сертификат дописи (PrefixIdentities).** Хранит точные UUID по 16 байт, флаг явно записанной части вместе с её UUID, упорядоченные хеши истории по 32 байта, произвольные UTF-8 CallId без изменения. Транспорт JSON: фиксированные записи закодированы base64. Старый формат по-прежнему читается, неизвестные форматы отвергаются, disposable cache может перестроиться; проверка SHA, границы источника и канонический журнал неизменны.
2. **Потоковая проекция архивов из одних записей истории.** Две вместо четырёх полных проходов рендера для причинно независимой истории. Сложные Tool/Model-журналы и сценарии с зависимостями от будущих фактов остаются на общем пути. Не распространять его цифры на обычные живые сессии без отдельного замера.
3. **Process SDK перестаёт клонировать готовое Value для успешного RPC.** Отдельный патч, не включён в основной парный замер; чтобы исправление попало во внешний worker, пересобрать его с изменённым SDK. В интерфейсе ничего не меняется.

## Как отделить готовность окна от кеширования

Проба stand/ready_bound.py нужна **только для эксперимента**: после строгой проверки и полного построения проекции она не пишет производный кеш, отдаёт те же точные 50 последних сообщений и проверяет их ID, текст, дату и неизменность журнала. Она намеренно не измеряет отправку и чтение старой страницы. Не включать эту ветку в приложение как готовый production-патч.

Боевой вариант потребует одного ограниченного по ресурсам задания на ревизию и временного доступа к той же неизменяемой проекции до публикации кеша. Не допускается повторное сканирование при первом scroll/export и потеря только что выданной ревизии при немедленной дописи. Запись head остаётся последней и проверяет источник. Отмена/закрытие должны остановить работу, а с точки зрения UI нужны полный быстрый эксперимент, первый send сразу после открытия, запрос старой страницы, cache fault и concurrent resume. Фоновая работа может конкурировать за CPU/I/O; сэкономированное время на первом экране не равно уменьшению всей работы.

## Как не ухудшить архивную прокрутку

#222 ускоряет запись и диапазонные операции, но отдельное чтение одного окна может загрузить весь блок, иногда два. Нужен ограниченный повторный доступ к уже проверенному блоку в пределах явно запрошенного диапазона, а не бесконтрольный prefetch. Исследовать отдельно варианты повторного использования при неизменной ревизии и снятия старого окна узким чтением. Случайные несмежные запросы и неисправный кеш проверять отдельно. Тёплый локальный hit не доказывает, что файл на диске не был удалён/повреждён после предыдущего чтения.

## Применение и воспроизведение

Рекомендуемый порядок: взять указанную базу Core, применить уже имеющийся #222, затем проверить и применить нужные патчи из каталога patches/. SDK-патч и исправление только его тестовой фикстуры отделены от двух оптимизаций Core. В боевом коде нет параметра R13_READY_BOUND. До применения проверять git apply --check; конкретная сборка внешних модулей должна использовать корректную версию SDK. Не нужно переносить тестовые скрипты в приложение.

В stand/ есть код использованной стендовой ветки и диагностические инструменты. Создайте отдельную копию источников; instrument.py добавляет синтетический libtest, strip-tests.py сокращает регистрацию прочих тестов для памяти сборки. Для диагностического варианта примените ready_bound.py после instrument.py. Запустите ровно app_server::http::tests::session_reads::r9_real_turn_fixed_active_history; сначала обычно с fresh worker; для отдельного режима контрольной нижней оценки R13_READY_BOUND=1. В run.py подставьте полный путь к этому бинарнику, локальному reference module, JSONL worker и папке Core. Два варианта сравнивайте с одним worker и на том же CPU. summarize.py проверяет наличие успешного теста и отсутствие WriteCache в измерении без публикации. Не путать запуск с полной сборкой проекта и нативным экраном.

Проверки: 3 изолированных контроля точного индекса, 48 тестов рендера на настоящих контрактах, SDK 13 целевых тестов и 4 процесса с IPC; для интеграции использован ограниченный набор AppServer JSONL совместно с проверкой прежнего префикса журнала. Полный тестовый набор проекта, SQLite AppServer и нативный GUI не запускались. Desktop headless-тесты в дополнительной записке проверяют существующий код выбора вкладок, не производительность GUI.

## Предварительная готовность без публикации

Контроль на 125 000 строк: 7,404 и 6,001 с; свежие 50 сообщений сверены по ID, содержимому и наличию даты, префикс журнала не изменился, кеш не записывался. Это две синтетические пробы незавершённого пути, а не замена полной готовности приложения.

## Измерения

Парные прогоны на 125 000 сообщений с одним worker и вариантом #222:

| Что измеряли | A: #222 → новые патчи Core | B: #222 → новые патчи Core |
|---|---:|---:|
| Холодное prepare + launch | 9,828 → 9,344 с | 9,704 → 9,583 с |
| Первый полный send после открытия | 1,949 → 1,160 с | 2,292 → 1,676 с |
| Подготовка представления после завершения | 0,987 → 0,232 с | 1,364 → 0,681 с |
| Трафик read+write одного точного индекса после хода | 29,28 → 11,01 МБ | 29,28 → 11,01 МБ |

Холодная полная готовность от двух патчей Core почти не сдвинулась в этой выборке. При первом открытии опубликованный индекс по wire уменьшился с 14,64 до 5,51 МБ. Это размер точной производной записи, не сжатие журнала и не сквозной объём всех RPC. Значения отправки с тестовой моделью в двух парах, не p95.

Отдельный SDK A/B с одним #222 AppServer на CPU 3: холодное открытие при 125 000 11,495 → 9,992 с и 11,233 → 9,894 с. На 50 000 4,507 → 4,669 с; заметный выигрыш для этого размера не подтверждён. В отдельном микротесте сборка RPC-обёртки для ответа 2,69 МБ не дублирует дерево JSON и выдаёт те же байты. Эти компонентные/непарные результаты нельзя складывать с экономией Core.

При подтверждении приоритета я бы следующим изменением сделал связку «готовая ограниченная страница → публикация проекции по той же ревизии», а не увеличивал размер блоков. Критический критерий: первый запрос истории или send не должен целиком вернуть на передний план отложенную работу.

Отдельный пробный запуск со всеми тремя работающими оптимизациями (SDK + два Core), одинаковый CPU 2: полное открытие **9,116 с**, первый send **1,543 с**. Это один дополнительный запуск, не третья пара к каждому из отдельных контролей. С той же комбинацией в диагностическом режиме без записи кеша: подготовка 3,616 + запуск 1,089 = **4,705 с** до выдачи проверенного хвоста. Тест не открывал старую страницу, не запускал send и ничего не сохранял. Это минимальный наблюдавшийся результат, не обещание для рабочего приложения.
