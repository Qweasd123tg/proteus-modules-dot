# R18: отправка в активный чат во время холодного обхода других архивов

Отдельный локальный патч к **Proteus-modules `2c2cee47ea76df12c6e208839594e32470a2c3f1`**. Не меняет Core, подписку SSE, протокол, модель или форматы хранения. В исходный репозиторий изменения не отправлялись. Операций с настоящими архивами не было. Работа устраняет конкретную причину задержки: строгий replay каждой закрытой сессии раньше выполнялся под общим mutex всего storage-сервиса, взятым на весь `List`.

**Фактический первый текст** во время холодного списка: **2627/2563 мс → 136/156 мс**. Оба раза с патчем весь ответ пришёл раньше окончания списка; без патча первый текст пришёл после списка. Сам список не ускорился.

**Что меняется.** Сканирования `List` / `prime_catalog` одного backend сериализованы отдельным mutex. При отсутствии валидного индекса read-only replay отделён от общего mutex writer-операций; перед публикацией заново проверяются locator/incarnation, journal/WAL/session.json и bounded-инвентарь blob-файлов. Если та же сессия изменилась во время чтения, только она пересчитывается один раз под общей блокировкой. Когда инвентарь изначально непроверяем, используется защищённая ветка. Ошибочный архив пропускается обычным списком, аудит возвращает ошибку. Итог упорядочен по timestamp фактически возвращённых дескрипторов и tie-break по ключу. Одновременный список не является атомарным снимком всех сессий. Сохранение малых индексов, проверка инвентаря и исключительный повтор всё ещё могут задерживать отдельные операции.

**Как измерялось.** Не `/send-async` ACK как подмена видимого ответа. Реальный HTTP AppServer с отдельным нативным JSONL worker, активный чат A из 100 сообщений, 100 закрытых синтетических сессий по 2000 сообщений с одним compaction до 100. Копии одного seed, пустые производные индексы закрытых архивов в начале каждого опыта. Один HTTP/SSE клиент предварительно видит session snapshot; затем начинается `GET /sessions`. После фактического появления первого индекса, но до окончания обхода, другой клиент отправляет один запрос. Время первого непустого `AssistantTextDelta` и `turn_output` снимается у подписчика монотонными часами, ACK отдельно. В каждом опыте проверяются единственный persisted ModelRequest, все 100 исходных ID сообщений и частей, новый ввод, итоговые 102 записи истории A, неизменные SHA256 journal/identity каждого закрытого архива. В overlapped списке ровно 101 уникальная сессия, только A активна, закрытые summary содержат 100 сообщений с preview. Локальные reference workflow и модель; внешнего провайдера и GUI-пейнта нет. Другие задачи на хосте возможны, Linux page cache не очищался. Индексы холодные, не обязательно диск. Два перекрёстных повтора, не p95/SLA; SQLite latency не измерялась.

**Проверка патча:** 50 тестов библиотеки (JSONL и SQLite) и 2 теста реального SDK-процесса прошли, 0 падений. Один штатный ручной performance-тест помечен ignored. Новые детерминированные проверки помещают commit либо delete/recreate между подготовленным replay и публикацией: старый count не попадает в индекс, новая incarnation не принимает старую проекцию. Проверены rustfmt и чистое применение к указанной базе. Локальный коммит `d3dd2b719e33789b3c5ddec24e78d4a7afa78e2b`, не отправлен на GitHub. Полная проверка workspace, реальные GUI и удалённый провайдер не запускались.

**Воспроизведение:** применить `git apply --check cold-catalog.patch` и `git apply cold-catalog.patch` к чистому указанному Modules, собрать `cargo build --locked --release -j1 -p proteus-session-storage-module`. Контрольный worker собирается на том же коммите без патча. Рекомендуемая проверка: `cargo test --locked -j1 -p session-storage -p proteus-session-storage-module`. На стенде SDK из того же точного закреплённого коммита `9bb1e06a3cb5773b446b4ab6d5ae43d8cf04d81c` подан через локальный cargo path override; зависимость, lockfile или pin в передаваемом патче не меняются.

```sh
python3 verify.py  # проверка записанных контрольных данных
python3 stand/overlap.py --source /path/to/Proteus-core --core /path/to/proteus \
  --reference /path/to/proteus-reference-module --control /path/to/stock-worker \
  --worker /path/to/candidate-worker --out /new/results --archives 100 --pairs 2
```

Сервер Core `2aad0ba29311f0dbf7c107efc281abc1202ce4c4` (stock release); общий reference host-local. Обе сборки worker релизные; точные SHA-256 в `evidence/binaries.sha256`. Вывод тестов и отчёты каждого прогона находятся в `evidence/`.
