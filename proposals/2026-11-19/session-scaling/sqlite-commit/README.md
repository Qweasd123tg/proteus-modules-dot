# Меньше памяти при записи большого сообщения в SQLite

**Узкий кандидат на экономию RAM, не на ускорение.** У рабочего процесса SQLite одинаковый большой commit потребовал примерно на один размер пользовательского текста меньше пикового RSS. На JSONL и на обычном коротком сообщении практически ничего не изменилось. CPU в полном процессе шумит; обещать его снижение нельзя. Это локальный эксперимент, не ускорение всего Proteus. Если условием переноса является доказанное одновременное уменьшение CPU и памяти, отложить до прогона на целевой машине.

Modules [`37b3d9c4`](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/service/commits.rs#L4-L88): сначала строился raw record, затем ещё один с теми же идентификаторами, номером и временем. [Патч](commit.patch) сначала проверяет сырое содержимое hook, затем передаёт владение payload в канонизацию и заменяет входную запись её очищенной версией. Исходная запись освобождается после построения JSON value и не живёт во время последующих аллокаций. В [проверке лимита после редактирования](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/codec.rs#L42-L51) используется существующий счётчик точной длины JSON из paging: тот же сериализатор и байтовый лимит, без временного `Vec` размером с payload. Чтение inline-записей не меняется. Проверки revision и наличия id читают один и тот же `Fold` под тем же mutex; проверка владения/пути непосредственно перед durable append и отдельная проверка при поиске старого ACK сохранены. Успешная новая запись возможна только при `expected == actual`, поэтому номер `expected+1` эквивалентен прежнему `actual+1`; переполнение по-прежнему проверяется до преобразования. Итого +32/−54 строки, включая перенос неизменённого счётчика.

### Два прогона настоящего worker

Нативные оптимизированные сборки Rust 1.95.0, `-C opt-level=3`, идентичные release-зависимости из штатного Cargo.lock; Linux x86_64, AMD EPYC 9V74. Настоящий SDK-процесс с JSON-RPC по stdin/stdout, реальный SQLite WAL или JSONL и blob storage. Временные каталоги на tmpfs: **не замер задержки физического диска**. В каждой паре свежие процессы и новые сессии, одна исключённая пара разогрева, далее чередование AB/BA. Нагрузки: 20 записей по 188 байт UTF-8 или одна запись на 2 485 512 / 4 971 024 байта. Текст с кавычками, переносами строк и Unicode; в metadata синтетический маркер, он должен быть скрыт до ACK. При первом большом входе 6 пар, клиент/worker закреплены на CPU 8/7; для второго 10 пар, CPU 5/6. Для каждой серии отдельно есть контроль коротких сообщений. Это синтетические сценарии, не распределение пользовательских сессий. RSS — Linux `VmHWM` рабочего процесса до последующей контрольной проверки, а не сумма аллокаций и не весь Desktop. CPU — process CPU clock, не wall и не процент CPU всей машины.

| Backend, текст UTF-8 | Пик RSS до → после, КиБ | Медиана CPU процесса до → после, мс/commit |
|---|---:|---:|
| SQLite, 2 485 512 Б | 25 272 → 22 966 (ниже 6/6) | 46,31 → 41,92 |
| SQLite, 4 971 024 Б | 40 200 → 35 544 (ниже 10/10) | 68,34 → 76,84 |
| JSONL, 2 485 512 Б | 18 974 → 18 868 | 35,37 → 34,17 |
| JSONL, 4 971 024 Б | 31 180 → 31 104 | 80,07 → 73,39 |

Парное снижение пика SQLite: −9,0% и −11,6%. У большой SQLite-нагрузки второй серии медиана парного отношения CPU показала −7,8% (лучше 6/10), хотя отношение отдельных медиан в таблице показывает противоположное. Это **не доказательство выигрыша/нейтральности CPU**. На коротком контроле пик в обеих реализациях различался менее чем на 0,12 МиБ. Полный wall сильно гуляет от нагрузки на общую машину; исходные результаты по всем запросам сохранены в [серии 1](wire.json) и [серии 2](wire_repeat.json). Общий пик всего приложения и физический SSD не измерены.

### Паритет и воспроизведение

Библиотека: 29 штатных тестов прошли до и после, штатный ручной benchmark пропущен. 2 штатных process tests в каждой версии, в том числе потеря ACK при завершении процесса. Отдельный [граничный probe](bound_probe.rs) подтвердил принятие ровно 64 МиБ канонического JSON и прежнюю ошибку на 64 МиБ+1 в обеих версиях. На обоих backend проверены редактирование маркера до выдачи ACK, канонический sequence, timestamp, thread_id, точное содержимое payload, идентичный повтор, отклонение изменённого повтора и исходной revision, чтение тех же записей с диска заново открытым worker. Production-патч не содержит нагрузочного теста. Полный workspace, UI и реальная модель не запускались.

Воспроизвести в Linux: `sh reproduce.sh /путь/к/Proteus-modules /путь/для/результатов`. Нужны исходный commit, Rust toolchain для проекта, Python 3 и Cargo-зависимости; скрипт собирает отдельно две копии. Параметр `PROTEUS_BENCH_WORKER_CPU` опционально закрепляет worker; `taskset` — клиент. [Драйвер](wire_probe.py) также принимает два уже собранных worker. В представленном измерении для экономии времени сами crate/worker/тесты пересобраны `rustc` против готовых release-артефактов этой ревизии, а не повторной сборкой всей зависимости с нуля. Для изолированной проверки вклада счётчика нужен отдельный A/B: пакетный выигрыш не приписывается одной строке.
