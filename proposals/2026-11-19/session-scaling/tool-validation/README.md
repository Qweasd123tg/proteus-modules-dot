# Core: не хранить схемы инструментов только ради проверки ответа модели

У каждой привязанной генерации Core после shaping и hooks создаётся [CompletedMessageProgress](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/bound_model.rs#L274-L305). Его [валидатор](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/bound_model/progress.rs#L23-L48) раньше клонировал весь список ToolSpec: descriptions, обе JSON-схемы, metadata, грамматики. Но [проверке поверхности](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-contracts/src/model_standard/canonical_response.rs#L165-L225) нужны только имя и одно из трёх состояний: function, freeform или provider-hosted. Это не проверка разрешений на исполнение.

[Патч](compact-tool-validation.patch) сохраняет только эти пары в прежнем порядке, не заводит кэша и не меняет публичные методы либо wire-формат. Проверка по ссылке по-прежнему не копирует ни имён, ни самих деклараций. Правило для неизвестного имени остаётся за workflow; при одинаковых именах выбирается первая декларация, как до патча. Схемы остаются в запросе к модели; экономится **лишь независимая копия для проверки ответа**. Изменено +35/−7 строк production в одном файле: это упрощение сохраняемых данных, не сокращение числа строк. Ранее в Core уже убрали удержание всей истории этим валидатором; здесь сокращаются сами данные о tools.

| Список в запросе | Аллокаций до → после | Живой Rust heap одного готового snapshot, Б | CPU на построение + освобождение, мкс |
|---|---:|---:|---:|
| Пустой | 0 → 0 | 0 → 0 | 0,010 → 0,009 |
| Только поставляемый read_file | 58 → 2 | 5 113 → 41 | 1,233 → 0,026 |
| 7 поставляемых file-tools + 2 git-tools | 466 → 10 | 40 580 → 371 | 18,595 → 0,157 |
| Стресс-контроль: 1 декларация с 256 КиБ схемы и 256 КиБ грамматики | 10 → 2 | 524 981 → 42 | 108,892 → 0,025 |

Девять определений извлечены из исходников поставляемых модулей [file-tools](https://github.com/Proteus-harness/Proteus-modules/tree/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/tool/file-tools/src) и [git-tools](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/tool/git-tools/src/lib.rs), не из пользовательской телеметрии и не из текущей динамической выборки tools в реальном сеансе. Последняя строка искусственная. Это микрозамер CPU потока, не скорость модели, не задержка чата и не изменение RSS. Построение самого запроса, RPC, получение ответа и другие владельцы ToolSpec исключены.

## Как проверено

- Оба измерительных бинарника на вариант компилируют сам файл canonical_response.rs и используют те же release-зависимости Cargo и неизменённые canonical DTO. Один бинарник считает системные запросы Rust-аллокатору (без измерения времени), другой без счётчика читает Linux CLOCK_THREAD_CPUTIME_ID и wall clock. Счётчик включает realloc по запрошенному новому размеру; live отражает логический размер живущих аллокаций без внутренних накладных расходов. В случаях выше не было освобождений до возврата snapshot: peak и сумма запросов совпали с live. Вход подготовлен заранее.
- A/B/B/A, два отдельных процесса на каждую версию, в каждом один разогрев и восемь измерительных батчей. По 4096 построений + освобождений на батч (256 для стресс-контроля). В таблице медианы времени одного вызова по 16 батчам. Сырые результаты и разбор в [results.json](results.json), файлах *-heap.txt, *-time-*.txt и [summarize.py](summarize.py).
- В каждом измерительном процессе десять сочетаний: оба типа вызова для первой из двух одноимённых деклараций, provider-hosted, workflow-function, strict-function и неизвестного имени. Проверены borrowed, owned, повторный into_owned и clone последнего, чёткие тексты ошибок. Без вызовов поставщика и инструментов. Отдельно на исходной и изменённой версии прошли все 153 штатных lib-теста contracts ([до](base-contracts-tests.txt), [после](candidate-contracts-tests.txt)); вся рабочая область и production с внешней моделью не запускались.
- Проверено точное наложение на git blob 1ce6ab1ee8a09ff1017c5e7e6e34e332252d06f0; после патча e9ac4799a4350174ccbd97fe5a225d27068e1225. Публичный main во время проверки возвращал тот же исходный blob.

Для воспроизведения: Linux x86_64, Rust 1.95.0, Python 3, git, tar, две локальные копии репозиториев с указанными ревизиями. Скрипт работает в новой папке, не меняя исходные checkout:

```bash
bash reproduce.sh /path/to/Proteus-core /path/to/Proteus-modules ./new-results
```

При наличии точных собранных зависимостей той же версии четвёртым параметром можно передать каталог release/deps (по одному rlib для proteus_contracts, serde и serde_json); именно этот режим проверен в данной среде. Для отдельной проверки полного набора тестов библиотеки выполнить `cargo test --release --locked -p proteus-contracts --lib` на базовом и изменённом исходниках.
