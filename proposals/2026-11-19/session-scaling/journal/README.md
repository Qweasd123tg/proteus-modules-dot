В pin Core `8ea2cdaf` вызов [runs.rs:205](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/runs.rs#L195-L213) держит резерв текущего хода, пока не закончит проекцию. [project_read_view](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/session_store/remote/view/incremental.rs#L17-L45) на удачном инкрементальном пути дописывает строки дисплея, но сперва [RemoteValidatedRead::open_with_cursor](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/session_store/remote/snapshot.rs#L188-L239) строит полное каноническое состояние из журнала. Проверка независимости новых display-строк [перебирает префикс ещё раз](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/transcript/journal/append.rs#L28-L52). На стороне storage [проверка префикса](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/snapshot.rs#L81-L105) тоже декодирует записи для проверки ревизии. Это отдельный путь от SSE и Markdown.
 
Порог в 50 строк ограничивает возвращаемую страницу, не работу над журналом. С ростом журнала при фиксированном новом хвосте работа закрытия растёт как минимум линейно по записи; сумма таких работ за N равноразмерных ходов квадратична в N. Это граница по объёму работы, не обещание числа по времени или памяти.

**Следующий эксперимент:** одно проверенное состояние, привязанное к точному идентификатору префикса и версии источника, плюс применение короткого хвоста в Core и storage. Сначала проверить, можно ли переиспользовать уже принадлежащее runtime состояние без новой полной копии. Не принимать произвольный cursor за доказательство. После холодного открытия, неподтверждённой замены, нарушения последовательности, compaction или утраты доказательства оставить полный проверенный путь. Проверки: чистый append, rewrite/repair, неверная ревизия, перезапуск модуля, совпадение видимых строк, расход памяти на сессиях с закрытыми старыми ходами.

`probe.rs` измеряет нативную проекцию через реальный JSONL worker, не настоящий ответ модели; это отдельный компонентный стенд.

## Измерение штатной проекции после дописывания

Один и тот же немногобайтовый новый текст после тёплого baseline, пять дописываний на каждую длину; в начале синтетические строки содержат около 720 байт, чередуются user/assistant, одна JSONL-запись на строку. Измерялся только `project_completed_transcript`: подготовка истории и собственно append не включены. Реальные pinned Core и отдельный release JSONL worker из Modules pin. Временные логи показывают объём реального валидирующего прохода, а не экстраполяцию. На каждом шаге совпали ожидаемые число и последняя строка; на каждом тёплом шаге работало подтверждение префикса. Компонентный Rust release-стенд, без модели, сетевого ожидания и Desktop. Полная сборка тестового бинаря Cargo была остановлена системой (SIGKILL); запущен фокусный test binary со штатной release-оптимизацией и ранее собранными зависимостями, не остальные тесты Core.
