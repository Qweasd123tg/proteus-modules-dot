# Desktop: поиск знакомых строк при подгрузке архива вперёд

**Найденное лишнее действие:** внутри `Transcript::append_page` для каждой строки входящей страницы Desktop заново вычисляет identity старых и новой строк по всему доступному live-хвосту. Когда identity — ID инструмента или дочернего агента, это настоящий `String::clone`, до трёх копий на сравнение. Это подбор identity уже десериализованных строк на UI-стороне, **не** повторный разбор JSON/Markdown и не новый вызов LLM.

[Desktop `210cc9f`: исходный цикл](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/transcript/mod.rs#L154-L176) · [конструктор identity](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/transcript/mod.rs#L522-L541) · [вызов при направлении Newer](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/history.rs#L257-L301). В обычном live-чате, при чтении отдельного SSE-события и при подгрузке назад этот метод не вызывается. Статический кандидат [index-history.patch](index-history.patch) только для Desktop: один временный индекс на операцию. Индекс хранит ссылки на строки, владеет строковыми ID и исчезает сразу. При дубликате, как прежде, выигрывает первая запись в live-хвосте. Порядок и число новых строк не меняются, никакого постоянного кеша. Среднее количество формирований identity стало O(live + page) вместо O(live × page).

**Только процессор и оборот выделений:** 50 disjoint старых и 50 новых tool-строк со строковыми ID по 36 байт, начальная архивная страница на 50 строк: 7 551 → 156 запросов к Rust allocator, 333 200 → 71 964 Б их суммарного объёма на один вызов. Измеренный максимум живых запрошенных байтов **над уровнем непосредственно до вызова** при этом **растёт**: 30 972 → 35 376 Б; итоговая разница к тому же уровню одинакова: −1 100 Б. Это не сокращение пика RAM. Для смешанной страницы со строками четырёх типов, наполовину пересекающейся с хвостом: 3 191 → 107 запросов, 176 240 → 70 200 Б суммарно; локальный пик 30 844 → 34 348 Б. Для 50 совпадающих UUID-сообщений, где ID и так не клонировались, 51 → 56 запросов, 63 200 → 68 364 Б суммарно.

Отдельная оптимизированная сборка **без** счётчика выделений: CPU текущего потока, на одну страницу, медиана каждой из четырёх серий (см. [cpu.txt](cpu.txt)). Для раздельных tool-страниц 202–298 → 27–50 мкс, для смешанной 105–149 → 22–29 мкс. На 50 совпадающих обычных сообщениях 9,8–14,5 → 11,1–13,3 мкс: устойчивого выигрыша нет. Не время от нажатия до экрана. Если live-хвост намного больше входящей страницы и совпадение в начале, новый индекс может быть невыгоден: на практике следует сверить распределение размеров страниц/хвоста до переноса. Отдельная проба простого линейного сканирования с заимствованием ID снизила суммарные выделения ещё больше, но регулярно проигрывала UUID-контролю; не выдаём её за безусловную замену.

**Проверки:** по 40 штатных тестов реального модуля transcript и 1 дополнительная проверка на обеих версиях: совпали дубликаты (первая в append / последняя и только один раз в reset), разграничение tool/subagent и role+UUID, анонимные строки, приоритет message_id, ключ, дата, повторное использование Arc для равного текста и замена для изменившегося. [Результаты stock](base/tests.txt) и [patch](index/tests.txt). Закреплённый checkout клиентского DTO `105f8253` сравнен рекурсивно с исходниками предварительно собранного `proteus-contracts` из runtime Core `8ea2cdaf`, каталоги крейта побайтово одинаковы. Настоящее окно, ввод/вывод HTTP, UI-кадр, RSS/PSS и сборка приложения целиком в этом измерении не участвовали.

**Воспроизведение (Linux x86-64, Rust 1.95.0).** Запустить `bash prepare.sh /path/to/Proteus-desktop /tmp/new-page-test`. Собрать зависимости: в закреплённом Core или чистом crate, зависящем от закреплённого proteus-contracts плюс serde_json и uuid с v4, подготовить release-артефакты Cargo. В `DEPS` указать каталог согласованных release/deps с единственным rlib каждого из трёх крейтов. Выбрать `RUSTC` того же toolchain. Выполнить три команды, напечатанные prepare.sh. Этот путь позволяет проверять сам штатный transcript-модуль без оконного движка. Инструментальная серия считает alloc, alloc_zeroed и новые размеры realloc (не размер копирования), отдельно — пиковую/конечную сумму живых запросов; освобождаемые входные данные входили в исходный уровень. Независимая серия без подмены global allocator меряет thread CPU Linux и wall-clock; в четырёх парных запусках на версию, в порядке ABBA BAAB, по 8 пакетов из 64 операций (нулевой прогрев отброшен), подготовка/проверка/освобождение результатов вне часов. Сырые CSV без заголовков: scenario, rep, wall_ns/op, alloc_calls/op, requested_B/op, cpu_ns/op, peak_live_delta_B, end_live_delta_B. Последние два поля значимы только в отдельном alloc-процессе при batch=1. Сценарии reset — неизменённый контроль, различия времени там не приписывать исправлению.
