# Codex Desktop: не считать старые аргументы инструментов по каждой дельте

В пределах последних **50 строк / 8 МиБ** на каждой принятой дельте текста, рассуждения или вывода инструмента Desktop заново оценивает ОЗУ *всех* строк. Даже если прибавились только 16 байт текущего ответа, он рекурсивно обходит каждый объект и массив предыдущих аргументов. Это отдельная проблема Codex-коннектора Desktop: в Core ответ уже группируется в совместимые события, и нет свидетельства, что Core перечитывает весь **сохранённый** диалог по каждому токену. Дельта не обязательно равна токену.

[Путь Desktop](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/codex/mod.rs#L139-L156): собирается пачка до 128 событий, но каждое вызывается отдельно. [После принятого изменения](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/codex/mod.rs#L342-L366) вызывается [проверка бюджета](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/transcript/external.rs#L192-L209), которая [считает размеры JSON по дереву](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/transcript/cache.rs#L34-L55). Это не повторный JSON-парсинг или Markdown. И нет сканирования самих байтов длинного tool-result: для строки берётся len; дорого большое число узлов arguments.

## Один скаляр вместо повторного обхода

[Кандидат](codex-tail.patch): после штатной проверки сохранить нижнюю границу свободных байтов в живой привязке Codex. Изменение *существующей* строки дельтой увеличивает учитываемый размер не более чем на число байтов дельты: меняется только длина текста либо результата. Когда места и числа строк заведомо хватает, вычесть эту величину; иначе выполнить прежний точный пересчёт. Для новой строки и канонических upsert полный пересчёт сохранён. Это не дополнительный кеш строк и не второй владелец истории. Даже когда дельта обрезается по UTF-8 или по лимиту строки, списываемая верхняя граница консервативна.

Границы: локальный optimistic send до входа через общий обработчик обнуляет запас; неудавшаяся отправка только убирает строку. Замороженное окно истории не пользуется этим полем. Не меняются политика вытеснения по каждому событию, идентификаторы, порядок, правила для одной строки сверх лимита и допустимый размер ответа. Не откладывать само вытеснение до конца пачки: это было бы другой семантикой. Нельзя расширять fast path на произвольное изменение строки. Если в будущем появятся другие пути увеличения live transcript, им надо либо войти через тот же механизм, либо сбросить запас.

## Что замерено

512 дельт по 16 байт, итоговый ответ 8 КиБ; число и структура ранее законченных инструментов различаются. Синтетические dynamicToolCall имеют реальные проектируемые аргументы: массив из F объектов с тремя полями (путь, номер строки, bool). Значения укладываются в лимит Codex-проекции. Время измеряется **после** инициализации посева, рукопожатия процесса и начальной установки бюджета. Вывод сверяется по размеру и количеству вытесненных строк. В расписании с процессом реальный транспорт proteus-codex-client читает stdout JSONL контролируемого дочернего процесса, после чего настоящий Desktop Router пропускает каждое событие через ограниченный канал, настоящий reducer меняет transcript, затем реальный контроль бюджета применяется по тем же условиям, что в UI. В этом стенде доставка сериализована на стороне потребителя, пакеты источника по 32. Окно, перерисовка и настоящий внешний сервис/модель не запускались. Это время **обработки пачки**, не время между токенами у модели и не время рисования чата.

AB/BA менялись по паре и конфигурации; Linux, Rust 1.95.0, release -O, процесс и его дочерний процесс на одном CPU. [Все 180 наблюдений](raw.csv), [медианы и min/max](series.txt). В серии с транспортом кандидат был быстрее в 4/9 пустых, 5/9 без заполнения списка файлов, 7/9 при 20×32 и 9/9 в двух более тяжёлых случаях. На простых чатах выигрыша по этому механизму не ожидается. Это не статистика реальных сессий; объём учёта Desktop не равен RSS/PSS. Порог для переноса: улучшение на реальном целевом workload, а не одна цифра из верхней строки нагрузки.

На втором закреплённом CPU, после **чистой** release-сборки из приложенного lock независимым скриптом, медианы с процессом: пусто 2,321 → 2,735 мс; 20×0: 2,575 → 2,373; 20×32: **9,364 → 3,123**; 20×256: **54,709 → 2,361**; 49×256: **90,113 → 1,871 мс**. Сильный разброс абсолютного времени: называйте сценарий и обе серии, не обещайте «ускорение интерфейса в N раз». На всех 180 A/B-парах обеих серий совпали логические объёмы до/после, число оставшихся и вытесненных строк и размер финального текста; оба применимых набора, 55/55 до и 56/56 после, повторно прошли. [Ещё 180 наблюдений](repeat.csv), [сводка](repeat.txt).

Для 49×256 штатный обход аргументов и метаданных за 512 дельт посетит 512×49×(3+4×256) = **25 765 376** JSON-узлов (выведено из формы входа и исходника; не таймер и не измерение RSS). После первоначального подсчёта запас у кандидата больше 8 КиБ, на всём стриме дополнительных обходов 0. Остальная работа не исчезает: выделение текста, поиск строки, маршрутизация, декодирование дельт.

## Проверка

Пин Desktop 210cc9f274ffe40533b390a0d9e940f251a9fa22, DTO Core 105f8253f43a62b0f5025d99e2d4ccdcb322e34c. git apply --check проходит на Desktop-пине. [55/55 штатных тестов этих модулей](stock-test-latest.log), [56/56 с дифференциальной проверкой](after-test-latest.log), включая диапазон из пяти бюджетов (от нуля), создание и замену строк, отсечение, переиспользование ключей, текстовые и tool-output дельты. Полная GUI-сборка и тесты приложения не выполнены; production reducer/transport тестировались непосредственно, а место его вызова в Chat проверялось по исходнику. Источников, аккаунтов и секретов реальных сессий не использовалось.

Для повтора из чистой рабочей директории, с отдельным новым каталогом результатов и закреплённым CPU: `CPU=6 sh reproduce.sh /path/to/Proteus-desktop /tmp/fresh-tail-output`. Скрипт читает файлы по закреплённому коммиту, работает с копиями, собирает release в новом каталоге и использует приложенный Cargo.lock. Нужны git, Rust 1.95, Python 3, taskset; без переменной CPU берётся первый разрешённый процессору номер. При холодном Cargo-кеше нужны зависимости из закреплённых источников.
