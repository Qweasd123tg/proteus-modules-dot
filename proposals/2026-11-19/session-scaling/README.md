# Proteus: стоимость длинной сессии и потокового вывода

Пины подтверждены по upstream main: Core `8ea2cdaf`, Desktop `210cc9f`, Modules `37b3d9c`, Extensions `a35cea08`. Стенд Codex Desktop берёт DTO из пина его lockfile (см. локальный README). Данные в стендах синтетические, кроме схем поставляемых инструментов. Патчи ниже не установлены в приложения. Полный нативный GUI не запускался: в Linux-стенде нет системного fontconfig/freetype и работающего дисплея. Не складывать микросекунды, миллисекунды и байты разных экспериментов в общий процент.

## Порядок переноса

1. [Поток Codex Desktop: не пересчитывать весь вес хвоста на каждом фрагменте](codex-tail/README.md). Кандидат для нативного QA. На 20 вызовах × 256 элементов результаты двух серий реального JSONL: 131,7 → 2,7 мс и 54,7 → 2,4 мс на 512 дельт. При 49 вызовах × 256: 290,8 → 2,5 и 90,1 → 1,9 мс. Нулевой контроль не быстрее; эти замеры без GPUI. Счётчик хранит нижнюю границу остатка уже действующего лимита, не добавляет копию либо кеш истории. На сомнительной мутации пересчитывается прежним методом.
2. [Валидатор ответа Core: имена и форма вызова вместо копии спецификаций](tool-validation/README.md). Кандидат с независимой матрицей проверок: 9 поставляемых инструментов, живые байты snapshot 40 580 → 371 на один активный экземпляр; около 18,6 → 0,16 мкс CPU на создать/удалить. Весь model request и его декларации остаются прежними.
3. [Закрытие хода: полный journal replay под формально инкрементальной проекцией](journal/README.md). Два профиля реальной проекции после дописывания одной короткой строки: медианы 9,8–11,6 мс на пустой истории, 233–254 мс на 512, 2,05–2,44 с на 2 048 старых сообщениях. Это исходный уровень стенда, не выигрыш. Устранять нужно повторное чтение доказанно неизменного префикса, не строгую валидацию.

4. [Транспорт архива: одна и та же полная карта страниц на каждой странице](history-wire/README.md). На 20 000 строк и 400 запросов стенд повторно передал между процессами не менее 32,6 МБ manifest JSON при 5,49 МБ HTTP-ответов. На 50 000 строк и 1 000 запросов: 201,6 МБ метаданных при 13,75 МБ HTTP-ответов, две серии по 9,76 и 10,61 с на всю выгрузку. Это измеренный исходный уровень, не ускорение и не время открытия чата. Тела страниц ограничены 50 строками. Стоит проверить чтение компактного индекса или индекс, привязанный к текущей ревизии, прежде чем менять формат.

## Локальные кандидаты с обменом ресурсов

- [Merge страниц Desktop](history-merge/README.md): профиль с двумя непересекающимися страницами по 50 tool-строк: CPU 202–298 → 27–50 мкс и вызовы аллокатора 7 551 → 156; пиковая аллокация этой операции выросла на 4,4 КБ. На рядовых UUID-строках устойчивого ускорения нет.
- [Files SDK](extension-files/README.md): убрать два клона JSON-дерева. На 128 файлах медиана построения+освобождения 4,21 → 2,18 мс, временный пик 1,97 → 1,03 МБ; готовый объект занимает на 5,7% больше. 16 сообщений Files совпали байт-в-байт; отдельный штатный тест Mermaid одинаково падает до и после.
- [SQLite commit](sqlite-commit/README.md): один объект записи вместо двух. Дополнительный выигрыш в пике RSS worker 2,25–4,55 МиБ на сообщениях 2,49–4,97 МБ в 16/16 пар. JSONL не выиграл, ускорение CPU не доказано. Не переносить как общее ускорение commit.
