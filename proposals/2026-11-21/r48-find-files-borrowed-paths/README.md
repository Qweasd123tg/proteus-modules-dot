# find_files: собрать результат без копии каждой строки ripgrep

База: **Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51**. Локальный commit `c22936d0204006593856d175466bffb5e42e0436`. Меняется только `tool/file-tools/src/find.rs`, не `list_dir` и не `edit_file`.

Прежний рендер создавал новую строку для каждого результата, даже если начального `./` не было, и затем склеивал строки. Новый код один раз резервирует итоговый буфер из суммы длин уже захваченных UTF-8-срезов после снятия префикса и одного LF между строками; резервирование не больше объёма старого склеенного текста. По мере добавления исходные строки освобождаются. Это не изменение лимита захвата: прежняя граница до 1 000 записей остаётся; отдельный лимит длины строки патч не вводит.

Не меняются поиск, порядок результатов, пути, glob/exclude, передача аргументов и рабочая папка, лимиты/таймаут и ошибки дочернего процесса, разделение строк `BufRead::lines` и сериализация ответа. Снимается ровно один начальный `./`. Один присутствующий результат, ставший пустой строкой, не считается отсутствием результатов; пустой список по-прежнему отображается как `(no matches)`.

## Измерение

Linux x86-64, rustc 1.95.0, ripgrep 15.2.0; обе версии собраны `cargo test --locked --release`. Замеряется обычный вызов `FindFilesTool::invoke_json` с настоящим дочерним `rg --files`, отдельный тестовый процесс на каждый вызов. Один поток в конфигурации ripgrep фиксирует порядок при подсчёте; код запуска и argv модуля не меняются между версиями. Считаются размеры запросов к Rust-аллокатору внутри вызова, включая потоки захвата, но исключая внешний процесс rg. При realloc засчитывается весь запрошенный размер независимо от выделения на месте. Это не RSS, не пиковая память и не оценка скопированных байтов.

Два независимых прогона: в каждом одна незачётная пара и девять измеренных пар на сценарий, порядок версий чередуется. Вот медианы:

| Сценарий | Запрошенные байты, прогон 1: до → после | Прогон 2 | Вызовы alloc/realloc, прогон 1 / 2 |
|---|---:|---:|---:|
| 1 000 длинных путей (лимит из 1 130 файлов) | 3 832 098 → 3 284 064 | 3 824 552 → 3 283 428 | 2 132 → 1 114 / 2 113 → 1 112 |
| 100 путей, лимит по умолчанию | 361 895 → 309 900 | 362 041 → 310 046 | 300 → 200 / 302 → 202 |
| Три пути в указанной папке | 16 015 → 15 975 | 16 015 → 15 975 | 109 → 106 / 109 → 106 |

На 1 000 путях объём запросов к аллокатору уменьшился на 541–548 тыс. байт (14,1–14,3%). **Ускорения нет:** медианы полного большого вызова 11,83 → 12,32 и 11,69 → 11,93 мс. Экономия относится к запросам памяти, а не к времени, которое тратит внешний поиск.

Во всех семи сценариях ответ источника и кандидата совпал побайтно, включая метаданные. Независимый вызов ripgrep подтвердил порядок, UTF-8 и разделители, glob/exclude, ограничения 100/1 000 и флаг обрезки при точном лимите; в набор вошли имена с CR/LF, Unicode и отсутствие совпадений. Реальное имя с невалидным UTF-8 сохранило ошибку. В опубликованных хешах временный путь заменён на маркер **только после** сравнения полных исходных JSON-байтов. Сырые выборки в `probe.log` и `recheck.log`.
