# Storage: реже писать временное представление больших JSONL-журналов

При холодном OpenDisplaySnapshot worker строго проверяет весь
канонический журнал и формирует временный display-файл. Для JSONL с
зафиксированным размером от 1 МиБ, если остаток staging-бюджета не
меньше 64 КиБ, временный writer теперь накапливает до 64 КиБ, а не
использует прежний буфер по умолчанию. На Linux в проверке это до
56 КиБ дополнительных временных байт только на один активный
захват под блокировкой State. Буфер освобождается на finish и не
увеличивает размер открытого снимка. Малые JSONL, SQLite и готовый
view не получают новый буфер.

Данные, SHA и порядок валидации не меняются. Остались прежними
ограничения на весь stage и отдельную запись, EOF/cursor, blob,
сверка префикса, публикация каталога и SDK. Принятые writer
байты всё так же должны пройти финальный flush до доступности
display reader. Первая внутренняя ошибка записи может обнаружиться
позже из-за накопления, но отказ push или flush по-прежнему
отключает staging и выдаёт пустую проекцию; неполный файл не
публикуется. Канонические записи, владение и durable sync не тронуты.

## Измерение

Это счётчики реальных вызовов записи Linux, **не замер задержки,
RSS или числа аппаратных операций диска**. Один и тот же release
worker переключал исходный и новый буфер, в двух парах с обратным
порядком. Из /proc/self/io берутся syscw и wchar отдельно внутри
потока staging и во время итогового flush. Запись каталога,
процессный ответ и запись отчёта вне интервалов. Сумма wchar
совпала с полным размером stage. Отдельная калибровка без SDK:
одна реальная запись дала ровно +1 syscw и её точный объём.

| Приватная валидная сессия | Системных вызовов записи до → после | Записано в stage |
| --- | ---: | ---: |
| JSONL, 125 000 сообщений / 1 251 запись | 6 442 → 803 (−87,5%) | 52 568 667 B |
| Малый JSONL, 1 000 сообщений / 11 записей | 57 → 57 | 461 033 B |
| SQLite, 1 000 сообщений / 20 записей | 46 → 46 | 372 072 B |

У каждого варианта остаётся один финальный вызов; у большого
JSONL его объём меняется с 6 878 до 36 999 B, но общий объём
байтов равен. Артефакты синтетические, записаны реальным stock
worker через стандартный контракт.

## Варианты и проверка

- [candidate.patch](candidate.patch): точный Modules
  9469e3b12529d08b1f4a76882693e2065e842c51, Core SDK
  0c1b7572313230e5d123e95c722e1258a2e9ecd6.
- [candidate-after-362.patch](candidate-after-362.patch): применять
  **вместо**, а не после первого варианта, на текущем стеке
  #331/#348/#362. #362 уже изменил соседний контекст чтения
  канонической строки; Writer-изменение то же. Отдельный locked
  release-воркер композиции подтвердил те же счётчики, контрольные
  размеры и SDK-байты на всех трёх входах. Это одна оптимизация.
- Native exact-main locked release: 65 тестов прошло, 0 неудач,
  один прежний ignored. Проверены размер буферов на пороге,
  одинаковые готовые байты, исчерпание бюджета и корректный отказ
  при записи в обычный тестовый файл, открытый только для чтения.
  Первоначальная сырая проверка читала только что завершённый файл
  на EOF; в тесте добавлена перемотка, как и при первой штатной
  странице. Production-порядок чтения не менялся.
- На каждой смеси оригинальный и измерительные worker дали один
  и тот же raw SDK OpenDisplaySnapshot и все ReadDisplayRecords
  ответы (20/1/1 страниц). Заменялся только случайный 36-байтный
  snapshot ID. Порядок sequence, revision, полный SHA и байты
  канонического журнала неизменны. Платформы за пределами Linux,
  workspace-матрица и сквозной latency не замерялись.
