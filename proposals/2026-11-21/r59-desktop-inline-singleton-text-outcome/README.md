# Desktop: результат одиночного текстового события без вектора на куче

Когда из живого потока чата приходит одно текстовое событие (или после проверки очереди осталось одно), транскрипт уже обрабатывает его отдельно. Раньше итоговый `Change` сохранялся в одноэлементный `Vec` перед тем, как чат читал его для рендера и оповещения подписчиков. Теперь итог хранится прямо в `TextRunOutcome`. Для серии событий остаётся прежний вектор.

Это не новый способ группировать поступающие события. Не изменились проверка порядка, фильтрация, границы серии, байтовые UTF-8 смещения, отметки времени, видимость, последовательность событий для подписчиков и правило выбора одного итогового изменения для лейаута.

База: [Proteus-desktop b6a7ec2d](https://github.com/Proteus-harness/Proteus-desktop/commit/b6a7ec2d8d7e486c8aba01291aa8c89774c4cded). SHA-256 патча: `3b3eb035ebd4ef03453ad7bd37159b9932caf9b7a060e313f748cb8f044cc10f`.

## Проверка

Взяты точные исходники транскрипта и типов Codex из Git-архива. Сверено **125** идентичностей зависимостей (имя, версия, источник, контрольная сумма), включая закреплённый `proteus-contracts`. В самой базе штатный проверочный набор включает 387 072 сопоставления UTF-8 операций и разбиений с поштучным reducer. Узкий стенд дополнительно сравнивает следы из двух отдельно собранных вариантов: начало и обновление строки, невалидные смещения, отсеивание событий до одного/нуля, события чужого потока, состояние строк и сигналы подписчикам и лейауту.

Оба исходных файла совпадают с базой в сводном снимке M100; `git apply --check` прошёл без его изменения. Файлы после применения #345 (ветки боковой панели), #351 (JSON дочерней сессии) и этой правки в обоих порядках побайтно одинаковы. Прямое и обратное применение, `git diff --check`, rustfmt прошли.

**41/41** штатных тестов до изменения, **42/42** после. Стенд дал побайтно одинаковые результаты в **46 656** сценариях.

## Запросы аллокатору на одно применение серии

| Сценарий | Запросы, до → после | Запрошенные байты, до → после |
|---|---:|---:|
| Одно событие начинает строку | 3 → 2 | 2 520 → 2 488 |
| Одно событие обновляет строку | 3 → 2 | 62 → 30 |
| Одно пустое событие без строки | 1 → 0 | 32 → 0 |
| Одно событие чужого потока | 1 → 0 | 32 → 0 |
| После отбора осталось одно событие | 3 → 2 | 2 520 → 2 488 |
| После отбора ничего не осталось | 0 → 0 | 0 → 0 |
| Четыре принятых события | 4 → 4 | 167 → 167 |
| Четыре события чужого потока | 1 → 1 | 128 → 128 |

На стенде Linux x86-64 сам краткоживущий объект результата стал на 8 байт больше (32 → 40). Результат одиночного события перестал отдельно запрашивать 32 байта на куче. Счётчик суммирует `alloc` и `realloc` только вокруг `Transcript::apply_text_run`; создание входной серии и отрисовка не входят в измерение. Пиковая память, RSS и время не измерялись.

## Как повторить

`git apply --check /путь/source.patch` из checkout базы. Узкая проверка: `bash verify.sh /путь/Proteus-desktop`. Нужны Bash, Git, Python 3.11+, Rust 1.95 с rustfmt и подготовленный локальный Cargo-кэш для `harness.lock`. Отдельный стенд собирается без сети в один Cargo job. См. [evidence.log](evidence.log). Полная нативная сборка и окно GPUI не проверялись.
