# SQLite ReadRecords: не перечитывать префикс при переходе к проверенной странице

[Патч](candidate.patch) для [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). Меняет только repositioning обычного `ReadRecords` для SQLite. На запросе к большой позиции раньше читались и декодировались все предыдущие строки, даже если в той же транзакции они уже были полностью проверены. Теперь после такой проверки запрос сразу использует штатное условие `sequence > after` и фиксированный верхний предел снимка.

**Доказательство не берётся из sidecar.** `SnapshotState` сохраняет полный semantic fold и проверку ревизии до выдачи записей для provisional snapshot. Дополнительно отдельный SQLite page cursor допускается только после того, как этот экземпляр read transaction завершил обычный полный проход и проверил точный EOF SHA-256. Кешированный descriptor сам по себе не разрешает seek, в том числе подтверждённый head writer из другого reader. Если proof отсутствует, транзакция уже завершилась, физическую таблицу не удалось подтвердить или запрошена нулевая позиция, переустановка использует прежний reset. Уже активный быстрый курсор отказывается выдавать строки при завершении исходной транзакции. Канонический read cursor и его hash state не переносятся и не подменяются.

Каждая выдаваемая запись проходит прежний decode, лимит размера, проверки sequence/session/schema и общий byte budget страниц. Состояние pending для лишней записи осталось общим, как и логика retry/invalid cursor. Актуальные изменения WAL не расширяют зафиксированный набор строк. JSONL, DisplayRecords, формат v1, сравнение префиксов и cold catalog #321 не меняются. Не оценивалось время запуска Desktop или первого отображения.

## Состав

- Основной патч накладывается только на указанную чистую базу. [#246](https://github.com/Qweasd123tg/proteus-modules-dot/pull/246) меняет BLOB decoder, [#253](https://github.com/Qweasd123tg/proteus-modules-dot/pull/253) меняет соседний SHA helper, [#321](https://github.com/Qweasd123tg/proteus-modules-dot/pull/321) меняет начало SQLite cursor для другого запроса. Это точки технического наложения, а не один и тот же эффект.
- Для стека `#246 → #253` используйте [вариант #321 поверх этих двух](321-after-246-253.patch) вместо обычного патча #321; после него [вариант R51 для этого стека](after-246-253-321.patch) **вместо** `candidate.patch`. Заимствованный BLOB #246 и форматирование SHA #253 в стеке сохранены. [Чистое наложение](composition.log) воспроизводит то же дерево; дополнительные варианты здесь приведены как source composition, не как новый выпуск или изменение milestone. SQLite выигрыш R51 измерялся на чистом base A/B, независимо от ранее опубликованных изменений.

## Проверки и измерение

- Свежая read-only транзакция с одной подсказкой writer, но без своего EOF: ожидаемые **28** декодирований для `after=26, limit=2`; оптимизация не включается. Первый глубокий запрос из provisional дискового индекса с 32 записями: обязательные **32** декодирования в Fold, затем **2** строки страницы. Четыре последующие страницы декодируют **7** строк суммарно. Обычный Commit между запросами оставляет старый snapshot на ревизии 32; после переходов назад, повтора и текущего чтения разговор/точные записи те же.
- С лимитом 4 MiB три отдельные 2 MiB записи отдаются без потерь/повторов и с тремя декодированиями. Новый локальный тест в самый момент продвижения быстрого cursor один раз возвращает обычный I/O `Interrupted`: retry выдаёт ту же страницу; SHA и отдельный prefix fingerprint не зависят от быстрого курсора, последующий обычный fold даёт прежнюю ревизию и SHA. Канонический журнал при инъекции не меняется.
- Существующий тест terminal page для SQLite теперь ожидает **9** вместо **16** декодирований (полный Fold из 8 и одна выдаваемая строка). JSONL по-прежнему **8**; прежние проверки точной страницы, курсора и SHA сохранены.
- Linux x86-64, Rust 1.95.0. [66 модульных и 2 процессных теста](native-release.log) прошли, один штатный ручной тест пропущен; [6 SQLite-тестов](decode-counts.log) заново запущены из того же бинарника со счётчиками. [Первый прогон](prior-counter.log) выявил единственное устаревшее ожидание 16 вместо 9; после точечной правки assertion и README production worker совпал с benchmark побайтно. Весь workspace и Windows не запускались.

Две независимые серии свежих release SDK workers на одном синтетическом дереве для каждой пары, **9 + 7** пар на сценарий после разогрева, CPU 6 и 7. Файловый кеш ОС не очищали. Замер от отправки `ReadRecords` до разобранного ответа, не включает предварительный `OpenSnapshot` и засев журнала. Первый запрос из provisional дискового индекса **всё равно полностью валидирует** зафиксированный префикс до выдачи строк. Пробы сверяют весь результат, запись, ревизию, fingerprint, границу, порядок и v1 побайтно; единственный нормализованный атрибут между процессами — заведомо случайный идентификатор открытого handle, который отдельно сравнивался с исходным запросом.

| Синтетическая история и запрос | Медианы stock → кандидат, мс, прогон 1 / 2 |
|---|---:|
| 256 × 128 KiB, первый запрос с `after=248` | 205,35 → 130,14 / 163,85 → 121,59 |
| Те же 256 строк, повтор `after=248` | 65,31 → 4,78 / 55,42 → 5,21 |
| Те же 256 строк, скачок к `after=240` | 65,28 → 4,78 / 50,77 → 5,22 |
| Те же 256 строк, начало `after=0` | 6,44 → 6,97 / 5,36 → 4,79 |
| Те же 256 строк, EOF `after=256` | 0,43 → 0,30 / 0,41 → 0,36 |
| 1 536 × 512 B, повтор `after=1 528` | 8,36 → 0,42 / 7,65 → 0,42 |

Длинные повторные/глубокие страницы быстрее в **16 из 16** пар. Малый журнал и начало чтения не показывают стабильного выигрыша. Это устранение повторного чтения пропущенной части обычной SQLite-страницы, не ускорение полного semantic Fold, DisplayRecords или startup Desktop. [Первый прогон](paired.csv) · [повтор](repeat.csv).

## Повторение

Применить один подходящий патч (`git apply --check …`, затем `git apply …`). Запустить `python3 scripts/test.py -p session-storage -p proteus-session-storage-module` или прямой Linux `cargo test --locked --offline --release -p session-storage -p proteus-session-storage-module` с закреплённым Core harness `0c1b757`. Собрать два разных release worker через `cargo build --locked --release -p proteus-session-storage-module` в разных target dirs, затем `python3 measure_pages.py STOCK CANDIDATE --output samples.csv`. Стенд создает только временные сессии и готовит sidecar обычным List. Нужны Linux, Python 3.11+, Rust/Cargo и закреплённые зависимости проекта.
