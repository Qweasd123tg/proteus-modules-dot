# Context: не собирать временный ключ при повторном показе окна

При обновлении уже открытой панели Context переиспользует ответ сервера, если выбранная сессия и компактный JSON использования совпадают. Раньше для этого сравнения копировалось имя сессии и заново собиралась строка ключа. Теперь сравнение читает из сохранённой строки те же части: имя сессии, ровно один LF, затем исходные сериализованные байты. Полный ключ по-прежнему строится тем же способом, но только когда прежнее условие требует запроса.

В кеше остаются те же данные и та же строка ключа. Порядок полей JSON, числовое представление, пустые/отсутствующие значения, Unicode, смена сессии, первый показ/повторное открытие, порядок запросов, ошибка обновления и визуальные результаты не меняются. Выбранную сессию, разрешения, маршрут, аутентификацию и лимиты запроса код не меняет.

Один патч подходит точному upstream `892f627570369ed60d7205eb0d351c753ec4305f` и точному M150 + Extensions overlays через #443 (25 изменений после M150; preimage `174c79453dacb3ad3cad54cd692b235a3377da428bc7e4058ebb92898fa46b29`). Контроль редких границ занимает один компактный тест; дополнительная матрица представлений и измерительный пробник лежат вне продукта.

Воспроизведение: `reproduce.py STOCK_REPO COMPOSED_REPO --target EXISTING_TARGET --lock COMMON_LOCK` проверяет локальные исходники без запуска. Уточнённый запуск требует `--admit-exclusive`, тёплый Cargo home с точными зависимостями, Rust/Cargo 1.95.0 и готовый общий lock. Создаёт только две изолированные экспортированные копии и не запускает весь workspace. Одна задача locked offline, 512 MiB на входе / 256 MiB stop на обеих файловых системах, с отдельными запасами 32/48 MiB перед экспортом. Никаких действий с реальными сессиями, изменений продукта вне двух новых рабочих копий, или очистки чужих кэшей. На каждой фазе Cargo-артефакт связан с точными источниками и выпуском, а не просто найден по имени в тёплом target.

Пробник измеряет только решение о попадании в кеш/формировании ключа до построения виджета и обращения по сети. Запросы аллокатора учитывают новые размеры при успешных перераспределениях; это не время, RSS или общая стоимость отрисовки. Протокол сравнивается отдельно на неизменённых релизных бинарниках.

## Проверка

Релизные тесты: upstream 3 → 4, накопленная версия 4 → 5. На обеих базах побайтно совпали 27 stdout-кадров (66 897 байт), а также порядок, маршрут, выбранная сессия и статусы 8 GET-запросов. Записей, action-команд и stderr не было. Проверка 503 возвращается к прежнему ключу без нового GET, затем успешно обновляет изменившийся контекст.

На 12 обычных повторных отображениях с путём сессии в 17 байт число запросов аллокатора 96 → 48, запрошенные байты 3072 → 1440; с путём в 79 байт 84 → 48 и 5232 → 1440. Число сериализаций, байты и ёмкость сохранённого ключа не меняются. Первый показ и обновление по-прежнему формируют полный ключ; исчезает только временная копия имени сессии. Без сессии сохранён прежний нулевой путь в пределах пробника.
