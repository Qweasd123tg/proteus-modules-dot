# Plan: считать завершённые шаги при построении списка

Второй обход готовых строк больше не нужен: ветка точного строкового статуса `completed` увеличивает счётчик, когда существующая проекция уже приняла текст шага. Порядок проверок, владение строками и построение того же списка сохранены. Пустая строка остаётся допустимым текстом; одинаковый текст в разных строках не объединяется. Нестроковый или отсутствующий текст/статус исключает строку, а незнакомый строковый статус остаётся `Pending`. Это не ускорение всей панели: выбор активного шага, сборка виджетов, декодирование и сетевой доступ не менялись.

- `source.patch`: точная upstream-база `892f627570369ed60d7205eb0d351c753ec4305f`.
- `cumulative.patch`: M150 Extensions seal `60c98d197045c6d41d5f568cf44a106c0ec89d9aed13028ea6dd463568a24ac8` + 24 существующих оверлея через #441 (M200 Extensions перед этим патчем: `22da344a7c85981f8e7718edf851ce171232ca3ab9b6fe863f7e596fe2666760`). Счётчик расположен в общем `from_args`, сохраняя заимствование строк текущего плана из #364 и владение строками декодированного или кешированного плана. В stock он находится в том же построении строк, внутри `from_tool`.

Старый путь посещает `R` исходных строк и дополнительно `V` успешно разобранных строк ради счётчика; новый посещает только `R` исходных строк, добавляя к счётчику в уже существующей ветке для завершённых шагов. Эксперимент использует обычные 6/12 шагов и отдельно проверяет кодированные/кешированные данные, пустой и смешанный планы. Счётчики отражают логические посещения строк, не время, RSS или число запросов. Пробник не входит в продуктовый патч; ёмкость результата и запросы аллокатора сравниваются внутри каждой базы.

Проверка охватывает текущий и сохранённый план, первый активный шаг (даже если перед ним есть ожидающий), пустую принятую правку, отказы и смену хода, показ завершённого плана во время выполнения, кэш свежего снимка и состояние «история ещё не готова». Настройки и Preview проверяются без изменения настроек. В протоколе нет action-кадров и записей: единственные обращения API — read-only loopback GET по точному имени `update_plan` в синтетической сессии. Команда расширения, границы входа/кадров и валидация tool-state сохраняются прежними; в продукте изменены лишь построение списка и тест.

`reproduce.py` принимает локальный Git checkout с точным upstream, sealed M150 Extensions, затем 24 оверлея в указанном в скрипте порядке SHA-256, существующие `--target` и `--lock`. Без `--admit-exclusive` выполняет только preflight. Для фазы запуска требуются тёплые зафиксированные зависимости, Cargo/Rust 1.95.0, существующий локальный Cargo home и неизменные пороги 512 MiB на входе / 256 MiB остановки на обеих файловых системах. Только один offline locked Cargo job. Не запускает полный workspace, GUI или реальную сессию.

## Результат

Релизные тесты: upstream 17 → 18, M200 Extensions 18 → 19, без падений. На каждой базе 28 реальных stdout-кадров (15 578 байт) побайтно совпали; обращения к loopback: два 200 и один 409, без stderr и записей. Во всех четырёх сборках одинаковые шесть измеренных проекций. Список из 6 шагов: 12 → 6 посещений; из 12 шагов: 24 → 12; смешанный случай: 17 → 11. В каждом случае на каждой базе совпали число и размер запросов аллокатора и ёмкость вектора.
