# Session-storage: обновление записи не должно вытеснять соседнюю

**Сбой воспроизведён в обеих очередях.** На базе [Proteus-modules@9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51) обновление одной строки в полном кеше оставляет 1 023 из 1 024 summary и prefix. Раньше перед каждым insert запись искали в очереди через retain, а затем при заполненной map безусловно выбрасывали самый старый оставшийся элемент. При замене число записей не растёт: вытеснение лишнее.

[Самостоятельный патч](source.patch), локальный commit `1ca15b2a41f431474f960fb8a2db346b492e30c3`. Общая логика двух очередей использует результат HashMap::insert: новый ключ при полной очереди вытесняет самый старый; замена существующего ключа сохраняет остальных и переносит обновлённый ключ в хвост. Если он уже последний, очередь не меняется. Обе map и очереди остаются независимыми. Вставка нового ключа больше не сканирует очередь; при замене ключа не в хвосте линейный обход по-прежнему возможен. Патч не изменяет требования к locator, stamp, digest, blob и snapshot, режим audit, диск, ответы протокола или лимит 1 024. Наличие в кеше само по себе ничего не разрешает.

### Детерминированная проба

Синтетическая последовательность под одним lock, реальные методы remember_prefix и remember_summary, без дискового I/O в измеряемой части. Временный счётчик учитывает **только сравнения SessionLocator при обслуживании двух очередей**; поиск ключей в HashMap, аллокации, диск и latency не измерялись. Каждая следующая фаза продолжает предыдущую.

| Операции сразу в обоих кешах | Сравнения: база | Сравнения: патч | Размер каждого кеша: база → патч |
| --- | ---: | ---: | ---: |
| 1 024 новых ключа из пустого состояния | 1 047 552 | 0 | 1 024 → 1 024 |
| 4 096 новых ключей при заполненных кешах | 8 388 608 | 0 | 1 024 → 1 024 |
| 100 замен самой новой записи | 204 602 | 200 | 1 023 → 1 024 |

[Счётчики и регрессия](observations.txt). Это устранение работы внутри очередей, а не оценка ускорения Desktop или полного List. Регрессионный тест отдельно обновляет и старейшую запись, и уже обновлённый хвост, проверяет актуальные значения, точный порядок, следующий выбор на вытеснение и ограничение размера.

### Проверка и применение

* На указанной базе: `git apply --check /path/to/source.patch && git apply /path/to/source.patch`. Green: 64 теста storage и 2 process-теста; один существующий ручной I/O benchmark пропущен. До патча regression red: фактические длины `(1023, 1023)`, ожидались `(1024, 1024)`.
* **Если уже применён [вариант #286](https://github.com/Qweasd123tg/proteus-modules-dot/pull/286):** прямое наложение основного патча не проходит по контексту в трёх файлах. Вместо него применить [after-286.patch](after-286.patch) поверх дерева с реализацией #286 (локальный commit `31a32672faa40316b3744a21974ce59b316e8c01` либо исходная база + source.patch из #286). Это тот же фикс, не второе предложение. На таком дереве проверено `git apply --check`, результат совпал побайтово с исходниками проверенной сборки; 65 тестов storage и 2 process-теста прошли, тот же benchmark пропущен. Оба варианта патча одновременно применять не надо.
* Для обоих деревьев: `cargo fmt --all -- --check`, `git diff --check`; `cargo test --locked -p session-storage -p proteus-session-storage-module -- --test-threads=1`. Исходный Python runner блокирует отсутствующий в offline-кэше android_system_properties 0.1.5 на этапе metadata, поэтому тесты запускались непосредственно Cargo. Не запускались полный workspace и release-профиль. Dev worker самостоятельного варианта установлен только в локальный тестовый runtime через package.py. Его SHA-256 совпал с манифестом: `4296d30437bf3c156b6e28d9cd238faf3c9021e69a66f29792736e740a8a041f`.
* Измерение: на двух одноразовых копиях указанной базы применить патч только во второй, затем в каждой выполнить `python3 /path/to/queue_probe.py .` и `cargo test --locked -p session-storage --lib queue_cost_probe -- --nocapture --test-threads=1`. Использовать разные target-dir, либо перед каждым запуском обновить mtime изменённых исходников, чтобы Cargo не переиспользовал test binary другой копии. Проба модифицирует только одноразовые рабочие копии; в продукт не включена.
