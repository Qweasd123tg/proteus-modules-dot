# Строгий каталог: не вытеснять найденные строки до их проверки

На неизменном синтетическом каталоге с 1 025 сессиями исходный worker при каждом полном повторном List перечитывал все 1 025 дисковых индексов. Кандидат перечитал один. При 1 024 сессиях оба обходятся без чтения индексов на повторе. Это пороговый эффект строгого List на тестовых данных, **не** объяснение задержки Desktop на реальной машине.

База: [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). Самостоятельный [патч](source.patch), локальный commit `31a32672faa40316b3744a21974ce59b316e8c01`. SHA-256 патча `9a064f8744f058f3e0df987916a41d95fab9ce3be18e991c26b17f6b57115727`.

### Что изменено

Только когда число путей превышает имеющийся предел 1 024 и audit выключен, List пытается получить из памяти набор путей, для которых есть и summary, и prefix. При занятом или отравленном State mutex остаётся обычный порядок. Подсказка содержит не более 1 024 копий путей: никаких журналов, строк каталога, префиксов или blob-списков. Mutex отпускается до линейной перестановки уже существующего массива путей. Затем worker штатно обрабатывает каждый путь: сначала возможные попадания, потом остальные. Это не резервирование записей и не замена проверки состояния. Не изменены лимиты, вытеснение и приём записей, скоуп, comparator итогового ответа, аудит, работа с отдельной сессией, проверка источника или запись sidecar. При несовпадении пути (например, alias) подсказка может не помочь. Порядок посещения при параллельной записи меняется; List по-прежнему не обещает общего атомарного снимка. Частота чтения дискового индекса не равна частоте всего I/O: и попадание в память заново проверяет метаданные и blobs.

### Замер настоящего worker

Linux tmpfs, Rust 1.95, неоптимизированная сборка через rustc с теми же зависимостями; Python 3.12. Отдельное синтетическое дерево для каждого backend; одна настоящая запись журнала на сессию с тремя непустыми текстовыми сообщениями. Индексы подготовлены штатным List на месте. Три холодных запуска **каждого** варианта на тех же файлах, порядок AB/BA/AB, tmpfs не очищался между вариантами. Измерение от получения scan mutex до конца сортировки, не RPC, не startup и не end-to-end Desktop. Проверены набор идентификаторов, message_count, preview, порядок убывания (updated_at_ms, key) и поштучная история доступа. В исходном worker порядок полного обхода на этом tmpfs стабильно N…1; на других файловых системах он не гарантирован.

| n и сценарий | memory / sidecar, база → кандидат | JSONL, мс | SQLite, мс |
|---|---|---:|---:|
| 1 024, повтор (6 наблюдений) | 1 024/0 → 1 024/0 | 109.17 → 127.45 | 117.04 → 105.55 |
| 1 025, повтор (6) | 0/1 025 → 1 024/1 | 358.56 → 126.73 | 338.89 → 115.24 |
| 1 025, после List 8 строк (9) | 0/1 025 → 1 024/1 | 340.51 → 132.63 | 336.67 → 111.01 |

Медианы шумные, особенно на первом проходе; выигрыш подтверждается прежде всего точными work counters. При первой загрузке 1 025 валидных sidecars было 0/1 025 у обоих вариантов. Медиана холодного SQLite в этой малой выборке (по 3 запуска) была хуже: 279.12 → 344.90 мс; ускорение холодного запуска не установлено. Тот же малый workspace сам имел 8/0 в обеих сборках: по его времени выигрыш не заявляется.

Отдельный прогон по 2 058 сессиям обоих backend (два непересекающихся workspace по 1 025, плюс 8 горячих): после переключения на второй workspace первый проход читал 1 025 индексов, повтор кандидата только один. Между малыми запросами широкий List дал 8/2 050 у базы против 1 024/1 034 у кандидата. **Следующий малый List у обоих снова читал все восемь индексов**: патч улучшает широкий обход, но не закрепляет горячие строки.

### Корректность и ограничения

- В новом процессе два намеренно отсутствующих/повреждённых sidecar дали ровно два настоящих replay; оба индекса были восстановлены. Подтверждены прямое чтение сессии и обычный append другим worker: прогретая строка показала 4 сообщения вместо 3. Повреждённый канонический identity после прогрева исключён из non-audit, audit вернул ошибку. Всё на обоих backend и за порогом.
- При статическом symlink-alias обе сборки вернули по две одинаковые строки одной сессии и одинаковое после декодирования упорядоченное содержимое всех 2 059 строк. Гарантий полного совпадения возврата при конкурентном изменении равных sort keys нет.
- [Затронутые тесты](suite.log): 64 библиотечных и 2 процессных прошли; 1 штатный ручной измеритель пропущен. Проверены cargo fmt, git diff --check и [установка dev-worker в тестовое дерево](stage.log), SHA-256 совпал с manifest. Полный workspace и release-сборка не запускались. Штатный Python runner требует отсутствующий в offline-кэше android_system_properties 0.1.5 на этапе cargo metadata; выполнена прямая проверка Cargo. При установке на реальной системе никаких изменений не делалось.

### Воспроизведение

1. На указанной базе: `git apply --check /path/to/source.patch`, затем `git apply /path/to/source.patch`, `cargo test --locked -p session-storage -p proteus-session-storage-module -- --test-threads=1`.
2. Для измерений подготовить dev target на базе через `CARGO_TARGET_DIR=/path/to/target cargo build --locked -p proteus-session-storage-module`. Вызвать `python3 build.py /path/to/checkout /path/to/target /tmp/base` и `python3 build.py --patch /path/to/source.patch /path/to/checkout /path/to/target /tmp/candidate`. При нескольких сборках в target задать `--fingerprint <суффикс>`; в этом прогоне `765ba9328ec6c0ed`. Build каждый раз извлекает точный commit через git archive и добавляет одинаковые диагностические вставки только для измерительных binary.
3. `mkdir -p /tmp/r42-fixture`. Запустить `python3 profile.py /tmp/base/module --candidate /tmp/candidate/module --repeat 3 --fixture-dir /tmp/r42-fixture --output paired.jsonl`, затем `python3 stress.py /tmp/base/module --candidate /tmp/candidate/module --fixture-dir /tmp/r42-fixture --output stress.jsonl`.
4. `python3 summary.py paired.jsonl stress.jsonl` проверяет точные счётчики данного tmpfs и выводит [сводку](results.txt). На другом порядке перечисления цифры базы могут не воспроизвестись. [Полные наблюдения](observations.json) содержат времена и точный порядок каждого обхода; `order` указывает индекс в `orders`, где пары [начало, конец] задают включительный диапазон с шагом +1 или −1. Проверенное преобразование: `python3 pack.py paired.jsonl stress.jsonl >observations.json`.
