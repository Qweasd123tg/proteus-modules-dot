# coding-workflow: убрать вторую копию истории при возобновлении Codex

База: **Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51**. Локальный commit `47bed2a676ad8cbc5e4dae72ff90352e475e0812`.

При первом запросе после возобновления Codex список сообщений уже передан во владение `CanonicalModelRequest`. Ветка без подготовки контекста копировала этот список ещё раз только для присваивания обратно. Теперь она сохраняет сообщения на месте; если подготовка действительно запрошена, как раньше используются её сообщения, отчёт и target. У нового, не возобновлённого запуска первый запрос идёт через pre-turn preparation, этот путь не ускоряется. Порядок сообщений, вызовы tool selection/preparation, ошибки и метаданные оценок и триггера остались прежними.

## Проверки

- Полный unit-suite crate `coding-workflow`: **111/111 → 112/112** в точном isolated Release с сортированными ключами и в Debug workspace-графе с `serde_json/preserve_order`. Оба исходника собраны rustc 1.95.0 x86-64 Linux по отпечаткам ранее собранных locked Cargo-зависимостей. Общий target не менялся; свежий полный Cargo workspace gate не запускался.
- **14 полных побайтных сравнений** (по три пары): весь подготовленный запрос, compaction metadata, target либо текст ошибки. Проверены пустой контроль, короткое/длинное возобновление, восстановленная оценка для opaque checkpoint, pre-turn preparation без изменений, с заменой и с ошибкой. Независимо проверены id и порядок сообщений, ключ кэша, сохранённая оценка, триггер и число вызовов test host.
- `rustfmt --check`, `git diff --check` и `git apply --check` на точной базе и M100. Контрольные хеши всех 100 выбранных патчей M100 сверены: ни один не меняет эти файлы. #357 относится к проекции записываемого checkpoint, а эта правка относится к сборке запроса модели.
