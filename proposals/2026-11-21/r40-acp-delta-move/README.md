# Core: передавать готовый фрагмент ответа в ACP без дополнительной копии

База: `Proteus-harness/Proteus-core@32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f`. Самостоятельный патч только для `app_server/acp/projection.rs`. SHA-256 `source.patch`: `ea60505da73aef633abc071a12eb505adb6c036342a3eb1ddecc459b79e79147`.

Когда редактор получает очередной фрагмент ответа или идентифицированного видимого рассуждения, Core оставляет его текст в истории проектора для проверки смещений и повторов. Раньше он также копировал текст в новую строку для исходящего ACP-уведомления. Теперь, если весь фрагмент новый и ёмкость строки равна её длине, в уведомление переходит исходная строка. Для частичного совпадения или избыточной ёмкости по-прежнему выделяется только нужный суффикс: короткое уведомление не удержит большой буфер. Проверка UTF-8, обработка разрывов и изменённых повторов, разделители сообщений и завершение потоков не меняются. Это уровень представления ACP, а не парсер провайдера или общая рассылка событий.

| Вход одного проектора | Запросы к аллокатору, до → после | Сумма запрошенных байт, до → после |
|---|---:|---:|
| 1 024 последовательных фрагмента × 32 Б | 2 060 → 1 036 | 565 396 → 532 628 |
| Один фрагмент 1 МиБ | 4 → 3 | 2 097 788 → 1 049 212 |
| 1 024 × 32 Б, все входные буферы с большим запасом | 2 060 → 2 060 | 565 396 → 565 396 |
| Первый новый, следующие 1 023 с частичным перекрытием | 2 060 → 2 059 | 565 396 → 565 364 |
| 1 024 пустых фрагмента | 1 → 1 | 180 → 180 |

Счётчики одинаковы при отдельных прогонах текста ответа и видимого рассуждения. Первые две строки используют настоящие `AppServerEvent::Runtime` из канала Tokio broadcast, как у ACP-получателя. События заранее подготовлены и получены; замерен только вызов настоящего проектора (включая выходной вектор и рост его истории), не подготовка входа, отправка уведомлений, модель или редактор. Считались alloc/alloc_zeroed/realloc, при realloc учитывался новый размер. Повторы ABBA совпали. Это не измерение задержки, RSS или частоты этих случаев у пользователей.

Воспроизводимый дифференциал собирает **полные** проекторы базы и кандидата в один Rust-бинарник с настоящими контрактами и ACP-схемой. Сопоставлены 1 296 пар трасс: 11 502 успешных результата и 1 458 ошибок совпали после сериализации; конечный fallback также совпал во всех парах. Проверены повторы и частичные перекрытия, разные сообщения, чужие thread/session, несовпадающие завершения, многобайтные и невалидные смещения. Три исходных unit-теста (два для проекции и один для плана) прошли для каждой версии, новый тест на владение буфером и обе диагностические проверки также прошли: 9/9 в бинарнике. Весь библиотечный test target Core отдельно прошёл typecheck с кешированными зависимостями Cargo (`rustc --test --emit=metadata`, 7 предупреждений вне изменённого файла). Проверены форматирование workspace, whitespace и прямое/обратное применение. Полный workspace и сквозной запуск ACP-клиента не выполнялись.

Повторить из чистого Core указанной базы, Rust 1.95 и lld; нужен один согласованный набор зависимостей в target:
```sh
cargo build --locked -p proteus-core --lib
python3 "$PROPOSAL/probe.py" . "${CARGO_TARGET_DIR:-target}/debug/deps"
```
Скрипт применяет патч только к временному дереву. Для обычного запуска тестов после применения: `cargo test --locked -p proteus-core --lib app_server::acp`.
