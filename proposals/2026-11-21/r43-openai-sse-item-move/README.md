# OpenAI Responses: сохранять исходный JSON завершённого элемента без глубокой копии

**Куда:** `Proteus-harness/Proteus-modules`, точная база `9469e3b12529d08b1f4a76882693e2065e842c51`. Самостоятельный `candidate.patch` меняет только `model/model-pack/src/adapters/openai/stream_state.rs` и его тесты.

При событии `response.output_item.done` адаптер полностью копировал дерево `item` в список для последующего восстановления ответа. Исходное дерево освобождалось в конце того же вызова. Теперь `Value::take` перемещает уже разобранный элемент в тот же список; декодер работает со ссылкой на сохранённое значение. Добавление в список по-прежнему идёт **до** проверки типа: неизвестные поля, будущие типы, ошибки разбора и непрозрачные checkpoint сохраняют прежнюю семантику. У `output_item.added` ничего не изымается и не сохраняется. Намеренно не меняли использование списка при приходе терминального события, в том числе повторного.

### Результат

Запрошенные у аллокатора байты **на один вызов штатного `OpenAiStreamState::translate`**, включая разбор JSON из строки. Строка уже подготовлена, состояние свежее. Медиана 31 пары, до неё 4 разогревочные пары; порядок чередуется. `realloc` учитывается по новому запрошенному размеру. Это не RSS, latency, сетевой трафик, стоимость полного ответа или расход токенов.

| Событие и содержимое | До, байт | После, байт |
|---|---:|---:|
| done: короткое сообщение, 229 байт SSE JSON | 7 041 | 4 977 |
| done: обычный текст 64 КиБ | 201 370 | 134 485 |
| done: непрозрачная подпись reasoning 256 КиБ | 789 336 | 526 520 |
| done: checkpoint с полем 1 МиБ | 2 099 291 | 1 050 048 |
| done: неизвестный тип, 512 вложенных объектов | 705 463 | 361 262 |
| added: короткое сообщение / checkpoint (контроли) | 3 136 / 1 049 921 | 3 136 / 1 049 921 |

Для вложенного объекта число запросов к аллокатору упало с 4 119 до 2 066. При текстовом, reasoning и других распознаваемых типах расходы на их каноническое представление остаются. При восстановлении пустого терминального ответа прежний код по-прежнему копирует сохранённый список: это отдельный этап.

### Проверено

- На свежем временном checkout точной базы: `git apply --check`, применение, `git diff --check`, `rustfmt --check`.
- 14/14 локальных целевых тестов: сохранение идентичности сообщения и вызова инструмента, отказа, восстановление пустого терминального ответа, прежний приоритет ошибок и неизвестные поля. Новый тест отличает событие `added` от `done` и проверяет полный порядок элементов на выходе.
- 1 024 трассы по 8 событий: попарное сравнение сериализованных канонических событий до/после. В наборе есть обычный и compaction-режимы, ошибочный JSON, неполные и неизвестные элементы, отказ, поиск, повторное терминальное событие, пустой и заполненный терминальный массив. Случайные идентификаторы сообщения/части переименованы взаимно-однозначно в пределах трассы; provider metadata и исходные ID инструментов сравниваются без изменений.
- Linux x86-64, rustc 1.95.0; адаптер и probe компилировались с `-O`, совместимые зависимости взяты из локального debug-кэша, включая закреплённый `proteus-contracts`. Локальный офлайн-срез не включает две незадействованные функции HTTP/URL и один subprocess-тест через полный Core. Полная сборка workspace, все тесты model-pack, сеть и установка Desktop **не запускались**.

**Воспроизведение:** `python3 reproduce.py /path/to/Proteus-modules`. При штатном запуске используется проектный Cargo runner в release-профиле с закреплёнными зависимостями, включая subprocess-тест. Вариант `--compiler` для прямой проверки с локальным кэшем документирован в скрипте. `checks.log` и `results.log` содержат фактический прогон с кэшем; `probe.rs` не включён в импортируемый патч.
