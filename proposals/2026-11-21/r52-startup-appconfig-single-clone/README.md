# Core: одна копия настроек при запуске AppServer

База: [Proteus-core 32e56ecb](https://github.com/Proteus-harness/Proteus-core/commit/32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f). Изменяется только AgentAppServer::launch_inner. Раньше старт держал три полных AppConfig: вход отдавался RuntimeBuilder, одна независимая копия читалась восстановлением выбора модели, ещё одна сохранялась в живом сервере. Теперь RuntimeBuilder получает отдельную копию, а первоначальный AppConfig читается при восстановлении и затем переезжает в существующий Arc<RwLock<AppConfig>>. Сквозной подсчёт копий внутри всей сборки не заявляется.

Восстановление выбора модели/профиля не перемещено относительно подготовки runtime или первой публикации готового состояния. Конфигурация хранения, startup hint, обязательная валидация истории, профильные фазы, порядок готовности и настройки уже открытого сервера не меняются. Не вводится общий изменяемый AppConfig для runtime и сервера. Save/reload и правила неподходящего профиля не изменены.

## Проверка

Измеритель подключается только в тестовой копии. Он вызывает существующий scoped счётчик Rust allocator на неизменённом AppConfig::clone в настоящем startup path, а затем проверяет штатный результат запуска. В каждой из четырёх форм профиля отдельно проверены свежая сессия и восстановление явно указанного сохранённого чата в другой временной папке. Сверяются полное сериализуемое состояние AppConfig, набор команд, рабочая папка, содержимое синтетического хвоста и сохранность журнала после чтения. Минимальный профиль уже пригоден для запуска, а искусственно длинные prompts являются проверкой предельной стоимости, не описанием нагрузки владельца.

В таблице отражены **только места копирования AppConfig в launch_inner**, включая запросы allocator на realloc, но не пиковая память, время запуска или UI. Другие копии (например, выбор storage) и холодное восстановление истории здесь не оптимизируются.

| Профиль, свежий старт | Запросов на выделение, до → после | Запрошено байт, до → после |
|---|---:|---:|
| Минимальный тестовый | 60 → 30 | 19 616 → 9 808 |
| 32 команды по 128 байт | 262 → 131 | 39 198 → 19 599 |
| 4 команды по 64 КиБ | 86 → 43 | 545 898 → 272 949 |
| 32 команды по 64 КиБ (стресс) | 262 → 131 | 4 225 306 → 2 112 653 |

Во всех восьми сценариях запуск делает две → одну копию в измеряемом узле. Путь preferred даёт те же количества вызовов; точные байты двух вариантов в probe.log. Стенд с внешним процессом хранения прошёл 7/7 startup тестов на исходнике и 7/7 на кандидате. Для кандидата отдельно прошли 13/13 тестов выбора модели: восстановление/изоляция настроек, валидация привязки, ошибка записи, отсутствие сокрытия повреждённого канонического журнала. SDK и процессы в обеих сторонах одинаковые. Слой HTTP транспорта, нативный Desktop, весь workspace и продолжение с реальным провайдером не запускались. Накладывается на канонический исходный набор M50; совмещённые тесты не выполнялись.

## Воспроизведение

Из чистого дерева Core указанной ревизии:

    git apply --check /abs/packet/source.patch
    # Rust 1.95; Cargo-зависимости доступны в локальном кеше.
    # Два заведомо совместимых тестовых процесса; те же файлы для обоих вариантов:
    export PROTEUS_TEST_REFERENCE_MODULE=/abs/proteus-reference-module
    export PROTEUS_TEST_SESSION_STORAGE_MODULE=/abs/proteus-session-storage-module
    python3 /abs/packet/probe.py . /abs/existing-cargo-target /abs/new-logs

probe.py инструментирует временную копию, компилирует обе стороны, проверяет фактические объёмы каждого клона и точный переход двух мест копирования к одному. Прямое/обратное применение и форматирование проверяются без изменения upstream.
