# Повторная загрузка blob без второй копии файла в памяти

При повторном `PutBlob` файл уже лежит в `images/<sha256>`. Чтобы исключить коллизию, session-storage сначала декодирует присланный Base64 и проверяет длину и SHA-256, а затем сравнивает результат с существующим файлом. Для последней проверки раньше читали файл целиком в растущий `Vec`. Патч читает его блоками по 16 КиБ и сравнивает каждый блок с соответствующим срезом уже декодированного входа. Для сравнения не выделяется память в куче; используется фиксированный буфер на стеке.

**Где это помогает:** повтор того же запроса после потери ответа или новый запрос с теми же байтами в одной сессии. При первой записи, чтении и отправке нового уникального изображения путь данных прежний. Патч не изменяет API, формат, имена файлов, алгоритм SHA-256, квитанции или порядок атомарной записи и синхронизации. Как и раньше, открывается обычный файл; сравниваются именно байты, а не хеш или метаданные. После первого несовпадения чтение продолжается до EOF или `maximum + 1`, поэтому сохраняется приоритет ошибки чтения или превышения лимита над ошибкой коллизии.

**База:** [Proteus-modules@9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). Патч самостоятельный, локальный commit `0a044fffc20ea2db127f50e66e16ffdbecd96546`, SHA-256 файла `source.patch`: `59e3ace8c51a1daf41e6899231528fc709e5092d6d6fd3af0814055cc0da04b1`. Ранее предложенные изменения SHA, JSONL, Gear или metadata CAS не нужны. В этом пакете нет правок их логики.

## Замер всей операции

Сумма размеров запросов к Rust-аллокатору на потоке `StorageService::execute(PutBlob)`, включая валидацию, декодирование, проверку SHA, работу с файлом и квитанцией. Уже готовый вход и проверка ответа не включены. Учитываются alloc, alloc_zeroed и новый запрошенный размер при каждом realloc. Оба варианта собирались одним Rust 1.95.0 в Cargo test-профиле, Linux x86-64. В таблице медианы шести наблюдений (JSONL и SQLite, по три измерения после одного прогрева).

| Вход, сценарий | Запрошено байт, до → после | Вызовы аллокатора, до → после |
|---|---:|---:|
| 64 байта, повтор той же операции | 14 151 → 13 927 | 218 → 215 |
| 256 КиБ, повтор той же операции | 1 324 551 → 276 007 | 230 → 215 |
| 4 МиБ, повтор той же операции | 20 985 351 → 4 208 167 | 234 → 215 |
| 4 МиБ, тот же файл, новый ID операции | 20 990 383 → 4 213 199 | 282 → 263 |
| 4 МиБ, первая запись (контроль) | 4 210 139 → 4 210 139 | 260 → 260 |

Это не пиковая память: сумма учитывает несколько размеров растущего вектора. Base64-запрос и декодированный вход не стали потоковыми. Блоки ограничивают размер одного чтения 16 КиБ и могут увеличить число системных вызовов. Время отклика, RSS рабочего процесса, сквозная скорость загрузки и частота повторных запросов в пользовательском трафике не измерялись.

## Паритет и воспроизведение

- На каждом backend сравнивались пять размеров (0, 64, 16 385, 262 144 и 4 194 304 байта) и три сценария: первая запись, повтор с прежним ID, повтор с новым ID. В 90 попарных измерениях ответы совпали с ожидаемой ссылкой и путём внутри каждой сессии. Сохранённые байты совпали с исходными, SHA-256 файлов квитанций совпал между версиями. После закрытия сервиса новый экземпляр прочитал исходные байты.
- В обеих версиях проверены пустой/короткий файл вместо ожидаемого, отличие байта, лишний хвост, обычный файл длиннее 64 МиБ и каталог вместо файла. Сообщения об ошибках совпали, журнал квитанций не изменился. Постоянный regression test проверяет оба backend, в том числе несовпадение последнего байта после нескольких блоков и успешный повтор после восстановления файла.
- `cargo test --locked --offline -p session-storage -p proteus-session-storage-module -- --test-threads=1`: **64 библиотечных и 2 процессных теста прошли**, один прежний ручной perf-тест пропущен. `cargo fmt --all --check` и `git diff --check` прошли. Общий Python runner остановился до тестов: офлайн-кеш не содержит Android-only зависимость `android_system_properties v0.1.5`. Полный workspace не запускался.
- `python3 package.py --profile dev --package session-storage --install /path/to/staging` успешно установил worker в отдельный staging-каталог; SHA-256 установленного бинарника сверен с module.json. Это локальная установка для проверки, а не публикация нового worker.
- Повтор A/B: из папки с этим README запустить `bash verify.sh /path/to/Proteus-modules /path/to/results` с рабочим Cargo/Rust и доступными зависимостями. Скрипт создаёт отдельный временный checkout базы и применяет патч только там. Если задан `CARGO_TARGET_DIR`, используется указанный кеш. Сырые пары и SHA находятся в `results.csv`; абсолютные числа аллокаций немного зависят от путей файлов и версии библиотек.
