# Desktop: читать короткие сообщения Codex прямо из буфера

Встроенный клиент Codex получал каждое JSONL-сообщение дочернего процесса через отдельный временный `Vec<u8>`, даже когда вся строка уже была в буфере чтения. Патч передаёт готовую строку обработчику по ссылке. Только сообщение, пересекающее границу буферов, собирается в отдельном векторе. После его доставки выделенная память не удерживается до следующего события. Публичный API, формат протокола, обработчик JSON и бюджеты очередей не изменены.

### Измерение

Один поток, Linux x86_64, Rust 1.95.0, оптимизированная сборка (`rustc -C opt-level=2`), один и тот же корпус из 16 384 синтетических UTF-8 JSON-уведомлений на каждую пару сравнений. Счётчик охватывает только вызов настоящей функции чтения в процессе. Источник в памяти, входной буфер, тестовые данные и печать исключены. Проверяются байты каждой строки и число доставок.

| Размер строки с LF / буфер | Вызовы alloc/realloc, до → после | Сумма запрошенных байтов, до → после |
|---|---:|---:|
| 128 Б / 8 КиБ (все строки помещаются целиком) | 16 384 → 0 | 2 080 768 → 0 |
| 117 Б / 8 КиБ (часть строк разрезана границей) | 16 614 → 462 | 1 920 552 → 46 920 |
| 117 Б / 32 Б (каждая строка разрезана) | 61 952 → 61 952 | 4 972 544 → 4 972 544 |

Когда к чтению добавлен настоящий разбор каждой 117-байтовой строки в `serde_json::Value`, результат при буфере 8 КиБ: **164 070 → 147 918** запросов к аллокатору и **14 536 232 → 12 662 600** суммарных байтов. Сам разбор JSON всё ещё выделяет память. Это замер временных аллокаций, не экономия пиковой памяти или RSS на эти суммы и не измерение скорости GUI. В реальном pipe разбиение на чтения зависит от поведения отправителя.

### Проверки

База: `Proteus-harness/Proteus-desktop` @ `b6a7ec2d8d7e486c8aba01291aa8c89774c4cded`. Изменён только `crates/codex-client/src/process.rs`. До: 1 модульный и 11 интеграционных тестов. После: 2 модульных и те же 11 интеграционных. Все прошли. Отдельно проверены короткие и разделённые строки, ровно лимит и выше лимита, пустая строка, обычный и оборванный EOF, остановка после ошибки обработчика. Синтетический дочерний процесс проверяет также ответы не по порядку, отмену при ожидающем подтверждении, переполнение очереди и завершение процесса. GPUI и полный workspace не собирались.

`source.patch` применяется из корня указанной базы: сначала `git apply --check /путь/к/source.patch`, затем `git apply /путь/к/source.patch`. Для независимой проверки обеих версий: `bash verify.sh /путь/к/Proteus-desktop`. По умолчанию скрипт использует временный checkout и Cargo с исходным lockfile. В этой среде проверки выполнены напрямую через rustc с уже собранными зависимостями (режим DEPS); исходники крейта, интеграционные тесты и peer те же. Скрипт не меняет переданный checkout. Полный вывод: `evidence.log`, исходник счётчика: `probe.rs`.
