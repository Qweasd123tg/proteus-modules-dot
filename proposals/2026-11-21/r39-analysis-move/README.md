# Core: не копировать содержимое выбранного хода для /analysis

База `Proteus-harness/Proteus-core@32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f`. Один самостоятельный патч; порядок относительно предыдущих предложений не важен. SHA-256 `source.patch`: `e6d498d4668811587987c52812346227d8b08f0b2b8685820a759ef7f98c7a48`.

И при подключённой сессии, и при холодном чтении Core уже получает проверенную проекцию во владение. Раньше обработчик анализа заимствовал её, копировал запросы и ответы модели, сообщения, записи хуков и результаты инструментов выбранного хода в ответ, затем сразу освобождал исходную проекцию. Теперь берёт из неё журнал, читает список ходов и переносит выбранные поля в ответ. Полное чтение и валидация журнала, выбор последнего или запрошенного хода, раскрытие diagnostics-хуков, порядок шагов и сериализованный контракт не меняются. Никаких изменений в файлах сессии, настройках доступа или схемах.

Невыбранные записи удаляются из локального вектора **на месте**, а не проходят как owned-значения через цикл разбора. Это существенно для длинной истории с коротким выбранным ходом. Изменение не обещает потоковое чтение и не уменьшает размер уже записанного журнала.

| Вход проектора (ответ строится полностью) | Запросы аллокатору, до → после | Сумма запрошенных байт, до → после |
|---|---:|---:|
| Пустая проекция | 0 → 0 | 0 → 0 |
| 16 байт в сообщении запроса выбранного хода | 85 → 46 | 12 012 → 8 931 |
| 1 МиБ в том же сообщении | 85 → 46 | 1 060 572 → 8 931 |
| 1 МиБ есть только в невыбранном ходе | 82 → 45 | 11 475 → 8 771 |

Это запросы Rust-аллокатору внутри `project`, не RSS и не I/O. Обе версии получают одинаковую заранее подготовленную синтетическую проекцию; ABBA, результаты одинаковы в обоих повторах. В отдельном Linux-контроле на 1 935 смешанных записях медиана CPU-потока за 24 измерения на вариант: выбран только первый блок 0,629 → 0,616 мс, только последний 0,600 → 0,604 мс, все блоки 3,133 → 2,508 мс. Для короткого выбранного хода это практически равные результаты, не доказательство общего ускорения. Это не измерение времени HTTP, открытия сессии или процесса хранения.

**Проверка:** в одном бинарнике собраны точные функции Core из базы и патча с настоящими типами контрактов. Сравнили 380 полных сериализованных отчётов и 500 ошибок (в том числе недопустимый выбор); совпали побайтно. Входы включают все виды journal entry, разные settlement-статусы, обрезанные/перемешанные последовательности, отсутствие turn ID, успешное раскрытие diagnostics и ошибку у некорректного хука. Это тест границы проектора; намеренно синтетические дефектные последовательности не выдаются за валидный журнал.

Существующий холодный тест `cold_analysis_preserves_historical_inputs_failures_and_unknown_effects` запущен для базы и патча: настоящие SessionStore и отдельный процесс JSONL, два хода, историческая модель/ошибка, шаги одобрения, неизвестный результат эффекта, проверки параметров и неизменности файла. Для теста и дифференциала извлечены точные исходники функций, парсера и исходного теста. Весь библиотечный test target Core отдельно прошёл typecheck с кешированными Cargo-зависимостями (семь предупреждений вне изменённых строк). Workspace fmt, diff whitespace, прямое и обратное применение прошли. Полный workspace/test и маршрут подключённой сессии end-to-end не запускались.

**Воспроизведение:** из чистого Core указанной базы с Rust 1.95/lld собрать `cargo build --locked -p proteus-core --lib` в отдельном target без дублирующихся rlib; передать бинарник совместимого session-storage модуля. Патч в рабочее дерево автоматически не вносится:
```sh
python3 "$PROPOSAL/probe.py" . "${CARGO_TARGET_DIR:-target}/debug/deps" "$PROTEUS_TEST_SESSION_STORAGE_MODULE"
```
