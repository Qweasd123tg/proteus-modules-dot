# Возврат writer lease после ошибки повторного AcquireWriter

[Патч](candidate.patch) для [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). Локальный коммит: `ecf8683d267f171be5e9b42f6b7663861bc296a1`.

Если один writer сессии уже есть, модуль выдаёт следующему клиенту независимый token, но OS-блокировку держит одну, пока есть хотя бы один handle. Раньше при ошибке проверки ревизии новый token оставался в учёте, хотя вызывающий код его не получал. После освобождения всех действительно выданных handles следующий владелец мог не получить блокировку до перезапуска сервиса.

В случае ошибки патч убирает только token неудавшейся операции и возвращает исходную ошибку. Перед удалением проверяются сессия, поколение и сам token. Редкое совпадение UUID с действующим token обнаруживается до любых дальнейших действий. Старые handles не переиздаются и не снимаются. Общий mutex, порядок блокировок, первое открытие writer, hibernate, условия эксклюзивного Delete и обычный Release не менялись. Потеря ответа на уже успешный AcquireWriter и отмена транспортного запроса остаются за рамками исправления. Канонические записи, проверка blobs, кеши, индекс v1 и протокол не менялись.

**Проверка ошибки.** Rust-тест использует нормальную временную сессию с одной подтверждённой записью и уже освобождённым первым handle. Только внутри теста подменяется интерфейс recovery: он возвращает стандартную ошибку I/O `Interrupted`. Файлы сессии и содержимое журнала для этого не изменяются. Исходная сборка с новым тестом падает на проверке передачи OS-блокировки ([лог](stock-oracle.log), остановка на JSONL). С исправлением тест прошёл и на JSONL, и на SQLite: тип ошибки сохранился, прежний действующий handle остался валидным, обычный повтор вернул исходную ревизию; после release второй экземпляр сервиса открыл запись при ещё работающем первом. Это проверка корректности, не заявления об ускорении.

**Проверки Linux x86-64, Rust 1.95.0:**
- [Отдельный патч](cargo-suite.log): 64 unit + 2 process passed, 1 штатный ручной тест пропущен. Есть проверки ownership, идемпотентной записи при потере ACK, pinned snapshots, кешей и целостности. `rustfmt --check` изменённых файлов и `git diff --check` прошли.
- [Два настоящих SDK worker](healthy-worker.log) на каждом backend: обычная выдача трёх разных handles, hibernate, освобождение и переход к другому процессу без перезапуска. Здесь не имитируется ошибка.
- [#296](https://github.com/Qweasd123tg/proteus-modules-dot/pull/296), [#303](https://github.com/Qweasd123tg/proteus-modules-dot/pull/303), [#310](https://github.com/Qweasd123tg/proteus-modules-dot/pull/310), [#311](https://github.com/Qweasd123tg/proteus-modules-dot/pull/311) и этот патч [дают один и тот же Git tree](composition.log), если наложить R49 до или после четырёх предыдущих патчей. У заново собранной [совмещённой версии](combined-suite.log): 71 unit + 2 process passed, 1 штатный ручной тест пропущен.
- Штатная обёртка не прошла [offline all-platform Cargo metadata](official-gate.log): в кэше нет Android-пакета. Прямые native locked-тесты прошли, весь workspace и Windows не проверялись.

**Повторение.** На указанном пине: `git apply --check candidate.patch`, затем `git apply candidate.patch` и `python3 scripts/test.py -p session-storage -p proteus-session-storage-module`. Для прямого запуска: `cargo test --locked -p session-storage -p proteus-session-storage-module`; если стенду требуется `PROTEUS_TEST_HARNESS_ROOT`, укажите дерево закреплённого Core `0c1b757`. Для отдельной проверки SDK: `cargo build --locked -p proteus-session-storage-module`, затем `python3 healthy_worker.py target/debug/proteus-session-storage-module`. Тест создаёт свои временные сессии.
