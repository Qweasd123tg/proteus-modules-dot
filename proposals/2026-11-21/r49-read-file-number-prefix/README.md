# read_file: переиспользование буфера номера строки

База: **Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51**. Локальный commit: `0039b7c92e9b8384c4ecbd3267bd28255794c2e1`. Меняются только цикл чтения одного файла в `tool/file-tools/src/read.rs` и тест его лимита в `read_budget_tests.rs`. Патч не меняет пакетное чтение `read_many_files`, схемы, разрешения или границы workspace.

При `line_numbers: true` каждый выбранный номер с табуляцией раньше форматировался в новый временный String. Теперь одна строка очищается и используется повторно. Длина учитывается до записи, как и прежде; добавление новой цифры на строках 10, 100 и далее не меняет лимит вывода. При выключенной нумерации буфер не выделяет память. Стандартное полное чтение вообще не проходит через этот цикл. Чтение файла, ограничение сканирования, обработка конца файла/UTF-8, разделители строк, метаданные и окончательная сериализация не изменены.

## Что измерено

Linux x86-64, rustc 1.95.0, release; замер всего `ReadFileTool::invoke_json` на настоящих временных файлах, включая открытия файла, парсинг и сериализацию ToolResult. Входные JSON-строки готовы до старта таймера, результат проверяется после возврата. Для времени отдельно собраны **неинструментированные бинарники**; для памяти отдельно считаются успешные alloc/alloc_zeroed/realloc внутри вызова. При realloc записана полная запрошенная длина. Пик — максимальное приращение суммы живых размеров, видимых Rust-аллокатору, с момента входа в вызов, не RSS. Используется прогретый файловый кэш. Замеры не включают транспорт процесса и чтение с холодного диска.

| Сценарий | Запрошено байт, было → стало | Вызовы аллокатора | Пик живых байт, было → стало |
|---|---:|---:|---:|
| 60 000 коротких строк, с нумерацией | 5 395 288 → 4 915 296 | 60 101 → 102 | 2 808 231 → 2 808 231 |
| Страница из 100 строк с номера 9 950 | 22 277 → 21 485 | 188 → 89 | 11 774 → 11 782 |
| Две строки с нумерацией | 13 154 → 13 146 | 75 → 74 | 9 709 → 9 717 |
| Две строки, стандартное чтение | 4 217 → 4 217 | 51 → 51 | 2 840 → 2 840 |
| 60 000 строк, стандартное чтение | 3 569 388 → 3 569 388 | 77 → 77 | 1 994 973 → 1 994 973 |

В обоих независимых прогонах на длинном нумерованном файле убрано **59 999 вызовов и 479 992 запрошенных байта (8,9%)**, но не пиковая память. В коротких нумерованных диапазонах пик иногда выше на 8 байт из-за удержания буфера. Медианы времени полного нумерованного чтения 60 000 строк: 14,11 → 12,27 мс и 9,41 → 8,87 мс. У небольших сценариев надёжного выигрыша во времени нет: для страницы из 100 строк 362 → 361 мкс и 326 → 335 мкс, для двух нумерованных строк 18,1 → 17,0 мкс и 13,0 → 13,5 мкс. Измерения времени шумные, не SLA; вывод об экономии относится прежде всего к числу аллокаций. Для столбцов времени последовательно чередовались девять пар прогретых процессов на основной сценарий (медианы средних времён отдельных процессов), по три пары для редких граничных сценариев. Все выборки в `bench.log` и `recheck.log`.

## Проверки

* Исходник: `cargo test --locked -p file-tools --lib` **29/29**. Кандидат: **30/30**. Новый тест фиксирует ширину префикса при переходе с 9 на 10: когда остались только четыре байта, строка 10 не попадает в ответ; пять байт позволяют записать разделитель, префикс и один байт текста. Прошли rustfmt --check для изменённых файлов и git diff --check.
* Источник, кандидат, инструментированные и обычные сборки: 10 сценариев дали побайтно одинаковые полные JSON-ответы. Помимо сравнения с исходником проверены ожидаемый текст/значимые поля для короткого и большого чтения по умолчанию, CRLF/LF и отдельного CR, пустого файла, пустой строки, Unicode, страницы через номер 10 000, выходного лимита и ошибки UTF-8. В публикуемом SHA-256 временный путь нормализован **после** сравнения байтов.
* [Пакет предыдущего раунда #276](https://github.com/Qweasd123tg/proteus-modules-dot/pull/276) оптимизирует другое средство, `read_many_files`. Патчи применены к указанной базе в обоих порядках; деревья file-tools совпали, совмещённый тест **31/31**. В delivery-репозитории также проверены ближайшие кандидаты по ключевым словам `numbered`, `ranged`, `read-file`, `file-tools`; [#124](https://github.com/Qweasd123tg/proteus-modules-dot/pull/124) касается сохранения окончаний строк.
* Штатная Python-обёртка в offline-среде остановилась на межплатформенном `cargo metadata --locked`: в кэше нет `android_system_properties 0.1.5`. Прямой native locked suite прошёл. Полная сборка workspace, install-gate и CI не запускались.
* Воспроизведение на Linux: `python3 reproduce.py /путь/к/Proteus-modules`. Нужны Python 3, Git, Rust, доступ к закреплённым Cargo-зависимостям; скрипт создаёт отдельные checkout указанного SHA. Применение из исходного чистого checkout: `git apply --check /путь/candidate.patch`, затем `git apply /путь/candidate.patch`.
