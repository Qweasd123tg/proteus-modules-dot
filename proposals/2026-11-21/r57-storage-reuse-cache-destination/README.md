# WriteCache: одна вычисленная цель для публикации и квоты

[Патч](candidate.patch) к [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). При успешном атомарном rename тот же PathBuf передаётся штатному evict как защищённый путь. До изменения путь вычислялся дважды с одинаковыми неизменяемыми dir и key; для второго вычисления повторялись SHA-256 ключа, encoding и аллокации имени/полного пути.

Путь впервые вычисляется на том же месте после sync временного файла и сверки идентичности. Ошибка rename по-прежнему удаляет временный файл и возвращает прежний результат; первая обработка ошибок evict/ETag остаётся после публикации. Квота, её read_dir и metadata, правило mtime, локатор/инкарнация, writer lease, источник/проверки SHA, ETag и v1 не меняются. Никакого межзапросного cache, периодического quota batching или переноса работы между процессами нет. [Исходное наложение](composition.log) на фактический writer M100/#277 проходит в отдельной копии; суммарный стек не запускался этим тестом.

## Почему этот путь

[Отдельный untimed SDK-трейс](COMPARE-REACHABILITY.md) для обычного JSONL-125k restore/resume и нормального локального хода показал ноль CompareSnapshots; предлагаемый двойной fallback не привязан к этому сценарию и оставлен без изменений. При отсутствующем view Base и M100 оба сделали **320 WriteCache**. Это число вызовов, не доля времени.

## Проверка

Нативный locked release scope: **63 unit + 2 process** на Linux, Rust 1.95; один прежний ручной тест пропущен. [Лог](native-release.log). Временная тестовая вставка включена в worker только для измерения; исходный патч её не содержит. Полный workspace и Windows не проверялись.

Один release worker с двумя режимами в измерительной копии: в stock-режиме после rename вычисляется старый второй путь, в candidate используется возвращённый правильный путь. Флаг установлен до любых запросов и читается без выделений. Один и тот же Rust allocator observer считает вызовы и запрошенный размер alloc/alloc_zeroed/realloc только на потоке внутри WriteCache, не IPC, другие потоки, SQLite/C, RSS или задержку. В обоих режимах совпадают точные ответы, независимый SHA ETag, SHA имени и содержимое каждой записи после исключения только случайного snapshot_id (до исключения его точное равенство исходному запросу проверяется). Первую, среднюю, последнюю запись читали также исходным отдельным production worker.

| Backend | Меньше alloc-запросов на запись | Меньше запрошенных байтов на запись | Всего меньше (alloc / B) |
|---|---:|---:|---:|
| jsonl | 41 | 1117–1117 | 39360 / 1072320 |
| sqlite | 41 | 1117–1117 | 39360 / 1072320 |

Три чередующиеся пары по 320 нормальных derived keys после одной пары разогрева; обе кампании используют те же canonical документы. [Сырые счётчики](allocate.jsonl). Это изолированная разница на точном upstream; предыдущее форматирование SHA из #253 в M100 уже дешевле, поэтому число аллокаций standalone нельзя обещать для интегрированной версии. Время выполнения и Desktop startup не измерялись.

## Повторение

На точной базе применить candidate.patch. В штатном checkout запустить locked native test двух packages session-storage и proteus-session-storage-module. Для отдельной измерительной копии после применения выполнить python3 instrument.py CHECKOUT, затем cargo test --locked --release -p session-storage -p proteus-session-storage-module; отдельно python3 measure_cache.py EXPERIMENTAL_RELEASE_WORKER --stock-original STOCK_WORKER. Нужны Linux, Python 3.11+, Rust/Cargo и зависимости из lockfile. Стенд использует только временные синтетические записи.
