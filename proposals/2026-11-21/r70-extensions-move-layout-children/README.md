# SDK Extensions: собирать контейнеры без повторной копии дерева

`stack`, `row`, `card` и `split` получают готовый массив дочерних виджетов во владение. Раньше `json!` преобразовывал этот массив обратно в JSON value и копировал всё поддерево, снова на каждом уровне вложенности. [Патч](source.patch) переносит массив в итоговый объект. Сигнатуры, порядок полей и детей, отсутствие заголовка в отличие от пустого и прежняя сериализация ширин остаются прежними. `fill`, который уже переносит детей, и `list`/`lanes` из #283 не меняются.

Реальные пути: Context (карточки и итоговый стек), Mode и Model (панели выбора), Usage (строки и карточки), Git (разделённая панель). Проверка ограничена собственно SDK и указанными ниже процессами, не нативным клиентом. База: [Proteus-desktop-extensions@892f627](https://github.com/Proteus-harness/Proteus-desktop-extensions/commit/892f627570369ed60d7205eb0d351c753ec4305f).

| Синтетическое построение на готовом узле | Успешных запросов | Запрошено байт |
|---|---:|---:|
| Строка с текстом 64 байта | 25 → 7 | 1 594 → 393 |
| Стек с текстом 64 КиБ | 25 → 7 | 67 069 → 396 |
| Четыре контейнера над одним узлом 64 КиБ | 147 → 29 | 271 575 → 2 204 |
| Карточка с пустым заголовком, 1 КиБ | 24 → 6 | 2 546 → 385 |
| Разделение со специальными дробными ширинами, 1 КиБ | 25 → 7 | 2 980 → 819 |

Контроль с одной строкой из буфера на 64 элемента: запросы снизились с 2 554 до 393 байт, но вместимость сохранённого массива выросла с 1 до 64 слотов. У пустого контейнера и `fill` результаты совпали. [Все наблюдения](measurements.log).

Счётчик включает успешные запросы выделения или перераспределения памяти на одном потоке при построении контейнера, без подготовки исходного дочернего узла, сериализации результата и HTTP. Числа не отражают задержку, RSS или удерживаемую память. Новый контейнер может сохранить запас ёмкости переданного массива: пустые слоты не копируются и не создаются повторно, но теперь остаются у результата. Уменьшение ёмкости намеренно не добавлялось.

- На точной базе в release: SDK **60 → 61** модульный тест и 1 doc-тест; Context **3/3**, Mode **4/4**, Model **10/10**. На точном M150 + #394: SDK **64 → 65** и 1 doc-тест; Context **4/4**, Mode **4/4**, Model **11/11**. Новый тест проверяет передачу того же буфера, неалфавитный порядок вложенных ключей, отсутствие и наличие пустого заголовка, ширины `None`, конечную, `-0.0`, `NaN` и обе бесконечности.
- Побайтное совпадение **9 кадров** обычных release-процессов Context, Mode и Model на каждой базе; тот же один GET Context. По **8** выходов измерительной сборки совпали побайтно. Счётчики повторились пять раз на каждую версию.
- Два порядка наложения с #394 дают одно дерево на M150; обратное наложение восстанавливает файлы. #393 в Desktop не затронут. [Проверки](checks.log).

Повтор в согласованном слоте: `python3 differential.py точный-git точный-m150-extensions патч-394 --target прогретый-target --lock общий-build-lock --admit-exclusive`. Нужен явный `CARGO_HOME` с уже доступными зависимостями. Без `--admit-exclusive` выполняется только проверка входов. Один Cargo job, locked/offline; стартовый минимум 512 МиБ на обоих томах, остановка при свободном месте ниже 256 МиБ. Входные исходники не меняются. Полный workspace, физическая упаковка и нативное окно не проверялись.
