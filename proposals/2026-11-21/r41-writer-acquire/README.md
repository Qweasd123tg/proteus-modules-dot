# Session storage: выдавать второй writer handle только после успешного восстановления

**Исправление корректности, не ускорение.** В JSONL и SQLite дополнительный `AcquireWriter` мог завершиться ошибкой, но оставить за собой зарегистрированный токен. После восстановления данных и освобождения всех действительно выданных handles процесс продолжал держать файловую блокировку. Другой экземпляр сервиса не мог продолжить запись без остановки прежнего.

Кандидат сначала проверяет locator и восстанавливает состояние журнала, и только после успеха создаёт и регистрирует новый токен. Проверка обычных запросов с уже выданной lease по-прежнему требует живого токена и правильного поколения. Восстановление общее для обоих путей и не зависит от того, жив ли первый выданный токен. Не меняются контракты, формат журнала, правила проверки принадлежности, сама файловая блокировка или её срок жизни при наличии настоящего владельца.

**База:** [Proteus-modules@9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51); Core SDK pin `0c1b7572313230e5d123e95c722e1258a2e9ecd6`. Локальный commit `172fa6851bd5b31ee1b856b311de4d3a4d16ba7e`. SHA-256 [source.patch](source.patch): `4f7e5c033d1c3b6d5702dfcc46c815bff6042a89db28e8d5823703e8209a58f8`.

## Проверка

В двух независимых тестах на временных сессиях проверены: штатная замена первого handle, hibernate, два отказа при восстановлении, успешный повтор, сохранение эксклюзивности у живого владельца и передача блокировки после его последнего release. У нового владельца из журнала прочитаны исходное сообщение и та же ревизия. Исходный экземпляр сервиса не останавливался. Оба экземпляра в тесте находятся в одном процессе и независимо открывают файловую блокировку.

| Сценарий | База | Кандидат |
|---|---|---|
| JSONL: другая инстанция получает lease после последнего release | Ошибка: блокировка занята | Получает lease и восстанавливает историю |
| SQLite: тот же сценарий | Ошибка: блокировка занята | Получает lease и восстанавливает историю |

[Красный прогон](before.log) и [зелёный прогон](after.log) используют одни и те же тесты, различается только production-код. Это не оценка частоты отказов, времени или потребления памяти. Реальные сессии не использовались.

- [Проверка затронутого scope](suite.log): 65 библиотечных и 2 процессных теста прошли, 1 существующий ручной замер пропущен. `cargo fmt --all --check` и `git diff --check` прошли. Полный workspace не запускался. Штатному Python runner в офлайн-кеше не хватило `android_system_properties v0.1.5` на этапе cargo metadata; затронутые crates проверены напрямую Cargo.
- [Проверочная установка dev-worker](stage.log): SHA-256 установленного бинарника совпал с module.json. Не релиз и не обновление работающего worker.
- Патч самостоятельный. На отдельных кандидатах metadata ETag, Gear, повторного PutBlob и WriteCache проверена применимость `git apply --check`; совместный прогон этих стеков не заявляется.

В чистой рабочей копии базы: `git apply /path/to/source.patch`, затем `cargo test --locked -p session-storage -p proteus-session-storage-module -- --test-threads=1`. Только новые проверки: `cargo test --locked -p session-storage --lib failed_additional_writer_acquire`.
