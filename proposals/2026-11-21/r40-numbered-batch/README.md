# read_many_files: нумеровать строки без промежуточного массива

Патч для `Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51`. Локальный commit: `42032aebae25011f4797efe592cbc4b6e9a45e7a`. Меняется только форматирование в Rust file-tools при `line_numbers=true`; интерфейс, single-file reader, поиск, Core, данные пользователя и зависимости не меняются.

До патча для каждого прочитанного файла создавалась отдельная строка на каждую строку текста, затем весь вектор склеивался через LF. Общий бюджет ответа применялся уже к склеенному результату. Новый код пишет в один `String`, останавливаясь после первой строки, которая выводит размер за бюджет. Именно **после**, а не при точном совпадении: иначе оставшийся текст мог ошибочно считаться полностью показанным. Общий код по-прежнему режет результат по границе UTF-8 и заполняет те же метаданные. Входной префикс по-прежнему полностью читается и проверяется на UTF-8 до форматирования; не заявляется никакого сокращения дискового I/O. Временный результат одного файла может превысить бюджет на последнюю строку: это не строгая граница heap.

## Что измерено

Прямой вызов реального JSON-обработчика `ReadManyFilesTool::invoke_json` в двух сборках исходников. Счётчик текущего потока охватывает разбор запроса, чтение файла, форматирование и сериализацию ответа, но не подготовку файла/аргументов, транспорт и проверку результата. Сумма байтов выделений включает полные новые размеры realloc, это не RSS или пиковая память. Linux x86_64, rustc 1.95.0, `-C opt-level=3` для проверяемого crate, неизменные кэшированные зависимости с pinned Core `0c1b7572313230e5d123e95c722e1258a2e9ecd6`. Три повтора в каждой сборке дали одинаковые счётчики.

| Вход | Выделения, до → после | Запрошенные байты, до → после |
|---|---:|---:|
| 12 000 строк `x\n`, всё помещается | 12 123 → 124 | 1 532 885 → 827 792 |
| 65 536 пустых строк, бюджет 65 544 байта вместе с заголовком | 65 661 → 124 | 4 649 179 → 793 750 |
| 3 короткие строки с CRLF/LF | 106 → 104 | 9 573 → 9 486 |
| 12 000 тех же строк без нумерации | 108 → 108 | 312 798 → 312 798 |

Побайтовая эквивалентность ответов (включая метаданные и ошибки) проверена на 8 сценариях: добавлены пустой файл, одна строка 64 КиБ, срез Unicode, неверный байт позднее видимого префикса. Ошибочный ответ сравнивается после замены только временного пути, одинакового для обеих сторон. Все значения и хеши в `results.log`. Латентность процесса, GUI и рабочий набор не измерялись.

## Проверки и воспроизведение

- Полный тестовый target библиотеки file-tools: **30/30** прошли, без пропусков; установлен ripgrep 15.2.0. `suite.log` относится к неизменённым после прогона исходникам кандидата. Новый тест запускает настоящий инструмент с бюджетами от отсечения части номера строки до точного попадания, включая пустые строки, CRLF, emoji, tab и завершающий LF.
- `cargo fmt --all --check` и `git diff --check` прошли. Исходники библиотеки скомпилированы непосредственно rustc с уже собранными реальными зависимостями от указанного pinned Core. Весь workspace, упаковка и интеграционный запуск из Desktop не проверялись.
- На обычном checkout с зависимостями в Cargo: `cargo test --locked -p file-tools --lib` (после применения патча). Для A/B запустите `python3 reproduce.py /path/to/Proteus-modules`. Стенд сам извлекает точный исходный commit в изолированные временные каталоги, применяет `candidate.patch` только к кандидату, компилирует тест с `probe.rs`, сверяет полный wire-ответ и счётчики. Можно передать внешнюю `CARGO_TARGET_DIR`, чтобы не пересобирать зависимости. Опциональный `--local-compiler` нужен только при использовании готовых локальных rlib. Сами числа байтов могут зависеть от сборки и длины временного пути.
