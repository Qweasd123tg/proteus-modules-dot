# Desktop: читать кэш высот блоками, сохранять в памяти только нужный префикс

При открытии истории Desktop может восстановить оценки высоты строк из дискового кэша. До патча читатель отдельно извлекал и подавал в SHA-256 каждое поле 17-байтовой записи. Кроме того, под результат он резервировал место по числу **всех** записей в файле, даже если после изменения истории можно было использовать лишь короткий подтверждённый префикс.

Теперь записи проверяются непосредственно в существующем буфере чтения. Копируется только запись на границе двух заполнений. Один вызов SHA-256 получает весь непрерывный фрагмент, при этом **каждая** запись по-прежнему проходит проверку, в том числе за границей возвращаемого префикса. Прерывания чтения повторяются, как и в прежнем `read_exact`. Для выходного вектора резервируется не больше числа сохраняемых строк: в каждом допустимом диапазоне есть хотя бы одна строка.

Не меняются формат на диске, байты контрольной суммы, выбор ревизии, округление частичного диапазона, бюджет, процессная очередь, загрузка страниц и геометрия нативного окна. Это отдельное изменение от [#293](https://github.com/Qweasd123tg/proteus-modules-dot/pull/293), где ускорялся пересчёт геометрии уже после загрузки.

**База:** [Proteus-desktop@b6a7ec2](https://github.com/Proteus-harness/Proteus-desktop/commit/b6a7ec2d8d7e486c8aba01291aa8c89774c4cded). SHA-256 патча: `396452f4ea0167d20931de0a019ca89a609164cc94bc501d18a1cdaac7b25a35`.

## Измерение

Замер всего `disk::load` с настоящим файлом, открытием, проверкой длины и SHA-256, построением результата. Файлы синтетические, кэш страниц ОС прогрет; запись fixture, проверка результата и освобождение загруженного snapshot вне таймера. Linux x86-64, rustc 1.95.0, релизный режим на одном логическом CPU. Медиана 12 процессов на каждую версию, порядок чередуется. Каждый процесс выполняет один отброшенный вызов и берёт медиану 32 остальных.

| Записей в файле и вид чтения | Медиана, мкс, до → после | Ёмкость выходного вектора, байт, до → после |
|---|---:|---:|
| 16, полный снимок | 3,75 → 3,47 | 384 → 384 |
| 200, полный снимок | 9,40 → 7,58 | 4 800 → 4 800 |
| 16 384, полный снимок | 532,47 → 277,27 | 393 216 → 393 216 |
| 16 384, подтверждено 8 строк | 504,70 → 249,36 | 393 216 → 192 |
| 16 384, подтверждено 200 строк | 507,22 → 249,59 | 393 216 → 4 800 |

Ёмкость рассчитана из фактической `Vec::capacity()` × размера элемента. Это не RSS и не пик памяти процесса. Для всех случаев от 200 записей кандидат был быстрее в 12 из 12 соседних пар измерений; небольшая разница на 16 записях несущественна. Замер не распространяется на холодный файловый кэш ОС, запуск Desktop или скорость показа чата.

## Проверки

- В изолированной проекции настоящих модулей карты высот и дискового кэша прошли 24 штатных теста до и 25 после, с зависимостями, совпадающими с исходным `Cargo.lock` по источнику, версии и checksum. Игнорируемый микрозамер запущен отдельно.
- Новый тест сохраняет 1 000 строк, восстанавливает две строки из первого диапазона, а затем изменяет **валидный** тег в отброшенном хвосте. Загрузка всего файла отклоняется по checksum. Проверяются также частичная высота и освобождение разрешения снимка. На всех пяти нагрузках стенд сравнивает каждый возвращённый диапазон и итоговые поля запроса с ожидаемыми данными.
- Проверены прямое и обратное применение, whitespace, rustfmt, совместное применение с #293 и 26 тестов карты и кэша на обоих патчах вместе. В комбинированной проверке не компилировался нативный потребитель геометрии; приложение, полный workspace и GUI не запускались.

Из checkout целевой ревизии: `git apply --check /путь/source.patch`, затем `git apply /путь/source.patch`. Для проверок и измерения: `bash verify.sh /путь/к/Proteus-desktop` с Linux, Python 3.11+, Rust 1.95.0 и заполненным Cargo-кэшем. Скрипт не меняет checkout и не запускает сеть. Можно закрепить на ядре, например `taskset -c 1 bash verify.sh /путь/к/Proteus-desktop`, если это ядро доступно. Полные результаты в `evidence.log` и `combined.log`.
