# Desktop: быстрее искать пересечение окон истории

Когда Desktop возвращается к последним сообщениям или открывает далёкий фрагмент истории, он ищет первую старую строку, ключ которой есть и в новом окне. Потом строит изменения списка, оставляя общий участок на месте. Если первые ключи не совпадают, прежний поиск мог многократно обходить почти всё новое окно. Для непересекающихся окон он проверял все пары строк.

Патч оставляет прямую проверку самой первой строки и небольшого префикса. Для дальнейшего поиска, если в новом окне хотя бы 16 строк, он сначала проверяет порядок ключей. Только в уже упорядоченном окне использует двоичный поиск, а ключи вне диапазона пропускает без него. При нарушении порядка продолжает прежний прямой поиск. Ничего не сортируется, не копируется и не индексируется, дополнительных аллокаций нет. При повторах по-прежнему выбирается самый ранний ключ в старом окне и первое его появление в новом; список `Change` строится в прежнем порядке. Не меняются навигация, высота строк, ограничения истории, ключи и сетевые запросы.

База: [Proteus-desktop b6a7ec2d](https://github.com/Proteus-harness/Proteus-desktop/commit/b6a7ec2d8d7e486c8aba01291aa8c89774c4cded). SHA-256 патча: `c900d9d1cec4badecef99eb2d9fc321de0403f7ae05fee25e40be4cf5177c424`. Это не исправление совпадающих идентификаторов [#274](https://github.com/Qweasd123tg/proteus-modules-dot/pull/274): здесь оптимизируется использование уже полученных ключей, а не их генерация. Проверено применение в обоих порядках.

## Ключи и замер на настоящем редьюсере Desktop

Фикстуры создают синтетические сообщения через исходные функции Desktop, а не вручную присваивают последовательные ключи. Codex-окно строится через `external_upsert` и штатное вытеснение до 200 строк/8 МиБ после каждого сообщения. Архив создаётся клонированием перед ростом живого окна. Свежая Core-страница создаётся через `Transcript::reset`, как в загрузчике истории; в исходном живом окне уже удалён первый блок. Контроль с загрузкой старой Codex-страницы использует `external_prepend`.

| Сценарий | Границы ключей нового окна | Порядок проверен | Медиана, мкс |
|---|---:|---|---:|
| Возврат Codex после 65 вытеснений | 66…265 | Возрастающий | 9,408 → 0,954 |
| Возврат Codex после 200 вытеснений | 201…400 | Возрастающий | 22,745 → 0,951 |
| Свежая 50-строчная страница Core | 1…50 | Возрастающий | 4,493 → 0,978 |
| Codex: контроль с добавлением старой страницы | 401…400 | Нарушен | 27,161 → 27,252 |
| Совпадающие 200 строк (контроль) | 1 синтетический диапазон | Возрастающий | 0,160 → 0,164 |
| Сдвиг на четыре строки (контроль) | 1 синтетический диапазон | Возрастающий | 0,667 → 0,673 |

Порядок ключей не предполагается для общего случая. Время включает только построение изменений из готовых окон, не загрузку или работу с текстом. Оптимизированный Linux x86-64 бинарник без счётчика, восемь чередующихся пар на одном логическом CPU. Все 11 замеров аллокаций дали тот же результат до и после; в сценариях с заменой окна один запрос на 32 Б. Ускорение не заявляется для близких совпадений или неупорядоченных окон.

## Проверка

- 41/41 исходный и 43/43 новых/исходных теста полного модуля транскрипта прошли на оригинальных контрактах. Новый тест проверяет первый дубликат на упорядоченном пути, второй проверяет исходный порядок выбора при перестановке.
- 3 994 сравнения полного списка `Change` с исходным алгоритмом. Есть пустые окна, поздние совпадения, повторы, перестановки, отсутствие пересечения и четыре описанные модельные фикстуры.
- Все 124 внешних зависимости сверены с исходным lock, включая Git-коммит контрактов. Проверены применимость, обратное применение, git diff --check и rustfmt. Оба порядка применения с #274 дают одинаковый исходный код. Результаты и замеры: [evidence.log](evidence.log).

## Как повторить

Из checkout указанной ревизии: `git apply --check /путь/source.patch`, затем при необходимости `git apply /путь/source.patch`. Узкая проверка: `bash verify.sh /путь/Proteus-desktop`. Нужны Git, Bash, Python 3.11+, Rust 1.95.0 с rustfmt и подготовленный локальный кеш для `harness.lock`. Для сопоставимого замера закрепите прогон на одном доступном логическом CPU через `taskset`. Проверка не правит checkout. Полный workspace, GPUI, настоящее окно и прокрутка не запускались.
