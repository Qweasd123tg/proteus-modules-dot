# Storage: сразу резервировать буфер для небольших существующих cache-файлов

При ReadCache worker уже открывает файл и проверяет, что это обычный
файл. Если его известный размер не превышает 64 КиБ и действующего
лимита чтения, этот размер теперь используется как начальная ёмкость
буфера. Раньше буфер многократно увеличивался при чтении. Для
больших файлов и всех не-кешевых читателей остаётся прежний режим.

Размер из metadata не участвует в принятии данных: чтение по-прежнему
проверяет реальный EOF и ограничено maximum + 1, после чего применяется
старый лимит. Чтение и metadata идут через тот же открытый дескриптор.
Не меняются JSON-проверка, ETag, сравнение source/revision, повторная
проверка инкарнации, запись cache и каноническое хранилище.
Отсутствующий файл не доходит до выделения буфера; пустой файл
не выделяет его. При обычной атомарной замене уже открытый файл
по-прежнему читается по своему дескриптору. Если другой код вручную
укоротит тот же открытый файл после metadata, буфер может временно
сохранить до 64 КиБ; фактически прочитанные байты и ошибки те же.
Буфер не хранится после запроса.

## Точный замер, без тайминга

Из существующего валидного view синтетического JSONL-125k прочитаны
320 реальных cache-документов (317 подходят под порог, три нет),
8 301 484 B. Один и тот же диагностический release-воркер
переключал старое чтение и подсказку в двух парах с обратным
порядком. На точном main в обеих парах:

| Что считали на 320 попаданиях | До → после |
| --- | ---: |
| Read-family syscalls процесса SDK-воркера | 7 385 → 4 850 (−34,3%) |
| Вызовы аллокатора внутри ReadCache | 113 933 → 111 395 |
| Запрошенные аллокатором байты внутри ReadCache | 40 646 117 → 37 567 496 (−7,57%) |

В обеих ветках SDK-воркер получил те же 8 714 601 B (Linux rchar,
включая запросы/identity). Syscr учитывает все read-family вызовы
процесса в этом сценарии, включая чтение запросов и identity, а не
только cache-файл. Аллокации включают проверки, парсинг и ETag, но
не SDK-сериализацию. Это счётчики, **не оценка задержки, RSS,
пиковой памяти или всех запросов при холодном восстановлении**.
Контроль отсутствующего ключа совпал в обеих ветках: 108 вызовов
аллокатора, 5 084 B на весь запрос, без аллокации буфера файла.

Отдельный std-probe того же набора файлов отделяет сам буфер от
остального worker: 2 904 → 366 alloc/realloc, 24 182 784 →
21 104 163 запрошенных B. Числа малого, пустого, предельного,
вообще отсутствующего и принудительно укороченного файла
сохранены как контроль. Строки режима 1 относятся к сравнительному
черновому cap, режим 2 принят (порог без изменения больших файлов).

## Варианты и проверки

- [candidate.patch](candidate.patch), точные Modules
  9469e3b12529d08b1f4a76882693e2065e842c51; Core SDK
  0c1b7572313230e5d123e95c722e1258a2e9ecd6.
- [candidate-cumulative.patch](candidate-cumulative.patch), **вместо**
  первого варианта для текущего R62 M150-preflight. Там уже есть
  streaming equality и новая cache-envelope константа. Изменение
  выдаёт metadata из того же существующего открытия и stat, не
  меняя проход equality. Отдельный composed release worker повторил
  тот же raw parity и 7 385 → 4 850 syscalls в обеих парах; alloc
  95 373 → 92 835, запрошенные B 40 298 597 → 37 219 976.
  На отсутствии ключа 62 вызова и 4 389 B в обеих ветках.
  Два варианта не складываются, это одна оптимизация.
- Точный main, locked release: **65 тестов прошли, один прежний
  ignored**. Новые тесты покрывают проверку файла, EOF/лимит,
  реальные рост и укорочение открытого локального файла.
- Сырые байты всех 320 ответов SDK и их ETag совпали со stock
  **без нормализации**, также совпали ответ на отсутствующий
  ключ и HEAD с указанным правильным source. Имена и SHA всех
  320 файлов и журнала продемонстрированно неизменны. Тест
  только читает приватный материализованный fixture R59.
