# Session-storage: не пересчитывать уже забытые байты при разбиении blob

База [Proteus-modules@9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51), локальный commit `4c4076f3c8ba42e1a15b4f0d695cf5693fb3c188`. Один файл: `storage/session-storage/src/blob_codec.rs`. Патч самостоятельный, не требует предыдущих предложений.

**Почему границы те же.** Первое разрешённое разбиение содержимого находится после 16 КиБ. На каждом байте аккумулятор Gear сдвигается влево на один бит, прибавляется табличное значение, арифметика идёт по модулю 2⁶⁴. Вклад всего, что предшествовало последним 64 обновлениям, в точности нулевой (множитель 2⁶⁴). Поэтому в новом чанке до первой проверки можно пропустить 16 320 байт. После неё состояние побитово совпадает со старым до следующей границы. Целый остаток до 16 КиБ включительно не имеет внутренней разрешённой границы. Максимум по-прежнему 64 КиБ; после разреза расчёт начинается сначала. SHA-256 каждого чанка и всего payload по-прежнему читает **все** соответствующие байты. Не меняются manifest, содержимое файлов, проверка коллизий, fsync, чтение, форматы журнала и внешние контракты.

**Замер** всей реальной `blob_codec::pack` на уже существующих чанках. Один Linux-процесс, одинаковые файлы и кеш ОС, порядок вариантов чередуется. Два отдельных запуска: в первом считали настоящие обращения к Gear; во втором счётчик в бинарнике отсутствовал. Для CPU взяли 24 пары после трёх начальных из 27. В таблице отношение CPU — медиана попарных отношений, а не отношение отдельных медиан.

| Вход | Чанки | Обновления Gear, до → после | Медиана CPU, мс, до → после | Отношение CPU |
|---|---:|---:|---:|---:|
| 256 КиБ, псевдослучайные | 6 | 262 144 → 164 403 | 0,834 → 0,635 | 0,830 |
| 256 КиБ, повтор фрагмента JSON | 4 | 262 144 → 196 864 | 0,702 → 0,604 | 0,860 |
| 4 МиБ, псевдослучайные | 97 | 4 194 304 → 2 614 761 | 12,980 → 10,782 | 0,838 |
| 4 МиБ, нули | 64 | 4 194 304 → 3 149 824 | 12,166 → 10,559 | 0,850 |
| 16 383 байта, bypass | 0 | 0 → 0 | <0,001 → <0,001 | без заявления о выигрыше |

Это стоимость упаковки синтетических данных при повторном использовании чанков, не скорость записи нового журнала или запуска Desktop. Время первой публикации с fsync, память процесса и частота таких входов у пользователей не измерялись. Сам код упаковки обеих версий собирался `rustc 1.95.0 -C opt-level=3`, с одинаковыми ранее собранными debug-rlib его зависимостей; это не измерение релизного бинарника продукта. В `timing.csv` для каждой пары также есть стеновое время. Поля row: вид данных, байты, число чанков, индекс пары, новый вариант, CPU нс, стеновое время нс, число обновлений (только в `work.csv`), SHA-256 всего сохранённого manifest либо raw для bypass.

**Совместимость и проверки.** Для 60 входов (12 размеров, включая 0, оба края 16 и 64 КиБ, до 1 МиБ; нули, текст, три seed) исходный и изменённый код в отдельных каталогах вернули байт-в-байт одинаковый результат. Обе версии прочитали и восстановили исходные байты из файлов обоих вариантов. Постоянный regression test фиксирует точный естественный cut на минимальной границе, принудительный максимум и семь границ старого детерминированного payload. `cargo test --locked --offline -p session-storage -p proteus-session-storage-module -- --test-threads=2`: прошли 64 библиотечных и 2 процессных теста, пропущен один существующий ручной perf-тест. `cargo fmt --all --check` и `git diff --check` прошли. `package.py --profile dev --package session-storage --install` собрал и установил worker в отдельную staging-папку, SHA сверена с manifest, версия `0.1.0-alpha.3`. Общий Python runner до запуска тестов не смог разрешить Android-only зависимость в офлайн-кеше, поэтому выполнены целевые тесты непосредственно через Cargo с неизменённым lockfile. Полный workspace не проверялся.

**Повтор.** `python3 verify.py /path/to/Proteus-modules ./measurements` (Linux, Rust 1.95, Cargo и lld), затем `python3 summarize.py ./measurements`. Первый скрипт создаёт отдельную временную копию точной базы, проверяет и применяет `source.patch`, по умолчанию компилирует пример в Cargo release. С необязательным `--cache /path/to/compatible/debug-target-root` он использует rustc и существующие зависимости, не пишет в Cargo target: именно так получены приложенные числа. Производственный патч не содержит измерительного кода.
