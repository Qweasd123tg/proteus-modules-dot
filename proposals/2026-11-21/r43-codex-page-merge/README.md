# Desktop: объединять страницу Codex с каталогом за один проход

Когда ответ `thread/list` приходит в окно, для каждой записи клиент линейно искал строку в общем векторе сессий. Одна страница из 50 новых записей в каталоге из 4 096 строк требовала более 200 тыс. сравнений. Это работа над метаданными на UI-потоке, не запрос к модели или загрузка истории.

Для нетривиальных страниц патч строит временный индекс только входящих Codex ID, без копирования строк ключей. Клиент один раз проходит существующие строки, при полном совпадении заканчивает досрочно, затем добавляет новые в исходном порядке страницы. Обновление не передвигает существующую строку. При повторяющемся ID позицию задаёт первое появление, данные берутся из последнего; протокол удаления и пространство ключей Proteus не меняются. При ≤8 входящих или ≤32 существующих строках остаётся прежний последовательный поиск непосредственно в обработчике. Постоянного индекса, дополнительных запросов или изменений пагинации нет.

**Измерено только слияние метаданных.** Синтетические ID и заголовки, std::time::Instant, Rust 1.95.0, `-C opt-level=3`. Исходные метаданные готовились до таймера; в таймер включено освобождение входных данных. Порядок и отпечаток значимых полей проверяли вне таймера. Каждое число ниже: медиана шести процессов на сторону, с чередованием порядка; каждый процесс выполнял один прогрев и 21 замер каждого сценария. Хост общий, короткие замеры шумные.

| Существующие / входящие | Сценарий | База, мкс | Патч, мкс |
|---|---|---:|---:|
| 4 096 / 50 | обновления в конце | 707,23 | 125,89 |
| 4 096 / 50 | все ID новые | 894,25 | 179,98 |
| 4 096 / 50 | обновления в начале | 8,77 | 14,44 |
| 4 096 / 1 | строка в конце | 32,59 | 26,30 |
| 32 / 16 | обновления в небольшом каталоге | 3,74 | 2,37 |

Индекс выгоден прежде всего для новых и дальних строк. По небольшой странице в начале нельзя обещать ускорение: здесь вариант с индексом проиграл на 5,67 мкс. Дополнительные замеры приведены в `evidence.log` (в том числе по четырём и пяти строкам, где прямой путь тоже дал более высокую медиану). Память, время до первого кадра, сетевые запросы и длительность работы нативного окна не измерялись.

**Проверено:** [точная база Desktop](https://github.com/Proteus-harness/Proteus-desktop/commit/b6a7ec2d8d7e486c8aba01291aa8c89774c4cded). На исходной версии 5/5, после патча 6/6 тестов настоящего модуля conversations; добавлено сравнение с последовательными upsert на смеси повторов, двух драйверов и исключённых удалений. Для всех десяти измерительных сценариев совпали контрольные отпечатки. Скрипт извлекает сами строки обработчика из обеих версий и компилирует их с настоящими типами Page/Summary, ConversationSummary и ChatKey; вместо окна используются только два его поля. Полной сборки и проверки нативного окна не было.

Применение: в checkout указанной базы выполнить `git apply --check /путь/source.patch`, затем `git apply /путь/source.patch`. Прямое и обратное применение проверены; SHA-256 патча: `be681888f9804d6ee0f9080898608d6807f609b940186be200e02ccb7f2eda19`.

Воспроизведение: `bash verify.sh DESKTOP_REPO SERDE.rlib SERDE_JSON.rlib UUID.rlib PROTEUS_CONTRACTS.rlib`. Нужны совместимые rlib из кэша зависимостей закреплённой версии Desktop (serde с derive), rustc в PATH, git, tar, Python 3 и lld на Linux. Проверка работает во временном каталоге. После применения в полной сборочной среде можно запускать штатные тесты через `python3 scripts/test.py --bin proteus-native conversations::`.
