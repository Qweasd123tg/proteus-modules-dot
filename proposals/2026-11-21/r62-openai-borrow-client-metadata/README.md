# OpenAI Responses: не копировать словари client_metadata перед сериализацией

База: **Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51**. Локальный commit `4a0ee6b17cadeb2d365b74992dc0b450f1b8da5e`. Меняется только формирование поля `client_metadata` и его тест.

Раньше адаптер глубоко копировал строки из профиля и запроса, объединял их, затем ещё раз выделял память при преобразовании в JSON. Теперь один непустой словарь сериализуется по ссылке. Если непусты оба, объединяем только ссылки в прежнем алфавитном порядке. Значение из запроса по-прежнему перекрывает профиль, даже если это пустая строка. Когда оба словаря пусты, поле отсутствует. Подготовку аргументов инструментов и содержимое других полей не меняли.

## Проверки

- **16 полных побайтных сравнений** (по три пары) для обычного запроса с отсутствующими, короткими и расширенными метаданными. Включены оба режима порядка JSON-ключей, Unicode, частичное/полное перекрытие и пустая строка как значение. Пробник отдельно сверяет объединение и порядок ключей.
- Целевые model-pack тесты построения OpenAI request: **14/14 → 15/15** в Debug workspace-графе. Для сравнения с Release sorted keys оба исходника собраны rustc 1.95.0 из тех же ранее собранных locked Cargo-зависимостей каждого графа. Общий target оставался без изменений. Полный workspace gate и реальный API не запускались.
- `rustfmt --check`, `git diff --check` и `git apply --check` на точной базе и M100. Все 100 выбранных патчей проверены по SHA256; пересечений нет. Патч #360 на том же файле меняет формирование аргументов инструментов; два порядка применения дают одинаковое результирующее дерево.
