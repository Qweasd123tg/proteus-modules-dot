# sqlite-memory: повторное использование подготовленного INSERT

**База:** `Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51`. Локальный проверочный commit `1e2a43d7ca44c3fe9901608ecd6a25aa89eec993`. `candidate.patch` затрагивает только `context_provider/sqlite-memory/src/lib.rs`. Это FTS SQLite-провайдер и инструменты `remember_fact` / `recall_memory`, не JSONL memory.

На прогретом соединении повторная компиляция неизменного SQL-шаблона INSERT не нужна. Теперь он использует имеющийся `rusqlite::Connection::prepare_cached`. Новых зависимостей, настроек и отдельной карты нет: на одном соединении задействован один ключ существующего LRU-кэша (у закреплённого rusqlite 0.41.0 вместимость по умолчанию 16). Обратная сторона: соединение держит одну подготовленную инструкцию для повторного использования; экономию RSS не заявляем. Оба запроса чтения оставлены без изменений: пилот с кэшем для SELECT не показал устойчивого выигрыша.

Тексты SQL, параметры, привязка к текущему соединению, mutex, порядок/ограничения выборок и передача данных через JSON не изменены. Параметры привязываются заново; закреплённый `CachedStatement::drop` очищает bindings перед возвратом в кэш, а rusqlite сбрасывает инструкцию после шага INSERT, в том числе после отказа SQLite. Не меняются настройки журналирования, FTS-токенизация, глубина разбора метаданных, обработка ошибок и wire-ответы.

## Проверки

* `cargo test --locked -p sqlite-memory --lib`: **11/11** на точном финальном патче, штатный crate исходника прошёл 10/10. Полный workspace/поставка не запускались. Штатная обёртка `scripts/test.py` остановилась при all-platform `cargo metadata` в offline-режиме из-за отсутствующего `android_system_properties 0.1.5`; прямой locked native Cargo-test прошёл.
* Вторая серия, одинаковая для исходника и патча: **4/4 на каждом**. Новый тест crate отдельно проверяет успешный INSERT с новыми параметрами после отказа триггера. Дополнительная серия проверяет обе реальные JSON-поверхности, вложенные метаданные и порядок/предел результатов, чтение с новыми параметрами после ошибки метаданных и ремонта, внешнюю запись через второе соединение с WAL и чтение после повторного открытия. Запись в сам модуль WAL не включает; WAL только в изолированной проверке. Проверено сохранение старого отказа для допустимого отдельно, но слишком глубокого внутри JSON-ответа внешнего значения (126 массивов), а также нулевой лимит.
* Применение: `git apply --check /путь/candidate.patch` на указанной базе, затем `git apply /путь/candidate.patch`. Проверки обеих версий: `python3 check-surfaces.py /путь/к/Proteus-modules`; парный замер: `python3 reproduce.py /путь/к/Proteus-modules`. Скрипты временно создают два checkout, не меняя исходный. Нужны Python 3, Git и Cargo с закреплёнными зависимостями.

## Измерения

Linux x86-64, Rust 1.95.0, `cargo test --release --locked`. Действительные `ToolModule::invoke_json` и `ContextProviderModule::provide_json`; SQLite in-memory, 96 посеянных записей на запуск; SQL, FTS и JSON остаются в измерении. Каждый замер охватывает 2000 вызовов на одном соединении, подготовка JSON-входов и сверка JSON-ответов вне таймера. Исходник и патч чередуются, одна разогревочная пара опускается. Это прогретый сценарий без записи на диск и без запуска нового worker-процесса для каждого вызова.

Два прогона, по девять измеренных пар в каждом. Медианы в мкс на вызов:

| Сценарий | Прогон 1, до → после | Прогон 2, до → после |
|---|---:|---:|
| `remember_fact`, подготовленный INSERT | 26,61 → 24,26 | 26,63 → 24,15 |
| Последние записи, контроль | 12,92 → 12,65 | 12,77 → 13,47 |
| FTS из инструмента, контроль | 66,20 → 60,67 | 65,64 → 66,26 |
| FTS из провайдера, контроль | 58,03 → 57,18 | 60,64 → 64,36 |

Время `remember_fact` снизилось на 8,9% и 9,3%; проверки чтения не показывают устойчивого изменения и код запросов не менялся. Во всех четырёх сценариях все выводы совпали побайтно в обеих версиях и в обоих прогонах; включены два контрольных чтения данных после 2000 INSERT. Сырые разметки времени и хеши ответов приведены в `bench.log` и `recheck.log`. Не переносить эти результаты на дисковый SQLite, перезапуски worker или весь агентский ход.
