# Markdown: один хеш новой границы вместо хеша на каждый блок кода

При открытии ответа с несколькими закрытыми блоками Markdown-расширение вычисляло хеш от начала текста до конца **каждого** блока с завершённой строкой. Следующий блок перезаписывал предыдущее значение. Для дальнейшего потокового обновления нужен только последний хеш. [Патч](source.patch) при обходе блоков запоминает последнюю подходящую границу и вычисляет её хеш один раз. Для блоков одинакового размера это уменьшает объём данных **на построение нового отпечатка** с квадратичного до линейного; остальной рендер так не оценивается.

База: [Proteus-desktop-extensions@892f627](https://github.com/Proteus-harness/Proteus-desktop-extensions/commit/892f627570369ed60d7205eb0d351c753ec4305f). [Место изменения](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/892f627570369ed60d7205eb0d351c753ec4305f/packages/markdown-render/src/render.rs#L103-L160). Проверка уже сохранённого префикса, CR/LF за закрывающей строкой, список разрешённых языков и исходный парсер остаются прежними. Хешируется тот же срез тем же алгоритмом. Новая граница хранит число сегментов, блоков и определений ссылок на том же смещении. Если новых завершённых границ нет, существующая не заменяется.

Блоки идут по порядку исходника: `fences::parse` фильтрует `root.children` без переупорядочивания. `references::collect` обходит то же дерево по детям слева направо, записывая смещения листьев-определений. Поэтому число определений до последнего выбранного конца совпадает с прежним нарастающим счётчиком. При разборе хвоста смещение определения относительно хвоста, а не всего документа.

Есть одно осознанное различие при аварийном выходе. Сегменты и описывающая их граница теперь покидают кэш вместе и возвращаются при успешной сборке. Если построение узла вернуло ошибку или SDK перехватил панику, само сообщение об ошибке не меняется; следующий запрос пересчитывает представление без устаревших индексов. Код не меняет обработку исходного сообщения, проверку содержимого или обработчик ошибок SDK. Штатный GFM-парсер без MDX не предполагает синтаксических ошибок; сбой в [проверке восстановления](reproduce.py) искусственный, а не найденный способ сломать парсер входным Markdown.

| Первый рендер, блоков | Байт исходника | Байт передано в функцию хеширования, до → после | Время запуска и ответа процесса, мс, до → после |
|---:|---:|---:|---:|
| 0 (текст) | 14 | 0 → 0 | 1,73 → 1,80 |
| 1 | 269 | 268 → 268 | 2,33 → 1,95 |
| 32 | 8 608 | 142 000 → 8 607 | 7,73 → 5,79 |
| 256 | 68 864 | 8 848 768 → 68 863 | 11,01 → 8,91 |
| 1 024 | 275 456 | 141 170 176 → 275 455 | 69,84 → 29,34 |

Внутри каждого синтетического блока `rust` 256 байт текста. При потоковом переходе от 32 к 256 блокам за **обе ревизии вместе**: 257 → 3 вызова, 8 857 375 → 86 077 байт. Три оставшихся вызова нужны для записи первой границы, проверки её на следующем входе и записи новой границы. Это не экономия выделенной памяти: сравнивается количество просмотренных байтов исходника.

Время измерено без счётчика: семь пар запусков release-процесса с чередованием порядка, медианы; включены старт, обмен JSON по stdio и завершение. Файловый кэш ОС прогрет, сам процесс и его кэш документа новые при каждом измерении. На коротком тексте и 1–32 блоках выигрыша во времени не заявляем. Это синтетическая нагрузка, не измерение GUI, RSS или всего чата. Уменьшение объёма хеширования отдельно проверено инструментированными бинарниками.

## Проверка и повтор

- Точный пакет `cargo test --locked -p extension-markdown-render`: база **51/51**, патч **52/52**; те же результаты в release. В обоих наборах три теста настоящего процесса. Новый тест проверяет сразу несколько новых закрытий, последнюю строку на EOF, CRLF, доступность ссылок и совпадение результата потокового обновления с чистым пересчётом.
- В отдельных тестовых бинарниках принудительные `Err` и `panic` при построении прозы после закрытого блока дали одинаковый `content_error` на второй ревизии. На следующей исправленной ревизии патч вернул обычный `view` с тем же корнем, что и запуск с пустым кэшем; база снова вернула ошибку. В исходном патче и измерениях времени тестовых триггеров нет.
- В семи синтетических сценариях процесс выдал **побайтно одинаковые** JSON-ответы до и после. Среди них добавление блоков, правка текста внутри сохранённого префикса, смена списка языков и Unicode. [Сырые значения, SHA-256 каждого ответа](measurements.log), [проверки](checks.log).
- `python3 reproduce.py /path/to/Proteus-desktop-extensions` запускает A/B в отдельной временной копии точного коммита. Нужны Python 3, Git, Cargo, rustfmt и зависимости из Cargo.lock; при прогретом кэше можно задать `CARGO_NET_OFFLINE=true`. Скрипт проверяет прямое и обратное применение патча, формат, release-тесты пакета, неизменность ответов, счётчики и времена. Нативное окно, полный workspace и упаковка не проверялись.
