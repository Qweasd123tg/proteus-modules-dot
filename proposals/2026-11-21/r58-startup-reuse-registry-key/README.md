# Core: переиспользовать ключ сессии при запуске HTTP-наблюдателя

База: [Proteus Core 32e56ecb](https://github.com/Proteus-harness/Proteus-core/commit/32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f). При запуске HTTP и добавлении нового или восстановленного runtime Core нормализовал путь сессии для реестра, а затем повторно разрешал тот же путь для наблюдателя за активностью. Теперь наблюдатель получает именно тот ключ, под которым runtime внесён в реестр. Это убирает один вызов файлового разрешения пути и не даёт реестру и подписке разойтись, если исходный alias изменится между регистрацией и запуском подписки.

Путь bootstrap остаётся исходным. У входящих запросов сохранены нормализация пути, альтернативное написание имени журнала и проверка актуального runtime. Удаление и его gate, повторная проверка активности, takeover/authority, журнал, кеш, storage RPC, ранний HTTP-сигнал, ACK и SSE не меняются. Работа не переносится на первый запрос.

## Что проверено

В одном тестовом бинарнике исходные методы регистрации извлечены дословно (кроме имён), рядом запущены production методы кандидата. Обе стороны используют реальный AppServer и процесс stock JSONL-worker. Счётчик на месте фактического `session_key` видит:

| Измеренный участок | До → после |
|---|---:|
| Создание HTTP state с начальной сессией | 2 → 1 |
| Добавление handle, включая неизменённую публикацию активности | 4 → 3 |

Обе строки повторились на сессиях с материализованным журналом и без него. Отдельно проверены событие активности для каждого из двух handle, alias на директорию и файл журнала, остановка и снятие первой записи по alias, атомарная смена ссылки на второй handle и её активность после снятия первой записи. Штатные тесты preferred startup, возврата к допустимой сессии, SSE, разделения двух runtime, отклонения изменившейся привязки storage и удаления с остановкой операции вошли в **12/12**. Это не подсчёт системных вызовов ядра, измерение времени запуска или RSS.
