# Core: запуск события сессии без снимка исполнения

База: [Proteus Core 32e56ecb](https://github.com/Proteus-harness/Proteus-core/commit/32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f). При открытии SSE, stdio или ACP, а также при создании новой HTTP-сессии lifecycle-метод `start_session()` прежде собирал полный снимок исполнения и каталога инструментов. Из всего снимка он использовал только выбранную модель для `SessionStarted`. Повторное открытие и непустая сохранённая сессия не отправляют это событие, но раньше всё равно несли затраты на снимок.

Теперь lifecycle считывает только выбранную модель из того же состояния, до того же mutex. Событие отправляется один раз, в прежнем формате и с прежним model ref; неудача при записи события позволяет повторить попытку. Начатый ход по-прежнему использует собственный неизменяемый снимок с моделью, инструментами и доступностью approval. Конфиг, выбор полномочий инструментов, фактические запросы approval, канонический журнал, проверки resume и границы HTTP ready/ACK не меняются.

## Измеренный участок

Один debug test binary с настоящим Core и локальным process worker JSONL. В нём baseline код `start_session` извлечён дословно (кроме имён методов) из закреплённого base, candidate использует production методы патча. При сравнении session data создаются до начала замера; счётчик фиксирует запросы alloc/realloc только на потоке вызова `start_session`, не время или RSS. Микроизмерение чередует порядок. «32» означает 32 синтетических тестовых спецификации с описаниями около 1 КиБ, не типичный профиль. Контроль с 0 тестовыми спецификациями оставляет остальную конфигурацию рабочего Core.

| Сценарий | Spec | Вызовы alloc | Запрошено байт |
|---|---:|---:|---:|
| Непустая восстановленная сессия, lifecycle ничего не отправляет | 0 | 123 → 2 | 6 589 → 17 |
| Непустая восстановленная сессия, lifecycle ничего не отправляет | 32 | 1 890 → 2 | 286 835 → 17 |
| Новая сессия, первая отправка `SessionStarted` | 0 | 128 → 5 | 7 496 → 907 |
| Новая сессия, первая отправка `SessionStarted` | 32 | 1 895 → 5 | 287 742 → 907 |

В сценарии с 32 спецификациями опрос флага видимости инструмента на lifecycle 32 → 0. Опрос возможности approval только для lifecycle 1 → 0; в настоящем ходе измерители подтверждают, что оба опроса остались. Повтор на том же runtime, свежая/восстановленная сессия, параллельный старт и восстановление после ошибки сохранения события проверены. Канонический JSONL при lifecycle-запросе не меняется. Это не замер времени загрузки истории, модельного исполнения, GUI или экономии памяти всего процесса.

## Повторение

С Rust 1.95, штатным LLD и существующими локальными Cargo-артефактами:

    python3 probe.py CORE_32E56ECB CARGO_TARGET STOCK_STORAGE_WORKER COMPATIBLE_REFERENCE_MODULE

Использованы worker [Modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51) SHA-256 `e3fd78af7bd2d8af3f86de719639f4cd7872bfe402da03aa6030471edc921502` и локальный reference-module SHA-256 `008ac5f927183fbdfc0c8dc5e26b59a2c4d5525409e943d7a7227ec69fc77b93`. Никаких удалённых моделей. Проверки: forward/inverse apply, форматирование, 11/11 целевых тестов включая SSE, startup, точное состояние допуска хода, synthetic durable event и неизменный журнал. Патч применим поверх sealed M100 по контексту; совмещённая сборка и бенчмарк не проводились. [Числа и гейты](proof.log).
