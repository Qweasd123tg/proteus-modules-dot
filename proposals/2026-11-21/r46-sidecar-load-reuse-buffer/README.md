# Каталог сессий: повторное использование буфера при чтении индекса

[Патч](candidate.patch) для [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). Меняется только подготовка контрольной суммы при **чтении** индекса с диска. Полностью декодировав владеющий данными `Envelope`, загрузчик очищает длину входного `Vec`, пишет в него канонический `Index` тем же Serde, вычисляет прежнюю SHA‑256 и освобождает буфер до проверки меток blobs. Порядок проверок и их результаты остаются прежними.

- Контрольная сумма по-прежнему считается от **типизированного канонического JSON**, не от сырых байтов файла. `serde_json::to_vec` в закреплённой версии 1.0.151 использует тот же `to_writer`, только с новосозданным вектором.
- Предел 4 MiB остаётся на исходном файле целиком; пересериализация не получает нового лимита и может вырасти сверх объёма исходного файла. Не менялись parser, отклонение ошибок, проверки типа файла, checksum, identity, меток источника и blobs, fingerprint, правила аудита и обязательная верификация канонического журнала. Постоянного буфера или второго кэша нет.
- Пропуски дискового кэша, первый List с отсутствующими индексами и попадания в память по-прежнему идут старыми путями; патч не ускоряет их. Запись и файловая транзакция не изменены. Патч записи из draft [#296](https://github.com/Qweasd123tg/proteus-modules-dot/pull/296) проверен на наложение в обоих порядках: итоговые файлы идентичны. Это проверка композиции патчей, не прогон объединённой сборки.

## Проверки

`cargo test --offline --locked`: **65 unit и 2 process passed**, 1 штатный ручной тест пропущен. Два новых теста отдельно прошли на неизменённом загрузчике. [Паритет stdio SDK](rpc-parity.log): на каждом backend три пары свежих процессов с одинаковыми 10 строками List и отдельным прямым OpenSnapshot, без изменения байтов или меток индекса. Официальная обёртка остановилась на офлайн `cargo metadata`, которой не хватило кэшированного Android-пакета; полная сборка workspace не запускалась.

Проверки добавлены к существующему каталогу Rust-тестов и идут на JSONL и SQLite. На каждом backend загрузчик напрямую открыл исходный компактный индекс, альтернативный JSON (поля обёртки в другом порядке, whitespace, Unicode-escape), позиционное представление с каноническим выходом длиннее всего входного файла. Смена типизированного значения при прежнем checksum отклонена. Отдельно проверены 4 194 304 байта исходного файла (принимается) и +1 (отклоняется). Прямой вызов исключает ложный успех после автоматического replay. Существующие тесты также проверяют порчу индекса, blob-инвалидацию, проверку канонического источника и поведение аудита. [Лог](validation.txt).

## Результат замера

По этому синтетическому тесту **reuse** снизил пиковый логический heap дисковой загрузки примерно на 27% при 492 файлах и на 32% около лимита. Нет подтверждённого общего ускорения. Ниже исходник → кандидат; размеры обоих backend совпали до округления.

| Blob-файлов на сессию | Sidecar на диске | Сумма запросов к аллокатору | Пик живых байтов |
|---:|---:|---:|---:|
| 0 | 1.1–1.3 KiB | 11 → 7 KiB | 4.9 → 3.0 KiB |
| 492 | 57.8–57.9 KiB | 556 → 429 KiB | 239 → 175 KiB |
| 12 000 | 3.53 MiB | 33.5 → 25.5 MiB | 12.53 → 8.53 MiB |

Раннее освобождение входа даёт тот же общий пик на этих fixtures, но не убирает повторный выделяемый буфер и его рост: при 12 000 файлах checksum-фаза запрашивает около 8 MiB против 368 байт у reuse (остаток относится к прежнему кодированию digest). Прямая потоковая SHA уменьшила пик внутри checksum-фазы, но не пик всей загрузки при 492 и 12 000 файлах: в нём доминируют две карты меток. При этом частые мелкие `hash.update` сильно увеличили CPU. У буферизованной SHA не было выигрыша общего пика на больших fixtures; на маленьких 8 KiB дополнительного буфера этот пик увеличили. Дальше усложнять загрузчик ради SHA без новой метрики не стоит.

Два прогона по 390 наблюдений: [первый свободный](raw.csv) / [его медианы](summary.txt), [повтор с привязкой к одному CPU](repeat.csv) / [его медианы](repeat-summary.txt). Выигрыш памяти повторился. В более стабильном повторе медианы полного CPU при 12 000 файлах: JSONL 198.3 → 200.7 мс, SQLite 198.8 → 198.1 мс. В первом прогоне длинный JSONL шумел (243.9 → 337.6 мс), и это различие не повторилось. При 492 файлах медианы CPU в повторе 2.98 → 2.99 / 3.00 → 2.96 мс. Это экономия аллокаций, а не доказательство ускорения List, API или сети. Наблюдавшийся таймаут пользователя тест не объясняет.

## Как измеряли и как повторить

Синтетический микробенч **настоящего** дискового загрузчика, Linux x86-64 tmpfs; история 8×512 байт, настоящий serde и проверка файловых меток. На каждой fixture поочерёдно проверены точные прежние summary/revision/hint/digest/stamps пяти вариантов. 16 повторов на 0 и 492 файлах на сессию, 7 на 12 000 файлах с длинными именами. Порядок циклически сдвигается. `session-storage` собран с opt-level=3, зависимые crates одинаково из test profile. Замеры не отражают реальные диски или CPU приложения.

- **stock**: вход остаётся до конца загрузки; новый вектор для SHA. **early_drop**: освобождает вход до создания нового вектора. **reuse**: канонические байты пишутся в исходный вектор. **stream**: передаёт каждый фрагмент Serde напрямую в SHA-контекст. **buffered**: то же, но с 8 KiB `BufWriter` и явным flush. Только **reuse** в производственном патче.
- В аллокационном проходе `requested bytes` считает суммарный объём запросов alloc/realloc, `peak` логические одновременно живые байты на потоке, не RSS и не внутренние переходные буферы аллокатора; `hash peak` включает ещё живой результат parse и входной буфер в соответствующей фазе. CPU / wall измерены отдельным проходом без активного учёта аллокатора. `load` включает bounded read, JSON parse, re-encode/SHA, сверки и перепривязку результата; `hash` только канонический re-encode и SHA.
- Сборка и обычная проверка: применить патч к указанному checkout, затем `python3 scripts/test.py -p session-storage -p proteus-session-storage-module`. На Linux host-only кэше допустима прямая команда `cargo test --offline --locked -p session-storage -p proteus-session-storage-module` с `PROTEUS_TEST_HARNESS_ROOT` на локальную копию закреплённого Core `0c1b757`. Stock-оракул запускается переносом только изменённого `catalog/tests.rs` в точный исходный checkout и `cargo test --locked -p session-storage --lib service::catalog::tests::sidecar_load_`.
- Ручной тест замера: только в одноразовой копии с патчем запустить `python3 instrument.py /path/checkout`. В ней: `R46_NEAR_LIMIT=1 cargo test --locked --config 'profile.test.package.session-storage.opt-level=3' -p session-storage --lib r46_measure_durable_sidecar_load -- --ignored --nocapture --test-threads=1 >benchmark.log`. Затем `python3 summarize.py benchmark.log --extract raw.csv`. Инструментатор добавляет отдельные test-only копии настоящего loader, меняя в них только подготовку SHA и таймеры; он не модифицирует production blob/version guards.
- Для stdio SDK-проверки `python3 rpc_parity.py /path/stock-worker /path/candidate-worker` использует две обычные бинарные сборки `cargo build --locked -p proteus-session-storage-module` (разные `CARGO_TARGET_DIR` для stock/candidate) и отдельные свежие процессы для каждой операции.
