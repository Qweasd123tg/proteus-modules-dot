# Unified exec: не копировать весь вывод перед усечением

**Репозиторий:** Proteus-harness/Proteus-modules. База: `9469e3b12529d08b1f4a76882693e2065e842c51`. Изменены только `tool/shell-tool/src/unified_exec/output.rs` и его тесты. Это стадия формирования ответа после получения байтов, общая для `exec_command` и `write_stdin`. Одноразовый `shell` не затронут.

Раньше на обычном UTF-8 рендерер копировал весь буфер, даже если были нужны только начало и конец. При неусечённом тексте создавалась ещё одна копия, затем текст с заголовком и metadata копировались при формировании JSON. Теперь валидный UTF-8 и текст, поместившийся в бюджет, заимствуются. Заголовок с видимой частью вывода собирается в одной строке; готовые строка и metadata перемещаются в JSON-объект.

## Результат на заранее собранных входах

Байты, запрошенные у аллокатора одним вызовом реального `render_result`, включая финальную сериализацию JSON:

| Вход → байтовый бюджет | До | После |
|---|---:|---:|
| Короткий stdout, 21 байт → 40 000 | 3 570 | 3 100 |
| 32 КиБ ASCII, поместились | 266 458 | 134 981 |
| 1 МиБ ASCII → 40 000 | 1 373 081 | 244 012 |
| 1 МиБ emoji → 257, с capture metadata | 1 055 739 | 5 391 |
| 32 КиБ невалидного UTF-8 → 257 | 236 510 | 234 748 |
| 1 МиБ: середина отброшена ранее, края невалидны → 40 000 | 7 143 775 | 7 062 323 |

Это **не** пиковая память процесса и не скорость выполнения команды. На невалидных байтах по-прежнему нужна lossy-нормализация; при уже потерянной середине прежний внутренний маркер по-прежнему собирается до второго, видимого модели ограничения. Проверка UTF-8 сохраняется, размер буфера и лимиты вывода не увеличивались.

## Проверка

- Чистый checkout точной базы: `git apply --check`, применение и `git diff --check`; `rustfmt --check` изменённых исходников.
- 13/13 целевых тестов `shell-tool` (включая новый): границы UTF-8, невалидный байт на лимите, исходные счётчики байтов, сохранение начала/хвоста, отдача stdout/stderr при poll, нулевой и ненулевой exit code, усечение реального вывода.
- 3 045 сравнений **полных сериализованных ответов, байт в байт**, между штатным и исправленным `render_result`: все совпали. Учитываются нулевой бюджет, управляющие символы и экранирование, метаданные не-объекты, capture, завершённые/живые процессы, Unicode и уже отброшенная середина. Ещё 8 профилей для счётчика, включая metadata 256 КиБ, также сравнивают оба ответа.
- 4 разогревочные + 41 измеренная пара с чередованием порядка для каждого профиля; подготовка входных `Vec`/JSON вне счётчика, при `realloc` считается запрошенный новый размер. Rust 1.95.0, Linux x86-64, probe и код рендера с `-O`, локальные совместимые зависимости из кэша в debug-профиле. Время в логе справочное: улучшение latency всей команды не утверждается.
- Полный workspace, все 130 тестов crate, установка в Desktop и end-to-end с моделью не запускались. Проверка не меняет запуск процессов, права, sandbox, capture retention или polling.

**Повтор:** `python3 reproduce.py /path/to/Proteus-modules`. Нужны Git с указанной базой, Rust 1.95.0, Cargo и закреплённые зависимости. Скрипт работает во временной копии. По умолчанию используется Cargo с `--locked --release`; на измерительном хосте использован альтернативный `--compiler` с локальными rlib, который компилирует весь test crate тем же rustc. `probe.rs` и `results.log` содержат условия и вывод сравнений; `checks.log` подтверждает отдельный прогон без probe.
