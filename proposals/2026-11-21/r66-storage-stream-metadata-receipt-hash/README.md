# R66 · Storage: хеш запроса CAS без сериализованной копии

Одна независимая правка для **Proteus-modules** ровно на `9469e3b12529d08b1f4a76882693e2065e842c51`, закреплённый SDK `0c1b7572313230e5d123e95c722e1258a2e9ecd6`, Rust 1.95.0 x86_64 Linux. `candidate.patch` содержит только код и регрессионный тест. Инструменты подсчёта в пакете отдельно от патча.

## Что меняется

Операция CAS метаданных сохраняет в ledger SHA-256 от компактного JSON исходного кортежа `(&key, &expected, &value)`. Раньше `serde_json::to_vec` выделял память под весь этот JSON перед хешированием. Теперь тот же кортеж сериализуется напрямую в SHA-256. Закреплённый serde_json 1.0.151 реализует `to_vec` как `Vec::with_capacity(128)` + тот же `to_writer`; между старой и новой реализацией различается только приёмник байтов. Нижний регистр hex, значения и порядок полей, порядок сериализации JSON объектов при текущих флагах остаются прежними. Сортировка ключей не добавляется.

Вывод SHA-256, валидация запроса и лимита SDK, проверка writer lease и ревизии метаданных, чтение прежнего ledger, повторы, записи объекта и ledger, `fsync` и доставка ответа прежние. Этот путь идёт до загрузки ledger, как раньше. Это не #263: там переиспользуется сериализация **тела** для объекта метаданных и его ETag, а здесь убирается временная копия всего **кортежа запроса** для отдельного отпечатка операции. Совместное применение после #263 и текущего Storage стека прошло проверку исходников; составной runtime не запускался.

## Воспроизведение

С точной локальной копией Modules, установленным Rust 1.95.0 и прогретым offline Cargo-кэшем:

```sh
bash reproduce.sh /path/to/modules /path/to/new/output /path/to/warm/target
```

Тесты выполняются с одним Cargo job. Probe добавляет только в тестовую сборку исходный `compare_exchange` из `git show HEAD` и потоковый allocator meter. Для каждого образца порядок A/B/B/A, A = stock, B = кандидат. Подсчёт включает запросы `alloc`, `alloc_zeroed` и `realloc` одного потока, а не пиковый RSS и не фактически зарезервированные страницы. Отдельные области: вычисление отпечатка, реальный локальный CAS с чистым каталогом, повтор операции с живым ledger. Подготовка входных данных, сериализация ответа, SDK admission и транспорт в метрики не включены. Никаких измерений времени.

## Проверка и результат

Нативный locked release: **65 прошли**, 0 ошибок, 1 прежний ручной тест пропущен. Новый тест вызывает SDK-типизированный CAS на JSONL и SQLite, проверяет совпадение с прежним способом хеширования, сохранённые receipts при записи и удалении обычных метаданных и повтор той же операции. Probe из той же сборки проверяет байт-в-байт ledger, имена и байты объектов и DTO между A/B; отвергает смену запроса при повторе operation ID и неверный ETag с теми же ошибками, без изменения файлов.

В обеих парах одинаковый результат. Запрошенные байты, на одну операцию:

| Синтетический валидный сценарий | Компактный кортеж | Только хеш | Локальный durable CAS | Повтор CAS |
| --- | ---: | ---: | ---: | ---: |
| Tombstone | 36 Б | 496 → 368 | 3 303 → 3 175 | 2 959 → 2 831 |
| Небольшая конфигурация | 135 Б | 752 → 368 | 6 356 → 5 972 | 6 549 → 6 165 |
| Большие пользовательские метаданные | 712 956 Б | 2 097 392 → 368 | 7 009 609 → 4 912 585 | 4 998 458 → 2 901 434 |

Убраны запросы памяти для одного временного Vec, включая запросы его роста: **128 / 384 / 2 097 024 Б** и **1 / 2 / 14** вызовов выделения/роста соответственно. Большой образец синтетический, укладывается в лимит метаданных 1 МиБ; это не типичная операция выбора модели и не замер старта/восстановления истории. Потоковый SHA-256 получает больше коротких вызовов update; без измерения времени из этих цифр не следует ускорение latency. Валидация входа, сериализация объекта, ledger и ответа остаются.

Проверки: чистое применение и обратная проверка на данном exact main, `git diff --check`, Rustfmt. Без варианта исходников поверх #386. `gate.log`, сырой `native-and-measure.log`, `counts.json` и `SHA256SUMS` прилагаются.
