# SQLite: строгий холодный каталог за один проход по payload

[Патч](candidate.patch) для [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). Меняется только SQLite-ветка полного replay каталога (локальный коммит `324764fc7580c69a63010582302cd9fc790b2974`): обычный холодный List, строгий аудит и адресный prime. Попадание в проверенный кеш, JSONL, writer recovery, OpenSnapshot и чтение страниц остаются на исходных путях.

Раньше каталог сначала читал все BLOB через отдельный SELECT для SHA-256, затем читал их повторно построчными SELECT … LIMIT 1, обновлял SHA-256 и применял каждый record к Fold. Кандидат делает один упорядоченный SELECT, берёт те же сырые байты для SHA-256 и тот же владеющий Vec для decode. Принимаются все те же ограничения на размер и проверки schema/identity, запись также должна пройти канонический Fold. Digest выдаётся только после EOF. Начальный session/schema check и верхняя граница берутся внутри той же read-only SQLite-транзакции. Пока действуют эти границы, внешний Commit не добавит в неё новые строки.

Однопроходное чтение используется только для обычной таблицы с физическим root page и непрерывным порядком положительных sequence до зафиксированной границы. Если порядок или тип таблицы не доказан, возвращается исходный eager+seek reader с новым Fold на **той же** открытой транзакции; частичный Fold сбрасывается. Нормальные ошибки чтения и проверки не повторяются. Ветка принимает только доказанный полный поток, но текст первой ошибки при нескольких одновременных дефектах ввода может отличаться. Сверки incarnation, journal/WAL, metadata и blobs перед публикацией не менялись; при обычном Commit между replay и публикацией каталог по-прежнему читает актуальную сессию заново.

## Что прошли

- [Точные данные SHA](rows.log) от независимой передачи сырых SQLite BLOB в SHA-256; совпали также revision, extent и значения v1. Счётчик подтвердил **24** декодирования в обоих вариантах; вспомогательный scan уменьшился с **802 642** байт до **0**. Для одной записи: **33 441 → 0** байт; на пустой таблице **0 → 0**. Это дополнение к проходу decode+SHA, который остался.
- Новый Rust-тест выполняет действительный Commit между первой и второй строками активного read-only cursor: первоначальный поток вернул ровно 3 строки и старый SHA; новый replay увидел 4 и новый SHA. Существующий тест дополнительно проверяет commit уже после replay, перед публикацией, и повторный List из сохранённого индекса.
- Linux x86-64, Rust 1.95.0: [65 unit + 2 process passed](native-standalone.log), один штатный ручной тест пропущен. `rustfmt --check` и `git diff --check` прошли. Штатная offline-обёртка остановилась на [`cargo metadata` без Android-зависимости](official-gate.log); весь workspace и Windows не запускались.
- [Наложение](composition.log): одинаковое дерево в обоих порядках с [#296](https://github.com/Qweasd123tg/proteus-modules-dot/pull/296), [#303](https://github.com/Qweasd123tg/proteus-modules-dot/pull/303), [#310](https://github.com/Qweasd123tg/proteus-modules-dot/pull/310), [#311](https://github.com/Qweasd123tg/proteus-modules-dot/pull/311) и [#316](https://github.com/Qweasd123tg/proteus-modules-dot/pull/316) вместе; отдельно с [#286](https://github.com/Qweasd123tg/proteus-modules-dot/pull/286) и [#287](https://github.com/Qweasd123tg/proteus-modules-dot/pull/287). Более ранний [#246](https://github.com/Qweasd123tg/proteus-modules-dot/pull/246) меняет эти же места SQLite-reader для устранения копии; чисто не накладывается в обоих порядках, [Совместимый патч после #246](after-246.patch) сохраняет заимствованный BLOB одновременно в старом reader и в новом каталоговом cursor. Накладывать его **вместо** standalone, только на базу с #246; не накладывать оба патча R50. Нативные проверки: [65 unit + 2 process](native-after-246.log) на #246 + совместимый R50; [73 unit + 2 process](native-stack.log) на пяти патчах каталога + standalone; [73 unit + 2 process](native-stack-after-246.log) на пяти патчах + #246 + совместимый R50. Один существующий тест пропущен в каждом запуске. Ни одна экономия #246 не считается результатом R50.

## Замер настоящего SDK List

Release-сборки с разных исходников, новый процесс на каждый List, журнал один и тот же для пары, v1 index удаляется перед каждой пробой. Файловый кеш ОС не очищался. Время от отправки запроса до разобранного ответа, после готовности SDK; сортировка, IPC и при обычном List запись sidecar включены. В двух прогонах порядок вариантов чередовался, CPU закреплён (7 и 6), по одной непротоколируемой паре на разогрев и затем 9 и 7 пар на каждый сценарий. Во всех пробах совпали полный ответ и весь файл v1; audit не записал индекс. Независимый SQL reader сверяет SHA сырых байтов в индексе.

**Отдельный контроль #246.** В обеих сборках BLOB читается заимствованным. Сравнивали только #246 с #246 + совместимая версия R50 в семи чередующихся парах на CPU 7. Медиана обычного List: 1 536 маленьких строк **15,18 → 11,31 мс**, 128 больших строк **121,93 → 86,98 мс**. Audit больших строк **118,51 → 86,48 мс**. Ответ и v1 побайтно совпали. Это не атрибуция экономии от #246 к R50 и не абляция одного SHA: изменения R50 и здесь включают один cursor и один raw hash. [Сырые пары](after-246.csv) · [лог](after-246.log).

## Повторение

`git apply --check candidate.patch`, затем `git apply candidate.patch` на указанной базе и `python3 scripts/test.py -p session-storage -p proteus-session-storage-module`. Прямой запуск на host-only Cargo cache: `cargo test --locked --offline -p session-storage -p proteus-session-storage-module`; Core harness из закреплённого `0c1b757`. Для счётчиков: `cargo test --locked -p session-storage --lib sqlite_cold_catalog_replay_hashes_the_strict_rows_once -- --nocapture`. Для paired SDK List собрать двоичные файлы stock и candidate через `cargo build --locked --release -p proteus-session-storage-module` в отдельных target dirs и запустить `python3 replay_bench.py STOCK CANDIDATE --output samples.csv`.
