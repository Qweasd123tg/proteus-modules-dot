# Context Pack: передавать метаданные без глубокой копии

База: **Proteus-harness/Proteus-modules@9469e3b12529d08b1f4a76882693e2065e842c51**. Локальный commit `893051b008c81d95268b3d95806631c4b0500189`. Ровно три рабочих замены `clone()` → `take()` в `context/context-pack`: после получения памяти, после отбора совпадений поиска и при добавлении профиля Codex.

В этих точках уже принадлежащее чанку JSON-значение раньше глубоко копировалось, а оригинал сразу заменялся. Теперь исходный JSON передаётся существующей функции обогащения без копии. Сами функции объединения не изменились: у объектов сохраняются значения и прежний приоритет полей, для скалярных значений/массивов/Null сохраняется прежняя обработка. Внешние провайдеры профиля RepoAware по-прежнему могут вернуть не-объект; нормализация профиля применяется только там, где она применялась до патча. Вызовы провайдеров, fallback при ошибке, порядок, устранение повторов, приоритет, сериализация JSON, бюджет и границы доступа не меняются.

## Дифференциальный тест и замер

На той же точной базе сравниваются полные JSON-ответы построителя, включая ошибки, и байты каждого запроса к провайдерам, включая порядок вызовов. Восемь сценариев: Codex с 95 чанками от поиска, памяти и внешнего источника; обычные 25 чанков; поиск через RepoAware; внешние данные смешанных типов; поиск с fallback; ошибка памяти; неправильная форма результата внешнего источника; тесный бюджет. Ожидаемое содержимое и количество чанков тоже проверяются независимо от совпадения со старым кодом. Фикстуры синтетические: вызов идёт через настоящий интерфейс Rust-построителя с локальным хостом провайдера, без сети и отдельного процесса.

Linux x86-64, rustc 1.95.0, locked Release. Для времени строятся отдельные бинарники без измерителя аллокаций, порядок версий чередуется, по девять пар процессов для основных сценариев. Счётчик охватывает весь вызов построителя после подготовки входного JSON: вызовы провайдеров, декодирование, объединение и сериализацию. Размер realloc считается целиком. Пик — логические живые байты Rust-аллокатора сверх состояния до входа, не RSS. Сбор трассы и вывод результата не входят в замер.

| Полный вызов | Запрошенные байты | Вызовы alloc/realloc | Пик живых байтов |
|---|---:|---:|---:|
| Codex, 95 чанков с вложенными метаданными | 3 425 834 → 1 947 449 | 20 932 → 9 272 | 1 286 137 → 1 298 297 |
| Codex, 25 чанков с обычными метаданными | 142 357 → 112 712 | 855 → 630 | 32 576 → 31 940 |
| RepoAware, 40 совпадений | 1 187 733 → 765 773 | 7 392 → 4 112 | 500 272 → 505 392 |
| Codex, тесный бюджет | 1 470 023 → 624 743 | 11 015 → 4 295 | 498 359 → 498 359 |

Экономия запрошенных байтов **43,2%** на вложенных метаданных и **20,8%** в обычной сборке. Пиковый размер не всегда уменьшается: на богатых метаданных он вырос примерно на 1% из-за удержания исходных буферов со свободной ёмкостью. Пробник показывает цену вызова построителя с этим объёмом данных, не RTT провайдеров или всей сессии. В пройденной полной серии медианы: богатый Codex 2,53 → 1,70 мс, обычный Codex 146 → 134 мкс, RepoAware 1,02 → 0,73 мс. Полные сырые выборки в `bench.log`.

Воспроизведение Linux: `python3 reproduce.py /путь/к/Proteus-modules`. Нужны Python, Git, Rust и доступ к закреплённым Cargo-зависимостям. Скрипт создаёт временные checkout и не меняет ваш; не делите `CARGO_TARGET_DIR` с параллельным запуском тех же тестовых пакетов. На чистой базе проверка патча: `git apply --check /путь/candidate.patch`.
