# Core: освободить историю до разбора журнала для /context

Патч к [Proteus-core@32e56ecb](https://github.com/Proteus-harness/Proteus-core/commit/32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f). У существующего HTTP-запроса `/context` при промахе кэша сводки есть два крупных набора данных: канонические сообщения сессии и временные буферы разбора общего событийного журнала. Исходный builder держит сообщения до конца чтения, хотя в ответе нужна лишь статистика истории. Патч сначала выбирает готовую сводку либо вычисляет её по тем же сообщениям, затем освобождает вектор и лишь после этого читает телеметрию. Изменён только порядок работы в одной функции.

Это именно снижение **пика одновременно живых данных** на пути с историей. В Unix при актуальной сводке HTTP-обработчик и так передаёт пустой вектор, поэтому большого выигрыша там нет. Полный обход событий при промахе кэша телеметрии и построение read model при промахе кэша истории остаются. Схема ответа, проверка сессии, обработка повреждённых строк, удаление приватного содержимого из сводки и проверка актуальности кэша не меняются. Если чтение журнала завершится ошибкой, будет та же ошибка, но подсчёт истории при отсутствии готовой сводки теперь уже выполнен.

## Измерение

Настоящие функции сборки контекста, подсчёта истории, чтения и кэширования телеметрии собраны в двух вариантах. На каждый размер создан отдельный путь к журналу с реальным сериализованным `ToolFinished`; первый вызов каждой версии холодный для её кэша. Для сравнения снимка обеим передаются тот же файл, session ID и содержимое истории. Инструментированный системный аллокатор считает приращение запрошенных живых байтов в одном потоке от начала создания вектора истории до возврата builder. Файл и исходное событие для записи подготовлены **до** измерения. За пределами окна остаются HTTP, storage, расходы ОС, выделенная ёмкость системного аллокатора и сериализация готового ответа. Это не RSS, не end-to-end память и не ускорение.

| Текст истории | Вывод события | Пик до → после, байт | Суммарно запрошено, до = после |
|---:|---:|---:|---:|
| 0 | 1 КиБ | 10 702 → 10 702 | 11 693 |
| 4 МиБ | 1 КиБ | 4 228 558 → 4 218 032 | 4 241 333 |
| 4 МиБ | 1 МиБ | 7 371 895 → 4 218 032 | 9 475 942 |
| 8 МиБ | 4 МиБ | 21 026 935 → 12 591 223 | 29 431 918 |

В последней фикстуре пик ниже на 8 435 712 байт (40,1%), хотя суммарный объём запросов к аллокатору совпал. Не установлен предел на объём самой истории или на размер строки журнала. При маленьком событии и большой истории максимум может определяться почти исключительно созданием самой истории.

## Проверки и воспроизведение

- Все четыре штатных теста модуля контекста прошли на базе и на патче. Два дополнительных дифференциальных теста сравнивают полные ответы, приоритет переданной сводки (в том числе при непустом history), диагностику отсутствующего/повреждённого журнала, ошибку невалидного UTF-8 и пик живых выделений. Итог **10/10**.
- Полный библиотечный test target Core прошёл типизацию на Linux x86-64 с `rustc --test --emit=metadata` (без полной линковки). Проверены `cargo fmt --all --check`, `git diff --check`, прямое/обратное применение. Патч отдельно применяется и поверх двух предыдущих изменений подсчёта размера JSON и превью инструмента (проверка индекса, не combined runtime test).
- Windows и macOS не собирались. Не-Unix ветка холодного HTTP передаёт `summary = None`; сам builder не использует платформенных ветвлений, а эта форма вызова проверена на Linux. Реальные HTTP, процесс storage и Desktop в данном замере не запускались. До/после относится к точной указанной базе, без других предложений.

На исходной копии Core с собранными зависимостями:
```sh
# PROPOSAL — абсолютный путь к этому каталогу
git apply --check "$PROPOSAL/source.patch"
python3 "$PROPOSAL/probe.py" . "${CARGO_TARGET_DIR:-target}/debug/deps"
git apply "$PROPOSAL/source.patch"
# Для обычного штатного прогона Core с настроенными fixtures:
python3 scripts/test.py -p proteus-core --lib app_server::context_map::
```

Для компактной проверки нужны git, Python 3, rustc 1.95 и lld; в переданном каталоге зависимостей должен быть один согласованный набор rlib. Скрипт извлекает точные production-модули из git, накладывает патч во временной директории и исполняет тесты, не меняя рабочую копию.
