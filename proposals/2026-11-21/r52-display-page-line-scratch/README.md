# ReadDisplayRecords: переиспользовать небольшой буфер одной страницы

[Патч](candidate.patch) для [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51). Меняется только чтение очередной строки из **временной проверенной** display-проекции. Вместо нового Vec на каждую прочитанную строку одна страница переиспользует свою scratch-область. Если её capacity выросла больше 8 KiB, она освобождается сразу после decode, до перевода записи в page/pending. Большие записи остаются разрешены, большой буфер не сохраняется ни между строками, ни между запросами. У открытого snapshot никакого нового постоянного кеша нет.

Прежний `read_until`, признак завершённой LF-строки, Serde и учёт размера строки без LF не изменились. Pending, rewind, пропуски sequence, byte budget, лимиты staging и размер выдачи не меняются. Никакого изменения канонического SQLite/JSONL, `ReadRecords`, проверок префикса, записи, durability или индекса v1. Патч уменьшает **запросы к аллокатору**; это не оценка RSS или времени запуска Desktop. Максимум 8 KiB маленького scratch теперь могут оставаться живыми в рамках одной страницы.

## Проверка

- [65 модульных и 2 процессных теста](native-release.log) прошли на Linux (Cargo locked release, Rust 1.95); один штатный ручной тест пропущен. Настоящее временное staging с короткими строками использует ту же выделенную область, большая строка освобождает её, все байтовые длины/результаты совпадают с сериализацией. Нативная проверка в обоих backend сверяет pending на границе 4 MiB, точную исходную sequence, продолжение и повторы страницы. Используются нормальные UTF-8 записи без изменения файлов журнала.
- [Исходное наложение](composition.log) проверено в обе стороны с совместимым стеком [#246](https://github.com/Qweasd123tg/proteus-modules-dot/pull/246), [#253](https://github.com/Qweasd123tg/proteus-modules-dot/pull/253), [#321](https://github.com/Qweasd123tg/proteus-modules-dot/pull/321), [#326](https://github.com/Qweasd123tg/proteus-modules-dot/pull/326). Получилось одно и то же Git tree. Это не прогон всего стека. Также не проверялся Windows или полный workspace.

- [Два SDK worker без измерительной вставки](plain-parity.log) также дали точное совпадение строк, курсора и projection в сценариях обоих backend, включая повтор, переход назад и oversize.

## Методика

Два обычных SDK worker с одной и той же внепроизводственной вставкой [instrument.py](instrument.py). Счётчик включается только на потоке реального `execute(ReadDisplayRecords)`, с проверкой locator, выполнением операции и decode. Не учитываются IPC-сериализация ответа, подготовка открытого snapshot и выделения SQLite/C. Считаются запросы к Rust allocator: `alloc`, `alloc_zeroed`, `realloc` (для realloc полный запрошенный размер, не реальная дополнительная память). Чередование stock/candidate, свежие процессы, одна непубликуемая пара для разогрева, затем 7 и 5 пар на сценарий. В каждом прогоне сравниваются полная projection и результат страницы для одного дерева, включая порядок записей и cursor. Единственный заведомо случайный атрибут, исключённый при сравнении между процессами, `snapshot_id`; перед этим он отдельно сверен с точным handle из запроса.

## Повторить

На чистой указанной базе применить `git apply --check candidate.patch`, затем `git apply candidate.patch` и `cargo test --locked -p session-storage -p proteus-session-storage-module` (Core SDK pin `0c1b757`). Для пробы только в одноразовых stock/candidate checkouts выполнить `python3 instrument.py CHECKOUT`. Собрать оба отдельно `cargo build --locked --release -p proteus-session-storage-module`, затем `python3 measure.py STOCK CANDIDATE --output paired.csv`. Linux, Python 3.11+, Rust/Cargo и закреплённые зависимости проекта. Все сеансы синтетические.
