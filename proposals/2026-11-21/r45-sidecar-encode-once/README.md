# Каталог сессий: одна сериализация вместо двух при записи индекса

[Производственный патч](candidate.patch) для [Proteus-modules 9469e3b](https://github.com/Proteus-harness/Proteus-modules/commit/9469e3b12529d08b1f4a76882693e2065e842c51) меняет **запись** `.storage-catalog-v1.json`, не загрузку. На 492 тестовых blob-файлах на сессию процессорное время этапа кодирования сократилось примерно на 39–47% по медиане попарных изменений. Это выигрыш одного этапа, не двукратное ускорение списка: полное время JSONL List заметно колебалось. Причину наблюдавшегося таймаута 30 с эксперимент не устанавливает.

## Что меняется

Раньше модуль сериализовал типизированный `Index` для SHA-256, а потом сериализовал его ещё раз внутри `Envelope { checksum, data }`. Теперь он оставляет в итоговом векторе место под 64 строчные hex-цифры, пишет `Index` обычным Serde, хеширует ровно этот срез, подставляет digest и закрывает объект. Внешнее обрамление занимает 87 байт. Проверка 4 MiB по-прежнему применяется ко **всему** объекту перед созданием временного файла. Ни дублирующего буфера с полной копией данных, ни ручного экранирования payload нет. При выходе из выражения временный `Index`, включая карту меток blobs, освобождается перед файловым I/O.

Сверка исходного журнала и меток blobs, правила десериализации, контрольная сумма при загрузке, режимы аудита/пропуска, типы ошибок и best-effort характер сохранения не менялись. Не менялись ни `create_new`, ни `write_all`, ни `sync_data → rename → sync_directory`, ни удаление неудавшегося временного файла. В патче один файл, две регрессионные проверки; внешних зависимостей или измерительных хуков в нём нет.

## Измерения

Настоящий SDK worker, stdio JSON-RPC, синтетика в Linux tmpfs. Rust 1.95.0. Для инструментированных сборок модуль хранения и main собраны с `opt-level=3`; остальные связанные зависимости одинаковы и взяты из dev target. Это не end-to-end release build и не тест реального SSD. Семь пар с чередованием порядка stock/candidate; два отдельных прогона по 112 измеренных запросов. Готовили 8 записей по 512 байт текста через реальные Commit RPC. Вариант «492» добавляет 492 пустых обычных файла в blobs каждой сессии; контроль «0» не добавляет файлов. Настоящие архивы не использовались.

Медианы при 492 blob-файлах на сессию. CPU: сумма времени текущего request-thread на кодирование, SHA и освобождение Index, без файловых проверок/sync. Полное RPC: клиентское wall time, включая ответ. Числа в ячейке: исходник → кандидат.

| Запрос | Backend | CPU кодирования, мс | Полное RPC, мс (тот же прогон) |
|---|---|---:|---:|
| Холодный List, 10 готовых сессий, индексы удалены | JSONL | 8.04 → 4.85 | 48.61 → 50.50 |
| То же | SQLite | 8.27 → 4.39 | 51.25 → 46.68 |
| OpenSnapshot с живым writer сразу после 9-й записи, 1 сессия | JSONL | 1.00 → 0.56 | 3.99 → 4.08 |
| То же | SQLite | 0.82 → 0.42 | 4.08 → 3.71 |

Обходов типизированного `Index`: **20 → 10** на List, **2 → 1** на обновление головы. Счётчик стоит на обязательном поле Serde, а не задаётся константой по варианту. При семи парах CPU этапа был меньше в 6/7 (JSONL List), 7/7 (SQLite List) и 7/7 для каждого обычного обновления головы. На маленьком SQLite List без добавленных blobs раздельные CPU-медианы даже выросли 0.20 → 0.22 мс; на таком масштабе и числе повторов общий выигрыш не гарантирован. [Все CPU/elapsed наблюдения](clock.jsonl) и [разброс](clock-summary.txt).

Независимый первый прогон без системного запроса thread-CPU дал медианы **wall time кодирования** 10.86 → 5.63 / 7.77 → 4.40 мс (JSONL / SQLite List), 0.82 → 0.49 / 0.84 → 0.53 мс (обычное обновление). [Первый прогон](raw.jsonl), [сводка](summary.txt). Абсолютные времена двух прогонов и R44 напрямую не сравниваются. Ключевой результат воспроизводится независимо от таймера: один реальный обход вместо двух при неизменных байтах.

## Что проверяли

- Для каждой пары List два разных worker на одном дереве возвращают **полностью одинаковые строки в том же порядке** и записывают байт-в-байт одинаковые sidecar. База сравнения включает timestamps, stamps и inode; SQLite read-only соединения удерживают пустой WAL стабильным между чтениями. Дополнительный независимый Python oracle заново собирает компактный envelope из декодированных полей и считает SHA-256.
- После Commit **до** OpenSnapshot файла ещё нет. С активной writer lease OpenSnapshot записывает проверенную голову. Параллельно открытый противоположный worker (сток для кандидата, кандидат для стока) повторяет обычный строгий List **по той же живой версии** и создаёт те же байты. После release обоих handles новый процесс читает итоговый sidecar, не заменяя его. У SQLite отдельно наблюдалось ещё одно сохранение при закрытии writer после checkpoint; его время не входит в OpenSnapshot. Равенство не выводилось из сравнения двух разных деревьев с разными метками. Отдельный проход [без измерительной инструментализации](unmetered.log) повторил побайтовую/функциональную сверку на тех же двух операциях и обоих backends.
- В патче: точное сравнение с прежним типизированным Serde-`Envelope`, экранированные текст/путь, Unicode, полный предел. Дополнительный [граничный тест](boundary_probe.rs) фактически записал и прочитал через штатный loader индекс **4 194 304 байта**; попытка сохранить **4 194 305** оставила старые байты и метки файла нетронутыми, без временного мусора. Исходник и кандидат, оба backend. Подгоняли синтетическое поле preview в тесте сериализатора, штатный предел пользовательского preview не меняли. Внешний probe с не-UTF-8 именем тестового файла в blobs на Linux также оставил старый индекс неизменным и сохранил семантику результата List при невозможности выполнить serde-encoding.
- [Протокол тестов](validation.txt): прямой `cargo test --offline --locked -p session-storage -p proteus-session-storage-module` на финальном патче: **65 unit + 2 process passed**, 1 штатный ручной тест проигнорирован. Обёртка `scripts/test.py` не дошла до тестов: её всеплатформенному `cargo metadata` не хватило кэшированного `android_system_properties 0.1.5`. Полный workspace и реальная установка не запускались.

## Воспроизведение

1. Получить чистый checkout указанного пина, проверить `git apply --check /path/candidate.patch`. В отдельной копии применить патч и выполнить штатную проверку двух пакетов. Для дополнительной проверки полной записи/отказа временно добавить содержимое `boundary_probe.rs` в конец `storage/session-storage/src/service/catalog/durable.rs` в двух одноразовых копиях и выполнить `cargo test --locked -p session-storage --lib r45_exact_boundary`.
2. Для замера подготовить совместимые dev-артефакты `cargo build --locked -p proteus-session-storage-module`. `python3 build.py /path/repo /path/target /tmp/stock` и `python3 build.py --candidate /path/repo /path/target /tmp/candidate` извлекут исходники из указанного git-объекта и соберут **отдельные тестовые worker**; каталог вывода должен быть новым и пустым. При нескольких bin-фингерпринтах выбрать `--fingerprint` (в нашем target: `765ba9328ec6c0ed`). `PYTHONDONTWRITEBYTECODE=1 python3 measure.py /tmp/stock/module /tmp/candidate/module --pairs 7 > raw.jsonl`; `python3 summarize.py raw.jsonl`.
3. Для CPU добавить `--cpu-clock` в обе сборки, выбрать новые каталоги и повторить runner. Только эта Linux-тестовая сборка использует уже скомпилированный transitive libc для `CLOCK_THREAD_CPUTIME_ID`. Вторая clock-free сборка позволяет видеть накладные расходы таймера. Для двух обычных бинарников без инструментализации: `python3 measure.py /path/stock /path/candidate --plain --pairs 1 --blobs 492`.
