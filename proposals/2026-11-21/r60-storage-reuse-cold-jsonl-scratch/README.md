# Storage: переиспользование сырого буфера при холодном проходе JSONL

При восстановлении без готового display view worker полностью проверяет
канонический JSONL и строит временное представление истории. Раньше чтение
записи могло каждый раз заново выделять временный буфер. Теперь один
OpenDisplaySnapshot переиспользует буфер в пределах прохода. Сохраняется
не более 128 КиБ ёмкости между чтениями; большие временные буферы не
удерживаются. Перед проверкой источника и публикацией снимка буфер
освобождается. На снимке он не хранится.

Не меняются контрольная сумма исходных строк, порядок чтения и проверок,
ограничения размера записи, проверка последовательности, внешний blob,
зафиксированный конец журнала, условия переиспользования префикса,
формат SDK, SQLite, staged pages, правила публикации и квота.

## Выберите один вариант

- [candidate.patch](candidate.patch) применяется к точному
  Proteus-modules 9469e3b12529d08b1f4a76882693e2065e842c51. Core SDK
  остаётся на 0c1b7572313230e5d123e95c722e1258a2e9ecd6.
- [candidate-after-256.patch](candidate-after-256.patch) применяется
  **вместо первого** после #256. #256 уже берёт готовую строку напрямую
  из BufReader; этот вариант переиспользует временный буфер только если
  строка пересекает границу. Проверен в текущем R59 M150-preflight
  Modules с #256, #331 и #348. #331 охватывает другой буфер чтения
  готовых страниц. #348 присутствует в сборке, но запись cache в
  этом узком SDK-сценарии не запускалась.

Это одна оптимизация, не два патча для подсчёта. Не складывать их.

## Измерение

Приватный JSONL-125k, 125 000 видимых сообщений, 1 251 каноническая
запись, 52 592 436 байт, точный SHA e00e71759… . Одни и те же release
артефакты переключались между свежим буфером на запись и reuse в двух
парах с обратным порядком. Считали вызовы alloc/alloc_zeroed/realloc
и запрошенные байты только внутри OpenDisplaySnapshot воркера
(StorageService::execute). Это не пиковая память, RSS, задержка или
весь путь восстановления.

| Исходная ветка | Медиана запрошенных байтов до → после | Разность в каждой паре | Вызовов аллокатора меньше |
| --- | ---: | ---: | ---: |
| Точный main | 850 318 421 → 772 947 354 (−9,10%) | 77 415 743 / 77 326 391 B | 2 057 / 2 032 |
| Композиция после #256 | 667 497 905 → 609 358 613 (−8,71%) | 58 192 360 / 58 086 224 B | 1 423 / 1 368 |

Повторы немного варьировали, сырые счётчики сохранены. Обе пары в
каждом из вариантов показывают уменьшение. Числа между ветками
складывать нельзя. В этом файле 802 из 1 251 строк пересекают
границы блоков 64 КиБ по их смещениям; это объясняет, почему польза
сохраняется после #256, но не подменяет измерение.

## Проверка

- Exact-main locked release: **64 теста прошли, 1 прежний пропущен**.
  Новый тест проверяет реальные смешанные размеры, ограниченное
  удержание буфера, точные хеши каждой границы, reset, неизменность
  старых страниц при нормальном append и обычный внешний blob.
- В обоих артефактах negotiated SDK ответ OpenDisplaySnapshot и все
  20 ответов ReadDisplayRecords совпали по сырым байтам с контрольным
  worker после замены только случайного 36-байтного snapshot ID.
  Сверены все 1 251 sequence, конец курсора, канонический SHA и
  побайтная неизменность журнала. Эталон main точный stock, эталон
  композиции фиксированный M100 worker (эти запросы не работают с
  публикацией cache).
- Прямое/обратное применение, форматирование и независимая проверка
  отчётов пройдены. Полного workspace-прогона, нагрузки writer/cache
  для композиции, Windows/macOS и замеров времени не было.
