# Core: не выделять буфер сортировки уже упорядоченного каталога при старте

База: [Proteus-core 32e56ecb](https://github.com/Proteus-harness/Proteus-core/commit/32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f). Путь — выбор последней сохранённой корневой сессии в рабочей папке, когда Core не получил пригодный явный выбор. При 32 и более кандидатах Core проверяет порядок своим прежним компаратором (время убывает, при равном времени — путь убывает). Только если весь ответ уже удовлетворяет компаратору, пропускается выделение временного буфера стабильной сортировки. Маленькие или неупорядоченные ответы сортируются прежним способом. Равные ключи сохраняют входной порядок.

Порядок ответа не принимается на веру: opaque storage key не подменяет путь, отсутствие пути, равенство и любые выходные порядки провайдера продолжают обрабатываться. Фильтр дочерних сессий, выбор первого пригодного кандидата, открытие/строгая проверка, пропуск повреждённых/пустых записей, явная/предпочитаемая сессия и готовность не меняются. Не затрагивает запрос ListCandidates, сетевой протокол, полномочия хранения, горячее чтение уже выбранной сессии или формат выдачи.

## Замер одного этапа, не времени старта

Один оптимизированный бинарник, Rust 1.95 + точный DTO StorageSessionDescriptor из закреплённых зависимостей. Он извлекает исходную сортировку и функцию из готового патча и сравнивает полные списки. Исходный каталог и две копии входа создаются **до** замера scoped allocator. Для каждого сценария 64 пары в чередующемся порядке; учитываются запросы alloc/realloc в сортировке. 420 дополнительных перестановок тестируют одинаковые даты, одинаковые и отсутствующие пути, устойчивость равенств.

| Вход | Запросы выделения | Запрошено байт |
|---|---:|---:|
| 128 строк настоящего stock ListCandidates, JSONL и SQLite, даты различны или все равны | 1 → 0 | 19 456 → 0 |
| 512 синтетических строк в нужном порядке | 1 → 0 | 77 824 → 0 |
| 4 096 синтетических строк в нужном порядке | 1 → 0 | 622 592 → 0 |
| 128 строк в обратном порядке, с поздней перестановкой или перемешанные | 1 → 1 | 19 456 → 19 456 |

Неупорядоченный большой ответ может добавить проход до первого нарушения перед прежней сортировкой; поздняя перестановка хуже ранней. Сохранены отрицательные контроли и синтетика до/после порога. В каждой из 128 реально созданных сессий находится одна каноническая строка. Фикстура сохраняет порядок и ключи сравнения, нормализует неиспользуемые в сортировке поля и префиксы синтетических путей. Процессы Core, полный холодный путь, RSS, GUI и пользовательская задержка этим замером не измеряются.

## Проверка и повторение

    git apply --check /abs/packet/source.patch
    python3 /abs/packet/fixture.py /abs/exact-stock-storage-worker /abs/new-fixtures
    python3 /abs/packet/probe.py . /abs/pinned-cargo-target/debug/deps /abs/new-fixtures

У компилятора должны быть Rust 1.95 и по одному артефакту pinned proteus_contracts/serde_json. Файл alloc.rs — существующий scoped измеритель из Core. Журналы создаются в очищенном окружении исключительно в каталоге синтетики.

Отдельная проверка в копии с применённым патчем: добавить real_startup.rs как test-only модуль в prepared.rs, передать совместимый PROTEUS_TEST_SESSION_STORAGE_MODULE и PROTEUS_TEST_REFERENCE_MODULE (одинаковые для всех запусков), запустить cargo test --locked -p proteus-core --lib startup:: и cargo test --locked -p proteus-core --lib prepared_startup_orders_a_real_large_provider_catalog. Второй тест использует настоящий внешний worker с 40 сохранёнными корневыми сессиями и проверяет, что после строгого отказа самого свежего повреждённого журнала выбран следующий исправный; канонические байты не меняются. Прошли 6/6 штатных startup-тестов и 1/1 дополнительный тест. Накладывается на исходники согласованной M50, но совмещённый запуск не делался. Материалы воспроизведения не входят в production diff.
