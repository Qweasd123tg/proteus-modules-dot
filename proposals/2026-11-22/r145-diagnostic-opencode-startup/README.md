# Диагностика Core: где теряется время перед запуском чата

Отдельный диагностический патч для Core из #455. Он не исправляет задержку и не меняет порядок запуска: только измеряет ответ инициализации процессной модели, обязательный `model.describe` и инициализацию выбранного контекста. С ним можно проверить, какой вызов занимает 4,66–5,16 с между появлением OpenCode Worker и Context Pack.

Применимость проверена на исходном Core `32e56ecb4cc6da324c60dd6ae2da78f3b7e46e7f`, составе M150 и точном Core с патчем #454. Из чистой отдельной копии: `git apply --check --whitespace=error -- /путь/startup-diagnostic.patch`, затем применить и собрать Core. Используйте диагностический Core в отдельной копии той же сборки Desktop и тот же способ запуска; на практической установке не заменяйте рабочий бинарник.

Перед пробным запуском задайте **в окружении фактического ярлыка/обёртки** `PROTEUS_CORE_STARTUP_TRACE_DIR` на новую абсолютную директорию текущего пользователя с правами 0700 на локальном диске (например, созданную `mktemp -d`). Если запустить ярлык из рабочего стола, переменная из произвольного терминала может не попасть в него. Это работает только при запуске нового локального Core с патчем, не при подключении к ранее запущенному backend. Core запишет в эту папку `core-startup.jsonl`; существующий файл не перезаписывается. Без переменной диагностика отключена.

Файл содержит максимум 12 строк, только фазы и числа. Для разбора достаточно трёх строк с `model_initialize`, `model_describe`, `context_initialize` и их `duration_us`. Не пересылайте полные логи, аргументы и конфиги. `start_us` отсчитывается от начала этой трассы, не от нажатия на ярлык. `ok` относится к измеренному вызову, не ко всему запуску.

**Проверка:** 3/3 изолированных Linux-теста точного модуля записи: схема, предел вывода, сохранение проверенного дескриптора, запрет перезаписи/ссылок и неподходящих прав. Полная сборка Core и прогон ярлыка с патчем не выполнены. Это диагностический материал, не продуктовый патч в счётчик.
