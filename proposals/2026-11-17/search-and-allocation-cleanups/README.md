# Точный поиск настроек и три небольших упрощения

Четыре независимых патча. Только первый меняет видимый порядок результатов; остальные сохраняют поведение на проверенных входах. Это каталог предложений: слияние **не** изменяет исходники Desktop, Core или действующий исторический прототип. Даты и результаты старых проверок не переписаны. Ни один тест не удалён ради счётчика.

## Desktop: точное название настройки не должно проигрывать префиксу

[Патч](desktop-exact-title.patch) к [settings/search.rs на Desktop 7b1c96e7](https://github.com/Proteus-harness/Proteus-desktop/blob/7b1c96e70395aafc7531c0698450f306112db6ed/src/ui/settings/search.rs). Раньше точное название и более длинное с тем же началом получали одинаковый ранг. В воспроизводимом списке из 60 названий «Шрифт чата 0» … «Шрифт чата 59», за которыми идёт «Шрифт чата», последняя настройка вообще не попадала в выдачу на запрос «  ШРИФТ   ЧАТА  ». После патча она первая, а второй идёт «Шрифт чата 0»; всего по-прежнему 60 результатов. Не утверждаем, что именно такой набор уже есть на стандартном экране.

Совпадение определяется по равенству последовательности слов после прежнего приведения к нижнему регистру и разбиения по пробелам. Сохранились требование присутствия всех слов, порядок равных по рангу элементов и предел выдачи. Если самих точных совпадений больше 60, показаны не все. В изолированной нативной проверке новый regression **падал до** и **проходит после**; при намеренном удалении предела снова падает (61 вместо 60). Два контроля подтверждают порядок остальных и одинаковых точных названий. Один regression входит в патч, а не весь стенд. Исходный blob `abe2f39f074403d12688a85e0d69bd1e5ab3b59f`; результат `6651f5db0be732b626a16e3ad288a79b6834167b`.

## Desktop: искать семейство шрифта в уже отсортированном списке

[Патч](desktop-font-lookup.patch) к [theme/fonts.rs](https://github.com/Proteus-harness/Proteus-desktop/blob/7b1c96e70395aafc7531c0698450f306112db6ed/src/ui/theme/fonts.rs). При инициализации список семейств один раз сортируется и очищается от повторов. Поиск при отрисовке названия больше не перебирает весь список до первого совпадения: используется двоичный поиск по тем же строкам, без нового кеша и без приведения регистра. Отсутствующее семейство, как и прежде, не подставляется вместо шрифта по умолчанию.

Проверено по точным версиям из Cargo.lock: `SharedString` 0.3.10 делегирует порядок `SmolStr` 0.3.6, а тот сравнивает содержимое `&str`. Обе версии функции были дословно скомпилированы с этими реальными строковыми типами; проверочный App предоставлял только список, а serde был локальным 1.0.228 вместо Desktop pin 1.0.229. На четырёх наборах (пустой, 264 найденных здесь семейства, девять различных специальных строк, 4 096 синтетических имён) все 4 422 поисковых запроса дали тот же ответ, включая пропущенные, отсутствующие и различающиеся регистром/Unicode имена. Регрессия с обратным порядком сравнения провалилась. Это снижение сложности поиска, **не измерение скорости GUI**. Исходный blob `90174899f0e1d2fe596847386d95633e79169cd7`; результат `ad899953310e4ccdde9eb8226a92266ca4ded96a`.

## Core: передавать имена файлов сразу в множество отчёта

[Патч](core-eval-paths.patch) к [eval_report.rs на Core 524c99ca](https://github.com/Proteus-harness/Proteus-core/blob/524c99cafcc4b307a9b98ed4da54d37f569fd8c0/crates/proteus-core/src/core/eval_report.rs#L227-L270). Вместо построения временного `Vec<String>` заголовки файлов передаются в уже существующий `BTreeSet` по мере чтения. Это обработка текста **для отчёта**, не выполнение patch. Лексикографический порядок и уникальные имена прежние. Создание строки на распознанный заголовок остаётся.

В нативном изолированном сравнении двух фактических функций (serde_json 1.0.151, у тестового ToolCall только прочитанные поля) 15 сценариев совпали с ожидаемым множеством до/после, в том числе Unicode, CRLF, переименование, дубликаты, пустой путь и похожая на заголовок строка в содержимом. На синтетическом входе с 4 096 разными именами пик одновременно выделенных байтов внутри этого вызова, включая итоговое множество, составил **367 832 → 269 528**, на 96 КиБ меньше. Для 100 разных имён: 9 820 → 6 748. Вход подготовлен заранее; это не RSS, не измерение времени и не оценка типичного журнала. Исходный blob `de3a9fd16c1f76532bb7383042d97adaf0c5c6de`.

## dot: один временный строковый буфер на построение индекса навыков

[Патч](dot-skill-index-scratch.patch) к [самостоятельному std-only прототипу из #57](https://github.com/Qweasd123tg/proteus-modules-dot/tree/556a48f5284dde8b27ddafa6709a748500d4edce/research/agent-architectures-20261028/modules/skill-index), исходный blob `77170d43d872e67f9092b52ac14ef872c5d2c7cd`. Только для этого прототипа, **не** для рабочего импорта skills, политики доступа или SDK-модуля. Раньше новый буфер выделялся для каждого названия, описания и индексируемого тела. Теперь память используется снова внутри одного build, а в начале каждого поля буфер очищается. Баллы, права, граница в 64 байта на слово и сброс неполного слова не меняются.

Один и тот же тест публичного интерфейса проходит до и после: Unicode «İ», независимость полей/навыков, веса, неполный последний терм и слишком длинное слово. Полный `cargo test --offline` изменённого **маленького пакета**: один integration test, ноль unit/doc tests. На пустом индексе 0 → 0 выделений; на 128 синтетических навыках без тел 1 156 → 901, а с предоставленными телами (64 индексируются) **1 284 → 965**, на 319 меньше. Измерены вызовы аллокатора только внутри build после создания входа, не объём памяти, длительность процесса или нагрузка реального агента. Диагностический счётчик не добавлен в библиотеку.

## Что сознательно не меняли

- В каталоге Modules на `99039de4` 34 различных пары «роль + имя», но только 31 имя: `jsonl_memory`, `rg_search`, `sqlite_memory` представлены и как `context_provider`, и как `tool`. Дедупликация просто по имени потеряла бы три роли. Это сверка готовых метаданных, не запуск модулей.
- В [dot usage-attribution](https://github.com/Qweasd123tg/proteus-modules-dot/blob/556a48f5284dde8b27ddafa6709a748500d4edce/consumers/usage-attribution/src/lib.rs) обнаружено лишнее копирование имён provider/model для временных ключей группировки. На данных примера удаление provider из ключа вместо заимствования склеило бы две разные группы (6 → 5). Точную Rust-сборку кандидата не подтвердили: 42 записи закреплённого графа не имели архива в локальном кэше. Это наблюдение, **не** поставленный патч или выполненная проверка consumer.

Проверки: Rust 1.95.0, контроль точных входных файлов, независимое ревью, строгое прямое и обратное наложение. Хеши четырёх файлов в [SHA256SUMS](SHA256SUMS). Для применения в отдельной рабочей копии сначала сверьте указанную базу и `git apply --check --whitespace=error <patch>`. Проекты целиком, GUI, живой журнал/host и CI не проверялись. Ни один защитный предел не снят.
