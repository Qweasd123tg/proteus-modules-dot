# Передать историю открытой сессии без полной копии

[Core, исходная ревизия](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/session_store/remote/snapshot.rs#L187-L243). После проверки журнала `RemoteValidatedRead::open_with_cursor` копирует все сообщения вместе с их частями и строками, чтобы затем освободить исходный вектор. Патч [move-validated-history.patch](move-validated-history.patch) передаёт вектор через уже существующий [`into_history`](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-session-semantics/src/journal/projection.rs#L103-L105). В этом пути у состояния один владелец; если владельцев несколько, сам метод сохранит семантику копирования. Ревизия всё так же проверяется после чтения всего журнала, но до сборки ответа. Остальные поля читаются до передачи владения. Дисковый формат, схема API, сохранение и порядок сообщений не меняются. Это путь открытия с проверкой; успешный показ уже кешированного представления сам по себе не становится дешевле.

## Что показал нативный замер

Медианы одного открытия (было → стало). В обоих непустых примерах 256 сообщений по 64 КиБ текста; различается только их размещение в журнале.

| Записи журнала | Все запрошенные байты | Пик дополнительных живых байт |
| --- | ---: | ---: |
| Пустая история | 16 163 → 16 163 | 16 094 → 16 094 |
| Одна запись с 256 сообщениями | 50 795 803 → 33 924 379 | 33 911 182 → 33 911 182 |
| 256 записей по одному сообщению | 55 585 133 → 38 702 741 | 33 940 576 → 17 272 094 |

При отдельных записях пик снизился с 32,37 до 16,47 МиБ, на 49,1%. При одной большой записи пиковое выделение происходит уже во время чтения и проверки, поэтому избавление от последующей копии уменьшает трафик, но не пик. Устойчивого ускорения не установлено: на 256 отдельных записях медиана времени отладочного запуска была даже выше (55,7 → 60,5 мс).

## Как повторить

Понадобятся Linux x86-64, Rust 1.95.0, Git, Cargo, системный C-компилятор и закреплённые в Cargo.lock зависимости. Передайте существующий checkout Core и имя **нового** каталога результатов:

```sh
bash reproduce.sh /path/to/Proteus-core ./results-core
```

Можно явно задать третий аргумент, commit. Скрипт проверяет Git blob изменяемого файла, делает отдельную рабочую копию, не затрагивает исходный checkout и берёт Cargo из PATH. При заполненном кэше зависимостей можно задать `CARGO_NET_OFFLINE=true`. Измерительное дополнение [open-resume-peak-probe.rs](open-resume-peak-probe.rs) добавляется **только к тестам обеих версий**; в рабочий патч не входит.

Пять штатных проверок представления охватывают независимое добавление, устаревший курсор, страницы и отказ записи кеша. Шестая проверка подаёт корректную запись и неверную итоговую ревизию: чтение завершается той же ошибкой после просмотра записи. Отдельный измерительный тест вызывает настоящий `RemoteValidatedRead::open` со штатным тестовым хранилищем в памяти и сверяет каждое возвращённое сообщение со входным.

Каждую конфигурацию прогоняем 8 раз в отдельном тестовом потоке: один раз для прогрева и семь для медианы. Сумма запрошенных байт включает новый размер при realloc. Пик – наибольшая дополнительная сумма живых запрошенных байт после входа в open с учётом освобождений. Это **не RSS**, не общая память Desktop и не замер сети или реального внешнего процесса. Время из отладочной сборки не доказывает ускорения продукта.
