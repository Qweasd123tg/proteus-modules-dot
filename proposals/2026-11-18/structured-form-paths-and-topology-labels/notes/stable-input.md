# Почему замена многострочного черновика компактным поиском не может быть исправлена в render.rs

**NO-GO, без патча.** Для расширения, которое хочет добавить поиск к редактируемой заметке, работает конкретный переход: оставить старый многострочный контрол с прежним ID **и тем же последним объявленным значением**, одновременно добавить отдельный `ui::search` с другим ID и своим запросом. Если нужно убрать заметку, сперва сохранить её отдельно с согласованным пользователем смыслом либо получить явное решение об отбрасывании. Удаление её ID из описания само по себе не сохраняет черновик. Это два разных поля, а не автоматическая миграция в поиск.

| Проверка на синтетическом вводе | Результат |
|---|---|
| Тот же ID, новое назначение `search`, последнее объявленное значение прежнее | 168/168 локальных текстов остались в старой Area, но поисковая ветка не показывает её. Это известная часть #201. |
| Затем новому поиску **того же ID** передали пустое значение вместо прежнего опубликованного `published note` | Уже в подготовке до рендера перезаписаны **167/167 непустых** черновиков. Оставшийся пустой до и после. Это штатная обработка явно изменённого значения; не утверждается, что всякое обновление стирает черновик. Изменение рендера после этого текста не вернёт. |
| Вместо этого: оставить прежний контрол и добавить `search("filter", "", "Искать", "filter.change")` | **168/168** исходных текстов и ID сущности остались у Area, для отдельного Search создана одноcтрочная сущность с собственными пустым значением и подсказкой. После удаления старого ID запись исчезла из карты полей во всех 168 случаях. |
| Попытка перенести полный Area-текст в обычный одноcтрочный `InputState` | Действующий нативный нормализатор изменил все **112** образцов с CR, LF или CRLF, сохранил **56** без них. Например, `a⏎b` и `ab` становятся неотличимы. Расширение не может считать это сохранением исходного текста. |

**Основание.** [Протокол](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/PROTOCOL.md#L462-L478) просит сохранять тип и назначение контролов при обновлении, ограничивает поиск одной строкой. [SDK](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/sdk/src/ui.rs#L201-L209) строит для `search` именно такое описание. Сохраняемая запись [подготавливается по ID](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/extensions/declarative/fields.rs#L335-L377); [удаление пропавших ID](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/extensions/declarative/fields.rs#L115-L166) и [поисковая ветка отрисовки](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/extensions/declarative/render.rs#L282-L346) — разные операции. Вызов [set_value](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/vendor/gpui-base/src/input/base/state.rs#L1299-L1329) сбрасывает selection и историю редактирования, а [обычный нативный нормализатор](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/vendor/gpui-base/src/input/base/state.rs#L4115-L4127) удаляет CR/LF в однострочном варианте. Это не отсутствие API для выделения: [selected_range/set_selected_range](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/vendor/gpui-base/src/input/base/state.rs#L3557-L3609) существуют, но не превращают нормализованную строку обратно в оригинал и не обслуживают несколько прежних выделений как одно. Для обычного однострочного текста возможное отдельное решение не исключается; без достаточного подтверждения оно не предложено.

**Границы проверки.** Выполнены точные чистые SDK builders `input/search/Node::with`, нативная ветка подготовки `Node::Input`, её часть учёта/prune ID, ветка выбора Search-vs-empty и тело `normalize_input` для обычного поля. Объекты хранения, окно, события подписки, виджеты и измерение заменены безвредными локальными коллекторами: обычная Area отмечается по типу, а не по пикселям. Модель различает локально изменившийся буфер и последнее опубликованное значение; она не подписывает потребителя и не отправляет пользовательский текст. Значения строк — только синтетические. Не проверялись реальная доставка, авторская программа, графический кадр, выбор/фокус/undo или дальнейшая судьба буфера за пределами карты редакторов. Реальный штатный модуль, который обязан менять тип именно на том же ID, не установлен. Обходные варианты с интерактивной устаревшей textarea или отображением текста не были предложены как `Search`.

**Повторение** на Desktop `2307e9c67125bbe66f15ced51317a2dfcc437aa4`, Extensions `ef064381d2194d95faef2b85f6cc3a1c34c6b975`, dot `cc320b43ab5b261259b78530ef45aac8b8bf0230`; использован rustc 1.95.0 и локальный serde_json 1.0.151. [#204](https://github.com/Qweasd123tg/proteus-modules-dot/pull/204) относится к действию виджетов/заголовкам, а не к переносу произвольного многострочного текста в однострочный поиск. Здесь новы доказательный контрпример для переинициализации в `set_value`, проверка момента перезаписи **до** рендера и обращение к автору насчёт одновременного существования контролов; это не новая заявка на тот же дефект.
