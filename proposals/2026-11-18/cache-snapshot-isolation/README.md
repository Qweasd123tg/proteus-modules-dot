# Запись кеша не должна закрывать снимок, который ещё читают

**Дефект в закреплённых исходниках.** Когда в одном экземпляре сервиса открыты 32 снимка, запись необязательного кеша вытесняет самый старый снимок. Они могут относиться к разным сессиям. Его следующий запрос чтения завершается ошибкой `snapshot handle expired or unknown`, хотя никто не открывал 33-й снимок для чтения. Записи журнала не удаляются. Это вывод по коду, не наблюдавшийся сбой Desktop.

1. Core [записывает кеш представления сессии](https://github.com/Proteus-harness/Proteus-core/blob/c2cbadee518788f306ffb2b5271036b2658ea8cc/crates/proteus-core/src/core/session_store/remote/view/cache.rs#L104-L121) через обычный запрос `WriteCache`.
2. Для проверки актуальности кеша Modules [открывает временный снимок, сравнивает префиксы и удаляет временный снимок](https://github.com/Proteus-harness/Proteus-modules/blob/0fe8e3b4dfb64ca2e07df8af016d7ccc3a7de45f/storage/session-storage/src/service/cache.rs#L60-L74). При полном реестре [открытие уже вытеснило старейшего читателя](https://github.com/Proteus-harness/Proteus-modules/blob/0fe8e3b4dfb64ca2e07df8af016d7ccc3a7de45f/storage/session-storage/src/service/views.rs#L62-L81). После удаления временного снимка остаётся 31 из 32. Это происходит даже при отказе в записи устаревшего кеша.
3. Из-за этого [поиск старого дескриптора для чтения](https://github.com/Proteus-harness/Proteus-modules/blob/0fe8e3b4dfb64ca2e07df8af016d7ccc3a7de45f/storage/session-storage/src/service/views.rs#L107-L118) больше не находит снимок. Насколько часто реальные клиенты достигают лимита, не измерялось.

**[Предложение исправления](cache-snapshot.patch)** для Modules `0fe8e3b4`: подготовка снимка и регистрация читателя разделены. Кеш сравнивает тот же дескриптор и не занимает место в очереди читателей. Явный 33-й запрос по-прежнему вытесняет самый старый снимок; формат хранения и критерий актуальности кеша не меняются.

**Что проверено.** Сверены исходные Git-объекты трёх файлов на указанной ревизии; `git apply --index --check`, наложение и обратное наложение прошли без остаточного diff. Отдельная модель очереди на 31 и 32 читателях подтвердила границу вытеснения; это не запуск реализации. Независимо проверены путь вызова из Core и порядок подготовки, регистрации и удаления в патче.

**Что не проверено.** Патч содержит один регрессионный тест на штатных фикстурах для JSONL и SQLite: актуальная и устаревшая запись кеша должны сохранить все 32 ранее открытых снимка, а следующее явное открытие должно вытеснить только самый старый. Rust/Cargo в окружении отсутствует: тест не скомпилирован и не запускался. Для квалификации перед переносом:

```sh
cargo test --locked -p session-storage --lib cache_writes_leave_public_snapshot_handles_alone
cargo test --locked -p session-storage --lib
```

Изменения опубликованы только как предложение. Upstream, зависимости, CI и установленное приложение не менялись.
