# A redraw in a second window can discard a pending tab drop

**Proposal:** keep the live strip arrangement on its owning Workspace, not in a shared thread-local cell. This is about reordering tabs in **window A**, not dragging them between windows.

In A, take an unpinned tab from `[pin, drag, a, b]`. For example, with other-tab centers at x = 20, 80 and 140, hovering at x = 95 selects the insertion point before `b`. Window B, containing unrelated items, paints a frame before release. In the original source, releasing in A then produces no insertion target at all, so the existing drop handler does not call `move_tab`. With the proposal, it still targets `b`: the intended order is `[pin, a, drag, b]`. The fixture exercises the targeting step, not a window or a persisted tab move.

## Why the sequence is possible

- [Workspace docs](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/docs/chat-workspaces.md#L3-L7) distinguish switching areas in a window from the explicit tab-detach command that opens a second system window. [The implementation](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/workspace/windows.rs#L370-L382) allocates a new Workspace/window through the same GPUI app context.
- Each window's [pane renderer](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/view.rs#L29-L59) asks for additional frames while its tab or pane animation is running. The [window implementation](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/vendor/gpui-fast/src/window.rs#L2765-L2772) schedules a notification of that view on its next frame. A second visible window that already requested such a frame does not require mouse input to draw it. Both ordinary and moving panes enter the [same strip renderer](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/view.rs#L276-L287). There is no claim that redraws always interleave this way or that this scheduling sequence was observed on an OS display.
- [The drag key is global to the App](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/drag.rs#L45-L51); [each strip filters it through its own layout](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/arrange.rs#L54-L74). When B does not have the dragged ID, its frame sees no drag. On the shared cell it clears the bounds and resets the target to Home. This does **not** require overlapping tab IDs or a drag received by B.
- The [existing visible strip handler](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/bar.rs#L53-L73) only calls the move method if there is an insertion target. Existing [movement](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/crates/tabs/src/tests/tree.rs#L93-L112) and [pin-order](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/crates/tabs/src/tests/pins.rs#L15-L30) tests already establish how the moved tab should be inserted, activated and constrained. This proposal leaves the model unmodified; it does not assert that a previously active *different* tab should stay active.

## Verification

`checks/tabs/run.py DESKTOP_ROOT [RUSTC]` compiles the actual pinned arrangement implementation (including all four functions and the group clamp) with synthetic layouts, frame/hover/release order, simple rectangle geometry and a refresh counter; it verifies which native call sites are wired to the handle. No Cargo, actual GPUI window, or operating-system input. The baseline exits 1 with mismatches. There are 128 cases per ordering of callbacks: same-pane vs cross-pane in A; reused or distinct pane IDs in B; disjoint or one shared **non-source** tab ID; pinned/unpinned source; eight pointer positions. Across all five orderings **372 of 640 wrong before, 0 after**. All 128 uninterrupted one-window controls were correct before and after. The A-hover → B-frame → A-release sequence was wrong 128/128 before; 0/128 after. Leaving the strip still invalidated the target in every case. The combined alternate on [#194](https://github.com/Qweasd123tg/proteus-modules-dot/pull/194) also passed 640/640.

The handle is scoped to a Workspace; its temporary clones in that window's render callbacks own only layout bookkeeping, not the Workspace or GPUI window. This does not add a process-wide window registry. It does not address the existing accumulation of old rectangle entries between drags or patch that cleanup policy. If both windows independently contain a tab with the **same ID as the source**, the existing App-global key can still pass both layout filters. This patch is not a cross-window source-identity solution, does not establish cross-window drop semantics, and makes no claim about every drag timing, FPS, or visual result.

**Dedup:** [#194](https://github.com/Qweasd123tg/proteus-modules-dot/pull/194) avoided copying tab names during hover in this file; the optional combined diff also retains that iterator. [#195](https://github.com/Qweasd123tg/proteus-modules-dot/pull/195) concerned split dividers, [#196](https://github.com/Qweasd123tg/proteus-modules-dot/pull/196) isolated the separate badge-order subsystem, [#202](https://github.com/Qweasd123tg/proteus-modules-dot/pull/202) chose neighboring panes from measured geometry; none fixed losing a drop between two ordinary per-window frames.
