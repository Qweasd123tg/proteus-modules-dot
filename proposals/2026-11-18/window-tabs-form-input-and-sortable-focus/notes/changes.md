# Git Changes: после выбора одного файла клавиатура может адресовать другой

**Подтверждённая диагностика, не production-патч.** На системах, где двоеточие разрешено в имени (например POSIX), пусть в одном разделе Git Changes видны два изменённых файла в порядке `file:notes`, `notes`. Выбрана строка файла `notes`. При повторной сборке дерева *обе* строки получают `selected=true`. После согласования курсора Enter формирует `open("file:file:notes")`: это строка другого файла, `file:notes`. При обратном порядке также отмечены две строки, но первая оказывается нужной. На Windows имена такого вида не являются обычными локальными именами; воспроизведение там не утверждается.

## Почему

[Построитель строки](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/git/src/panel.rs#L113-L171) сравнивает одно `Option<&str>` и с идентификатором строки, и с исходным путём. Идентификатор кодирует раздел (`file:`, `staged:` либо `unstaged:`) и весь путь. [Обработчик выбора](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/ef064381d2194d95faef2b85f6cc3a1c34c6b975/packages/git/src/list.rs#L27-L31) проверяет декодированный путь и сохраняет именно идентификатор строки. [Desktop::Tree::set_rows](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/extensions/declarative/tree.rs#L89-L135) выбирает первую отмеченную строку перед прежним положением курсора. Независимо от двоеточий, корректная прежняя модель для одного частично проиндексированного файла такова: сырой аргумент `notes` отмечает обе строки *того же файла*, а `unstaged:notes` — только его строку в одном разделе.

## Почему не предложена перестановка приоритетов

Одни и те же байты `Some("file:notes")` могут означать две разные вещи при одних и тех же данных и видимости: штатный row ID выбранного `notes` либо сырой путь другого файла `file:notes`. Один и тот же детерминированный приоритет не восстановит оба намерения. Скрытие исходного раздела или исчезновение записи не превращает сохранённый row ID в сырой путь другого файла. В тесте после скрытия Staged для `notes` отмечается `unstaged:staged:notes`. Для общего решения нужно определить источники значения и разделить представления RowId и RawPath там, где происхождение ещё известно. Наличие реального внешнего клиента, передающего сырые значения, не доказано: это существующая возможность функции и проверка сохранения семантики. Смена API/хранилищ не исследована.

## Что проверено

- 6 допустимых исходных путей, включая Юникод, пробел, вложенную папку и двоеточие; 3 префикса (оба режима группировки); оба порядка строк. **36/36** наборов выбрали две строки разных файлов; **18/36** записали Enter не на тот путь; **36/36** при удалении настоящего выбора сохранили отметку на чужой строке. Входные данные синтетические, не состояние пользователя.
- **72** контроля без конкурирующего имени, 1 скрытый раздел и 2 контроля частично проиндексированного файла.
- В Rust выполнялись настоящие тела `change_rows`, модели секций, построителя заголовков SDK, выделения пути и сохранения выбора, `Tree::step / key / act` и участок согласования курсора из `set_rows`. Меню, GUI, список и транспорт заменены локальными структурами; `act_at` только записывает id и тип события. Не запускались приложение, расширение, Git, обновление/открытие настоящих файлов либо изменение индекса. Неверное **направление события**, не утверждение об открытом или изменённом на диске файле. Не измерялись частота имён, скорость и пиксели.

```sh
python3 checks/changes/replay.py "$DEPS" --rustc "$RUSTC" --extensions "$EXTENSIONS" --desktop-tree "$DESKTOP/src/ui/extensions/declarative/tree.rs" --desktop-schema "$DESKTOP/src/declarative/tree.rs"
```
