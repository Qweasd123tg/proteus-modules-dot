# Вкладки разных окон, незавершённый ввод и длинные сортируемые списки

Три независимых предложения к исходникам Desktop. Самая простая потеря данных для пользователя: начать писать JSON в поле формы и нажать кнопку «JSON». Утрачивается ещё не распарсенный текст, не сохранённый файл. Отдельно приведена диагностика выбора другого файла в Git Changes; патч для неё намеренно не предлагается.

| Что видно пользователю | Причина и предлагаемое изменение | Что реально проверено |
|---|---|---|
| Перерисовка соседнего окна может сорвать перестановку вкладки в первом. | Цель сброса и измеренные границы общие для всего потока; второе окно считает, что drag не идёт, и сбрасывает их. [Состояние на Workspace вместо глобального](patches/tab-arrangement-per-window.patch). | В синтетической последовательности «наведение в A → кадр B → отпускание в A» неверная цель 128/128 до и 0/128 после. Во всей матрице: 372/640 → 0/640. [Источник, пример и границы](notes/tabs.md); [независимо](checks/tabs/peer/VERDICT.md) 13/16 → 0/16. |
| В форме параметров нажатие «JSON» стирает незаконченный ввод в поле с ошибкой. | Режим восстанавливается из последней валидной модели, а редактор с ошибкой удаляется без вопроса. [Оставить переключение в один шаг для валидной формы; для ошибочной показать явный выбор «Отбросить ввод с ошибками и открыть JSON»](patches/confirm-invalid-form-before-json.patch). | [48/48 случаев потери → 0/48](notes/settings.md), включая уже отрисованную кнопку. После исправления текста открывается исправленное значение. [Независимый контроль](checks/settings/peer/VERDICT.md): 36 864 перехода и их немедленных повторов; соседи не затронуты. |
| В длинном сортируемом списке при подготовке **каждого кадра** производится квадратичное число сравнений идентификаторов, даже без перетаскивания. | Для очистки focus-handles каждый ключ линейно ищется в ряду, хотя соседняя строка уже строит необходимую таблицу высот по тем же ключам. [Использовать существующий индекс](patches/reorder-focus-index.patch), без второго набора и без пересоздания focus-handles. | На 4 096 строках при сверке живых дескрипторов: **8 390 656** сравнений до; **4 096** хеширований и **4 112** сравнений после (фиксированный хешер). Это счётчики операций, не измерение времени или FPS. 2 592 тестовых набора; [независимо](checks/focus/peer/REVIEW.md) 12 288 смен набора строк на версию с проверкой идентичности и удаления старых ссылок. |

Длинный список не выдуман как недостижимый API: [нативный Sortable](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/extensions/declarative/render.rs#L447-L480) и [экран тегов](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/settings/tags.rs) используют общий компонент. Реальный десериализатор и валидатор приняли узел с 4 096 и 4 999 строками и отклонили 5 000 строк плюс корневой узел. Частоту таких списков у пользователей не измеряли. Упрощается только одна операция в prepaint, не весь рендер. Для вкладок это исправление сброса **внутри A** при перерисовке B: перенос между окнами и совпадение самого ID перетаскиваемой вкладки между окнами не исправлены. Меню формы не переносит неверный синтаксис в raw JSON: либо поправьте в форме, либо явно откажитесь от него.

### Git Changes: диагностика без патча

С файлами `notes` и `file:notes` в одном разделе сохранённая строка `file:notes` может быть одновременно идентификатором первого и путём второго. При восстановлении выделения обе строки отмечены. Порядок строк может направить Enter на другой файл. В 36/36 синтетических парах отмечены две строки разных файлов, в 18/36 не тому файлу *адресовано событие*, при удалении исходной строки в 36/36 выделяется другой файл. Реальные файлы не открывались. Одинаковые байты несут два возможных намерения, поэтому перестановка сравнений не гарантирует правильный выбор. [Диагностика, ссылки и контрольные случаи](notes/changes.md).

### Как воспроизвести

Из корня пакета: Python 3, Git, POSIX `patch`, rustc с поддержкой Edition 2024 (проверено на 1.95.0), совместимые собранные rlib для `serde`, `serde_json`, `anyhow` и их зависимостей. Нужны локальные репозитории с указанными ниже объектами; никакие зависимости или исходники не скачиваются самим тестом.

```sh
python3 checks/verify.py --desktop "$DESKTOP_REPO" --extensions "$EXTENSIONS_REPO" --dot "$DOT_REPO" --deps "$RUST_DEPS" --rustc "$RUSTC"
```

[Записанный результат](checks/recorded.log), [контрольные суммы](SHA256SUMS). Перед тестами проверяются суммы файлов. Во временном каталоге проверены обе очередности трёх патчей и побайтовый откат. Для тех, кто уже применил [#194](https://github.com/Qweasd123tg/proteus-modules-dot/pull/194), вместо отдельного tab-патча применяйте [вариант поверх #194](compat/tabs-after-hover.patch). Он прошёл те же 640 случаев, независимый сценарий и контроль #194 (60 480 вариантов порядка, 0 аллокаций на 120 наведений при каждом размере набора). Обе очередности с tab-badge предложением [#196](https://github.com/Qweasd123tg/proteus-modules-dot/pull/196) дали одинаковые исходники; это не компиляция полного приложения.

Проверены **извлечённые функции** на Rust с небольшими подстановками для UI, синтетическими событиями и состоянием в памяти, а не запущенный Desktop, настоящий пользователь или демонстрация в реальных окнах. Полная сборка GPUI, зрительное и клавиатурное взаимодействие с меню, профили, реальные репозитории и производительность на экране не проверялись. В upstream ничего не вносится. Поиск пересечений с опубликованными предложениями доведён до [#204](https://github.com/Qweasd123tg/proteus-modules-dot/pull/204); не заявляется повторная валидация всех прежних предложений.
