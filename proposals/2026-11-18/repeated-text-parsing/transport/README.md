# Потоковый ответ ассистента: какие разборы повторяются, а какие нет

**На одном законченном ответе в 53 762 байта** штатный процесс расширения и штатный транспорт Desktop доставили проверенное дерево за **18,35 → 10,19 мс** (вторая серия). Если отправить тот же ответ 64 растущими префиксами и дождаться каждой промежуточной версии, суммарное время составило **571,55 → 306,59 мс**. Но если все 64 изменения придут к поверхности до обработки первого ответа, Desktop **уже сейчас** пошлёт расширению лишь первый и последний префиксы: **19,72 → 10,38 мс**. Сравниваются закреплённый Markdown-рендерер и кандидат, пропускающий построение дерева для поиска структурных блоков при заведомом отсутствии нужных признаков. Это не патч очереди, не plain-text оптимизация и не замер отображения в окне.

### Три разные вещи, которые легко принять за «обрабатывать один текст снова»

1. **Те же байты, язык и контекст в той же строке.** При стабильном Arc, формате и списке языков [Replies::part](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/replies.rs#L44-L62) вообще не зовёт обновление. Если этот короткий путь не сработал и равные байты снова предложены, [updated_content](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/content.rs#L86-L103) сравнит их до создания нового payload. В тесте 64 предложения одного текста: 1 запрос, 1 дерево, 1 компиляция HTML, не 64. Не обобщать на смену языка/контекста или новый view. Отдельный контроль: **принудительные invalidation**, с ACK после каждого, дали 64 запроса одной ревизии, 64 идентичных дерева, 3 998 784 суммарных байта HTML. В расширении всё равно **1** проход компилятора HTML на все 64 запроса, благодаря [кэшу одного prose-сегмента](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/a35cea08be83ee8e5ecbfce9ef5050a1c00eb247/packages/markdown-render/src/render.rs#L29-L45). Отрисовка кадра не является явной инвалидацией.
2. **Растущий ответ.** Каждый префикс содержит прежние байты, но в обычном потоке это другое состояние. [Приём событий](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/stream_batch.rs#L5-L19) сначала выбирает до 256 уже готовых событий, [сворачивает совместимые соседние delta, не проходя сквозь барьеры](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/stream_batch.rs#L52-L75), [материализует итоговый текст строки](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/transcript/text_run.rs#L137-L198). Затем [для роли Assistant выбирается text/markdown](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/thread.rs#L189-L222). 64 предложения поверхности в эксперименте **не** означают 64 сетевых токена, кадра или промежуточных обновления в реальном чате. [Очередь](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/runtime/content_queue.rs#L1-L43) [материализует wire-копию только для допущенного запроса](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/runtime.rs#L280-L315) и, получив ответ, берёт последнюю сохранённую версию. В burst из 64 уникальных состояний всего 2 запроса, 2 разных HTML, 1 ответ актуален по revision. В последовательном потоке 64 разных HTML на 64 разных состояния. Это не 64 обработки одной и той же версии.
3. **Разные представления одного состояния.** В исходной версии на выбранной обычной прозе есть построение Markdown AST для [маршрутизации блоков и определений](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/a35cea08be83ee8e5ecbfce9ef5050a1c00eb247/packages/markdown-render/src/fences.rs#L21-L42) и отдельно [компиляция GFM → HTML](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/a35cea08be83ee8e5ecbfce9ef5050a1c00eb247/packages/markdown-render/src/inlines.rs#L217-L223). На 64 последовательно принятых версиях это **64 + 64** вызова API по 1 747 211 входным байтам на каждый этап. Кандидат дал **0 + 64**. Он не убрал саму HTML-компиляцию и не сделал её инкрементальной. После транспорта [проверяется версия до показа](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/view.rs#L169-L183). Принятый HTML обрабатывается как HTML, не как исходный Markdown; у существующего native блока [равный HTML не передаётся в set_text](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/extensions/declarative/rich_text.rs#L21-L36). Байты HTML, дерева и исходника нельзя складывать и называть «объёмом повторного Markdown-парсинга» или экономией RAM.

### Одни и те же финальные 53 762 Б

Свежий хост и дочерний release-рендерер на запуск, короткий прогрев специальной другой поверхности до таймера. По 6 пар A/B попеременно AB/BA; хост и его ребёнок на одном ядре, отдельный повтор на другом. Медианы **полного прохождения всех префиксов** без пауз между группами, не на запрос и не p95. Запуски делят машину с другими процессами; разброс между сериями заметен. Содержимое, число вызовов и хеши при повторе совпали. Первая и вторая серия, мс:

| Предложения поверхности | Дошли до renderer / актуальны по revision | Байт исходника отправлено | Исходная → кандидат (CPU 7) | Повтор (CPU 4) |
|---|---:|---:|---:|---:|
| 1 полный текст | 1 / 1 | 53 762 | 19,00 → 9,93 | 18,35 → 10,19 |
| 4 разных, ACK каждого | 4 / 4 | 134 403 | 49,62 → 26,51 | 54,04 → 29,76 |
| 16 разных, ACK каждого | 16 / 16 | 456 963 | 170,21 → 84,58 | 165,45 → 87,47 |
| 64 разных, ACK каждого | 64 / 64 | 1 747 211 | 723,83 → 314,30 | 571,55 → 306,59 |
| 64 разных, группами по 8 до обработки ACK | 16 / 8 | 436 804 | 158,13 → 81,08 | 147,22 → 77,13 |
| Все 64 до обработки первого ACK | 2 / 1 | 54 601 | 27,55 → 16,42 | 19,72 → 10,38 |
| 64 подачи полностью одинакового текста | 1 / 1 | 53 762 | 42,92 → 18,33 | 19,38 → 10,73 |
| 64 принудительных render той же ревизии, ACK каждого | 64 / 64 | 3 440 768 | 64,82 → 58,92 | 48,42 → 43,60 |

Это управляемые крайние режимы при одном retained view. Время начинается с первого предложения borrowed UTF-8 исходника; вызываются настоящее тело updated_content на последующих предложениях, настоящие ContentQueue, manifest discovery (до таймера), Process::send, дочерний Markdown renderer, JSONL, protocol::parse/Node::validate и Signals::recv. Обвязка ставит фиксированный валидный контекст, проверяет view/session/revision, учитывает актуальную ревизию так же, как show_with_revision, проверяет простую форму тестового дерева. Локальные служебные счётчики тоже попадают в таймер; хеширование и запуск fresh-view oracle нет. Не исполнялись GPUI Runtime::handle/show, native parse HTML, layout, кадры, сеть/Core и upstream TextRun. Модель группировки определяет, **когда** хост забирает ответы, а не подменяет код очереди. Суммарные байты исходника исключают метаданные/экранирование JSON; это не measured wire frame sizes или резидентная память.

**Контрпример против «достаточно обработать дописанный хвост».** Вторая fixture содержит ссылку в первом абзаце и определение в самом конце. Ответ на ранний префикс содержит буквальное `[отчёт][verify]`, но при завершении это уже `<a href="https://example.org/late-destination">отчёт</a>` в **первом** абзаце. Все промежуточные результаты признаны равными свежему рендеру. Если подать все 64 префикса разом, конечная версия требует полной маршрутизации в обеих реализациях: на CPU 7 21,46 → 21,61 мс, на CPU 4 19,53 → 19,11 мс, то есть выигрыш не установлен. В последовательном потоке из 64 запросов кандидат пропустил маршрутизацию на 63 префиксах, но не на последнем. Кэширование только по длине, игнорирование поздних ссылок или склейка старого HTML с HTML хвоста неверны.

### Проверка и воспроизведение

[Первый прогон](results.json), [повтор](repeat.json), [контроль каждой выданной ревизии](proofs.json), [отдельные счётчики парсеров](counts.json). Всего 13 конфигураций, 240 промежуточных ответов для каждой стороны в каждой correctness-серии. Для каждого проверяли **полное равенство деревьев** retained и свежего view через PartialEq в Rust. Сравнивали также digests между ELF, raw HTML и результат при одинаковом финальном тексте. Каждая correctness-серия заново проверяла эту матрицу. В отдельном процессе воспроизведён именно список допущенных ревизий на инструментированных бинарниках: все HTML SHA сверены с полученными от реального хоста, полный stdout обоих counter-ELF идентичен на каждой конфигурации. Счётчики отмечают вызовы/входные байты публичных API Markdown (не все внутренние проходы по байтам). Логирование и проверки fresh-view отключены в latency-сериях.

Входные данные синтетические, полностью воспроизводимые: `prose.md` SHA-256 `a26645d9e976f9729c7b2b59306f0a12244b3c2ffc0b393e773f7d0005158a90`; границы округляются вниз до целого UTF-8 символа. Провайдеры, темы и порядок поставлены постоянными. Linux, Rust 1.95, опубликованный Desktop `210cc9f` и Extensions `a35cea0`; для компиляции нужны закреплённые crates, git dependency и каталог crates.io `gpui-kit-assets-0.8.1`. Переменные BEFORE и AFTER ниже — пути к каталогам `packages` с исходным и изменённым release markdown-render. CARGO_HOME можно предварительно заполнить штатной загрузкой зависимостей; для чистого офлайн-повтора передать `--offline`. В headless shell перечень иконок заменён точной lookup-таблицей имён SVG из закреплённого GPUI assets; конфигурационный путь — неиспользуемая заглушка; в этих ответах они не задействованы.

```sh
python3 fixtures.py "$FIXTURES"
python3 prepare.py "$DESKTOP" "$GPUI_KIT_ASSETS" "$BUILD"
cargo build --release --locked --manifest-path "$BUILD/Cargo.toml" --target-dir "$BUILD/target"
python3 run.py "$BUILD/target/release/desktop-transport-probe" "$BEFORE" "$AFTER" "$FIXTURES" "$OUT" --cpu "$CPU"
# BEFORE_COUNT and AFTER_COUNT: отдельно собранные те же две версии,
# instrument.py из эксперимента markdown-render добавляет MDFRAME/MDPASS в stderr.
python3 replay_counts.py "$DESKTOP/src/declarative/protocol.rs" "$FIXTURES" "$OUT/proofs.json" "$BEFORE_COUNT" "$AFTER_COUNT" > "$OUT/counts.json"
```
