# Повторяемый разбор текста: что действительно можно убрать

**Первым я бы перенёс маленький патч Markdown-рендерера.** На потоке из 64 редакций обычного, но форматированного ответа в 53 762 байта он убрал 64 полных построения дерева для поиска конструкций, которых в тексте нет. Все 64 преобразования Markdown → HTML остались. На реальной очереди и транспорте Desktop с отдельным процессом расширения суммарное время упало с **572 до 307 мс** (повторная серия). Ни общий кеш, ни изменение протокола не понадобились.

Вторая находка меньше, зато это буквальный дубль: диспетчер отложенного вызова инструмента два раза нормализовал те же аргументы. Снятие одного прохода ускорило сам обработчик на 29–40% в двух нагрузках. Ускорение полного длинного хода **не** подтвердилось.

## Что считалось повтором

| Участок | Что происходит | Вывод |
|---|---|---|
| Core: модель → журнал/события | На одной и той же строке из 37 Б четыре дельты дали пять SSE-кадров и одно завершение. Когда OpenCode включил item и в MessageCompleted, и в Response, Core два раза построил строку для показа, но отправил её как завершение один раз. Это проекция на финализации, а не Markdown-парсинг на каждой дельте. | Не вводить общий кеш между провайдером, хранилищем и экраном. [Трасса Core](core/README.md) |
| Desktop: одна строка с неизменным контекстом | 64 обычные подачи идентичного текста дали **один** запрос, не 64. Даже при 64 принудительных обновлениях одного простого сегмента HTML-компилятор был вызван лишь один раз. | Не путать перерисовку, запрос и разбор. [Очередь и контроль](transport/README.md) |
| Desktop: растущий текст | Если ждать ответа на каждую редакцию, могут обрабатываться все разные префиксы. Если подать все 64, пока первый в работе, штатная очередь отправляет лишь первый и последний. | Порядок доставки важен; нельзя умножать стоимость полного сообщения на число токенов. |
| Расширение Markdown | Оно искало блочный код, display math и определения ссылок во вспомогательном дереве, а HTML строило отдельно. Пока необходимых маркеров нет, первый этап не даёт результата. | [Патч 1](markdown/routing-prefilter.patch) пропускает только первый этап. Полный GFM-компилятор и обработка подозрительных случаев не меняются. |
| Модули: deferred tool-call | Между двумя нормализациями нет нового входа или смены фазы. С сохранённой исходной JSON-строкой это 4 разбора тех же байтов → 2; 2 проверки схемы → 1. | [Патч 2](workflow/deferred-parse.patch) передаёт вызов существующему владельцу нормализации. Итоговая валидация, проверка фазы, идентичность вызова и независимый checkpoint сохранены. |
| Native rich text | Сгенерированный HTML является **другим** представлением, не текстом для повторного Markdown-парсинга. Повторно разобрать точно те же HTML-байты пришлось в 15 из 35 специально подобранных малых plain-примеров, но ни в одном из 36 проверенных Markdown-ответов. Не выделять общий кеш на этой основе. | [Диагностика Native](gpui/README.md), без третьего продуктового патча. |

## Сравнение на одинаковом входе

Исходная и изменённая release-сборки рендерера, неизменный Desktop-host без окна. 6 чередующихся AB/BA-пар на закреплённом CPU, отдельно повтор на другом CPU. Вторая серия ниже, первая и полный разброс в [материалах транспорта](transport/README.md). Время от подачи до получения и проверки деревьев, для всей последовательности. Не время запуска модели, получения первого токена или первого отображённого кадра.

| Доставка одного и того же конечного Markdown | Запросов в renderer | До → после, мс |
|---|---:|---:|
| Статичный текст 53 762 Б, одна доставка | 1 | 18,35 → 10,19 |
| 64 растущих редакции, подтверждать каждую | 64 | 571,55 → 306,59 |
| 64 растущих редакции, группами по 8 | 16 | 147,22 → 77,13 |
| Все 64 до первого подтверждения | 2 | 19,72 → 10,38 |
| Контроль: определение ссылки в самом конце, все 64 сразу | 2 | 19,53 → 19,11 (выигрыш не подтверждён) |

Позднее определение ссылки действительно меняет первый абзац. Нельзя «отрендерить только хвост», сохранив прежний HTML префикса. И проверка маркеров здесь консервативна: на полноценном документе с ограждениями прежний путь остаётся. На 652 целых входах из корпуса CommonMark построений вспомогательного дерева стало 212 вместо 652, а HTML-компиляций осталось 666. На трёх целых документах самого Proteus это всего 3 → 2 и неизменные 18 HTML-компиляций. Это набор для проверки семантики, **не** статистика текстов пользователей. [5 237/5 237 побайтно одинаковых ответов](corpus/README.md).

**ОЗУ:** в четырёх отдельных A/B-парах на 64 последовательных редакциях максимум суммы PSS одного и того же хоста и дочернего renderer составил **10,87 → 10,68 МиБ**, диапазоны перекрылись. Для поздней ссылки в одной пачке **8,72 → 8,79 МиБ**. Устойчивое снижение памяти не установлено; это не PSS всего Desktop. [Сырые выборки и метод](memory/README.md).

Для второго патча были 12 пар: 139 Б JSON в обработчике **25,34 → 14,94 мкс**; 151 617 Б **784,60 → 556,35 мкс**. На полном `CodingSingleLoopWorkflow::run_json` с контролируемым хостом большая нагрузка была быстрее лишь в **4 из 12** пар. Не переносить проценты из обработчика на все вызовы модели. [Полные результаты, штатные тесты и 12 сценариев](workflow/README.md).

## Что проверено и что поставляется

- Два патча меняют существующие функции и тесты; нет глобального кеша или новых зависимостей. Сборка настоящих Rust-пакетов, исходники воспроизводителей, сырые времена, счётчики и хеши доступны в [markdown](markdown/README.md), [transport](transport/README.md), [corpus](corpus/README.md) и [workflow](workflow/README.md). Счётчики parser API и замеры времени запускались **раздельно**. Для рендерера: 47 → 48 unit, по 3 process-теста и 2 Python streaming-теста с обеих сторон. Для workflow: по 111 штатных тестов.
- Пины поставки: [Desktop 210cc9f](https://github.com/Proteus-harness/Proteus-desktop/tree/210cc9f274ffe40533b390a0d9e940f251a9fa22), [Extensions a35cea0](https://github.com/Proteus-harness/Proteus-desktop-extensions/tree/a35cea08be83ee8e5ecbfce9ef5050a1c00eb247), [Core 8ea2cda](https://github.com/Proteus-harness/Proteus-core/tree/8ea2cdaf4195ae24e941354f68d4e97335d139d7), [Modules 37b3d9c](https://github.com/Proteus-harness/Proteus-modules/tree/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979). Использованы синтетические сообщения и публичные документы. Рабочее окно Native и отрисовка пикселей не измерялись; входные байты парсеров не являются объёмом RAM.
- Это **предложения переноса в dot**, не изменение работающего приложения или upstream. Предыдущие [#215](https://github.com/Qweasd123tg/proteus-modules-dot/pull/215) и [#216](https://github.com/Qweasd123tg/proteus-modules-dot/pull/216) о другом пути: `text/plain` и его доставке. Этот Markdown-патч испытывался без патчей #215/#216; результаты не складываются.
