# Core: что происходит с обычным текстом ответа

Здесь «внутренний текст» — содержимое `ContentPart::Text` / `event.text`, а не JSON модульного протокола или SSE. На исследованной ветви Core этот текст **не становится Markdown-деревом и не подаётся в JSON-парсер как документ**. Приходят типизированные части; байты текста переносятся между объектами, экранируются на проводе и восстанавливаются на принимающей стороне.

Есть локальный повтор: **тот же завершённый item дважды превращается в строку для показа**, если провайдер вернул и `MessageCompleted`, и этот же item в терминальном `Response`. Это *два прохода на завершение*, а не разбор растущего ответа на каждой дельте. Лишнее временное построение на втором проходе реально; насколько оно влияет на время чата, не измеряли. Отдельный продуктовый патч не предлагается.

## Три трассы

Тестовый ответ один и тот же: четыре куска, 37 байт, русский текст, Markdown-ограждение и намеренно невалидный как JSON префикс. Для первых двух сценариев используется скриптованный провайдер. Для третьего события генерирует реальный [OpenCode NativeResponseCollector](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/model/opencode-provider/response.mjs#L141-L156); он отдаёт именно тот же объект в `MessageCompleted` и `collector.finish()`. Это форма [основного включённого в конфигурации провайдера](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/configs/config.toml#L6-L14) и его [streaming-протокола](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/model/opencode-provider/adapter.mjs#L82-L99). Сетевая модель не вызывается; JS-файлы и Rust-протокол из совместимых пинов Desktop.

| Вход BoundModel для одного item | Парных вызовов display_text + reasoning_text | Публичных событий: дельты / completed | Кодирований и декодирований **SSE-оболочки** | Записей в events.jsonl | В execution journal: завершённый item / терминальный ответ |
|---|---:|---:|---:|---:|---:|
| Только терминальный ответ | 1 | 0 / 1 | 1 + 1 | 1 | 0 / 1 |
| 4 дельты, затем только терминальный ответ | 1 | 4 / 1 | 5 + 5 | 1 | 0 / 1 |
| 4 дельты, item completed и тот же item в терминальном ответе (OpenCode) | 2 | 4 / 1 | 5 + 5 | 1 | 1 / 1 |

Во всех трёх случаях после завершения в текущей проекции **одна** строка с точным исходным текстом и `streaming=false`; дельты имеют корректные байтовые offsets. Проверены typed-события, байты поля text после SSE-перехода, записи на диске и каждое вызванное построение строк для показа. Число сообщений в журнале относится к двум указанным типам записей, а не к полному числу служебных записей. Включённая запись каждой дельты (`persist_deltas=true`) и клиенты, которым нужна повторная синхронизация, изменят объём транспорта. Тест не открывает окно Desktop и не измеряет производительность: он делает воспроизводимый подсчёт причин, а не сравнение по времени.

## Точки ответственности

1. [present_stream и emit_message](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/bound_model/presentation.rs#L17-L75) сообщают новую дельту с длиной и offset без проверки синтаксиса текста. На item-completed и response вызывается один и тот же [финализатор](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/bound_model/presentation.rs#L114-L164): сначала собирает reasoning и текст, затем сравнивает со старыми значениями. В [проекции CanonicalMessage](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-contracts/src/model_standard/content_part.rs#L149-L176) это отбор подходящих частей, `trim().is_empty()`, соединение строк через `\n`. Для последней формы материализуются 37 + 37 байт presentation text, а полный completed уходит один раз.
2. [TurnProgress](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/turn_progress/text.rs#L5-L44) находит строку по ID и роли. Последующие дельты дописываются через `push_str`; authoritative completed **заменяет**, а не добавляет полный текст, чтобы применить возможную коррекцию. Поиск строки и копирование — не разбор. Проверены обычные ответы с одним ID; для reasoning есть отдельная проверка перекрытий и UTF-8, не Markdown-парсер.
3. [AppServer event log](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server.rs#L626-L639) разветвляет события: потоковая проекция получает дельты, а в обычном events.jsonl [по умолчанию они отсекаются](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/config.rs#L519-L548). Отдельно [execution recorder](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/session_journal/recorder.rs#L128-L159) сохраняет item-completed и авторитетный терминальный результат как **разные факты**. Два экземпляра текста в них не означают, что он был дважды обработан как Markdown или что его можно безусловно удалить: журнал используется для восстановления.
4. [Core SSE](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/http/sse.rs#L110-L122) сериализует **выходной объект** в JSON. [Desktop](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/api/mod.rs#L386-L428) выделяет data и выполняет один `serde_json::from_str::<StdioOutput>`. Это кодирование/декодирование рамки, не два прохода синтаксического разбора ответа. Данный тест вызывает настоящий кодировщик и независимо декодирует его результат как StdioOutput; он не учитывает количество JSON-конверсий в полном модульном IPC и не отправляет кадр по TCP.
5. При полном восстановлении истории [transcript_from_scan](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/transcript/journal/source.rs#L53-L178) делает четыре последовательных сканирования выбранных **записей** для разных задач видимости и вывода. Это не четыре Markdown-парса и не четыре раза на дельту. [Дедупликация касается part ID](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/transcript/journal.rs#L359-L387), [вывод обычного текста](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/transcript.rs#L235-L257) соединяет части, но не интерпретирует их. Этот пункт — проверка исходника, не замер восстановления истории. Такая проекция не является поводом убирать строгую валидацию.

## Воспроизведение

`bash reproduce.sh /path/to/Proteus-core /path/to/Proteus-modules new-output-directory`. Нужны Rust 1.95.0, Node, git и зависимости Cargo. Скрипт работает в чистых копиях checkout, формирует события реальным JS-коллектором и запускает один Rust-тест. Патч только для тестовой инструментализации: две диагностические точки и fixture, без каких-либо изменений рабочего поведения. [Сырой результат](trace.txt). Эта проверка **не** охватывает общую стоимость клика, смену тредов, Markdown в Desktop, сторонние хуки или внутренности LLM.
