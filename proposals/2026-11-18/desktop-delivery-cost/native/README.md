**Граница будущего замера.** На Linux с работающим дисплеем и точным release-ELF используйте [штатный синтетический стенд](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/examples/performance/native-stream/history_demo.py#L125-L160), передав синтетический transcript, отдельный профиль и по очереди каждую из двух сборок расширения. Одинаковое окно, шрифты, тексты и состояние кешей; холодные запуски отдельно от тёплых. Для первого *читаемого* текста нужен зарегистрированный кадр с маркером в области сообщения, а не изменение любого пикселя. Для результата самого расширения нужен отдельный сигнал принятия ответа именно для проверяемой ревизии контента, затем соответствующий показанный кадр; первый читаемый текст может прийти из временного отображения исходника. Проверяйте, что запрос действительно дошёл до нужного ELF: если проверяемый маршрут не вызывает расширение, это самостоятельный отрицательный контроль. Указывайте точность временной метки кадра и частоту дисплея; отдельно измеряйте `smaps_rollup/Pss` идентифицированного дерева (Desktop и дочерние процессы расширений), отделив стенд и compositor. Проверка здесь этих будущих шагов не заменяет.
