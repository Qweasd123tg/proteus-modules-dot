# Два одинаковых для A/B входа в настоящий Desktop

Одна пользовательская строка в пустой истории: **53 762 Б** многострочного UTF-8 либо тот же текст с ` https://example.org/x` в конце перед суффиксом (53 784 Б). Это входы из [предыдущего измерения #215](https://github.com/Qweasd123tg/proteus-modules-dot/blob/402cb995dc922f5a9c9d36e05ea224a50c2cc616/proposals/2026-11-18/runtime-cost-second-pass/plain-text/compare.py), суффикс ` 0`. URL не открывается. Роли, сообщения и сессии синтетические, локальных пользовательских данных не требуется. [Хеши](fixture-hashes.json).

На Linux с checkout Desktop `210cc9f274ffe40533b390a0d9e940f251a9fa22`:

```sh
python3 make_fixture.py "$DESKTOP" "$OUT/fixtures"
python3 check_snapshot.py "$DESKTOP" "$OUT/fixtures"
```

**Что выполнено здесь:** генерация двух DTO штатной функцией и получение обеих историй через HTTP/SSE с настоящего loopback-сервера [HistoryFixture](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/examples/performance/native-stream/history_demo.py#L60-L87). В каждой ровно одна завершённая строка с ролью user, без курсора. Полные DTO и хеши исходного текста совпали. Прошли также все пять штатных тестов `test_history.py`. Это проверка воспроизведения данных, не запуск приложения.

**Как замерить именно окно на Linux с дисплеем.** Ниже протокол для машины с той же версией собранного Desktop; результаты этих шагов в этом отчёте отсутствуют.

1. Подготовить один release ELF Desktop, зафиксировать его SHA-256. Подготовить два независимых каталога собранных пакетов Extensions из одного пина: A без патча, B с [четырьмя строками из #215](https://github.com/Qweasd123tg/proteus-modules-dot/blob/402cb995dc922f5a9c9d36e05ea224a50c2cc616/proposals/2026-11-18/runtime-cost-second-pass/plain-text/plain-links.patch). Манифесты и параметры одинаковы, SHA-256 исполняемых файлов Markdown различаются. Не брать старый опубликованный Desktop вместо текущего.
2. В отдельном локальном display, без других задач, запускать по одной паре A/B, чередуя порядок, один прогрев и не менее 8 измеренных пар отдельно для каждого входа. Пример одного запуска:

   ```sh
   PROTEUS_STARTUP_TRACE=1 python3 "$DESKTOP/examples/performance/native-stream/history_demo.py" \
     --native "$NATIVE" --extensions "$PACKAGES_A" --transcript "$OUT/fixtures/plain.json" \
     --output "$OUT/A-plain-01"
   ```

   Для B заменить только каталог пакетов и выход; для URL выбрать `url.json`. Каждый output должен отсутствовать до запуска. Остановка: создать `control/stop` в output. Runner передаёт случайный токен только локальному fixture и использует отдельные HOME/XDG. [Он подключает ровно markdown-render и сохраняет хеши](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/examples/performance/native-stream/code_blocks.py#L151-L169); это не память системы со всеми расширениями.
3. **Первый читаемый кадр и первый кадр с принятым rich text — разные события.** Синхронизировать захват представленных кадров и серверный trace на общей monotonic clock, записывать интервал между последним кадром без текста и первым читаемым. Учитывать, что upstream `event_written` записан *после* flush: это контрольная точка доставки, не начало ввода и не гарантированно раньше первого кадра. Для строгой доставки от старта записи следует поставить тестовую monotonic-метку непосредственно перед записью SSE; в обеих сборках одинаковую. `READY`, `chat.transcript.render`, `chat.transcript.layout` и ответ расширения не заменяют presented frame. На тексте без URL fallback и форматированный результат могут выглядеть одинаково; подтверждать отдельной меткой коммита конкретных HTML, view и source_revision, привязанной к представленному кадру (просто `is_ready()` может означать готовность предыдущей версии), либо оставить время готовности неизмеренным. Обычное равенство конечных скриншотов не даёт этой метки. Указать частоту захвата/неопределённость; не обещать различить 5–10 мс камерой 30 Гц.
4. Параллельно (лучше отдельной серией без влияния sampling на latency) идентифицировать PID Desktop и фактического дочернего markdown-render по `/proc/PID/exe`. В одних и тех же временных срезах снимать Linux `smaps_rollup:Pss` у обоих живых процессов; максимум **суммы по каждому срезу** и устойчивое состояние после готовности публиковать раздельно. Снимать также до появления renderer и отметить отсутствие процесса. Не складывать индивидуальные максимумы, RSS, VmHWM или значения из разных запусков; PSS не равен RSS. Исключить Python fixture, X-сервер/композитор, чужие процессы; описать включённые PID и дискретность. Для GPU-сценария VRAM не входит в PSS.
