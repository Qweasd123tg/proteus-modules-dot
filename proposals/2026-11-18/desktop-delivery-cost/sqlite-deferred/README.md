# SQLite: размер записи между страницами. Не включать в поставку

При лимите страницы 4 МиБ следующая запись иногда уже прочитана и измерена, но не помещается. Проверили идею сохранять её измеренный размер до следующей страницы. **В реальном worker устойчивого выигрыша нет.** Производственное изменение не рекомендуется.

Медианы полного чтения по JSON-RPC, мс; в каждой ячейке «исходный → экспериментальный». Клиент отправляет следующий cursor после разбора ответа.

| Сценарий | Обычное планирование | Повтор: клиент CPU 2, worker CPU 3 |
|---|---:|---:|
| 12 коротких записей, одна страница | 0,90 → 0,86 | 0,77 → 0,98 |
| 8 записей с ~2 МиБ текста, лимит 64, 8 страниц из-за бюджета | 204,15 → 216,36 | 430,78 → 410,77 |
| Те же 8 записей, лимит 1: обработка отложенной записи **не вызывается** | 193,77 → 220,93 | 389,75 → 415,07 |

В основном сценарии меняется даже знак разницы. Peak RSS процесса worker: 29 550 → 29 576 КиБ и 29 586 → 29 644 КиБ при повторе. Экономии RAM нет. Разницу не считаем ни доказанным ускорением, ни общим регрессом. Сокращение семи ожидаемых повторных подсчётов не равно сокращению всей стоимости чтения.

Modules [37b3d9c4](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/snapshot.rs#L139-L173), Rust 1.95, release. В каждой серии один настоящий SQLite-журнал на сценарий, обычный файл локального overlay, созданный через Create / Commit фактического worker, закрытый и переоткрываемый обеими сборками. На каждую фикстуру 12 чередующихся измеренных пар с новыми процессами плюс один исключённый прогрев. Открытие snapshot, запись фикстуры и глубокая сверка не входят в задержку перелистывания; JSON-RPC, передача ответа, клиентский JSON-парсинг и все запросы страниц входят. Независимо сверены полные значения и порядок с записями из ACK, привязка к snapshot, размеры страниц, повторы cursor и ошибка выхода за границу.
