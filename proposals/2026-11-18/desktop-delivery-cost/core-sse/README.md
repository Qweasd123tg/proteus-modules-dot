# Core: писать JSON сразу в кадр SSE

**Изменение.** [`encode_sse_output`](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/http/sse.rs#L110-L122) создавал полный JSON как `String`, а затем копировал его в другой буфер вместе с заголовком SSE и двумя завершающими переводами строки. Патч сериализует в один растущий `Vec<u8>`. После неудачной сериализации частичный кадр освобождается, а ответ об ошибке записывается в новый небольшой буфер. `reserve_exact(2)` перед завершителем предотвращает удвоение буфера ради одного-двух недостающих байтов.

**Где это видит Desktop.** [Фоновый поток Desktop](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/connection.rs#L153-L173) при подключении и переподключении вызывает [GET /events](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/api/mod.rs#L288-L313). В Core этот запрос [обслуживает SSE](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/http/reads.rs#L75-L93), и [поток отправляет закодированный кадр](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/app_server/http/sse.rs#L63-L72). Получив `SessionSnapshot`, [чат вызывает apply_snapshot](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/pump.rs#L123-L132), который [передаёт transcript модели истории](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/session.rs#L137-L157). Патч не меняет Desktop, хранилище, протокол, фильтрацию либо ограничение страницы.

## Измерение

Rust 1.95.0, Linux x86-64; обе версии Core собраны с одним Cargo.lock в release. В каждой подняты действительные AgentAppServer, HTTP-маршрутизатор и Hyper-соединение через TCP 127.0.0.1. Хранилище — процесс JSONL из pinned Proteus-modules (это [выбор основного профиля](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/configs/config.toml#L163-L166)); в остальном используется конфигурация официального HTTP-теста с reference-модулем. Никаких внешних запросов к модели. Четыре формы: 0 строк; 1 короткая; 50 × 1 КиБ и 50 × 64 КиБ текста, плюс UTF-8, кавычки, переносы и обратная косая черта.

До замера канонические сообщения пишутся в реальный JSONL, читаются штатной проекцией и передаются уже работающему серверу. Время протокола — от начала нового TCP-соединения до чтения полностью принятого HTTP chunk, в котором заканчивается первый SSE `SessionSnapshot`; не до первого заголовка/heartbeat. Разбор и сравнение самого snapshot происходят после фиксации времени. Это повторное открытие тёплой сессии, не холодный старт и не время от клика до пикселя. Контрольный клиент — тестовый потребитель HTTP/1.1, не Desktop. Четыре запуска в порядке baseline → candidate → candidate → baseline; в каждом 2 прогревочных и 8 зачётных подключений для каждой формы (16 зачётных на версию). Перед каждым GET отдельно измеряется кодирование статичного объекта, пакетами по 512, 64 или 8 вызовов.

Медианы; сумма измерений на ячейку — 16. Для коротких путей небольшие разницы не отделены от шума измерения.

| Форма | Кодировщик отдельно, мкс: до → после | GET до snapshot, мс: до → после | Медианы GET по отдельным прогонам, мс: до / после |
|---|---:|---:|---:|
| Пустая | 0.40 → 0.59 | 0.161 → 0.222 | 0.158; 0.186 / 0.222; 0.256 |
| Короткая | 0.95 → 1.14 | 0.204 → 0.232 | 0.174; 0.218 / 0.222; 0.232 |
| 50 × 1 КиБ | 47.12 → 47.10 | 0.334 → 0.474 | 0.296; 0.386 / 0.331; 0.516 |
| 50 × 64 КиБ | 4265.59 → 3780.13 | 7.167 → 6.154 | 7.099; 8.024 / 12.764; 4.958 |

## Выделения кодировщика

Только сам вызов `encode_sse_output`; вход уже создан. Аллокатор перенаправляет вызовы в системный и считает размеры, запрошенные у Rust-аллокатора; это не RSS. Пик измеряется относительно входа, живые байты — после возврата, до уничтожения `Bytes`; для realloc учитывается разница размеров, не внутренние временные копии системного аллокатора.

| Форма (байт в статичном SSE) | Сумма запрошенных байтов, до → после | Дополнительный пик, Б | Осталось на возврате, Б |
|---|---:|---:|---:|
| Пустая (262) | 1 232 → 920 | 800 → 536 | 544 → 536 |
| Короткая (546) | 3 620 → 1 944 | 2 136 → 1 048 | 1 112 → 1 048 |
| 50 × 1 КиБ (61 916) | 358 029 → 174 783 | 210 188 → 87 640 | 123 852 → 87 640 |
| 50 × 64 КиБ (3 287 516) | 18 227 853 → 8 367 807 | 10 790 156 → 4 216 408 | 6 575 052 → 4 216 408 |

Отдельно проверены **12 795 форм**: 1, 2 и 50 строк, длины текста 0…4096 и значения вблизи степеней двойки вплоть до 1 МиБ на строку. Длины кадров совпали, во всех этих точках пик, сумма и оставшиеся живые байты уменьшились; это не утверждение о любом возможном событии. Исходный вариант без `reserve_exact(2)` иногда удерживал на 2 байта больше у границы; результат в таблице относится к исправленному патчу.

## Что проверено

* Фиксированные `StdioOutput`: побайтовое совпадение с исходным кодировщиком для пустого, малого, многострочного Unicode и одного большого сообщения. На Unix дополнительно проверен путь изображения с невалидным UTF-8 после уже записанного текста: ровно прежний валидный кадр ошибки, без частичного JSON. Граничная выборка сравнивает размеры, не подменяет побайтовые тесты.
* В каждом HTTP-замере сравниваются **все поля каждой полученной строки** с ожидаемыми строками штатной проекции, включая их порядок. Фактические session/stream IDs, директории и время независимы в разных запусках; побайтовое равенство динамических GET-ответов между процессами **не** заявляется. Параметр bytes в сырых строках FRAME — размер статического образца кодировщика, не HTTP-ответа.
* Сценарии уже подключившихся клиентов, steady-state токены, отрисовка GUI, долговременная загрузка процесса и другие ОС здесь не измерялись. Все числа относятся к тестовым данным и этой машине.

## Воспроизведение

1. Нужны git, Rust 1.95.0, стандартная Linux-среда сборки, Cargo-кэш либо доступ к зависимостям. Подготовьте два checkout с указанными коммитами: [Core](https://github.com/Proteus-harness/Proteus-core/commit/8ea2cdaf4195ae24e941354f68d4e97335d139d7) и [Modules](https://github.com/Proteus-harness/Proteus-modules/commit/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979).
2. Вызовите `bash reproduce.sh /path/to/Proteus-core /path/to/Proteus-modules new-output-dir`. Скрипт работает в **новых копиях**, исходные checkout не изменяет. Только `sse-direct-frame.patch` является продуктовым изменением. `probe.patch` — отдельная тестовая оснастка; `allocation.rs` связывается с действительными Cargo.lock-зависимостями Core и извлечённой из каждой версии функцией.
3. Сырые логи прилагаются в [baseline-output.txt](baseline-output.txt) и [candidate-output.txt](candidate-output.txt). Медианы, диапазоны, счётчики граничной выборки и SHA-256 получаемых скриптом CSV — в [native-results.json](native-results.json). Для медиан отфильтруйте строки FRAME с `rep>=2` и объедините два прогона каждой версии отдельно по форме; 1 мс = 1 000 000 нс.
