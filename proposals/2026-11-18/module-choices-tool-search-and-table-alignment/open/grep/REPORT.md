# Штатный grep: конечный пробел исчезает даже из раскрытого аргумента

**Диагностика без патча.** Для публично документированного поля `grep.pattern` карточка Desktop показывает `"done "` и `"done"` одинаково: заголовок `done`, раскрытый текст тоже `done`. Это не только сокращение заголовка: два разных исходных строковых значения дают один и тот же результат в обоих проверенных представлениях. Регулярное выражение может использовать пробел буквально; например, запись `done[ ]` делает конечный пробел явным и показывается целиком. Это не утверждение, что пользователь не может получить исходный JSON другим способом.

**Цепочка.** Штатная [декларация grep](https://github.com/Proteus-harness/Proteus-modules/blob/0fe8e3b4dfb64ca2e07df8af016d7ccc3a7de45f/tool/file-tools/src/search.rs#L22-L44) описывает `pattern` как обязательный `string` с содержанием регулярного выражения. В Desktop у известного имени [выбирается этот аргумент](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/tool_display/mod.rs#L38-L52), а [нормализация заголовка](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/tool_display/mod.rs#L214-L248) отрезает пробелы по краям каждой строки. [Раскрытая секция](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/chat/tool_row.rs#L402-L446) передаёт непустой исходный строковый subject в [короткую ветку Fold::block](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/chat/tool_row.rs#L180-L196), но там вызывается ещё и `text.trim_end()`. Отсюда важное различие:

| Строковое значение (в JSON-нотации) | Заголовок | Текст в раскрытой секции |
|---|---|---|
| `"done"` | `done` | `"done"` |
| `"done "` | `done` | `"done"` |
| `"  done"` | `done` | `"  done"` — отличается от первой |
| `"    "` или `""` | нет subject | строка `pattern:`, значение пустое |
| `"done[ ]"` | `done[ ]` | `"done[ ]"` |

В последнем столбце кавычки обозначают точные байты строки, а не дополнительный элемент интерфейса. Для одного лишь пробела заголовок не создаёт subject, остальные аргументы показываются через `other_args/arg_preview`; путь отличается от случая `"done "` (непустой subject).

**Нативная проверка.** 50/50 непустых выражений с дополнительным конечным пробелом, табом, CRLF или Unicode-пробелом полностью совпадают с исходным непаддированным текстом в обоих местах, а 50/50 вариантов с начальным пробелом остаются различимы в раскрытом тексте. 16 пустых/пробельных вариантов в двух группах (с опциональным `path` и без) неразличимы внутри каждой группы. 6 контрольных вариантов явной записи regex сохранены. Введены только короткие синтетические значения. Выполнялись точные тела `subject_text/single_line/other_args/arg_preview`, участок выбора subject ключа для известного имени, `argument_details` и короткая ветка `Fold::block`. Вместо GPUI и поступившего объекта — коллектор строк и синтетический DTO. Значения сравниваются **до растра**, это не утверждение о пиксельной видимости самого конечного пробела.

Отдельной ветки для имени `grep` и изменения общего Fold не предлагаю: это повлияло бы на другие типы данных или требовало бы общего правила отображения точных аргументов и невидимых символов. Не проверялось принятие выражения модулем при реальном вызове, совпадение с файлами, выполнение поиска, запись результата, буфер обмена, история или иные экраны. #208 касается массива путей в `read_many_files`, а не этого превращения двух скалярных аргументов в одну видимую проекцию.
