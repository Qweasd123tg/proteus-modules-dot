# Core: two tables disregard the slot DTO’s display order

**Verified at the public snapshot→formatter boundary.** The slot DTO [documents `order` as its display order](https://github.com/Proteus-harness/Proteus-core/blob/c2cbadee518788f306ffb2b5271036b2658ea8cc/crates/proteus-contracts/src/app_protocol/topology.rs#L29-L44). The diagnostic map already uses a [stable sort on this field](https://github.com/Proteus-harness/Proteus-core/blob/c2cbadee518788f306ffb2b5271036b2658ea8cc/crates/proteus-core/src/core/topology_render/helpers.rs#L1-L8). But when the wire order is noncanonical, one Markdown document can present two different slot sequences: [its embedded diagnostic map](https://github.com/Proteus-harness/Proteus-core/blob/c2cbadee518788f306ffb2b5271036b2658ea8cc/crates/proteus-core/src/core/topology_render/markdown.rs#L37-L48) follows the numeric order, while its following slot table iterates the input array. The [standalone plain-table formatter](https://github.com/Proteus-harness/Proteus-core/blob/c2cbadee518788f306ffb2b5271036b2658ea8cc/crates/proteus-core/src/core/topology_render/table.rs#L15-L33) likewise iterates the input array, although it includes active entries only.

Example input, in received order: `custom:900` (active), `first:1` (inactive), `beta:10` (active), `alpha:10` (active). The map shows `first, beta, alpha, custom`. Before the patch Markdown's slot table shows `custom, first, beta, alpha`, and the plain table shows `custom, beta, alpha`. After the patch Markdown's slot table matches the map and the plain table shows `beta, alpha, custom`. Equal numeric positions retain incoming order: `beta` still precedes `alpha`. The patch neither changes the membership of either table nor interprets slot order as execution order.

**Scope and limits.** These are actual Core formatters used by the [CLI format selection](https://github.com/Proteus-harness/Proteus-core/blob/c2cbadee518788f306ffb2b5271036b2658ea8cc/crates/proteus-core/src/main.rs#L388-L399). Public DTOs can represent the demonstrated ordering. We did **not** establish that Core's own snapshot producer emits out-of-order rows in normal operation, that the CLI accepts an arbitrary saved snapshot as input, or that a live user has seen this. This is a public presentation inconsistency, not proof that ordinary CLI output from a canonical snapshot was broken. On already-ordered input the rendered bytes do not change. Do not frame the patch as an optimization: the shared helper materializes a view of slot references and stably sorts it. The alleged alternative quadratic bottleneck was not benchmarked or proposed.
