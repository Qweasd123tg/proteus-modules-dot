# Desktop: respect a module author's multiline string-list declaration

**Result:** when the Core schema describes an array of ordinary strings with multiline=true, the normal settings form currently uses single-line tags. Pasting the plain text “Header [LF] Body” as a new tag yields one string “HeaderBody”. An author who chose multiline cannot reproduce a paragraph-valued list item through that control. Existing multi-line values are not auto-corrupted merely by rendering; the old raw-JSON *module* editor is already a workaround. No loss of files or saved profile data was tested or alleged.

**Cross-component provenance.** [Core's schema](https://github.com/Proteus-harness/Proteus-core/blob/c2cbadee518788f306ffb2b5271036b2658ea8cc/crates/proteus-contracts/src/domain/config_schema.rs#L47-L68) carries the string multiline flag inside array items. The [Desktop dependency](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/Cargo.toml#L51) pins Core b6f48cdaaec0e97a083ac81c6292c711a10fe65d; its config_schema.rs is the same Git blob 5c1cb74d5d7afc957c05165c1b916019529a5129 as Core main c2cbadee518788f306ffb2b5271036b2658ea8cc. The [Desktop schema classifier](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/settings/schema.rs#L100-L113) distinguishes single- and multiline string arrays. But [tag eligibility](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/settings/tags.rs#L21-L32) ignores multiline, and [UI control construction](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/settings/editors.rs#L315-L349) chooses its tag branch first. [A single-line paste strips LF](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/vendor/gpui-base/src/input/base/state.rs#L3282-L3293). The receipt uses a synthetic author declaration that crosses the real serde boundary, not a claim about a particular shipped module.

**Candidate:** multiline-array-editor.patch, SHA-256 f306743af95285977a21584dd9143860f244c9d7187658e4e01149bac70ec851, against Desktop 2307e9c67125bbe66f15ced51317a2dfcc437aa4. Only an explicitly multiline, nonsecret array of strings gets the typed JSON textarea. A prior generic-JSON version was **rejected** because the normal form would also accept a scalar or array of other values. The reviewed version requires an array entirely of strings; blank or JSON null remain standard reset gestures, while [] is a present empty list. JSON itself is not narrowed. The edited field no longer has tag chips, their reordering shortcut or suggestion buttons; users enter a JSON array such as ["Header\nBody"], not unquoted pasted prose. Ordinary single-line strings, string enums and scalar multiline fields keep their controls.

**Existing and new data:** strings containing LF/CRLF, quotes, leading/trailing whitespace and Unicode, duplicates and empty elements round-trip in the form. Only the display/editor/parse choice changes. It does not write a migration, normalize existing data, reinterpret previously collapsed text, or reconstruct already lost line breaks.

**Verification.** The standalone check extracts the actual public Core declaration/builders, serde round-trip, Desktop gate, schema classifier, pure formatter/parser, single-line normalization statement and tag value construction. It additionally checks wiring by source. In the old UI the scenario feeds text to the tag entry; in the new UI the user supplies a valid JSON array, so the inputs are deliberately not claimed to use the same syntax. Nine ordinary cases before: 9/9 mismatched the intended appended item; after: 0/9. Old neighboring data preserved, 8 unrelated array routes plus scalar multiline unchanged; 10 invalid JSON shapes/syntax cases rejected. Independent review: 90 routing cases, 576 array round-trips, 12 wrong shapes, empty-list and five reset cases, broad JSON unaffected. Forward/reverse patch checks succeeded. The two overlapping #201 patches for numbers and literal tag matching also apply alongside the new patch and the combined source gate passes. This is not #201's same-ID input replacement or a change to tag matching.

**Reproduce:** python3 checks/multiline/check.py CORE_CHECKOUT DESKTOP_CHECKOUT PATH_TO_SERDE_RLIB PATH_TO_SERDE_JSON_RLIB --rustc PATH_TO_RUSTC --expect before (or after). The libraries' target dependency directory must be next to the serde rlib. Native evidence: rustc 1.95.0, serde 1.0.228/serde_json 1.0.151 available from Core; Desktop's lock uses 1.0.229/1.0.152. No full GUI/OS input, clipboard, module host, profile persistence or release. Upstreams untouched.
