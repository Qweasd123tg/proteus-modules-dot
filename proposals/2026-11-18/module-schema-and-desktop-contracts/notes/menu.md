# Tab menus: derive close availability from the actual neighboring tabs

**Behavior stays the same; work on the ordinary tab-strip render path is reduced.** The proposed patch does not change which tab closes, which tab becomes active, or when the menu captures its flags. No tabs were closed to run the checks.

On every strip render, [the normal path walks all tabs, not just an opened context menu](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/bar.rs#L84-L104). [Each tab constructs its `TabMenu`](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/tab.rs#L185-L198) and only then [installs a callback to show it](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/tab.rs#L289-L293). The constructor [asks for both complete owned lists to inspect only their emptiness](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/menu.rs#L23-L33). [The pure model clones each eligible tab ID](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/crates/tabs/src/pins.rs#L21-L42). No mouse/keyboard gesture is necessary to incur those copies.

For 100 unpinned tabs in a pane, one strip render therefore prepares 9,900 candidate names for “Close others” and another 4,950 for “Close to the right,” before anybody asks for either. The proposal removes all **14,850 candidate-name copies**; it does not remove the tab's own saved menu ID, other parts of tab painting, or all allocations and scans.

The model resolves the ID's **owner**, not whichever pane happens to paint the menu: [drag preview can paint an existing tab in a different pane](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/src/ui/tabs/bar.rs#L118-L132). A tab already removed from the layout can still be drawn during its exit animation. Two borrowed slices now express the existing rule, “unpinned entries before and after the queried tab.” Both the menu flags **and** the ordered IDs used by the close methods come from exactly those slices; callers that need owned target lists still receive owned lists. The count/index rule is not reimplemented in the UI. [Existing pin tests](https://github.com/Proteus-harness/Proteus-desktop/blob/2307e9c67125bbe66f15ced51317a2dfcc437aa4/crates/tabs/src/tests/pins.rs#L39-L56) agree. Diligently retaining the owner's identity matters: using only the painted pane's tab count would be incorrect on a drag.

**Reproduction**: `python3 checks/menu/run.py DESKTOP_ROOT [RUSTC]`; run first on unmodified Desktop `2307e9c67125bbe66f15ced51317a2dfcc437aa4`, then on a tree to which the patch was applied. Uses the actual menu constructor, candidate/eligibility methods, positional lookup, traversal and split predicate, with fixture-only trees, lock-state predicate and a String stand-in for the saved menu ID; counts native allocations in the constructor only. No workspace application build, command dispatch, tab mutation or GUI.

- **64,800 observations:** both original and proposed constructors match the independently enumerated eligible rows and both ordered lists in all cases. Mixed pins, three panes, asymmetry, empty groups and missing IDs/destinations, differing painted/current pin state. All other menu fields are equal. Not an OS or keyboard test.
- **Allocation control, exactly 113-byte ASCII IDs, 100 unpinned tabs:** 14,950 → 100 ID-sized allocations in the complete constructor fixture, of which 100 pay for the queried menu IDs. The additional 14,850 correspond exactly to names in the discarded lists. Including other sizes and reallocations, this fixture reports 16,520 → 300; these are not whole-UI allocation counts. Wholly pinned negative control: no candidate names to copy, hence 100 → 100 ID-sized allocations.
- Both versions still find the ID in the layout and compute `can_split`; depending on the layout this involves pane collection and scanning other tab IDs. No O(n) claim for the full strip, no measured FPS/latency/RSS.
- Dedup through dot `3647395`: [#194](https://github.com/Qweasd123tg/proteus-modules-dot/pull/194) concerns tab IDs being cloned **while hovering a drag**; [#205](https://github.com/Qweasd123tg/proteus-modules-dot/pull/205) scopes the strip drop target to a window. Those do not alter the menu constructor or the model's two target enumerations. [#202](https://github.com/Qweasd123tg/proteus-modules-dot/pull/202) concerns directional pane focus/other paths, not closing or a context-menu preflight.
