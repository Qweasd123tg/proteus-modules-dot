# Снимок текущего диалога без второй копии всех сообщений

При запросе текущего разговора storage worker полностью читает и проверяет журнал. Затем он глубоко копировал уже проверенные сообщения в ответ и сразу уничтожал исходную историю. [Патч](current-conversation.patch) передаёт эту историю в ответ через существующий `into_history()`. Никакого нового кеша, SQL или формата. Исторические срезы и состояние активного writer по-прежнему владеют своими данными; их общая функция не изменена.

Это **не** опубликованное в [#214](https://github.com/Qweasd123tg/proteus-modules-dot/pull/214) избавление от копии на стороне Core при `RemoteValidatedRead::open`. Здесь меняется [отдельный worker Modules](https://github.com/Proteus-harness/Proteus-modules/blob/37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979/storage/session-storage/src/snapshot.rs#L182-L186), выполняющий запрос `ReadConversation(Current)` из [`conversation_snapshot` / `load_messages` в Core](https://github.com/Proteus-harness/Proteus-core/blob/4c032eeb7c51b2467064d7cd10fc6f8008ae51e4/crates/proteus-core/src/core/session_store/remote/mod.rs#L180-L194). Эти эффекты не нужно складывать.

## Release A/B: весь запрос чтения, включая JSONL replay и валидацию

| Фикстура | Время до → после | Пик RSS до → после |
|---|---:|---:|
| Пустая история | 13,74 → 13,70 мкс | 4,10 → 4,11 МиБ |
| 8 сообщений по 265 байт текста | 112,77 → 102,90 мкс | 5,31 → 5,40 МиБ |
| 128 сообщений по 128 КиБ + 9 байт, суммарно 16 778 368 байт текста | **65,17 → 55,08 мс** | **37,82 → 21,95 МиБ** |

На длинной истории это примерно 10 мс и 15,87 МиБ. Для коротких историй измеренный выигрыш времени мал, разницу памяти не считаем улучшением.

Значения — медианы 10 свежих Linux-процессов на каждую версию и каждую фикстуру, порядок A/B чередовался; первая пара исключена как прогрев. Базовый бинарник создаёт один настоящий журнал для обеих версий через Create / AcquireWriter / Commit / ReleaseWriter. Бинарники собираются с Rust 1.95.0 в release из чистых копий Modules `37b3d9c4db0b8cb5c4ca6cec690ebf7ce64c1979`, с Core `4c032eeb7c51b2467064d7cd10fc6f8008ae51e4`. Никаких патчей из #213 или #214 в замере нет.

Таймер охватывает `StorageService::execute(ReadConversation { point: Current, ... })` на заранее открытом snapshot. Linux VmHWM охватывает **весь процесс**, включая открытие snapshot; он снят до создания эталонных сообщений. Ответ проверяли как Rust-значение, без сериализации в wire-формат. Процессная граница RPC, UI, запуск Desktop и задержки с непрогретым диском не измерялись. Методы и типы рабочие, данные синтетические.

## Корректность и воспроизведение

Для каждой версии и каждого прогона проверены полное равенство всех typed messages с независимо построенным ожидаемым значением (текст, роль, идентификаторы и порядок), обе ревизии и model context (пустой в этих фикстурах). В одном дополнительном прогоне каждой непустой фикстуры изменён и восстановлен первый байт после открытия snapshot; оба варианта выдали точную одинаковую ошибку `invalid journal record: expected value at line 1 column 1`. Успех не получен пропуском проверки.

```sh
python3 run.py /path/to/Proteus-modules > results.json
```

[Драйвер](run.py) создаёт две временные копии; [service_probe.rs](service_probe.rs) — одинаковый внешний клиент публичного Rust API в обеих сборках. Исходное рабочее дерево не изменяется. [Сырые значения и ошибки](results.json). Память измерена на JSONL; перенос цифр на SQLite не проверялся.
