# Быстрее показать сообщение, прочитать диалог и собрать статистику

**Первым я бы перенёс патч для обычных пользовательских сообщений:** он добавляет четыре строки, не меняет правила распознавания ссылок и на большой многострочной вставке убирает почти весь расход на ненужный разбор Markdown. Вторым — передачу уже проверенных сообщений из storage worker без копирования.

| Изменение | Что показали одинаковые нагрузки до → после |
|---|---|
| [Обычные сообщения без ссылок](plain-text/README.md) | Настоящему процессу расширения на сообщение 53 762 Б потребовалось **9,59 → 0,54 мс**; во второй серии 9,62 → 0,60 мс. На большой синтетической вставке 860 162 Б пик RSS процесса **50,59 → 7,48 МиБ**. При наличии `://` остаётся штатный парсер: устойчивого ускорения на тексте со ссылкой нет. |
| [Текущий разговор, storage worker](storage/README.md) | На настоящем JSONL с 128 сообщениями по ~128 КиБ запрос `ReadConversation(Current)` занял **65,17 → 55,08 мс**; пик RSS отдельного процесса **37,82 → 21,95 МиБ**. На коротком или пустом диалоге заметной экономии не установлено. |
| [Панель Usage](usage/README.md) | Для 800 запросов/2 моделей содержимое панели строилось за **2,79 → 2,13 мс**; для 2 048 запросов/64 моделей **33,84 → 4,33 мс**. При 64 моделях пиковая память этапа группировки *выросла* на 7 776 байт, пик всей проекции не изменился. На коротких сеансах стабильной разницы нет. |
| [Восстановление индекса карточек в Core](page-repair/README.md) | В **запасном** пути с отсутствующей карточкой и 10 000 строк, разделённых по размеру, Core читал **400 → 201** страниц: 48,18 → 26,52 мс на штатном тестовом хранилище в памяти. Обычное чтение исправной карточки не меняется. |
| [Завершённая компакция OpenCode](compaction/README.md) | Локальный hook на 512 сообщениях без готовой оценки: **14,72 → 8,97 мс** при детерминированном ответе модели. Оценка *суммарных* аллокаций за вызов **14,64 → 9,79 МиБ** (не пик памяти). У пропущенной компакции устойчивого эффекта не было. |

Это разные операции и разные способы измерения; цифры не складываются и не обещают уменьшения RSS всей установленной программы. Обработку обычного сообщения измеряли **через протокол запущенного расширения**, не включая рисование окна; в Usage проверяли полное содержимое панели, без внешней шапки и передачи в Desktop. Реальные модели не вызывались.

**Проверки на совместимость.** У рендерера совпал полный поток ответов для 1 162 входов; 47 модульных и 3 процессных теста прошли до и после. У Usage — 882 совпадения итогов (включая биты суммы стоимости) и 1 470 побайтно одинаковых представлений; 10/10 штатных тестов до и 12/12 с патчем. У storage — проверки на настоящем JSONL, короткая/пустая история, повреждённая запись, 29 библиотечных и 2 межпроцессных теста. Для восстановления кеша прошли 5 штатных проверок Core и дополнительная отрицательная проверка страниц у обеих версий. У компакции — 17/17 штатных тестов и ещё 1 регрессионный на закреплённых OpenCode SDK и Node. Полный рабочий стол не собирали.

Отдельно проверили совместное применение прежних предложений: [#213](https://github.com/Qweasd123tg/proteus-modules-dot/pull/213), SQLite из [#214](https://github.com/Qweasd123tg/proteus-modules-dot/pull/214) и нового патча storage: **31 прошёл, 1 штатный ручной замер пропущен**. С патчем Analysis из #214 и двумя новыми патчами расширений на общем Cargo.lock также прошли Analysis 12, Markdown 47+3 и Usage 12. Это не означает, что старые предложения внедрены upstream.

[Ещё два кандидата не вошли](not-selected.md): выигрыш на обычной нагрузке слишком мал либо сопровождается ростом памяти.

У Modules свой compile-time Core `4c032eeb`. Изменения публикуются как патчи для указанных ревизий, никаких upstream-изменений, новых установок или изменений HOLD. Методики и исходные измерения — в подпапках.
