# Восстанавливать указатель на карточку инструмента по настоящим страницам истории

**Где помогает.** Если свежий заголовок кеша ссылается на последнюю карточку инструмента, но саму карточку прочитать не удалось, Core восстанавливает компактный указатель из сохранённого transcript. Это запасной путь. Обычное чтение исправной карточки, первичное открытие сессии и отрисовка Desktop не меняются.

[Исходник Core](https://github.com/Proteus-harness/Proteus-core/blob/8ea2cdaf4195ae24e941354f68d4e97335d139d7/crates/proteus-core/src/core/session_store/remote/view/cache.rs#L430-L477) восстанавливает указатель логическими окнами по 50 строк. Сохранённая страница ограничена не только 50 строками, но и объёмом: окно может захватить части двух страниц. Следующее окно заново читает целую общую страницу, проверяет её хеш и декодирует. Кроме того, для каждого окна снова проверяются дескрипторы всех страниц.

[Предлагаемое изменение](repair-physical-pages.patch) читает сохранённые страницы по порядку один раз. Заголовок проверяется перед входом в восстановление. У каждой страницы по-прежнему проверяются хеш и точное число строк; проверка актуальности источника перед публикацией сохраняется. Порядок карточек и правило выбора последней не меняются. Общий помощник проверки длины также используется при обычном чтении диапазона и чтении неполной страницы перед добавлением строк. Патч не меняет формат данных и не зависит от [#214](https://github.com/Qweasd123tg/proteus-modules-dot/pull/214).

## Измеренный результат

| Нагрузка | Сохранённых страниц | Чтений страниц, до → после | Медиана вызова, мс, до → после |
| --- | ---: | ---: | ---: |
| Пустая сессия, обычный поиск | 0 | 0 → 0 | 0,009 → 0,008 |
| 1 строка | 1 | 1 → 1 | 0,067 → 0,058 |
| 50 коротких строк | 1 | 1 → 1 | 0,174 → 0,146 |
| 10 000 коротких строк | 200 | 200 → 200 | 23,276 → 20,723 |
| 10 000 строк, две крупные в начале | 201 | 400 → 201 | 48,180 → 26,518 |

Две крупные строки расположены в позициях 0 и 25, каждая чуть больше 2 МиБ; суммарно они не помещаются в один лимит 4 МиБ. На длинной истории с этим сдвигом число обращений упало с 400 до 201. На длинной истории с ровными страницами читается столько же страниц; там устраняются повторные проверки списка страниц. На коротких случаях выигрыш в количестве чтений отсутствует.

Данные: [сводка в JSON](native-results.json), [вывод исходной версии](baseline-output.txt), [вывод с патчем](candidate-output.txt).

## Проверка и воспроизведение

На каждой версии проверяются пять штатных тестов кеша и отдельный отрицательный тест на отсутствие страницы, подмену содержимого и правильный хеш с неверным числом строк. Во всех трёх случаях результат не публикуется; заголовок не изменяется. Измерительный тест сравнивает всю возвращённую компактную карточку и ревизию с ожидаемыми, включая выбранную последнюю принятую запись перед более поздним отказом. Чтений записей канонического журнала в измеряемом окне нет.

Использованы Rust 1.95.0, профиль release, одинаковая нагрузка и штатное тестовое хранилище Core в памяти. При каждом замере перед вызовом удаляется только содержимое одной компактной карточки. Исключение: в пустой сессии такой карточки нет, измеряется обычный отрицательный поиск без восстановления. Счётчик учитывает обращения за страницами transcript; служебные обращения за заголовком и карточкой в это число не входят. Тестовый backend возвращает копию данных и вычисляет etag на чтении. Это замер пути Core в данных условиях, не задержка диска, сети, окна Desktop или всей сессии. ОЗУ не измерялось.

Файл [probe.patch](probe.patch) добавляет **только тестовые** фикстуры и счётчик. Для повтора нужен checkout Core с указанной ревизией, Cargo из PATH, обычный Linux-инструментарий и зависимости из Cargo.lock. Скрипт создаёт отдельную копию, не меняя переданный checkout:

```sh
bash reproduce.sh /path/to/Proteus-core ./new-results
```

При заполненном Cargo-кэше можно установить `CARGO_NET_OFFLINE=true`. Порядок запусков release-бинарников: исходный, изменённый, изменённый, исходный. На форму данных и процесс приходится один прогрев и семь измерений. Итог — медиана 14 замеров каждой формы и версии. Полный набор тестов и реальный внешний storage-worker не запускались.

Проверены исходные Git blob (`cache.rs`: `8233554c` → `5172f332`; `cache/pages.rs`: `15c015d4` → `9f7faeb8`), строгое наложение и возврат к исходным байтам. В дереве предложений после #214 (`6e357a1b`) поиск по имени пути и функции не нашёл прежнего патча этого обхода. #213 касался записи в кеше Modules, а #214 в Core — передачи владения проверенной историей, не обхода сохранённых страниц.
