# Не запускать Markdown-парсер для обычного текста, в котором не может быть HTTP-ссылки

Когда [Desktop показывает пользовательское сообщение](https://github.com/Proteus-harness/Proteus-desktop/blob/210cc9f274ffe40533b390a0d9e940f251a9fa22/src/ui/chat/thread.rs#L190-L204), расширение получает формат `text/plain`. [Рендерер](https://github.com/Proteus-harness/Proteus-desktop-extensions/blob/a35cea08be83ee8e5ecbfce9ef5050a1c00eb247/packages/markdown-render/src/plain.rs#L9-L109) выводит текст буквально, но ищет ссылки через дерево Markdown. В итоге он принимает только диапазоны **исходного** текста, которые начинаются с `http://` или `https://`.

[Патч](plain-links.patch) добавляет четыре строки: если в тексте нет даже `://`, не создавать дерево, а продолжить обычное экранирование и вывод. Если разделитель встречается в любом месте (даже в `ftp://`), используется весь прежний парсер: границы URL, пунктуация и правила отображения не меняются. Это не замена парсера регулярным выражением и не ограничение размера текста. MDX-конструкции отключены; [контракт закреплённого markdown 1.0](https://docs.rs/markdown/1.0.0/markdown/fn.to_mdast.html#errors) исключает синтаксические ошибки в таком режиме.

## Измерения реальных процессов

Два release-бинарника расширения Rust 1.95.0, Linux x86_64, отдельные каталоги сборки и разные SHA-256. Для каждой нагрузки две независимые серии; в каждой один прогрев пары и восемь измеренных чередующихся пар. Время — от отправки готового JSONL-запроса в запущенное расширение до получения полного ответа, с вводом/выводом, сериализацией и подготовкой HTML, без разбора ответа клиентом и без отрисовки окна. Память — пиковый Linux VmHWM самого процесса, не память Python-клиента и не всего Desktop.

| Вход на сообщение | Время до → после, мс (серия 1 / серия 2) |
|---|---|
| Короткий текст, 114 Б | 0,063 → 0,048 / 0,079 → 0,056 |
| Короткий текст со ссылкой, 144 Б | 0,060 → 0,062 / 0,072 → 0,075 |
| Многострочный текст без ссылки, 53 762 Б | **9,59 → 0,54 / 9,62 → 0,60** |
| Тот же текст с URL в конце, 53 784 Б | 9,17 → 9,58 / 9,75 → 9,54 |
| Большая многострочная вставка без ссылки, 860 162 Б | **447,86 → 6,65 / 553,71 → 8,55** |

На большой вставке медиана пика RSS процесса была **50,59 → 7,48 МиБ** и **50,62 → 7,47 МиБ** во второй серии. Результаты относятся к заданным синтетическим сообщениям: текст со ссылкой оплачивает короткую предварительную проверку и прежний разбор, ускорение ему не обещано. Не измерялись Markdown-ответы ассистента, скорость генерации, отрисовка GUI или суммарная память программы.

**Проверка.** У обеих версий 47/47 тестов модуля и 3/3 штатных тестов с настоящим процессом. У 1 162 контрольных входов совпал SHA-256 полного потока ответов; проверены пустые строки, переводы строк, NUL, Unicode, HTML и Markdown как текст, похожие на адреса последовательности, настоящие ссылки и пунктуация. Все ответы в сериях замеров также совпали. Git blob исходного файла `9beecc7926acca7f9b71496b6b085fec3d0bd1f3`; применение и возврат проверены. Исходные числа: [первая серия](native-results.json), [повторная серия и SHA-256 бинарников](repeat.json).

**Как повторить.** Возьмите две отдельные копии Extensions `a35cea08be83ee8e5ecbfce9ef5050a1c00eb247`, примените патч во второй. В каждой выполните `cargo test --locked -p extension-markdown-render` и `cargo build --locked --release -p extension-markdown-render`, не разделяя между копиями `CARGO_TARGET_DIR`. Затем на Linux: `python compare.py /path/before/target/release/markdown-render /path/after/target/release/markdown-render > measurements.json`. Драйвер не меняет checkout и не вызывает внешние сайты или модели.
